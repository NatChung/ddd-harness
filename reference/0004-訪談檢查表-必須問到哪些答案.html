參考卡 04 · DDD × Agent Harness

訪談檢查表:必須問到哪些答案

清單先寫死,不是訪談當下想出來的。標不出「這題補哪一格」的題目就不要問——那是閒聊。

這張卡在治什麼

需求方丟一句話進來(「我要一個系統,客人能下單,我能看到所有訂單」), 訪談 agent 的工作不是開始設計,是把這句話問到每個答案都有格子可以放。 這張卡就是那些格子:哪些答案非拿到不可、答案用什麼分類、沒拿到的怎麼追、 以及哪幾格有機器在數、哪幾格靠自覺。

一句口訣

「還缺什麼」這句話,要問得出口,就得先有分母。

把「該問什麼」交給 LLM 自由發揮,就沒有分母——它漏了不會知道自己漏了。 這張卡把分母寫死:8 列路由 → 13 節產出合約 → 11 條收齊判準。

11 條收齊判準 收尾前掃一遍 每條都是可判定的一句話;不通過就是訪談還沒完

8 列路由:聽到什麼 → 追問什麼 → 餵給哪一節

這張表的每一列,在產出合約都有對應的必填欄。問了卻沒地方放 = 白問。

他說出這種話你追問餵給哪一節
一個名詞 這個詞別的部門講的是同一件事嗎? §1 GLOSSARY;不一樣 → §1.1 Bounded Context
一個數字或金額 單位?怎麼表示?可不可以是負的?有沒有第二種幣別? §1,型態必須判定是不是 Value Object
「當…就…」 失敗的時候呢?做到一半、系統掛掉的時候呢? §2 GWT,必含系統中途失敗那條
「不可以 / 一定要 / 不能超過」 這條違反了,是誰的錯? §3 契約:呼叫方錯 = pre / 實作方錯 = post / 隨時成立 = invariant
「…之後,要…」 誰在等這件事發生?跟前一步同一筆交易內嗎? §4 Domain Event 清單
任何會改變狀態的動作 這個動作失敗的時候,狀態要停在哪?會不會留下半筆? §3 postcondition(失敗路徑)
「這一段是誰負責」 這兩段之間是同一筆交易嗎?一段的資料另一段看得到嗎? §1.1 邊界 + §9 ARCHITECTURE 相依方向
他沒提到的 (不要自己補) §5 明確不在範圍,標「規格沉默」
分類之前先問「這句話在描述什麼東西」

不要看句子裡最顯眼的關鍵字就分類(參考卡 02)。 而且同一條規則常常兩個載體都要:「已成立訂單不能改」= precondition(拋例外) 加上一條 GWT(測試驗它真的拋)。不是二選一。

答案用什麼分:五格來源標記

每條寫進 spec 的東西必須標來源。查無來源的 = 捏造,不得存在。 不得自創第六格。

標記意思限制
[Qn]第 n 題直接問出來的,他親口說的 只能標他真的說過的話。改寫語意就不算
暫定 [Qn]他說了,但原話是「先這樣吧 / 再看看」 不可當穩定規則實作,必須列進待確認
推導自 [Qn]從他的答案算出來、或邏輯上必然的 要寫出推導哪一步
模板既定架構常備前提,指向文件行號 只能指向被授權為架構模板的文件。沒有這種文件時這格就是空的—— 寧可空著,也不要找一份指得出行號的東西來充數
本案自決他沒說、但非決不可 必須附依據與待確認點,並記進 ASSUMPTIONS
最貴的一種造假

把 本案自決 偽裝成 模板既定。歷史上模型兩輪都這麼做過—— 所以它現在住第 1 階:四張 store 表各配一個 trigger, 白名單為空時那個值物理上寫不進 DB。靠自覺守不住的規則就往上搬 (第 9 課)。

產出合約:13 個區塊,缺一即未完成

§內容硬條件
1GLOSSARY DDD 型態必須從固定清單選(Decimal、String 不是 DDD 型態); 量值先判斷是不是 Value Object;必須有禁用同義詞清單
1.1Bounded Context 發現同名不同義時才有。切界是一個決定,要標來源
1.2wire shape 逐欄寫明對外 JSON。需求方不懂技術,這節標 本案自決 是對的, 但自決完必須寫成合約
2GWT 清單 每個改狀態的行為,失敗路徑至少覆蓋:業務規則不通過 / 外部系統回失敗 / 系統中途失敗。第 3 類不得缺席
3領域契約 invariant 與 precondition 必填「守在哪個聚合根內」; 需要看聚合根以外的資料 → 標「跨聚合根,邊界可能錯」並回報。 postcondition 不得只有成功路徑
4Domain Event 訪談中每句「…之後,要…」都要找得到對應。一句都沒有要寫為什麼
5明確不在範圍 逐項標「訪談否決」或「規格沉默」;標出哪些是阻斷級, 並指名阻斷了哪幾條契約
6ASSUMPTIONS所有 本案自決 的集中處
7內部矛盾 列出來、指出哪兩條、不要自行調和,標「需求方裁決」
8未答追蹤清單從頭到尾沒被回答的,原樣保留
9ARCHITECTURE 每條規則要有「出處」與「由誰強制」——指名哪條 ArchUnit 規則 / 哪個測試, 或寫「目前無機械檢查(第 4 階)」
10PROMPT 凍結清單、要填的範圍、指名哪幾套測試的完成定義、歧義處置、 不得開工的部分
11INTERVIEW-LOG 逐字稿每一個答案都指得出落點。指不出來 = 漏接

11 條收齊判準

  1. 8 列路由每一列都在產出裡找得到對應(或明寫「本案無此類」)
  2. 四格盤點無漏格(有落點,或明寫空缺)
  3. 每條規則都有五格來源標記之一;模板既定 指得出被授權的架構模板文件
  4. 每條 invariant / precondition 都標了守在哪個聚合根內;跨聚合根的已回報
  5. postcondition 含失敗路徑的狀態保證(失敗後停在哪、有沒有留半筆)
  6. §4 Domain Event 非空,或寫明為何空
  7. §1 有禁用同義詞清單
  8. §9 每條架構規則都有出處與「由誰強制」;無授權模板文件時 模板既定 必為零筆
  9. §9 對 §3 每條「跨聚合根」都有處置(新增聚合根 / 移到別處 / 明寫待裁決)
  10. §10 有凍結清單、指名的完成測試、以及 §5 阻斷級構成的「不得開工」清單
  11. §11 逐字稿的每一個答案都指得出落點

問不到的:「猜錯了,誰賠錢?」

到收尾仍未答的每一項,必須給建議 + 依據,並分成兩類。判準只有一句話。

類型判準例處置
技術判斷 猜錯了「只是工程不好維護」 金額精度、單號格式、重試次數與退避 採用建議,標 本案自決,列待確認點
業務政策 猜錯了「客人或公司會賠錢 / 被客訴」 期限從哪天算、多少錢以下公司吸收、零頭算誰的、誰付運費 不採用,留在「規格沉默」,附建議供他日後挑

收尾時單獨列一張表:「以下 N 條沒人答,是照建議填的」。 而 §5 標阻斷級的規格沉默,會逐條被搬進 §10 給實作 agent 的「不得開工的部分」—— spec 包裡有洞是正常的,把洞交出去而不標明,實作 agent 就會自己填。

追蹤:三張人寫的,兩支機器數的

這條線反覆出現的失效是「轉交了 ≠ 記下來了」。所以追蹤分兩層。

誰查什麼
訪談者自己寫
(語意判斷)		 四格盤點表(每輪貼一次)/ 未答追蹤(這輪沒答到的原樣列出, 下輪重問,不准默默消失)/ §11 逐題落點對照
relay_ledger 每筆 answered 都要有對應的 relayed。判準刻意寫得很笨—— 寫成「大致上都有轉交」的話,原本那個洞就會被形式滿足
landing_check 第 N 輪問出去的每個題號,要出現在第 N+1 輪開頭那張表格的某一資料列裡。 散文寫一句「收到了 Q8 到 Q11 的回答」不算——那句話裡 Q9、Q10 一次都沒出現
「不適用」不算「通過」

離開碼 0 通過 / 1 有漏接或掃到卻掃錯 / 2 用法錯誤 / 3 整份不適用。

為什麼一定要有第 3 類:實測把一份 15 題的真實逐字稿,只把題號寫法 **Q1. 改成 **Q1:(其他一字不動),舊版守衛就印出 「可比對 3 輪 / 0 題;通過 0、漏接 0」而 exit 0。 訪談者換個標點,守衛靜靜地不再適用,而沒有人會發現。

再往下:落檔那一端有哪些名詞

第二幕把散文轉成 18 張表的 SQLite。這裡的欄位名就是這套 harness 的名詞—— 散文裝不進去的東西,下游一步都看不到。

訪談那份清單:7 個 DDD 型態

訪談 prompt §1 寫死,不得用實作型別: Aggregate Root · Entity · Value Object · 識別碼 · 階段或狀態 · 外部規則集 · 角色。

但 schema 沒有鎖這 7 個

glossary_term.ddd_type 是自由文字,刻意不做成固定清單。 查過兩份真實詞彙表之後放棄鎖:它們的型態用語幾乎不重疊,鎖清單會逼下一份詞彙表 把自己的詞硬塞進別人的格子——那會製造假資料,不是擋假資料。

所以這 7 個型態今天只住第 4 階:規格層讀得懂,沒有任何機械檢查在看。 累積到看得見真正的值域再走搬階。

微尺度與詞彙那兩組是 2026-08-18 才補的。在那之前它們只活在散文裡—— 於是一條 invariant 進得了 store 的唯一形式,是被寫成某條情境的斷言 (invariant 被降級成 example);而「實作命名必須照詞彙表」那句話 沒有任何一步會去讀。

必填欄,與空著會怎樣

表必填的名詞擋法
architecture_rule id · rule · provenance · provenance_ref · enforcement enforcement='none' 就必須填 ladder_note (搬階清單的原料);enforced_by 由生成器回填, agent 自己寫 import 會拒收
domain_contract id · kind · statement · provenance · provenance_ref · guarded_in · crosses_aggregate kind 三選一;crosses_aggregate=1 必須填 disposition,而且存本文不存指標——「見某某節」的幾種寫法 擋在第 2 階;零列指名測試必須填 no_named_test_reason
contract_named_test contract_id · scenario_id FK。指向一個不存在的情境編號(打字錯)寫不進去——第 1 階
glossary_term term · definition · ddd_type · provenance · provenance_ref · seq wire_field 是 UNIQUE:兩個詞宣稱同一個對外欄位名 = 對譯有歧義, 寫不進來。空白有語意(不上線 ≠ 漏填)
glossary_banned_synonym banned · note use_instead FK 指回 glossary_term—— 叫人改用一個詞彙表裡不存在的詞,寫不進來。 NULL 時必須填為什麼沒有替代詞
wire_contract 12 個對外欄位名 CHECK (id = 1) 讓第二份合約寫不進來。列表的總金額欄改名, Σ(數量×單價) 那條不變式就認不到人——所以守衛的認人方式跟著合約走
四張表的 provenance 逐字相同

architecture_rule / acceptance_scenario / domain_contract / glossary_term 的五格值域 一個字都不能差,也不得為新表改格名——同一條規則寫在多個地方會漂。

六支 script 數「少了什麼」

語意判斷歸 LLM,「少了什麼」歸 script。判準刻意寫笨—— 寫成「大致上都有記到」這支就白做了。

誠實性標註:哪幾格有機器在數

11 條收齊判準裡,訪談當下只有 1 條有 script

這張檢查表是清單級強制:LLM 照固定清單自查,比「你檢查一下」強很多 (該有哪幾格不是它決定的),但不是 script 級。

訪談當下只有第 11 條(逐題落點)有 landing_check 在旁邊數題號。 第 3 條(來源標記)與第 8 條(由誰強制)要等第二幕落檔之後才有 provenance_check / contract_triage 部分接得上—— 而接不上的部分,以及其餘八條,靠訪談 agent 自覺,漏了不會知道自己漏了。 §11 那張收尾表是訪談者自己寫的,不進判定——不能拿來把「不適用」補成「通過」。

來源
