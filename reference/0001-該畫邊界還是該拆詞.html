該畫邊界,還是該拆詞?

「兩群人對同一個詞講不一樣」有三種原因,三種解法。用錯解法會讓問題更糟。

三十秒版

狀況解法接點
① 一方其實是誤用
其中一側講錯了,不是需求不同		 直接修正。這不是邊界,是 bug 不需要
② 同一條時間線上的兩個點
兩側先後發生,不會同時存在		 拆成兩個詞,各自定義那一刻
(第 1 課的解法)		 不需要 —— 本來就是一條線
③ 兩條平行、各自獨立演化的線
兩側同時存在、各自變化		 畫 Bounded Context,各自建模
(第 2 課的解法)		 需要 —— 通常是識別碼

怎麼分辨

照順序問這三題,第一個答「是」的就是答案:

Q1 —— 有沒有一側其實只是講錯了?

如果把兩邊拉到同一間會議室,其中一方會說「喔對,我用錯了」——那就是 ①。 真正的邊界不會被一次對話消滅,兩邊都會堅持自己是對的,而且兩邊都真的對。

Q2 —— 兩側是同一個東西的不同時刻嗎?

測試法:畫一條時間線,兩個意思能不能各自落在一個點上? 落得上去,而且有明確先後 —— 那是 ②,你需要的是兩個詞,不是兩個模型。

再一個測試:問「A 的意思發生時,B 的意思是不是還沒發生?」 答「是」就是同一條線上的兩點。

Q3 —— 兩側需要各自獨立演化嗎?

問:「其中一邊改了規則,另一邊應不應該被迫跟著改?」 答「不應該」就是 ③,畫邊界。這通常伴隨不同的變更節奏、不同的負責人、不同的關注點。

接點測試(判斷邊界畫得對不對)

找出③之後,還要驗證接點:你想拿來當接點的東西,跨過邊界之後意思會不會變?

  • 不會變 → 它是合格的接點。通常是識別碼(訂單編號、使用者 ID)—— 它指向同一個東西,但不承載任何一側的語意。
  • 會變 → 它不是接點,它就是爭議本身。把它當接點等於假裝爭議不存在。

推論:狀態、金額、日期幾乎都當不了接點,因為它們承載語意。 能當接點的東西通常很無聊——這是好事。

例子

案例類型為什麼
電力公司的「meter」:
裝機部門 vs 計費部門		 ③ 畫邊界 兩邊同時存在、各自演化。計費規則改了,實體電表的型錄不該跟著改。 接點是電表序號。
電商的「訂單」:
結帳 vs 倉儲 vs 財務		 ③ 畫邊界 三個平行狀態機,各自獨立跑。接點是訂單編號。
「訂單成立」vs「訂單完成」 ② 拆詞 同一筆訂單的兩個時刻,有明確先後。不需要兩個模型,需要兩個名字。
PM 的「完成」(含 QA) vs
RD 的「完成」(code done)		 ② 拆詞 同一個 feature 的兩個時刻:RD 完成 → QA → PM 完成。 不是邊界——兩邊在交付同一個東西,不需要各自獨立演化。 拆成 Code Complete 與 Ready to Ship。
行銷的「使用者」(來源渠道、LTV、分群) vs
系統的「使用者」(id、認證、權限)		 ③ 畫邊界 同一批人,兩個平行模型,各自獨立演化。行銷加一個分群欄位, 認證系統不該被動到。接點是 user id。
最常見的誤判

把 ② 當成 ③。看到兩群人講不一樣就急著畫邊界、建兩個模型, 結果做出兩份會不同步的資料,還得寫同步邏輯—— 而真正需要的只是多取一個名字。

症狀:你發現自己想找的「接點」是一個狀態、一份定義文件、或一個需要兩邊同意的東西。 真正的接點應該無聊到不需要討論。

標註

①②③ 這個分類法是本教材整理出來的判準,不是 DDD 文獻裡的既有框架。 ③ 對應 Fowler 談的 Bounded Context,②③ 的區分則是我們自己加的。 對外講的時候值得標清楚。
