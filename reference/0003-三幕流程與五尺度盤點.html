參考卡 03 · DDD × Agent Harness

需求 → spec 包:三幕流程

幕 = 時間,尺度 = 清單,階梯 = 強度。三個各就各位,誰也不用讓位。

這張卡在治什麼

拿到一句 stakeholder 需求(「我要一個系統,客人能下單,我能看到所有訂單」), 到手上有一包可以凍結、可以餵給任何實作 agent 的 spec——中間發生什麼事、 誰做哪段、每一步問哪個問題。三個框架(時序三幕、五尺度、第 9 課五階) 常被混為一談,這張卡把它們釘在各自的位置上。

一句口訣

幕回答「什麼時候發生」,尺度回答「有沒有漏」,階梯回答「夠不夠硬」。

幕是時序敘事(上一幕的產出是下一幕的輸入);尺度是盤點清單(五格掃一遍, 漏格 = 有一類洞沒人管);階梯是強度量尺(同一條約束,住第 4 階會被模型飄走, 住第 2 階換誰都擋)。

三幕(時間軸)

幕發生什麼核心問題產出
第一幕:對話
(event storming)		 追問 stakeholder,把一句需求逼出十幾條決策。 每個問題的答案都是一條決策——AI 追問、起草,拍板一定是人 「這件事還有什麼沒說死?」 決策清單(訪談紀錄)
第二幕:落檔 每條決策按型態進檔案:詞 → GLOSSARY、行為 → SPEC 的 GWT、 結構 → ARCHITECTURE;被否決的 → 「明確不在範圍」。 幕尾跑五尺度盤點(見下)——漏格 = 回第一幕再問 「這條約束是哪個尺度?落哪個檔?」 spec 包(散文版)
第三幕:搬階 對每條規則問「能不能讓機器判?」——能判的翻成先紅的驗收(第 3 階) 或 ArchUnit(第 2 階),還不能的暫住散文(第 4 階)。 然後凍結,harness 成形 「能不能機械判?住哪一階?」 骨架 + 機械檢查(commit = harness)

後續(第四幕實作、第五幕 review 與洞回頭改 harness)見第 9 課的迴圈; 這張卡只管 spec 包的生產線。

為什麼不按尺度分五幕

五個尺度不是依序發生的:大尺度(架構 starter)在對話開始之前 就存在;需求約束和微尺度(契約)是同一場對話混著出現的——主管說 「成立就鎖定」,同時餵了 GWT 和 invariant;中尺度要到實作開工才登場。 按尺度分幕 = 把真實對話剪碎重排成假時序,敘事因果就丟了。

第二幕尾:五尺度盤點

落檔完、收尾前,拿這張清單掃一遍。判準:每尺度有落點,或明寫空缺; 漏格 = 訪談還沒完。

尺度約束什麼落點常見漏格
需求行為(event storming → BDD 驗收) SPEC 的 GWT「查無顧客」這類例外路徑沒情境
大尺度架構(簡潔架構 + DDD + CQRS) ARCHITECTURE(常備模板 + 本案追加)只抄模板,本案邊界例外沒寫
中尺度sub-agent 職責(AI 活在合適的 context) harness 過程層,不進 spec 包——允許「明寫空缺:本輪單 agent」 整格忘記存在(空格要現形,不是跳過)
小尺度coding standards(命名、介面規範) GLOSSARY 鐵律 + 禁用清單有詞彙表、沒有「不得另創同義詞」那句
微尺度Design by Contract SPEC 領域規則,每條標 pre / post / invariant + 配不配測試 規則寫了但沒標型態,postcondition(如失敗原子性)整類缺席
微尺度「看不到」的原因

DbC 常常不是缺席,是拆散住在三個地方:precondition 落在 「非 DRAFT 丟 IllegalStateException——這是呼叫方的 bug」(實作後住第 1 階)、 invariant 落在「總額一致由 Order 自己維護」、postcondition 最容易整類漏 (「失敗時狀態不變」沒人寫)。盤點時逐條貼標籤,缺哪類一眼可見。

尺度 × 階梯:矩陣才是全圖

尺度和階梯是正交的兩軸:尺度決定它是哪一類約束,階梯決定它多可靠。 任何尺度的約束都可以住任何一階——所以 harness 的健康檢查是掃矩陣: 每個尺度有沒有約束?每條約束住的階夠不夠高?

尺度住第 4 階(散文)的樣子往上搬後的樣子
