參考卡 02 · DDD × Agent Harness

先問「這是什麼」

再問「它屬於哪一類」。順序反了,分類就會錯。

這張卡在治什麼

分類的時候,句子裡最顯眼的那個詞會搶先跳出來,你會不自覺地拿它當判準。 這叫做被表面特徵帶走,而且它有個特徵:錯得很有道理—— 你選的那個答案跟句子的字面高度相關,所以當下不會覺得可疑。

兩步,順序不能顛倒

第一步:這句話在描述一個「什麼東西」?
一段程式碼?一條 CI 規則?一個測試?一句寫在文件裡的話?一個介面宣告?

第二步:那個東西屬於哪一類?

幾乎所有分類錯誤,都是跳過第一步造成的。

三個實際踩過的例子

例一:「提示詞每次都提醒『改完明細記得 total 要重算』」
被什麼帶走「每次都」——聽起來像自動化、像有機制在跑
第一步該問這是什麼東西?→ 一句話,寫在提示詞裡
正解第 4–5 階,文字約定
這個例子背後有個獨立的重點

自動被送進 context ≠ 自動被擋下來。

提示詞、CLAUDE.md 這類東西每次都會被讀進去,所以「感覺」像個機制。 但自動的是注入,不是遵守。

機械檢查的定義是:違反會有明確的 fail。提示詞裡沒有 fail 這回事, 只有「希望它照做」。看到「每次都⋯」,先問一句:不照做的時候,會發生什麼? 答案是「沒事」的話,那就是文字約定。

例二:「一個測試:對已成立的訂單呼叫 addItem 必須拋例外」

被什麼帶走「拋例外」——那是最強那一階的關鍵字
第一步該問主詞是什麼?→ 一個測試
正解第 3 階,可執行驗收

同一條規則有兩個載體:例外是第 1 階(堵住路),測試是第 3 階(驗證那條路真的堵住)。 這句話是後者在描述前者。階數由載體決定,不由內容決定。

例三:「OrderView 這個回傳用的 record 住哪一層?」

被什麼帶走它是要吐給前端的——面向外面,所以放外層
第一步該問判準是什麼?→ 誰的程式碼裡出現了它的名字
正解Use Cases 層

「面向誰」是這個型別的用途,不是它的歸屬。歸屬看 import 方向。

通用的自我提問

分類之前,先問這四句
  1. 這句話的主詞是什麼?(是「一個測試」還是「一個例外」? 是「一句提醒」還是「一條規則」?)
  2. 我是被哪個詞吸引的?把它圈起來,然後問:這個詞是判準嗎? 通常不是——它只是最顯眼。
  3. 這一課的判準到底是什麼?說得出來嗎?說不出來就先回去找,別硬猜。
  4. 如果把那個吸引我的詞換掉,答案會變嗎? (「一個測試:⋯必須回傳 false」——還是第 3 階。那就證明「拋例外」不是判準。)

各課的真正判準

需要的時候翻這張表,不要憑印象:

課要分類什麼真正的判準常被誤用的表面特徵
第 2 拆詞 vs 畫邊界 是同一條線上的兩個點,還是兩條平行演化的線 「兩邊講的不一樣」(兩種情況都會不一樣)
第 4 同不同一個 Aggregate 允不允許有一瞬間對不起來 關係緊密、常一起查、同一張表、有 FK
第 5 住哪一層 誰的程式碼 import 它(所有用到它的層,取最內) 它「面向」誰、它放在哪個資料夾
第 6 Command vs Query 會不會改變系統狀態 句子裡有沒有「讀」「查」、複不複雜
第 7 Event vs Command 時態:已經發生了,還是還沒發生 句子在講哪個名詞
第 8 哪一種條款 先問是不是契約(有人寫錯 vs 生意就是這樣),再問時機 句子的形狀長得像前置條件
第 9 規則住第幾階 載體是什麼(程式碼/CI/測試/文字) 句子裡的關鍵字(「拋例外」「每次都」)

看最右欄——那些表面特徵每一個都跟正確答案高度相關, 所以用它們猜,大部分題目會猜對。錯的都是刻意設計的那幾題, 而現實裡真正會出事的,也正是那幾種。

來源

這張卡不是引用來的,是從本教學實際發生的錯誤歸納出來的—— 見 learning-records/ 的 0007(用面向而非 import 判斷層別)、 0009(跳過「是不是契約」那一關)、0010(用關鍵字而非載體判斷階數)。 三次同型,所以抽成一張跨課的卡,而不是在三課各補一段。

這件事本身就是第 9 課 那道階梯的示範:同一個問題重複出現 → 把散在各處的散文往上搬一階, 變成一份可以被翻閱、被指向的東西。
