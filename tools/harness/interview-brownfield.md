## 一、你多拿到一份輸入:候選表

`act0-candidates.yaml` 是幕零從既有 code 抽出來的**候選**,不是規格。它的每一筆長這樣:

```yaml
- id: K12
  kind: glossary | architecture | wire | contract | scenario
  value: "Booking"                      # 抽到的東西
  source: "app/lib/booking/booking.dart:17"   # 讀出來的那一行
  note: "同檔另有 Reservation(:44),疑似同義"
```

**候選表是拿來對帳的,不是拿來照抄的。** 每一筆你只能做三件事之一:
拿去問(變成一題,標它要補哪一格)、標「需求方未確認」放進 §5 或 §7、或標「片外」不處理。
**不准**不問就直接寫進規格 —— 那是第二種捏造。

一輪問的決定點上限照正本(≤ 5)。候選表很長的時候,**先問會改變邊界的**(同義名、跨 package 的 import、
守衛裡的數字),再問細節。

## 二、第六格:`既有程式碼 <path>:<line>`

正本 §二的五格照舊。本檔加**第六格**,只給從 code 讀出來的東西:

| 標記 | 意思 | 限制 |
|---|---|---|
| `既有程式碼 <repo>/<path>:<line>` | 這條規則是從那一行 code 讀出來的 | 指**規則所在的那行**,不是相關的檔;沒有行號不算 |

**三條鐵律:**

1. **確認後不洗白。** 需求方對候選表的值說「對」,標記寫
   `既有程式碼 app/lib/order.dart:41,經 [Q3] 確認` —— **不得**改成純 `[Q3]`。
   你念 code 給他聽、他點頭,來源仍是 code。洗成 `[Qn]` 就是 `provenance_check` 抓的那種造假的新變體。
2. **需求方不認的,不調和。** 標 `既有程式碼 X:12,需求方未確認`,進 §7(他說的跟 code 打架)或
   §5(他說不需要、但 code 有)。**這一格是 brownfield 最值錢的產出**:code 裡沒人記得為什麼的規則清單。
3. **他說的跟 code 不一樣,當場攤出來。** 「code 在 `x.dart:41` 只允許取消整張單,你剛說可以部分取消 ——
   哪個對?」不要替他選,不要假設 code 是對的、也不要假設他是對的。

## 三、每一輪多做一件事:對 code 查證

正本 §四的「問題 / 盤點 / 未答追蹤」照舊。brownfield 多一段 **「對帳」**:

- 他這輪講到的每一件「系統怎麼運作」,查候選表(或 code)同不同意。同意 → 標第六格 + 經 `[Qn]` 確認;
  不同意 → §7;候選表沒有 → 純 `[Qn]`(這是他的新需求,不是 code 的)。
- 盤點表多一列:**候選表消化了幾筆 / 剩幾筆**。剩的不會消失,下輪繼續。

## 四、提供方狀態:「等 server」是兩件事

§1.2 wire shape 每個端點多一欄 **提供方狀態**,三選一:

| 狀態 | 意思 | 後果 |
|---|---|---|
| `已實作` | server 有這個端點,形狀從 code 讀得到 | 第六格標出處 |
| `替身` | 形狀兩邊講好了,server 還沒寫 | **不擋開工**:app / web 對 HTTP 假服務做到全綠 |
| `形狀未定` | 欄位 / 錯誤碼 / 誰算總價還沒定 | **阻斷級**:進 §5、進 §10「不得開工的部分」,對應情境與契約不生成、不實作 |

追問句固定:「這個 API 的長相你們定了嗎,還是等 server 那邊說?」定了 → 問是不是已經在跑 → `已實作` / `替身`;
沒定 → `形狀未定`,**並問誰、什麼時候定**,寫進 §5 那一條。

## 五、`[human-eye]`:只有人眼判得了的驗收

§2 GWT 每條可帶尾標 `[human-eye]`。**只給真的機器判不了的**:「看起來對」「動畫順」「排版舒服」。

- **先磨成可測的。** 「按下去出現確認框」「列表有 5 筆」「錯誤訊息文字是 X」都不是 `[human-eye]`。
  它是最後手段,不是逃生口。
- 帶了標記就要寫**誰**確認、確認**什麼**(例:`[human-eye:Lena,首頁 banner 排版]`)。沒寫誰 = 永遠等。
- **禁止用機器指標代理**:截圖相似度 95% 不是「看起來對」—— 這是 `CONTEXT.md`「代理編碼↔假驗收」在 UI 上的樣子。
- 落檔後 `human_eye = 1` 的情境:**不生測試**,驗收報表自成一類「待人眼確認 N 條」,**永不折進通過**。

## 六、產出合約的差量(其餘照正本 §六)

| 節 | 多什麼 |
|---|---|
| §1 GLOSSARY | 來源可為第六格;候選表的近義名成對列進**禁用同義詞清單**,並寫哪個留、哪個廢、為什麼 |
| §1.1 Bounded Context | 多一段「片內 / 片外」:這次只切哪一片,片外的 code 當外部系統 |
| §1.2 wire shape | 每端點多「提供方狀態」欄 |
| §2 GWT | 可帶 `[human-eye:誰,什麼]` |
| §5 明確不在範圍 | 多一類:**既有程式碼,需求方未確認**(逐條列 `path:line`) |
| §7 內部矛盾 | 「他說的 vs code」也算矛盾,列出來、不調和 |
| §9 ARCHITECTURE | 規則分兩欄:**現況**(第六格,從 import 圖來)與**理想**(本案自決或 `[Qn]`);brownfield 的機械檢查目標是**不變差**,不是全綠 |
| §11 INTERVIEW-LOG | 多一欄「候選表編號」:每題若源自候選表,寫 `K12` |

## 七、完成判準的差量

- 候選表每一筆都有落點:問過(→ §11 有題號)、未確認(→ §5 / §7)、或片外。**一筆都不准消失。**
- 第六格出現的每一筆,`provenance_ref` 都是 `path:line` 形狀。
- 沒有任何一筆「候選表的值」被標成純 `[Qn]`(落地票 PREDICTION 第一條就釘這個)。
- `形狀未定` 的端點,對應情境與契約都在 §10「不得開工的部分」裡。
- `[human-eye]` 每條都有誰、什麼。
