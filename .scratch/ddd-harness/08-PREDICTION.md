# 票 08-A 的預測(寫在寫程式之前,2026-08-18)

形狀已由 `docs/adr/0005` §1 / §4 / §5 定死,這裡不重複論證形狀。這份只寫死一件事:
**詞彙表真的進 store、對譯檢查真的跑起來之後,會量到什麼數字** —— 逐條寫得出
「什麼結果會讓它落空」。

「詞彙表落檔數 > 0」不可能失敗,**不用**。ADR §5 已經手算過一次起點
(7 個列表欄位裡 4 個對得到、3 個有問題),下面每一條都比那個更精確,
而且其中一條**跟那個手算的答案不一樣** —— 那個差就是本票的主要發現。

## 它做什麼

三件事,都不碰實作層:

1. `schema.sql` 加 `glossary_term` + `glossary_banned_synonym`(接在 `contract_named_test`
   之後),provenance 五格逐字照抄,白名單 trigger 另取名字。
2. `spec_store.py` 加選填的 `glossary_terms` / `banned_synonyms` 兩段與它們的第 2 階。
3. `glossary_check.py` —— **第 2 階報告**,不是 FK:把「wire 合約的每個欄位名對不對得到
   詞彙表的一個詞」印成分診佇列,並印出**對不到的那 N 個是哪幾個**。

**不碰 B 半**(命名類的第四個 ArchUnit rule kind):那題還沒拍板。
**不碰 `PRAGMA foreign_keys`**:06-A 已經讓它承重,有兩支行為測試盯著。

## 預測(逐條可落空)

### P1 第二幕那組:**7 個列表欄位,機器一個都對不到(N = 7 / 7)**

**這是本票最重要的一條,而且它跟 ADR §5 手算的答案不一樣。**

那份詞彙表 11 個詞全是中文(訂單 / 訂單明細 / 已成立 / 客人 / 客人編號 / 商品 /
數量 / 單價 / 總金額 / 幣別 / 成立日期),而且**連「對外欄位名」這一欄都沒有**。
所以:

- **宣告對譯**(`glossary_term.wire_field` = 欄位名)= **0**,因為那一欄整欄不存在。
- **撞名**(詞本身就含那個英文識別字)= **0**,因為 11 個詞裡一個 ASCII 識別字都沒有。
- → `orderId` / `customerId` / `items` / `currency` / `placedAt` / `status` / `totalCents`
  **七個全部對不到**。請求側 7 欄(customerId / items / productId / quantity /
  unitPriceCents / currency / totalCents)同理,也是 **7 / 7 對不到**。

**ADR §5 手算的是 4 個對得到、3 個有問題;機器量到的是 0 個對得到、7 個對不到。**
差在哪:那 4 個是**人在腦裡做的翻譯**(客人編號 → `customerId`),
規格裡**沒有任何一格記著這件事**。而落檔 agent 明明做對了 —— 它把完整的對譯寫在
`agent-acceptance.yaml` 的**註解**裡(「欄位名一律照 §詞彙表對譯,不另創同義詞:
客人編號→customerId、訂單明細→items…」)。**做對了,而且沒有留下任何機器看得見的痕跡。**
那正是這張票要抓的東西:自律換個模型就沒了,而且**連「上一個模型做對了」都證明不了**。

落空條件:任何一個欄位被判成對得到(表示我讀錯了那份詞彙表的欄位,或撞名的判準寫鬆了)。

### P2 凍結那組:**5 個列表欄位裡恰好 1 個對得到,N = 4**

凍結的 `GLOSSARY.md` 15 個詞大多**本身就是英文識別字**(`Order` / `OrderId` /
`CustomerId` / `ProductId` / `Money` / `OrderStatus` / `OrderRepository` /
`OrderListItem` / `PlaceOrderUseCase` …),所以撞名這條路走得通;
但它同樣**沒有「對外欄位名」這一欄** → 宣告對譯一樣是 0。

列表 5 欄:`orderId` ✅ 撞上 `OrderId`;
`customerName` ❌、`statusLabel` ❌、`totalCents` ❌、`placedAt` ❌。
→ **N = 4 / 5,而且撞得到的那 1 個是撞名不是對譯。**

請求側 6 欄(`req_total_field` 是 null):`customerId` ✅、`productId` ✅、
`items` ❌、`quantity` ❌、`unitPriceCents` ❌、`currency` ❌ → **2 / 6 撞得到,4 對不到。**

**這一條的意思比數字大**:凍結那份詞彙表開頭寫著「實作中的類別、方法、**欄位**命名
必須使用這裡的詞」,而它自己那份合約的列表欄位有 **4/5 不在表裡** ——
因為那份詞彙表管的是**第 3 階的類名**(`OrderRepository`、`PlaceOrderUseCase`),
wire 欄位是**第 4 階**。散文那句「必須照此表」把兩組不同的詞講成同一組。

落空條件:N ≠ 4(例如 `placedAt` 被判成撞上「下單 / place」—— 那表示撞名用了子字串比對,
而子字串比對就是票 03 那種懲罰寫得好的一方的假陽性,**必須是完整 token 相等**)。

### P3 本輪訪談那組:**唯一一份填了「對外欄位名」的詞彙表,卻是唯一一份量不到 N 的**

17 個詞裡 **12 格填得出欄位名、5 格空白**。但這場的情境一份都沒落檔 → **沒有 wire 合約**
→ 對譯檢查**沒有對面可以比**。

→ **預測:這一份走「不適用」,離開碼 3,而且它是 ADR §6 沒想到的第二種不適用。**
ADR §6 只寫了「詞彙表 0 條 → 不適用」;這一份是**詞彙表 17 條、合約 0 份**。
報表必須把這種也印成不適用、印在最上面,**不准因為「詞彙表有東西」就折進通過。**

落空條件:找得到一份配得上這場規格的 wire 合約(已查證:沒有)。

**這三條合起來是一句話**:唯一做對了對譯的那份規格量不到,量得到的兩份都沒做對譯。

### P4 「空白 = 這個詞不上線」這個語意,**三份語料裡只有一份撐得住,而且撐得不完全**

ADR §4 寫「對外欄位名可空,空白 = 這個詞不上線,不是漏填」。實際:

- **本輪訪談那份**:5 格空白 —— 會員系統 / 商品價目系統 / 內部人員 **3 格**真的是界外、
  不上線 ✅;訂單那格寫的是「(整個物件)」、金額那格寫的是「(見下三列)」,
  **這 2 格散文有寫東西,只是寫的不是一個欄位名**。
  → **「空白 = 不上線」只有 3 / 5 成立。**
- **另外兩份**:整欄不存在 → 11 格、15 格**全部空白**,而它們的詞幾乎都上線。
  → **0 / 11、0 / 15 成立。**

→ **預測:空白這一格裝了三種東西** —— 真的不上線 / 散文寫了但不是欄位名 / 這份詞彙表
根本沒有這一欄。**計數分不開這三種**,報表必須明講,不准把「空白數」讀成「不上線的詞數」。
落空條件:5 格空白全部是界外概念(表示我把「(整個物件)」讀錯了)。

### P5 禁用同義詞:**兩份訪談產出各有一列叫人改用一個詞彙表裡不存在的詞,FK 兩次都擋得下**

- 本輪那份 1.1 的「會員 / 買家 / 使用者 → **客人 Customer** / 客人編號 CustomerId」——
  **詞彙表裡沒有「客人」這個詞**(有「客人編號」「客人名字」,沒有裸的「客人」)。
  → FK 逼我只留得住「客人編號 CustomerId」那半,`客人 Customer` 那半掉進 note。
- 第二幕那份的「建立、下單 → **成立**(動作)/ 已成立(狀態)」——
  **詞彙表裡沒有「成立」**(有「已成立」,那是**狀態**不是動作)。
  → 這一列**沒有替代詞可指**,`use_instead` 只能是 NULL + 必填理由。
  **不准為了讓 FK 過而指去「已成立」** —— 那跟跨 run 硬配對是同一種造假,只是縮到一列。

→ **預測:2 / 2 份訪談產出都出現這個破口,而且散文自己看不出來。**
落空條件:兩處的「一律改用」其實都在詞彙表裡(表示我漏看了某一列)。

### P6 子表的列數:散文 6 列 → **15 列**,而其中 **6 列沒有替代詞**

本輪那份 1.1 的「禁止裸用的詞」一格裡塞了好幾個講法(「會員 / 買家 / 使用者」是 3 個)。
一個詞擋得掉好幾種講法 —— 那正是 ADR §4 說的一對多。

→ **預測:散文 6 列展開成 15 列;其中「購物車 / 草稿單 / 未完成訂單」3 列、「商品名稱」1 列、
「訂單狀態變更 / 狀態機」2 列,共 6 列沒有替代詞**(散文寫「(不得使用)」),
必須靠 `no_replacement_note` 才分得出「真的沒有替代詞」與「還沒填」。
第二幕那份 4 列 → **10 列**;凍結那份的散文只有一句話(「不要把 Order 叫成 Purchase、
不要把成立叫成 confirm」)→ **2 列**。
落空條件:任何一份的展開數不是 15 / 10 / 2。

### P7 子表**不能有自己的五格來源標記,也不能有 NOT NULL 的「為什麼」**

兩份語料的 1.1 表**欄位不一樣**:本輪那份是 禁止裸用的詞 | **為什麼** | 一律改用
(**沒有來源欄**);第二幕那份是 禁止裸用 | 一律改用 | **來源**(**沒有為什麼欄**)。

→ **預測:硬要一個 NOT NULL 的「為什麼」會逼第二幕那份憑空生出理由;
硬要五格 provenance 會逼本輪那份憑空生出來源標記。** 兩者都是「鎖清單逼出假資料」
(ADR §4 殺掉固定 DDD 型態清單的同一條理由),只是換成**欄位存在性**而不是值域。
→ 本輪的做法:子表只有一格 `note`,**逐字裝散文那一列多出來的那格**(有為什麼就裝為什麼、
有來源就裝來源)。三份語料每一列都有東西可裝,所以 NOT NULL 是安全的、而且沒有捏造。
落空條件:找得到某一列兩格都空(那 NOT NULL 就會逼出假資料,要改成可空 + 理由)。

### P8 對譯檢查做成 FK 會**量不到上面任何一個數字**

`glossary_terms` 是選填的,而**三份語料裡沒有任何一份的 wire 合約對得到自己的詞彙表**
(P1 的 0/7、P2 的 1/5)。做成 FK:第二幕那份**匯入直接失敗**,凍結那份也只進得了 1 欄。

→ **預測:FK 版本的產出只有「匯入失敗」四個字,拿不到「差幾個、差哪幾個」。**
這就是 ADR §5 不做 FK 的理由,而上面的 N 是它的證據。
落空條件:找得到一種 FK 寫法能同時擋住又報得出差額(找不到,那是兩種東西)。

## 已知上限(**三條全部印進報表**,不是只寫在票裡)

1. **「類別名必須來自清單」對不上「一個詞可以有多個類別」。** 詞彙表有「訂單」,
   實作可以正當地長出 `Order` / `OrderItem` / `OrderRepository` / `OrderController`。
   白名單比對會把正當的衍生名判成違規 —— **所以本票不做任何類別名檢查**(那是 08-B,未決)。
2. **禁用同義詞的檢查容易假陽性。** `customer` 出現在 `customerId` 是對的,出現在
   `CustomerService` 也是對的。跟票 03 同一種病:**懲罰寫得好的那一方**。
   → **所以本票只把禁用同義詞變成「查得到的清單」,一行機械掃描都不做。**
3. **中文詞 ↔ 英文識別字的對譯沒有唯一解。**「客人編號」→ `customerId` 是訪談者**選**的,
   不是推導出來的。這條檢查只驗得了「對得到一個詞」,**驗不了「對到的是正確的那個」**。
   → P1 就是這條上限的量化版本:機器對不到,不是因為對譯錯了,是因為**沒有人把選擇寫下來**。

外加本輪量到的兩條:

4. **空白裝了三種東西**(P4),計數分不開。
5. **撞名不是對譯**(P2):它只在詞彙表本身用英文識別字寫的時候會亮,中文詞**永遠**走不到
   那條路。撞得到 ≠ 這份規格有做對譯。
