## 每一份 prompt 都要寫死的四句(subagent 預設不會做)

1. **先寫預測,而且 commit 在實作之前。** 預測落成
   `.scratch/ddd-harness/<NN>-PREDICTION.md`(格式照既有的 `03-PREDICTION.md`),
   先 commit,再開始寫 code。
2. **預測要挑得出「哪個結果會讓它落空」。**
   「落檔數 > 0」「標記數 > 0」這種不可能失敗的寫法**不算預測**(票 03 的教訓)。
   落不了空的預測 = 這一輪白跑。
3. **已知上限要印進報表**,不要只寫在票裡。讀報表的人拿不到票。
4. **完成 = tooling 綠,不含「量到差異」。** 量差異要付費跑一次落檔 agent,**併到下次**。
   不要為了「看到數字」自己去跑。

外加一條本輪新增的:

5. ⚠️ **「不適用」不准算成「通過」。** 沒東西可查的時候,報表要讓它自成一類、印在最上面
   (ADR 0005 §6)。折進「通過」的計數就是這條線最常見的那個坑。

**做什麼**:一支跑完之後對 run 目錄跑的檢查(**選項 B**,跟 `provenance_check.py` 同一層)。
逐輪比對:每一輪的每一題題號,要在**下一輪開頭那張落點表**裡出現。

**不要做**:不開任何 schema 表(這張票的產物是報告,不是中途產物);不動 `orchestrate.py`
(那是選項 A,沒有被選)。

**原料**(逐輪已經分開落地):
`examples/shop/harness/runs/2026-08-18-act1-opus-rerun/rounds/rN-{questions,answers}.md`,
以及 `SPEC-draft.md` §11 那張收尾的逐題落點表。

**判準要刻意寫笨。** 寫成「大致上都有記到」這張票就白開了。明確答「沒有」「還沒想過」的
**也算落點** —— 它們該進 §4 或未答追蹤,不是消失。

**已知上限(印進報表)**:題號出現 ≠ 記對了。這個檢查抓得到「整題消失」,

**「不適用」的實例**:最後一輪沒有下一輪,沒有落點表可比。那是不適用,**不是通過**。

## 派工 B —— 票 06-A:`domain_contract`(先做,動 schema.sql)

**做什麼**:讓 §3 領域契約在 store 裡有位置與分診。原料是
`examples/shop/harness/runs/2026-08-18-act1-opus-rerun/SPEC-draft.md` 的「領域規則」一節。

**形狀照 ADR 0005 §1–§3,逐條不得自行更動。** 特別是:

- `enforcement` / `ladder_note` / `enforced_by` **跟「指名測試」是兩欄,不准合併。**
  合併就是把 invariant → example 的降級蓋住,而那正是這張票要抓的東西。
- **預期大多數列的 `enforcement` 會誠實寫 `none`。那是產出,不是失敗** ——
  數字難看不要去湊。
- 「指名測試」關聯表的「零列時必填理由」那條規則,SQLite 的 CHECK **寫不出來**,
  它住 `spec_store.py` 的**第 2 階**。註解不准把它講成第 1 階。
- 「守在哪個**物件**內」—— 不是「聚合根」。C8 填的是 Value Object。
- 「處置」存**本文**,不准存「見 §9」。

**順手補**:`PRAGMA foreign_keys` 的**行為**測試 —— 驗 FK 真的擋得住,
不驗「那一行還在」。⚠️ 它有兩份載體(`schema.sql:15` / `spec_store.py:581`),
而且 `schema.sql` 那份實測是生效的;測試要做到**任一份被刪都會紅**。

**可落空的預測寫法舉例**:落檔後「有指名測試」的契約會**少於一半**。
(「契約落檔數 > 0」不可能失敗,不准用。)

⚠️ **schema 註解不要寫具體資料值** —— agent 讀得到,寫進去就是洩題。
2026-08-18 已經因此洩過一次(Alice / Bob)。

## 派工 C —— 票 08-A:`glossary_term`(等 06-A 落地後才開始)

**做什麼**:讓 §1 詞彙表在 store 裡有位置,加一條第 2 階的對譯檢查。
原料是同一份 `SPEC-draft.md` 的「一、GLOSSARY(§1)」與「1.1 禁用同義詞清單」。

**形狀照 ADR 0005 §1、§4、§5,逐條不得自行更動。** 特別是:

- **「DDD 型態」是自由文字**,不准做成固定清單,而且表註解要明寫它只住**第 4 階**。
- **「對外欄位名」可空,空白 = 這個詞不上線,不是漏填。**
- **對譯檢查是第 2 階報告,不是 FK。** 做成 FK 就量不到「差幾個」,而這張票的價值
  就在那個數字。

**已知上限(印進報表,三條全部)**:

1. 「類別名必須來自清單」對不上「一個詞可以有多個類別」(訂單 → `Order` /
   `OrderItem` / `OrderRepository` 都是正當衍生)。
2. 禁用同義詞的檢查**容易假陽性**(`customer` 出現在 `customerId` 與 `CustomerService`
   都是對的)—— 跟票 03 同一種病:**懲罰寫得好的那一方**。
3. 中文詞 ↔ 英文識別字的對譯**沒有唯一解**。「客人編號」→ `customerId` 是訪談者**選**的,
   不是推導出來的。所以這條檢查只驗得了「對得到一個詞」,**驗不了「對到的是正確的那個」**。

**預測的起點已經量過一次了**(手算,見 ADR 0005 §5 那張表):真正餵進第二幕那份規格的
詞彙表對上落檔出來的 7 個列表欄位,`orderId` 完全對不到、`totalCents` 單位漂了、
`status` 對到的是值不是欄位。**寫預測時要比這個更精確,不要再寫「落檔數 > 0」。**

**不要碰 B 半**(命名類的第四個 ArchUnit rule kind)—— 「實作層要不要驗」這一題
**還沒拍板**,它牽到「這條線要不要開始約束實作的內部命名」,是要當面決定的取捨。
