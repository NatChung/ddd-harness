# 票 03 的預測(寫在寫程式之前,2026-08-18)

偵測器要拿已知陽性驗,而且**漏抓的預測要寫在跑之前** —— HL1 那次的規矩。
這裡先寫死:它抓得到什麼、抓不到什麼、以什麼形式出貨。

## 它做什麼

規格裡標 `[Qn]` 的**具體值**(數字、格式字串、識別碼),應該出現在
**需求方那一輪的回答文字裡**(`rounds/rN-answers.md`)。找不到 = 標記。

**只讀產物,不碰儀器** —— 不動訪談 prompt、需求方 prompt、orchestrator、schema。
(停損規則:偵測器不是儀器改動,不汙染 opus 那跑的可比性。)

## 兩個已知陽性(形狀不同,門檻已達)

| 形狀 | 語料 | 該被抓到的東西 |
|---|---|---|
| **B 訪談者餵值再標成親口確認** | `runs/2026-08-18-act1-interview/` | `SPEC-draft.md` 說 100/120 是「他在 Q9 親口確認的」,而需求方回答裡**沒有 100 也沒有 120** |
| **A 需求方自己編** | `runs/2026-08-18-act1-haiku-roleplay/roleplay/` | `ORD-20260818-001`、「秒級」——**出現在答案裡**(所以本檢查抓不到,見下),但不在凍結 SPEC 裡 |

## 預測:抓得到 B,**抓不到 A**

**這是設計上的,不是缺陷 —— 但一定要先寫下來。**

- **B 抓得到**:值不在答案文字裡,字串比對就現形。
- **A 抓不到**:需求方**真的說了** `ORD-20260818-001`,值就在答案裡,本檢查放行。
  A 要靠**票 04**(需求方回答 vs 凍結 SPEC),那是另一個比對、另一份基準。
  → **兩張票各做各的,合起來才完整。** 只做 03 就宣稱「來源可信」是錯的。

## 其他預測的漏抓(逐條寫死)

1. **同義改寫 / 單位換算**:答案說「一百二十元」,規格寫 `12000`(cents)。
   字串比對必漏。**這是最常見的一種,漏抓率會很高。**
2. **暗示但沒說出口**:需求方說「跟前面那個一樣」,規格把前面那個值填進去。
3. **跨輪引用**:值出現在第 2 輪答案,規格標 `[Q9]`(第 3 輪)。
   → 緩解:比對**全部答案語料**而非單輪,代價是抓不到「標錯輪次」。**選前者。**
4. **假陽性**:規格作者自己算出來的值(總額 = Σ 單價×數量)本來就不會出現在答案裡,
   但它標的是 `推導自` 不是 `[Qn]`。→ **只掃 `[Qn]`,不掃 `推導自` / `本案自決`。**

## 出貨形式:分診佇列,不是判決

跟 mutation testing 那次一樣。上面第 1 條(單位換算)就足以讓它不能當判決用。
**報表要自己講出這個上限**,不要讓讀的人以為「零標記 = 來源都可信」。
