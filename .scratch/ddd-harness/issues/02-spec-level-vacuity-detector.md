# 02 — 規格層假驗收的偵測器:等第二個已知陽性

**What to build:** 一個抓得到「代理編碼」的偵測器 —— 情境的 fixture 不包含它的
Given/When 所描述的動作,於是**那條斷言不可能因為它宣稱要測的原因而失敗**。

**現在刻意不做。** 目前只有**一個**已知陽性:

> **S10「商品事後調價,舊訂單金額不動」** 被編成「同一商品送兩筆不同單價的訂單,
> 各自斷言自己的金額」。沒有任何東西調過價 —— 兩條斷言都只是「app 有沒有把送進去的
> 值回傳回來」,而那是 S1 早就測過的事。

而這個 repo 的鐵律是:**一個樣本證明不了偵測器,做偵測性工具要先找兩個形狀不同的
已知陽性。** 假驗收那輪就是這樣量出來的 —— HL2 上看起來很好的主指標,拿 HL1 一驗
當場漏抓,而那次漏抓在跑之前就預測到了。

**這一格跟前兩個已知陽性不同層,所以不能沿用那套工具:**

| | HL1 / HL2 | S10 |
|---|---|---|
| 層 | 斷言層(測試恆真) | **規格層**(情境的語意被誤述) |
| mutation testing | 抓得到(有上限) | **抓不到** —— 程式有被測到,是情境宣稱錯了 |

**已經做了的那半(不需要偵測器):** `acceptance_scenario.proxy_for` 欄位。
fixture 若不包含 given_when 描述的動作就必須填,`SELECT ... WHERE proxy_for IS NOT NULL`
就是分診佇列。**它不是偵測器** —— 擋不住存心不填的;買的是「誠實的情況查得到」,
而 S10 那次是 agent 自願揭露的,自願的東西換個模型就沒了。

**怎麼拿到第二個陽性(不要等它自己撞上來):** 下次跑第一~四幕時,把
「找出這輪有沒有代理編碼」列成產出的一部分。

**Blocked by:** **再度 blocked(2026-08-18 稍晚重新判定)—— 缺的是「不同密度」的第二個樣本。**

~~第二個形狀不同的已知陽性~~ —— 2026-08-18 的第二幕重跑拿到了,而且是三個。
**但那三個(S8/S9/S12,形狀 B)與原本那個(S10,形狀 A)來自同一份 `input-SPEC.md`
(逐位元組相同)** —— 形狀不同,**密度相同**。

⚠️ **這正是票 03 崩掉的那個坑。** 03 也是拿兩個「形狀不同、密度相同」的陽性當門檻,
結果換到第二份規格上精確度 100% → 0%。03 自己把教訓寫下來了:

> 「兩個不同的樣本」不夠,要問:**不同在哪個維度?那個維度會不會讓它失效?**

**這張票的樣本在「密度」這個維度上沒有變異,而假驗收偵測器最可能失效的正是那個維度**
(規格寫得越細,可疑的候選越多 —— 同 03 的「假陽性率與規格品質正相關」)。
→ **要等第二份密度不同的規格**,而那要等骨架跑通、幕四產出一份新規格才拿得到。

## 已知陽性(現在有兩種形狀)

| 形狀 | 實例 | 長相 |
|---|---|---|
| **A 替換動作** | S10 | 用「同商品的第二筆訂單」近似「調價」—— 至少還動了兩筆資料 |
| **B 替換整個前提** | **S8 / S9 / S12** | 建一筆正常訂單、斷言它長得正常,宣稱那覆蓋了「拒絕」或「故障」 |

**B 比 A 難抓得多**:它的斷言集合跟 S1(單純的成功情境)幾乎一模一樣。
S12 最極端 —— 「系統寫到一半掛掉,不該留下任何東西」被編成「建一筆訂單,斷言它存在」。

**偵測器至少要在這兩種形狀上都不漏抓**,而漏抓的預測要寫在跑之前
(HL1/HL2 那次的規矩)。全部四條的原文在
`examples/shop/harness/runs/2026-08-18-act2-rerun/`。

## 同時要處理的:`proxy_for` 是逃生口

那一跑量到:加了 `proxy_for` 之後,**落檔率從 4/12 變成 12/12,而真實覆蓋只有 8**。
它把「表達不出來」這個硬失敗訊號降級成軟註記,於是**落檔率不再是覆蓋率的代理指標**。
偵測器要回答的不只是「哪些是代理編碼」,還有**「代理編碼要不要算落檔」**。

**Status:** **blocked** —— ⚠️ **但解 blocked 的第一項條件 2026-08-19 可能已滿足**(4 個 `proxy_for` 來自一份不同密度的規格,成因是新的一種「概念不存在」)。清單另兩項(偵測器在兩個上都不漏抓 + 漏抓的預測寫在跑之前)仍未做。**與票 15 併場 grill**,見檔末。

## 2026-08-19 · 可能可以解 blocked 了(**要逐條對清單,先不要直接解**)

本票的 blocked 條件是「缺的是**不同密度**的第二個樣本」。

`runs/2026-08-19-act2/acceptance.yaml` 有 **4 個 `proxy_for`**,而它來自一份
**完全不同的規格**:`runs/2026-08-19-act1-human-stakeholder/SPEC-draft.md`
(42,601 B,**真人需求方**六輪 30 題的產出;兩段式結帳/付款、有運費與庫存鎖),
與 `input-SPEC.md`(25,598 B)**沒有任何位元組關係**。**密度不同。**

成因也是新的一種:

| | 成因 |
|---|---|
| 先前那批(S10 / S8 / S9 / S12) | **動作**不存在 —— schema 沒有「調價」這個動作 |
| 今天這批(G1 / G2 / G13 / G17) | **概念**不存在 —— fixture 詞彙裡沒有「運費」;本檔沒有「身分」 |

實例(G13 的自白原文):

> 散文的 When 是「**後台人員**呼叫 GET /orders」。本檔沒有身分…故此處以「不帶身分呼叫列表」
> 代替「後台人員呼叫」,驗的是「三張都在同一份列表裡」,**驗不到「後台人員」與「用戶」的
> 可見範圍差異**。

⚠️ **只滿足清單第一項。** 本票還要求:偵測器在兩個上都不漏抓,**而且漏抓的預測寫在跑之前**。
那還沒做,所以 **Status 不動**。

⚠️ 另一個要當場檢查的:今天這批**是 agent 自願填的**,跟先前那批一樣。
**自願的東西換個模型就沒了** —— 拿自願樣本當偵測器的訓練/驗證集,本身要先想清楚。
