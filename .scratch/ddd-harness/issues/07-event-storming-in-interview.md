# 07 — Event Storming 要不要進訪談 prompt

**這是第六題** —— 十三題裡唯一還沒答的一題。這張票是把它從口頭懸念變成可追蹤的決定,
**不是要開工實作**。

**What to decide:** 訪談 prompt 要不要納入 Event Storming 的機制;納入的話納入哪一個部分。

## 現況:訪談是被動的

追問表的每一列都長成「**他說出這種話 → 你追問**」。需求方講出某個句型,訪談者才追問。
**他沒講到的東西,只能靠訪談者盯著四格盤點猜哪裡空著。**

Event Storming 是主動掃時間線:事件按時間排一排,**空隙自己會現形**。

## 買到什麼(四條,每條都指得出這條線上的實際漏洞)

| | 買到 | 這場訪談的對應漏洞 |
|---|---|---|
| 1 | **逼出「之前」** | 從頭到尾沒人問「訂單成立**之前**發生什麼事」。草稿那段是需求方自己在 Q9 講出來的,**不是被問出來的** —— 換個需求方就沒了 |
| 2 | **逼出 policy** | Q17 只問了「有誰要被**通知**」,沒問「這個事件之後有沒有規則會**自動做下一件事**」。追問表只有「…之後,要…」這個句型,而需求方不會用那個句型講話 |
| 3 | **邊界從事件聚集浮現** | 目前判定「會員是界外」的依據是 Q7 那一句「那是另一套系統在管的」—— **單點證據**。Event storming 是看事件之間的時間 / 責任斷點 |
| 4 | **事件名是詞彙表的原料** | 詞彙表現在是**從答案裡撈裸詞**,需求方沒提到的詞就不存在 |

## 代價(先寫下來,因為它可能只換來形式)

- **Event Storming 本來是給一群人開工作坊用的。** 一面牆、便利貼、爭論。
  它有一半的價值在「不同部門的人當場發現彼此講的不是同一件事」——
  **單一需求方(agent 或真人)沒有那個場**。
- **跟 5 個決定點上限直接打架。** 第一步「把你想得到的事件全講出來」是開放式問題,
  一次可能倒出 20 個,而那條上限的理由(超過會漏答)在真人身上仍然成立。
- ⚠️ **最可能的失敗模式:訪談者自己列一堆事件,問「這樣對嗎」,需求方說「大概吧」。**
  產出的是**訪談者的模型 + 需求方沒否認**,而它照樣標得出合法的 `[Qn]`
  —— 那正是票 03 形狀 B 那個病,**而票 03 的偵測器對它精確度是 0%**。
- **開放式問題會放大票 04。** 需求方 agent 已知不穩定;把一個「你自己講」的大題丟給它,
  變異只會更大。

## 建議的最小形狀(草案,不是定案)

**不要整套搬進來,取它的一個機制:在某一輪插入「時間線掃描」。**

問法要是需求方答得出來的口語,不要出現「事件」這個詞:

> 「**從客人開始挑東西,到你在清單上看到那張單,中間依序發生了哪些事?**」

三個好處:

1. **算一個決定點**,不炸上限;
2. **不誘導** —— 他自己講順序,而不是訪談者列一張表請他點頭;
3. **可以被機械檢查** —— 掃出來的每一個時間點,要在 §2 GWT 或 §5「明確不在範圍」
   找得到落點,找不到就是漏接。**這正好是票 05 要做的那種檢查的形狀。**

## ⚠️ 動它就是改受測品

`tools/harness/interview-prompt.md` 是受測品。`act1/README.md` 的規矩:
**改了任何一個,後續的跑就不能跟先前的比** —— 要當成新版本,並在 run 的報告裡標明。

所以這張票真的要做的話,順序是:**先寫預測 → 改 prompt(標版本)→ 重跑 → 跟現有那跑比**。
比什麼要先講清楚,不然「多問了一輪、規格變長了」會被讀成「變好了」。
可落空的預測舉例:**預測時間線掃描會逼出至少一條現有規格完全沒有的行為
(而不是把既有的講得更詳細)**。
