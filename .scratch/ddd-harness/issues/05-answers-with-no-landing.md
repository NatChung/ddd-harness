# 05 — 中途沒有任何檢查在看「這個答案有沒有落點」

**What to build:** 一個機械檢查:逐字稿裡的每一個答案,都要指得出它落到規格的哪一節、
哪一條編號。指不出來的 = 漏接,當場報出來,而不是等收尾。

## 為什麼現在漏得掉

第一幕唯一的機械檢查是 `relay_ledger.verify` —— 它只問**「每一輪的答案有沒有被轉交」**。
轉交了之後那個答案有沒有被記進落點表、有沒有進最終規格,**它一概不看**。

而「每個答案都指得出落點」這條判準是存在的,寫在 `interview-prompt.md` 第六節 §11:

> **完成判準:逐字稿裡的每一個答案都指得出落點。指不出來 = 漏接。**

問題有兩層:

1. **只在收尾時查一次。** 四輪跑完才查,而那時漏接的那一輪早就滑過去了 ——
   訪談者不會在第三輪回頭問「Q7 你上次那句我好像沒記」。
2. **是 agent 自己查自己。** §11 那張表由訪談者自己寫,漏接的答案通常也不會出現在
   它自己列的表裡 —— **漏了的東西不會知道自己漏了**。

中途唯一的記錄是**落點表**(每輪開頭貼的那張「他說的原話 / 我記成什麼 / 來源標記」)。
它是散文、在訊息裡、不是檔案,**沒有任何東西在讀它**。

## 這是哪一家族

同一條病的又一個實例:**規則寫得可被形式滿足,就會被形式滿足。**
「完成判準」寫在產出合約裡,但**實際會執行它的只有被檢查的那個 agent 自己**。

以及另一條:**寫在該寫的地方 ≠ 接上了。**
判準寫進了 prompt,而管線裡沒有任何一步讀它。

## 怎麼做(草案,實作前要先寫預測)

原料是現成的、逐輪落地的:

- `rounds/rN-answers.md` —— 答案語料
- `rounds/rN+1-questions.md` —— 下一輪開頭那張落點表(記到了什麼)
- `SPEC-draft.md` §11 —— 收尾時的逐題落點表

最笨、最先該試的版本:**每一輪的每一題題號,要在下一輪的落點表裡出現**
(明確答了「沒有」「還沒想過」的也算落點 —— 它們該進 §4 或未答追蹤,不是消失)。
判準要刻意寫笨,寫成「大致上都有記到」的話這張票就白開了。

⚠️ **先寫預測再動手**,而且預測要挑得出「哪個結果會讓它落空」——
不要再寫一次「落點數 > 0」那種不可能失敗的預測(見票 03 的教訓)。

⚠️ **已知上限先寫下來**:題號出現 ≠ 記對了。這個檢查抓得到「整題消失」,
抓不到「記成別的意思」。後者是不同的檢查,不要混進來當賣點。

## 為什麼不是「邊問邊把詞彙表落檔」

考慮過、否掉了。中途落檔會把候選當定案:

- 「金額」第一輪只是裸詞,幣別 / 單位 / 有沒有小數要到第二輪才問到,
  相等性判準更後面 —— 第二輪落點表寫的是**候選**,不是定案。
- §4 Domain Event 那節**不得為空**。提早開一個空的 events 檔會誘發「湊幾個進去」;
  現在的做法是等問到,然後把「沒有」**寫成一句話**。

所以這張票要的是**檢查**,不是**中途產物**。

**Blocked by:** None —— 原料在 `examples/shop/harness/runs/2026-08-18-act1-opus-rerun/rounds/`,
四輪的問題與答案都逐輪分開落地。

**Status:** **done**(2026-08-18,選項 B 落地為 `tools/harness/landing_check.py`;見本檔末「落地紀錄」)
## 先決定的一題

**這個檢查跑在哪一段?** 三個選項,決定它抓得多早:

| | 什麼時候跑 | 抓得到 | 代價 |
|---|---|---|---|
| A 每輪之間 | orchestrate 在轉交下一輪前跑 | **當場**,還來得及重問 | 要能中斷/回饋給訪談者,orchestrate 要多一條路徑 |
| B 跑完之後 | 跟 `provenance_check` 一起,對 run 目錄跑 | 事後,只能當報告 | 最便宜,不動 orchestrate |
| C 只驗收尾 | 只比 §11 那張表 vs 逐字稿 | 事後,而且信 agent 自己寫的表 | 幾乎沒買到東西 |

A 最有價值也最貴(而且它會讓訪談者知道自己被查 —— 那本身可能改變它的行為,
要當成受測品的變更處理)。B 是先做得出來的那個。**不要直接挑一個開工。**

## 2026-08-18 · 稽核後補洞:一條靜默綠燈路徑(AUDIT §二.A)

**上面那份落地紀錄漏報了一件事,而且漏的正是這張票宣稱避開的坑。**

05-PREDICTION 的落空條件明寫:「interview 那場印出綠燈 → 犯了票 03 那條**掃不到東西
不算通過**」。實作的守衛是 `if comparable_rounds == 0: return 1` —— 它擋的是
**「沒有成對的 rN/rN+1 檔」**,不是「一題都沒比對到」。**只避開了一半。**

檔案成對、而題號的正規式一個都沒認出來,那一輪照樣算 `compared`、`asked = 0`、
漏接 0。獨立重現(**不用改任何一行 code**):把 `runs/2026-08-18-act1-opus-rerun`
複製一份,只把題號寫法 `**Q1.` 改成 `**Q1:`(4 個檔 20 處,其他一字不動)——

```
小計:可比對 3 輪 / 0 題;通過 0、漏接 0;另有 0 題不適用(未檢查)。
REAL_EXIT=0
```

**一份原本有 15 題可查的 run,因為訪談者換了個標點,靜靜地變成綠燈。**
而 `test_landing_check.py` 當時 14 支測試沒有一支蓋這條路
(`test_沒有逐輪提問檔_不算通過` 蓋的是 `rounds == []`,是另一種情況)。

這正是 `schema.sql` 對 `res_total_field` 那句警語的形狀——
**守衛沒有壞掉,是不再適用了,而不適用不會有人發現**——只是這次發生在
為了防這件事而寫的那支檢查自己身上。

### 修了什麼

1. **「這一輪一題都沒認出來」= 不適用,不是通過**(`na_kind = "no_questions"`)。
   它是**異常的**不適用,跟「最後一輪」那種預期之內的分開記、分開印。
2. **一輪都比不了 = 整份不適用 → 離開碼 3**,跟「有漏接」(1)分得開。
   `landing_check` 因此跟 `contract_triage` / `glossary_check` 對齊
   (0 / 1 / 2 / 3),CI 只看離開碼也分得出「全過」與「什麼都沒查」。
   ⚠️ 「只有答案檔的舊 run」那份從 exit 1 變成 exit 3 —— 預測只釘了「exit ≠ 0」,
   **凍結的預測檔沒有被動到**。
3. **「掃到卻掃錯」也一起關掉**:粗體題號但判準認不出來的寫法(`**Qn:`、`**Qn)`)
   單獨印成「題號寫法可能漂了」,並把離開碼頂成 1 ——
   **混合形狀**(15 題裡只認出 1 題)整份不會掉到 0,exit 3 那條救不了它。
   近似比的是**位置**不是集合:同一輪 `**Q1.` 與 `**Q1:` 併存時,集合相減會吃掉後者。
4. 順手修掉 §三.2 那條**假理由**:輪次斷號(有 r1、r3,沒有 r2)時,第 1 輪印的是
   「沒有 r2-questions.md(**最後一輪**)」—— 分類沒錯,理由是假的。
   現在分成 `gap` 與 `last_round` 兩種,而 `gap` 算異常(離開碼非 0)。

### 關不掉的那一半(已印進報表的上限段)

**題號連粗體都不用的漂移,這支看不見。** 近似只認得出**粗體**的 `**Qn`;
訪談者寫成 `Q1:` 或 `1. …`,這支既認不出題號、也吵不出近似 ——
那一輪會落進「不適用」(**不會假綠燈**),但報表**分不出「真的沒問一題」與
「寫法完全不同」**。

### 新增的守衛(7 支,`test_landing_check.py` 15 → 22)

`test_題號寫法漂掉的run_不算通過而是整份不適用` 把上面那個重現**變成永久測試**
(複製真 run、就地改標點、**當場斷言改到 4 檔 20 處**再驗 exit 3)、
`test_整份不適用的離開碼跟有漏接分得開`、`test_一輪認不出題號_混在正常輪裡也要吵`、
`test_近似寫法混在認得出來的輪裡也吵得出來`、
`test_近似寫法在四份真實語料上不假陽性`(近似要是對真資料亂吵就會被關掉)、
`test_引用形式不算近似寫法`、`test_輪次斷號的不適用_理由不准謊稱是最後一輪`。

**逐個驗過會紅**:把 `landing_check.py` 還原成稽核當下那一版,這 7 支加上
`test_沒有逐輪提問檔_不算通過` 共 **8 支翻紅**;headline 那支的訊息是
`assert 3 == 0`(comparable_rounds 應為 0,舊碼算成 3 輪)。

### 補一刀:修的當下自己又寫了一次假理由

小計那句「其中 N 輪是**異常的不適用**」原本讀的是整份 `anomalies`,
而那裡面還裝著「**比對過了、也通過了**、只是同一輪另有一個認不出來的寫法」的
compared 輪 —— 於是一輪通過的會被講成「異常的不適用」。
**那正是這一輪要修的 §三.2 那個病(分類對、理由假),寫進了修它的那個 commit。**
過濾成只講 `status == not_applicable` 的輪,並補
`test_異常摘要不准把比對過的輪講成不適用` 釘住(拿掉過濾就紅)。
