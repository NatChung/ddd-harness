# 01 — 情境的動詞集合:step 只表達得了「送出一筆訂單」

**What to build:** 讓 store 表達得了「送出訂單」以外的動作,使 S8 / S9 / S12 落得了檔。

2026-08-18 量到:訪談產出的 12 條情境,只有 4 條進得了 store。8 條落不了檔,
而那 8 條是**兩種**洞 —— 一種是 fixture 違法(5 條),已由 ADR 0003 解決;
另一種是**動詞不夠**,就是這一張票:

| 情境 | 需要的動作 |
|---|---|
| S8 修改已成立的訂單,拒絕 | 對既有訂單發動修改 |
| S9 取消已成立的訂單,拒絕 | 對既有訂單發動取消 |
| S12 寫到一半掛掉 | 注入持久化故障 |
| (S10 調價後舊單不動) | 調整商品單價 —— 目前是**代理編碼**,見 issue 02 |

**為什麼跟 ADR 0003 分開做:**(a) 是放寬/搬移約束,(b) 是**在 store 裡長出一套動作
模型** —— 要決定一個情境可以有幾個動作、動作之間的順序與狀態怎麼表達,
那實質上是在 store 裡重建 BDD 的 Given/When 序列,是新的建模工作不是擴充。
兩類混在一起做,做完會不知道是哪一半讓驗收過的。

**已知會先撞到的限制:** ADR 0003 把 `expects_rejection` 掛在**情境**上,所以一個情境
不能同時有「成功的前置訂單」與「被拒的請求」。S8 正是那種形狀
(given 一筆已成立的訂單 → when 改它 → then 拒絕)。**做這張票要重審 ADR 0003。**

**先問再做的一題:** S12 在訪談那份規格裡是 `本案自決` 的技術判斷,**不是需求方說的**
—— 它可以整條不做。真正來自需求方的只有 S8 / S9 兩條。所以第一步是問 Nat:
這張票要做三條還是兩條。
