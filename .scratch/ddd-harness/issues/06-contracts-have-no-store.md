# 06 — 微尺度沒有進 store:invariant 被降級成 example

**What to build:** 讓 §3 的領域契約(C1…Cn)在 spec store 裡有自己的位置與檢查,
而不是只活在散文裡、只靠「有一條情境剛好蓋到它」間接成立。

## 事實

`schema.sql` 目前 14 張表:

```
authorized_template / architecture_rule / forbidden_dependency /
forbidden_annotation / forbidden_return_type / wire_contract / wire_list_field /
acceptance_scenario / scenario_step / step_item / rejected_request /
rejected_request_item / scenario_assertion / rejected_assertion
```

**沒有任何一張放契約。** 大尺度有 `architecture_rule`(而且配了 `gen_archunit`),
小尺度有 `wire_contract`(而且生成器兩側都讀它),**微尺度什麼都沒有**。

於是 C1「總額 = Σ(數量 × 單價)」進得了 store 的唯一形式,是被寫成某一條情境的
`list_field_equals_number` 斷言 —— 也就是它只被**「有一個例子成立」**驗到。

> **規格說「任何時候都成立」,驗收只證明了「S2 這一筆成立」。**
> invariant 被降級成 example。

第 8 課教的是「同一條規則常常兩個載體都要:precondition(拋例外)+ 一條 GWT(驗它真的拋),
**不是二選一**」。目前這條線只有後者。

## 順帶掉掉的另一樣東西

§3 每條 invariant / precondition 必填一欄「**守在哪個聚合根內**」,
而且判定「要看這個聚合根以外的資料 → 這條守不住,標『**跨聚合根,邊界可能錯**』並回報」。

那個標記也只在散文裡。這場訪談的 C3(下單當下客人須存在)就標了跨聚合根 ——
**而下游完全看不到這件事**。§9 要對每條跨聚合根給處置,同樣沒有任何機械檢查在看。

## 這是哪一家族

跟票 05 同一條:**判準寫在產出合約裡,而管線裡沒有一步讀它。**
差別是票 05 掉的是「答案有沒有落點」,這張掉的是「契約有沒有載體」。

## 候選做法(**不要直接挑一個開工**)

| | 做什麼 | 買到什麼 | 代價 / 疑慮 |
|---|---|---|---|
| **A 只落檔 + 分診** | 新增 `domain_contract` 表:編號 / 型態(pre/post/invariant)/ 守在哪個聚合根 / 指名測試 / 來源標記 / 跨聚合根旗標 | 「這條契約有沒有指名測試」變成 SELECT 查得出來;「跨聚合根」變成分診佇列 | 不產生任何可執行的東西。**但它是唯一不 blocked 的那半** |
| **B 生成結構性檢查** | 結構型的 invariant → ArchUnit 規則(例:`Order` 不得有 setter、`items()` 必須回傳複本) | 真的可執行,而且骨架時就紅 | 只蓋得到**結構型**;算術型(C1)這條路走不通 |
| **C 生成契約骨架** | 契約 → 生 Java 的前置檢查 / 例外骨架給實作 agent 填 | 覆蓋最完整 | **會綁實作類名**,跟「驗收刻意不 import 任何實作類別」直接衝突。先想清楚再說 |

## ⚠️ 兩個先寫下來的上限

**一、算術型 invariant 要驗,得先有動詞。** C1 的原文是「**任何改變明細的操作**,
總額必須在同一個方法內重算」。要驗它必須能在一個情境裡**建單 → 改明細 → 再看總額**,
而 schema 沒有「改明細」這個動作 —— **這半段 blocked by 票 01**。
現在的 S2 只證明了「建構當下算對了」,實作只在建構時算一次也會綠。

**二、不要為了讓契約「有機械檢查」而把它塞成一條情境。**
那正是 `proxy_for` 那個病:把「表達不出來」降級成一個看起來有蓋到的軟註記。
契約表達不出來的時候,**要讓它顯眼地表達不出來**。

## 還要先想的一件事

大尺度的 `architecture_rule` 有一欄「**由誰強制**」(指名哪條機械檢查,或明寫
「目前無機械檢查」)。微尺度的表要不要有同一欄?
有的話,**這張票做完之後,大部分契約那一欄會誠實地寫「無」** —— 那是對的,
比讓它空著好。但要先接受那個結果,不要做到一半覺得數字難看又去湊。

**Blocked by:** 部分 —— B/C 的算術型那半 blocked by 票 01(動詞不夠);
**A 完全不 blocked**,原料是 `SPEC-draft.md` 的 §3。

**Status:** **A 半 done**(2026-08-18,`domain_contract` + `contract_named_test` + `contract_triage.py`;見本檔末落地紀錄);**B / C 仍 blocked by 票 01**
⚠️ **實作前先寫預測**,而且預測要挑得出「哪個結果會讓它落空」
(見票 03:「標記數 > 0」那種不可能失敗的預測)。
這張票特別容易犯 —— 「契約落檔數 > 0」同樣不可能失敗。
可落空的寫法舉例:**預測落檔後「有指名測試」的契約會少於一半**。

## 2026-08-18 · 稽核後補洞(AUDIT §二.B / §二.C / §二.D)

三個守衛缺口,**數字一個都沒錯,錯的是覆蓋**。

### 一、分診報表的閘門一支測試都沒有(§二.B)

全 `tools/harness/` 只有 `test_domain_contract.py` 提到 `contract_triage` 一次
(exit 3 那支)。**exit 1 那條路(20 條契約、3 條守不住)一次都沒被斷言過**,
報表的內容也一行都沒被斷言過。稽核的兩個破壞在 24 支測試下**全綠**:

- `return 1 if (crossing or total - with_test) else 0` → 無條件 `return 0`
- **把「有指名測試」折進「宣稱有機械檢查」**(`with_enforcement = with_test`)

第二個是 ADR 0005 §2 明文禁止、也是**這張票整個命題**所在的合併 ——
被折掉了沒有任何一支測試會紅。

補了 2 支:

- `test_有分診項目時離開碼是1而且逐條印得出來` —— 真實轉寫 → exit **1**、
  「契約:20 條」、「有指名測試的:0 條;指不出任何測試的:20 條」、
  「跨聚合根):3 條」、C12/C13/C14 逐條印得出來、上限段也在。
- `test_有指名測試不等於有機械檢查_兩欄分開印` —— 刻意造一個
  **with_test = 1 而 with_enforcement = 0** 的 store(`negative-scenarios.yaml`
  + `named_tests: [S4]`),兩個數字**必須不一樣**;順帶釘住 exit **0** 那條路
  (所以「無條件 return 1」也擋得住)。

**逐個驗過會紅**:重放稽核的 M15 → `test_有分診項目時…` 紅;
重放 M16 → `test_有指名測試不等於有機械檢查…` 紅。兩次都先 grep 確認破壞真的落地。

### 二、`test_載體二` 的「破壞先生效」守衛是恆真形狀(§二.C)

兩支 PRAGMA 測試都寫 `assert PRAGMA_LINE not in schema.replace(PRAGMA_LINE, "")`
—— `PRAGMA_LINE` 一旦跟 `schema.sql` 對不上(空白、換行、大小寫),`replace` 是
no-op,而 `X not in stripped` **恰好因此空洞地成立**。
**這正是本線反覆講的「破壞式驗證要先確認破壞本身生效了」,而它出貨在測試碼裡。**

實測:把 `schema.sql` 的 PRAGMA 只改空白(`= ON;` → `=ON;`,語意完全不變)——
**載體二那支綠著,而它此刻驗的是載體一**(載體一那支會紅,那是運氣不是設計)。

修法:抽出 `_schema_without_pragma()`,**驗破壞本身**而不是驗「改完之後找不到」——
`PRAGMA_LINE in schema`(常數漂了要當場吵)+ `stripped != schema`(replace 不是 no-op)
+ 原本那條。**兩支載體測試都改**,不只被點名的那支。
同一個空白破壞現在**兩支都紅**,訊息直指常數漂掉。

### 三、「處置存本文不存指標」只擋行首(§二.D)

`POINTER_ONLY` 只錨行首,所以 `處置:見 §9` ——**整格就是一個指標,一個字的本文
都沒有**—— 只因為前面多了兩個字就過關。ADR §3 要的是「存本文」,買到的是
「開頭不是『見』」。

補一條 `LABELLED_POINTER_ONLY`:**短標籤 + 冒號 + 指標詞 + 一小段引用,然後就沒了**。
刻意收得窄(「寧可只擋整格就是一個指標的情況」)—— 正當的處置本文裡本來就會出現
「見」字,擋過頭會把真的處置逼成假的。兩邊界線都釘進測試:

| 寫法 | 現在 |
|---|---|
| `見 §9-A9` / `詳見 §9` / `同上` | 擋 |
| `處置:見 §9` / `處置: 見 §9` / `理由:見上` | **擋(新)** |
| `不新增聚合根,詳見 §9-A9` | 放行 |
| `處置:不新增聚合根,檢查移到 application 層` | 放行 |
| `殘留風險見下段說明,處置是不新增聚合根` | 放行 |
| `同 C12 的處置,見上` | 放行 |

**驗過會紅**:把檢查改回只錨行首的舊規則,`test_處置寫成指標會被擋` 翻紅
(`DID NOT RAISE SpecError`)。

### 四、順手驗到的第四個:「五格來源逐字相同」那支測試的名字沒有對應的斷言

稽核 §三.3 列在「可疑但沒驗到底」——**補驗過了,疑點成立。**

`test_五格來源與架構規則逐字相同`(`test_domain_contract.py` / `test_glossary.py`
各一支同名)的內容是「這 4 個值匯得進去」,**跟 `architecture_rule` 一個字都沒比**。
給 `domain_contract` 的值域偷加第六格:

```
mutated ok:第六格 '訪談者判斷'(不是任何測試用過的字串)
194 passed
```

**全綠。** `test_自創第六格來源寫不進去` 只試 `'訪談推測'` 一個字串,換個字就整條漂走
——ADR 0005 §1「**不得為新表發明第六格或改寫格名**」在測試層等於沒有守衛。

修法:讓那個名字兌現 —— 從 `schema.sql` 掃出**四張表**的 provenance 值域,
斷言只有一種寫法、而且逐字是 `'Qn', '暫定', '推導自', '模板既定', '本案自決'`。
少一張表(新增表時漏掛 provenance)也會紅。同一個第六格破壞現在直接翻紅。
