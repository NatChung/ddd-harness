# 08 — 詞彙表沒進 store,所以它只是 glossary,還不是 ubiquitous language

**What to build:** 讓 §1 詞彙表在 spec store 裡有位置,並決定「實作層的命名」
要不要有機械檢查 —— 把目前的「規格層一致」推到「四處一致」。

## 名詞先分清楚

`GLOSSARY` 是檔名 / 節名;**ubiquitous language 是那份表要達成的性質**。
一份詞彙表只有在**每一處都照它**的時候才叫 ubiquitous ——
沒有人遵守的話,它就只是一份 glossary。

## 事實

`schema.sql` 目前 14 張表,**沒有一張放詞彙**。大尺度有 `architecture_rule`、
小尺度有 `wire_contract`、需求尺度有 `acceptance_scenario` 那一組,
**詞彙表跟領域契約(票 06)一樣,只活在散文裡**。

## UL 要一致的四處,現況

| | 一致機制 | 狀態 |
|---|---|---|
| 1 需求方講的話 ↔ 2 詞彙表 | 來源標記 `[Qn]` | ✅ 有(精確度另見票 03) |
| 2 詞彙表 ↔ 4 wire 欄位名 | 訪談者 / 落檔 agent 自己對譯 | ⚠️ **自律,沒有檢查** |
| 2 詞彙表 ↔ **3 實作的類別 / 方法 / 變數名** | — | ❌ **完全沒有東西在看** |

自律那條有實際證據可查:2026-08-18 那跑的訪談者**自己**在落點表多加了一欄
「對外欄位名」,把領域詞跟 wire 名綁在同一列;落檔 agent 也在 yaml 註解寫
「欄位名一律照 §詞彙表對譯,不另創同義詞:客人編號→`customerId`…」。
**兩邊都做對了 —— 而那正是問題**:做對的時候看不出有沒有守衛,
換一個模型就沒了(同「自願的東西換個模型就沒了」)。

## ⚠️ 第 3 條有個結構性張力,不是忘了做

**驗收刻意不 import 任何實作類別**(為了讓兩份長得完全不同的實作能被同一套驗收判定,
見 ADR 0004 的鄰居討論與 MISSION)。那就表示**驗收這條路徑天生看不到實作叫什麼名字**
—— 實作叫 `Order` 還是 `PurchaseOrder`、方法叫 `place()` 還是 `submit()`,
驗收永遠不會知道,而且**這是刻意的,不能靠放寬驗收來解**。

唯一看得到類別名的是 **ArchUnit**。但現有三種 rule kind
(`forbidden_dependency` / `forbidden_annotation` / `forbidden_return_type`)
**沒有一種是命名類的**,而「第四個 rule kind」先前被判定**報酬遞減、延後**
—— 這張票正好是重新評估那個判定的理由。

## 候選做法(**不要直接挑一個開工**)

| | 做什麼 | 買到什麼 | 代價 / 疑慮 |
|---|---|---|---|
| **A 詞彙落檔 + 對譯檢查** | 新增 `glossary_term` 表:詞 / 定義 / DDD 型態 / 單位或表示法 / 來源標記 / **對外欄位名** / 禁用同義詞。再加一條跨列檢查:`wire_contract` 的每個欄位名都要對得到一個詞 | 2↔4 從自律變成機械;禁用同義詞變成查得到的清單 | 不碰實作層。**但這是唯一不 blocked 的那半** |
| **B 命名類 rule kind** | 加一種 ArchUnit 規則:類別名必須落在詞彙表的清單內 / 禁用同義詞不得出現在任何識別字 | 2↔3 真的驗得到 | 要重開「第四個 rule kind」那個判定;而且見下面的上限 |
| **C 明寫放棄實作層** | 不做 B,在 §9 逐條寫「由誰強制:目前無機械檢查(第 4 階)」 | 誠實、零成本 | 那 MISSION 第一條「說明它擋掉哪一種漂移」就只答得出一半 |

## ⚠️ 三個先寫下來的上限

1. **「類別名必須來自清單」對不上「一個詞可以有多個類別」。** 詞彙表有「訂單」,
   實作可能有 `Order` / `OrderItem` / `OrderRepository` / `OrderController` ——
   規則若寫成白名單比對,會把正當的衍生名判成違規。
2. **禁用同義詞的檢查容易假陽性。** 英文字根會撞(`customer` 出現在
   `customerId` 是對的,出現在 `CustomerService` 也是對的)。
   這跟票 03 的假陽性是同一種病:**懲罰寫得好的那一方**。
3. **中文詞 ↔ 英文識別字的對譯本身沒有唯一解。**「客人編號」→ `customerId`
   是訪談者選的,不是推導出來的。所以 A 的檢查只驗得了「對得到一個詞」,
   驗不了「對到的是**正確**的那個詞」。

## 別重蹈的一條

**先寫預測,而且要挑得出哪個結果會讓它落空。**「詞彙表落檔數 > 0」不可能失敗
(票 03 的教訓)。可落空的寫法舉例:**預測 wire 合約的 7 個列表欄位裡,
會有 N 個對不到詞彙表的任何一個詞**。

**Blocked by:** B 那半 blocked 在「第四個 rule kind 值不值得」的判定上;
**A 完全不 blocked**,原料是 `SPEC-draft.md` 的 §1。

**Status:** **A 半 done**(2026-08-18,`glossary_term` + 子表 + `glossary_check.py`;見本檔末落地紀錄);**B 半仍卡在「實作層(2↔3)要不要驗」那個沒拍板的取捨**
## 先決定的一題

**實作層(2↔3)要不要驗?** 這題的答案會決定 B 做不做,而它牽到一個更大的問題:
**這條線要不要開始約束實作的內部命名。** 目前整套設計刻意只約束**邊界**
(HTTP 欄位、package 相依方向),不碰內部 —— 那是「兩個模型都能被判定」買到的自由度。
約束命名會吃掉一部分那個自由度,**而那可能正是對的**(UL 本來就是要約束命名)。
但那是一個要當面拍板的取捨,不是順手做掉的事。

## 2026-08-18 · 共同形狀 grill 的裁決(ADR 0005)

**A 半(詞彙落檔 + 對譯檢查)的形狀已定,見 `docs/adr/0005`。** 摘要:

- `provenance` / `provenance_ref` 五格,與另外三張表逐字相同;白名單 trigger 也掛。
- **禁用同義詞另開子表**,「一律改用」欄 FK 指回 `glossary_term`。
- **「對外欄位名」可空,而空白有語意** —— 「會員系統」「商品價目系統」「內部人員」
  是界外概念,API 上不出現。空白 = 這個詞不上線,**不是漏填**。
- **「DDD 型態」自由文字**,並在表註解明寫它只住**第 4 階**。
  原本要做固定清單,查完兩份實際詞彙表後放棄:它們的型態用語幾乎不重疊
  (凍結那份有「動詞」「狀態的顯示文字」「View Model」;訪談那份有「識別碼」
  「外部規則集」「角色」)。**鎖清單會逼出假資料。**
- **對譯檢查走第 2 階報告,不做 FK。** 硬擋只拿得到「匯入失敗」,拿不到「差幾個」,
  而這張票的價值就在那個 N。
- 新頂層區塊 `glossary_terms` **選填**;「不適用」不准算成「通過」(ADR 0005 §6)。

**已經先手算過一次,答案不是零** —— 拿真正餵進第二幕那份規格的詞彙表(11 個詞,
**連「對外欄位名」這一欄都沒有**)對落檔出來的 7 個列表欄位:
`customerId` / `items` / `currency` / `placedAt` 對得到;
`status` 對得到的是**值**不是欄位;`totalCents` **單位漂了**(詞彙表寫「小數 2 位」);
`orderId` **詞彙表裡根本沒有訂單編號這個詞**。
→ 可落空的預測寫得出來了,不要再寫「落檔數 > 0」。

**B 半(命名類的第四個 ArchUnit rule kind)仍未決** —— 「實作層(2↔3)要不要驗」
這一題**這場沒有拍板**,它牽到「這條線要不要開始約束實作的內部命名」,要當面決定。

### 量到的三個答案

| 語料 | 詞彙表 | 對外合約 | 列表欄位 | 對不到 |
|---|---|---|---|---|
| 凍結那份 | 15 詞(**沒有「對外欄位名」欄**) | `harness/acceptance.yaml` | 5 | **4**(唯一對得到的是**撞名**:詞本身就是那個識別字) |
| 第二幕那份 | 11 詞(**沒有「對外欄位名」欄**) | `act2-rerun/agent-acceptance.yaml` | 7 | **7** |
| 本輪訪談那份 | 17 詞(**唯一有那一欄的**,12 格填得出來) | **不存在** | — | **不適用(不是通過)** |

**唯一做對了對譯的那份規格量不到,量得到的兩份都沒做對譯。**

### 主要發現:機器量到的比手算的難看,而那個差就是這張票

ADR §5 手算第二幕那組是「4 個對得到、3 個有問題」。**機器量到的是 0 個對得到。**
差在哪:那 4 個是**人在腦裡做的翻譯**,規格裡**沒有任何一格記著這件事**。
落檔 agent 確實做對了 —— 它把完整的對譯寫在 `agent-acceptance.yaml` 的**註解**裡。
**做對了,而且沒有留下任何機器看得見的痕跡。** 那正是這張票的命題:
自律換個模型就沒了,而且**連「上一個模型做對了」都證明不了**。

### 順手抓到的三個結構性破口

1. **凍結那份詞彙表寫著「實作中的類別、方法、欄位命名必須使用這裡的詞」,
   而它自己那份合約的列表欄位 4/5 不在表裡** —— 因為那份詞彙表管的是**類名**,
   wire 欄位是另一組詞。散文那句話把兩組不同的詞講成同一組。
2. **兩份訪談產出各有一列「一律改用」指向一個詞彙表裡不存在的詞** ——
   一份叫人改用一個裸詞(表裡只有那個詞的編號版),一份叫人改用一個動作詞
   (表裡只定義了狀態版)。**散文自己看不出這個破口。**
   ⚠️ 措辭要準:**FK 在真實語料上一次都沒有 ABORT** —— 它的存在**逼轉寫當場處理**
   (一份只留得住存在的那半、一份只能誠實記成「沒有替代詞」+ 理由)。
   FK 真的擋得住那一半驗在合成測試裡,不是驗在語料上。
3. **「不適用」有第二種,而 ADR §6 只寫了第一種**:詞彙表有東西、而沒有合約可比。
   這種更難看見 —— 計數上什麼都不缺。報表把它另外印,離開碼一樣是 3。

### 刻意沒做的(不是忘了)

- **B 半一行都沒碰**:不加任何命名類的 rule kind,不掃任何識別字,不看任何類別名。
- **不跨 run 硬配對**:本輪訪談那份規格的情境一份都沒落檔,`runs/` 底下的 act2 產出是
  **別份規格**的 —— 那一份誠實走「不適用」,不借別人的合約湊一個好看的數字。
- **對譯檢查不做成 FK**:做成 FK 只拿得到「匯入失敗」,拿不到上面任何一個數字。
