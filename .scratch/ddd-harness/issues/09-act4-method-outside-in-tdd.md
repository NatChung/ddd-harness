# 09 — 幕四沒有方法論:「填到全綠」不是一個做法

**What to decide:** 幕四的實作要不要走 **outside-in / double-loop TDD**
(外圈 = 生成的驗收,紅著;內圈 = red-green-refactor,直到外圈變綠),
以及要不要外包給既有的 `mattpocock-skills:tdd` / `:implement`。

**這是決定題,不是實作票。** 而且它會**改變骨架那場 grill 要問什麼**(見最後一節)。

## 現況:§10 只說「填到驗收全綠」

那不是方法,是驗收條件。中間怎麼填**完全沒有規定** ——
而那正是 agent 最容易鑽的地方:寫出剛好滿足驗收字面的東西。

幕一有四條鐵律 + 追問表 + 產出合約;幕二有 schema + 兩階檢查 + 完成的定義;
**幕四只有「全綠」兩個字。** 五幕裡唯一沒有方法論的一幕,也正好是唯一沒跑過的一幕。

## 買得到的三件

1. **內圈測試是微尺度的天然載體。** C1「總額 = 各明細加總」寫成 `Order` 的單元測試很自然;
   寫成一條驗收情境就只是**一個例子**(票 06 的核心抱怨)。
   → **06 與本票是同一件事的兩端**:06 問「契約要有什麼載體」,答案可能就是內圈測試。
2. **它是骨架問題的第四個答案。** 先前列的三個是「生成 / 手寫一次 / 從凍結的 app 改」,
   漏了「**TDD 長出來**」。但要切開:
   - **wiring 那半**(啟動、build 檔、生成的測試放對位置)**TDD 長不出來** → 仍要手寫或改凍結的
   - **domain 那半**(`Order` / `Money` / `OrderItem`)**可以從第一個 red 長出來**
3. **「逐條可紅」的紀律往內圈延伸。** 目前那個檢查只在驗收層,內圈完全沒有。

## ⚠️ 三個要先想清楚的

**一、agent 自己寫測試、自己讓它過 —— 這個失效模式本 repo 已經量到過。**
分層實驗的 HL1/HL2,`no-setter` 反射測試**恆真**(掃不到任何真 setter),
測試是綠的而且**不管實作怎麼寫都會綠**。`vacuous_tests.py` 就是為了那件事做的。
→ **無人監督的 agent TDD,產出的內圈測試預設就該假設有恆真成分。**
而 `vacuous_tests` 交的是分診佇列不是判決(它分不出「恆真」與「碰不到」),
所以「用 PIT 守住內圈」目前撐不起來。

**二、內圈測試會綁死實作類別名 —— 而那是刻意被避開的。**
驗收不 import 任何實作類別,才能「兩份長得完全不同的實作被同一套驗收判定」。
內圈測試會 import `Order`、呼叫 `addItem()`。
→ **內圈測試是每份實作各自的,不得算進「全綠」的定義。**
這件事要在 §10 寫死,否則驗收的意義會被污染
(同「代理編碼生到另一個 class」那條:算不算數要用結構分開,不能靠自律)。

**三、內圈測試從哪來?** 兩條路各有代價:
- **從 §3 契約來** → 要先做票 06(契約現在只在散文裡,沒有結構化清單)
- **讓 agent 自己想** → 回到第一點

## 外包給既有 skill

`mattpocock-skills:tdd` / `:implement` 都在,而且**這裡沒有現成的東西**
—— 不像 BDD 工具那題是「已經有一套但我們沒用」。省的是「怎麼寫 §10 的 PROMPT」那一整塊。

⚠️ 但要先確認一件事:那兩個 skill 的完成定義是什麼,會不會跟這裡的
「空骨架全紅 / 可滿足性 / 逐條可紅」三段檢查打架。**沒讀過就外包等於換一份沒讀過的合約。**

## 對骨架那場 grill 的影響(這是這張票現在最要緊的用途)

原本要問的是「**骨架從哪來**」。加上這條之後變成:

> **骨架要提供到哪一層?** wiring 到哪裡為止、domain 留多少給 TDD 長?

那是不同的一題,而且**先答它才問得清楚原本那題**。所以這張票**排在骨架 grill 之前**,
或者直接併進那場 grill 的題目裡。

## 可落空的預測(真的要做的時候)

不要寫「內圈會產生 N 條測試」(不可能失敗)。可落空的寫法舉例:
**預測 agent 產出的內圈測試裡,拿 `vacuous_tests` 掃會有 ≥1 條進分診佇列**
—— 或反過來預測一條都沒有,然後去看它是真的乾淨還是偵測器又失效了。

**Blocked by:** 骨架不存在(幕四整體);內圈測試若要從契約來則 blocked by 票 06。
**但這張票是決定題,不 blocked。**

## 2026-08-18 · 裁決(`docs/adr/0006`)

**這張票的前提被推翻了一半:骨架存在。** `examples/shop/app/` 是 checked in 的,
建立它的 commit(`4567d31`)訊息逐字叫它「骨架」——build 檔、gradle wrapper、
17 行的 `Application.java`(javadoc 寫「由 harness 提供」)、`data.sql`、兩支測試,
`main/java` 底下**零個實作 class**。不存在的是**服務訪談那份規格的骨架**。

七題的定案:

1. **「三套全綠」保留,但架構那套的「不適用」必須顯形。** 它每條規則都帶
   `allowEmptyShould(true)` → **空專案掃不到 class 就全綠**,什麼都不寫的 agent
   免費拿一套。不拿掉那個旗標(會把「沒東西可掃」偽裝成「違規」),改成報「不適用」。
2. **外部替身站在進程外(HTTP 假服務)。** 資料表表達不出「逾時」(C17 就驗不到);
   Java 介面 + Fake 會逼骨架宣告 port 型別,**打破「測試不 import 實作 class」**。
   ⚠️ §10 那格要改寫,而那是替規格做決定,標 `本案自決`。
3. **package 形狀歸規格擁有**,並加落點檢查(宣告過的 package 必須真的有 class)。
   否則 agent 換個 package,整套架構檢查**靜靜地不適用** —— 綠的,而且看起來像全合規。
4. **走 outside-in TDD,但不外包整包。** `:implement` / `:tdd` 三處打架:完成訊號是
   「完整測試套件綠」(內圈會混進來)、seam 要「跟使用者確認」(隔離跑沒有人)、
   收尾要 code-review + commit(bare dir 沒有 git)。**借三樣**:tautological 的定義、
   seam 改成**由 `domain_contract` 指定**、vertical slice。
5. **內圈測試不算進全綠,而且用結構分開**(單獨 source set / task),不靠自律。
6. **內圈的檢查 = 落點 + 恆真分診,兩個都不是判決。** 落點 = 每條契約要指得出至少
   一條內圈測試(上限:靠方法名指認,只證明落點存在,不證明真的在驗那條)。
   PIT 守內圈**不做**(本票已判定撐不起來)。
7. **骨架從凍結那個改**(生成是搬階目標,卡在「外部系統沒進 store」),
   而且**骨架歸類為受測品**,配三條紀律(檔頭警語 / 每跑留快照並 diff / 洩題面清單)。

**票 06 與本票在這裡接起來**:`domain_contract` 那張表就是內圈測試的 seam 清單來源。
