# 票 06-A 的預測(寫在寫程式之前,2026-08-18)

形狀已由 `docs/adr/0005` 定死,這裡不重複論證形狀。這份只寫死一件事:
**把 §3 那 19 條契約真的塞進去之後,會量到什麼**——包含哪幾格塞不進去。

「契約落檔數 > 0」不可能失敗,**不用**。下面每一條都寫得出「什麼結果會讓它落空」。

## 它做什麼

`SPEC-draft.md`(`runs/2026-08-18-act1-opus-rerun/`)的「領域規則」一節,C1–C19,
逐條轉寫成 `domain_contract` 的列 + `contract_named_test` 的關聯列,再跑一句 SELECT
當分診佇列。**只落檔 + 分診,不生成任何可執行的東西**(B/C 半 blocked by 票 01)。

## 動手前先查證過的一件事(不是預測,是事實)

這場訪談的 S1–S21 **沒有任何一份落檔的 acceptance yaml**。`runs/` 底下三份 act2 產出
(`act2-opus` / `act2-from-interview` / `act2-rerun`)都是**別份規格**的情境集:
編號撞名而語意不同(這場的 S10 是「數量為 0」,`act2-from-interview` 的 S10 是
「調價後舊訂單金額不動」)。**拿它們配對就是造假連結**,不做。

## 預測(逐條可落空)

### P1 「守在哪個物件內」會有格子填不出來,而且**恰好 1 條**

拆三欄之後,C12 / C13 / C14 的散文原格全被 ⚠️ 警報佔滿,沒有指名任何物件。
但 §9-A9 替 C12 / C13 給了守衛位置(移到 application 層的 `PlaceOrderService`),
C14 的 §9-A10 明寫「待裁決前不決定」。

→ **預測:19 條裡恰好 1 條(C14)在散文裡找不到「守在哪個物件內」的答案。**
落空條件:3 條都填不出來(表示 §9 那兩條我讀錯了),或 0 條(表示散文其實有寫)。

### P2 分診佇列會是 **3 條**,而**逐條重判至少會多出 2 條**

忠實照散文的 ⚠️ 落檔 → 佇列 = C12、C13、C14。
但用同一條判準(「判定需要看這個物件以外的資料」)逐條重判,**C17**(會員/商品價目
系統不可用時不建立訂單)與 **C19**(清單查詢時會員系統不可用 → `customerName` 為 null)
的判定同樣要看訂單以外的資料,散文卻沒標。

→ **預測:忠實轉寫 = 3 條;同判準重判 ≥ 5 條。**
→ 意思是:**這一欄記的是「散文標了什麼」,不是「重判的結果」——漏標照樣漏。**
落空條件:重判之後 C17 / C19 其實守得住訂單內部(那 = 4 條或 3 條)。

### P3 「有指名測試」= **0 / 19**,而且那個 0 **不是量出來的**

散文 19 條裡有 18 條寫了指名測試(只有 C14 寫「無法指名,規格沉默」)。
但 FK 指 `acceptance_scenario`,而這場訪談的情境**一份都沒落檔** → 一條連結都建不起來。

→ **預測:落檔後「有指名測試」的契約 = 0 條(0%),遠低於一半;但這個數字是語料逼出來的,
不是這張票量到的東西。報表必須把它跟「契約自己沒指名」分開印。**
落空條件:轉寫時找得到任何一份配得上的情境落檔(已查證過:沒有)。

### P4 **真正會量到降級的是 `enforcement` 那一欄,不是「指名測試」**——而下一輪才驗得到

**這是本票最重要的一條,而且它預測的是下一輪:**
等這場訪談的 S1–S21 真的落檔之後,「有指名測試」會跳到 **≥ 15 / 19**(散文 18 條有指名,
扣掉指名裡混了非情境的那幾格),看起來「大部分契約都有人在守」;
而 `enforcement` 仍然是 **0 / 19 有機械檢查**。

→ **兩欄合併就會把這個差(≥15 vs 0)整個蓋掉。** ADR 0005 §2 不准合併,理由就是這個數。
落空條件:下一輪落檔後「有指名測試」< 10 / 19(表示散文的指名有一大半指向不存在的情境)。

### P5 `enforcement` 值域只有 `none`,所以「19 條全 none」**不是發現**

`architecture_rule` 的 `enforcement` 值域是三個 archunit kind + `none`。
**照抄那個清單會讓契約宣稱一個沒有人履行的機械檢查**(沒有任何生成器讀 `domain_contract`,
而那三個 kind 的參數子表 FK 全指向 `architecture_rule`)。

→ **本輪把 `domain_contract.enforcement` 的值域寫成只有 `'none'`。**
「照抄」照的是那三欄的**語意**(宣稱誰強制 / 沒有就必寫階梯說明 / `enforced_by` 只由生成器回填、
spec 不准自己寫),不是值域清單。⚠️ **這是我對 ADR §2「照抄」的解讀,Nat 可以否決。**
→ 後果:`enforcement=none` 必然 100%,**所以它不算預測、不准當成發現**,報表要標明是 CHECK 逼的。
落空條件:發現 19 條裡有任何一條今天就真的有生成器在強制它。

### P6 「指不出來的理由」會有**兩種**,而 schema 只有一欄裝

C14 的零列理由是「規格沉默」(真的指不出來);其餘 18 條的零列理由是「情境未落檔」
(指得出來,只是對面還不存在)。**兩種零列在計數上長得一樣。**

→ **預測:報表只印計數會分不開這兩種,必須逐字印理由原文。**
落空條件:發現有辦法用一欄的結構化值域把兩種分開,而且不會逼出假資料。

### P7 FK 的行為測試**一支不夠,要兩支隔離測試**

`PRAGMA foreign_keys` 有兩份載體(`schema.sql:15` / `spec_store.py:581`),而且
**任一份單獨存在就足以讓 FK 生效**(ADR 0005 §7 實測)。所以「刪任一份都會紅」
**不可能由同一支測試達成** —— 一支測試最多只證明「FK 現在是開的」。

→ **預測:要兩支測試,各自把另一份載體拿掉再驗。**
落空條件:找得到單支就能讓兩份載體各自承重的寫法。

## 已知上限(要印進報表,不是只寫在票裡)

1. **「有指名測試」≠「有機械檢查」。** C1 指名了 4 個情境,但 C1 說的是「任何時候」,
   情境只證明「這一筆」。**invariant → example 的降級,這張表看得到但擋不住。**
2. **散文的指名有損。** 「S10–S15」是**範圍寫法**、「S16 + §9-A5 機械檢查」與
   「S6, S19 + §9-A8」在同一格裡混了**架構規則**——關聯表只吃得下情境編號,
   混在裡面的那半**落檔時會掉出來**(改寫進 `ladder_note` 的本文)。
3. **跨聚合根那一欄記的是自律的產物**(見 P2):散文沒標的,表也不會知道。
4. **「指名測試」今天的值域只有驗收情境,那是今天的值域不是定義**——票 09 若走 TDD,
   內圈測試也會是候選(ADR 0005 Consequences)。註解不准把語意鎖死。
5. **契約 0 條時 = 這項檢查不適用,不是通過**(ADR 0005 §6),自成一類印在最上面。
