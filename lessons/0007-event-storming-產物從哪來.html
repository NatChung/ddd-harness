第 7 課 · DDD × Agent Harness

Event Storming

前六課都假設你已經知道要建模什麼。這一課補那個假設。

一個一直沒回答的問題

第 1 課要你列詞彙表——你怎麼知道要列哪些詞?
第 2 課要你畫邊界——你怎麼知道邊界在哪裡?

前六課教的都是產物長什麼樣、以及怎麼檢查它對不對。沒有一課告訴你那張表上的 第一個詞是怎麼冒出來的。

而且這件事不能靠坐著想。你在第 2 課的練習裡填的那個歧義——PM 的「完成」跟 RD 的「完成」 不一樣——那不是想出來的,是兩個人講話的時候撞出來的。 問題在於:大部分時候沒有人會撞,大家各自用各自的意思,一路用到上線。

Event Storming(事件風暴)就是一個刻意製造那種碰撞的方法。

為什麼這一課排在第七,而不是第一

實際做事的順序,這一課是第一步——先開工作坊撞出東西,才有詞彙表可列、有邊界可畫。 順序是 7 → 1 → 2 → 3 → 4。

學習的順序刻意反過來,理由有兩個:

  • 這一課最後那張「牆上的東西 → 前六課的產物」對照表,是它真正的價值。 但你得先知道 Aggregate 是什麼、邊界是什麼、Given-When-Then 是什麼, 那張表才成立。否則牆上就只是一堆彩色便利貼。
  • 「hotspot 是產物」這句話要有份量,得先知道一個沒被發現的歧義有多貴 ——那是第 1、2 課的內容。

通則:先給判準,再給生成方法。否則你沒有能力評估自己產出了什麼。

它是什麼

Alberto Brandolini 的原始定義,一句話:

a flexible workshop format for collaborative exploration of complex business domains

一種彈性的工作坊形式,用來協作地探索複雜的業務領域。

實體形式:一面很長的牆、一大堆便利貼、6–8 個背景不同的人(業務、RD、PM、客服⋯⋯)站在牆前面。 沒有投影片,沒有輪流發言,大家同時貼。

一、從「已經發生的事」開始

第一步只做一件事:把所有「已經發生過的事」寫成橘色便利貼,貼上牆。 名字一律用過去式:訂單已建立、付款已授權、庫存不足。

Brandolini 對Domain Event(領域事件)的說明:

A Domain Event is something meaningful happened in the domain. It can be easily translated into software, but the real value here is that it could be quickly grasped from non-technical people.

Domain Event 是領域裡發生過的、有意義的一件事。它很容易翻譯成軟體,但它真正的價值在於:非技術背景的人也能立刻看懂。

為什麼是事件,不是名詞

因為名詞可以各自想像,發生過的事不行。

你說「訂單」,五個人腦中有五種東西,而且他們都覺得自己懂了,沒有人會發問。 你說「訂單已成立」,馬上就會有人問:「成立是指授權成功,還是錢真的進來?」

同一個含糊,包在名詞裡是隱形的,包在過去式的事件裡會當場現形。 這就是為什麼第一步不是列詞彙表——列表會列出大家都同意的詞,貼事件會逼出大家不同意的詞。

二、排上時間軸,讓熱點浮出來

橘色貼滿之後,依時間順序排。這時候三件事會自動發生:漏掉的步驟被看見、 順序爭議浮上檯面、以及最重要的——吵起來。

吵起來的地方貼一張Hotspot(鮮粉紅)。ddd-crew 的定義是拿它來

visualise and capture hot conflicts. Conflicts caused by inconsistencies (in language), frictions, questions, dissent, objections, issues.

把激烈的衝突呈現出來並記錄下來——那些由(語言的)不一致、摩擦、疑問、分歧、反對、爭議所引起的衝突。

注意第一項:inconsistencies in language——語言的不一致。那正是第 1、2 課在處理的東西, 只是這裡它不是被「找出來」的,是自己跳出來的。

Brandolini 對這種場面的建議很具體:討論變熱的時候,就去 「define a clear acceptance test」——把爭議變成一條可判定的驗收。 那就是第 3 課。

熱點不是失敗,是產物

工作坊結束時牆上還留著五張 hotspot,那五張就是最有價值的產出—— 它們是本來就存在、只是從來沒被說出口的分歧。今天不撞,就會在上線後撞。

Brandolini 自己的說法:「Embracing incompleteness will make the workshop less boring and more fruitful.」(接受它就是不完整的,會讓工作坊少一點無聊、多一點收穫。) 目標不是把牆填滿,是把不知道的東西留在牆上、看得見。

三、往回推,前幾課的東西自己長出來

橘色事件排好之後,往回問:這件事為什麼會發生?答案只有三種—— 有人下了指令(藍色 Command)、 某條規則自動觸發(紫色 Policy)、 或是外部系統送進來的。

標記法(顏色與定義引自 ddd-crew 的 cheat sheet):

便利貼顏色是什麼
Domain Event橘 領域裡發生過、而且對領域專家有意義的事
Command / Action藍 「decisions, actions or intent」——人下的指令,或自動流程觸發的
Actor小張黃 圍繞著某組事件的人:一群人、一個部門、一個具體的人
Policy紫 「whenever X happens, we do Y」——接在事件與下一個 command 之間的反應
Query Model綠 actor 要做決定時需要看到的資訊
Hotspot鮮粉紅衝突、疑問、講不攏的地方
System寬粉紅外部的、已經部署的 IT 系統

(小註:ddd-crew 的 cheat sheet 把 Aggregate 標為 legacy 用法,改用大張黃色的 Constraint。Brandolini 的原文與多數繁中材料仍用 Aggregate,第 4 課也是—— 知道有這回事就好,不影響你理解。)

走一遍

小型電商的下單流程,牆上大概長這樣(→ 是時間順序):

[顧客]  ─ 送出結帳(藍) ─→  訂單已建立(橘)
                                  │
                    policy(紫):每當訂單已建立,就預留庫存
                                  ↓
                          預留庫存(藍) ─→ 庫存已預留(橘)
                                       └→ 庫存不足(橘)  ← 這條分支一開始沒人想到
                                                  ↓
                                         付款已授權(橘)
                                                  ↓
                                          訂單已成立(橘)
                                                  ↑
        🔥 Hotspot:「訂單已成立」是授權成功,還是錢真的入帳?
           業務說前者、財務說後者、客服說的「處理完」又是第三個時間點

那張 hotspot 就是第 2 課那個練習的真實版本。沒有人是故意含糊的—— 三個部門各自的說法在自己的脈絡裡都完全正確,只是從來沒有人把它們並排放在同一面牆上。

牆上的東西怎麼變成前六課的產物

牆上變成
橘色事件的名字 第 1 課的詞彙表——而且是動詞形式,比名詞難含糊
🔥 hotspot 第 1 課要拆的詞 + 第 3 課要寫的驗收(Brandolini 自己這樣建議)
名字開始改變的位置 第 2 課的 Bounded Context。第 2 課引的 Fowler 那句 ——語言在哪裡變,邊界就在哪裡——在這面牆上是看得見的
藍 command → 橘 event 的每一組 第 4 課:哪些東西必須在這一瞬間同時正確 → Aggregate 邊界
紫色 policy「whenever X, we do Y」 第 3 課的 Given-When-Then 骨架,幾乎是逐字對應
藍色那一側 vs 綠色 Query Model 第 6 課的 Command / Query 兩側,在牆上是兩種不同顏色的貼紙

陳建村還指出一個很實際的用途:

使用 Event Storming,依據時間軸來思考領域事件,再寫出相對應的 Command, 系統的行為就會慢慢浮現出來。

他用這個方法發現原本設計的一個 use case 其實該拆成兩個—— 事件會告訴你 use case 的天然切法,連帶告訴你票該怎麼切。

這對 harness 的用途

以下的對應是推論

Event Storming 是既有方法(Brandolini 2013)。但下面「發散 vs 收斂」這個角度, 以及「agent 做不了這件事」的判斷,是本教學自己接上去的,不是引用來的。

這一課跟前六課有個根本差異:前六課都在收斂(把東西講清楚),這一課刻意發散(把分歧攤開)。 而這正是 agent 做不到的部分。

為什麼「叫 agent 幫我做 event storming」基本上是矛盾的

LLM 天生只會收斂。你要它產出一面事件牆,它會給你一面整齊、完整、沒有 hotspot 的牆 ——所有含糊的地方都被「照訓練分佈猜一個合理的」抹平了。

而 hotspot 才是產物。一面沒有 hotspot 的牆,不代表沒有分歧, 只代表分歧被藏起來了——這比沒做還糟,因為你會以為自己對齊了。

所以分工是這樣:

agent 可以agent 不可以
產生候選事件、補你漏掉的分支(「庫存不足」那條通常是它想到的) 替你決定 hotspot 怎麼解——那需要領域裡的人做決定,不是需要一個合理答案
把貼好的牆整理成詞彙表、驗收條件、票 假裝沒有 hotspot

實務上最有用的一條規矩:要 agent 產出任何規格或事件流時,規定它「凡是需要猜的地方, 一律標成問題,不要填答案」。這跟 hotspot 是同一件事—— 把「我不知道」變成一個看得見的物件,而不是一個看起來很合理的句子。 (Spec Kit 之類的 SDD 工具包也用同一招, 它們的模板明令 LLM 標記歧義而不是自行假設。)

動手練習

不用揪人開會,自己一個人也做得起來(效果打折,但足夠看出東西)。 挑你系統裡一條真實的流程,只做第一步與第二步:

自我檢查
  • 全部都是過去式嗎?寫成「建立訂單」而不是「訂單已建立」的那幾行, 多半其實是 Command 混進來了——那代表你在寫系統該做什麼, 而不是發生了什麼,方向反了。
  • 第三格是 0 嗎?那幾乎一定是你只寫了順利的路徑。 真實流程裡失敗分支通常跟成功路徑一樣多。
  • 第二格是 0 嗎?比第三格更可疑。一個人做的時候不會吵架, 所以 hotspot 只能靠「我自己都覺得怪」來抓——完全沒有,通常是抓得不夠用力。
  • 最後一格如果答得出具體的人跟具體的行,那就是你下一步該去談的對話。
