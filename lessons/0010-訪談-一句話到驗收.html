一句話到驗收

前九課是工具。這一課是拿著它們,從一句廢話走到跑得起來的驗收。

丟進去的只有這一句

我要一個系統,客人能下單,我能看到所有訂單。

沒有附件、沒有既有系統、沒有架構模板。這一課跟著 2026-08-19 那一整條真的跑完的線走八段: 訪談者問了什麼、需求方怎麼答、據此追什麼、落成什麼、進 store 變成什麼、 生成的 Java 長什麼樣、跑起來紅在哪、實作填完之後全綠到底證明了什麼。

這一跑跟先前幾跑不一樣的地方

需求方是真人(run-meta.json:"stakeholder": "human: Nat"), 不是扮演需求方的 agent。而且訪談者刻意沒拿到平常那份開場 prompt —— run-meta 逐字寫著理由:「那份會白送三樣情報:需求方的身分與技術程度、 『沒有既有系統』、『沒有既有架構模板文件』—— 最後一項正是「模板既定」造假那一格的答案。 本跑要它自己問出來。」

同一份檔也寫著:因此本跑不得與先前給了 prompt.txt 的跑比較基線。 下面所有數字都只描述這一跑。

⚠️ 出處講清楚:上面那句需求是這條線的固定輸入(PIPELINE.md L15、 act1/interviewer/prompt.txt L6)。而這一跑自己的產出裡逐字 attest 的是後半句 ——SPEC 有三處寫著「需求方第一句原話『我能看到所有訂單』」(§1 後台人員、§2 G13、§6 A-8)。 整句與那半句的差別不影響下面任何一個數字,但別把它當成這一跑量到的東西。

每一段結尾都問同一件事:這一段擋掉什麼。道理從實例後面帶出來,不要反過來。

這一課的核心

含糊不會消失,它只會換一個人填。

需求方沒講的東西,下游一定有人補上——不是實作 agent 憑訓練分佈猜一個, 就是訪談者「因為看起來合理」自己寫進去。整條線的每一道閘門,做的都是同一件事: 讓「誰填的」變成查得出來的一格,而不是不留痕跡地被填掉。

這一跑走完之後,還多了第二句:查得出來的那一格,要能活過每一道邊界。 這一跑的主發現就是它沒有活過去(第五段、第八段)。

一、第一輪:五個決定點

訪談者開工只讀一份東西:interview-prompt.md(四條鐵律、追問表、產出合約)。 那句需求是丟給它的,不是它自己去撈的;而這一跑連需求方是誰、懂不懂技術都沒告訴它。

五題不是題數上限,是「決定點」上限

工作指示原文:「沒有題數上限,但一次不要丟超過 5 個需要他做決定的點——超過他會漏答。 子問題也算決定點,不要用 (a)(b)(c)(d) 把十個問題塞進一個編號。」

第二句是補漏洞用的。少了它,「Q1(a)(b)(c)(d)(e)」就形式滿足了上限, 而人照樣會漏答——規則寫得可被形式滿足,就會被形式滿足,這一課會看到它至少五種變體。

第一輪的五題,逐字:

題問什麼(括號是訪談者自己標的「補哪一格」)
Q1你這門生意賣的、或提供的是什麼?
(補:小尺度—§1 GLOSSARY 名詞)
Q2客人下一張單,這張單上面要有哪些內容,你才算收到了一張單?
(補:小尺度—§1 GLOSSARY 訂單的組成)
Q3從客人決定要買,到這張單進到你手上為止,中間實際會經過哪些步驟?

每一題後面都掛著「補哪一格」的帳。標不出來的題就不要問——那是閒聊。 這是四條鐵律的第三條,而且它同時是判斷訪談者有沒有在亂問的機械判準。

Q5 是這一輪最值錢的一題,而它問的不是需求

來源標記有五格,其中一格是 模板既定 <文件名 L行號> —— 「架構常備前提」。工作指示對它的限制寫得比別格都重: 「只能指向明確授權為『架構模板』的文件。本份訪談指示不是架構模板,不得引用它的行號。 沒有這種文件時,這一格就是空的——寧可空著,也不要找一份指得出行號的東西來充數。」 再加一句:「嚴禁把 本案自決 偽裝成 模板既定。這是最常見、也最貴的一種造假。」

需求方對 Q5 的回答是「沒有」。於是最終規格 §9 開頭寫著: 「本案沒有被授權為『架構模板』的文件([Q5]「沒有」),因此『出處』欄的 模板既定 為零筆」——而那個零是它自己問出來的,不是別人告訴它的。

先前幾跑這件事是白送的(開場 prompt 裡就寫著「沒有既有架構模板文件」)。 這一跑把那句話拿掉,就是為了看它會不會自己去要。它要了。

而 [Q2] 那一行八個名詞,是整份規格的骨架起點:鞋子 SKU / 單價 / 數量 / 總價 / 運費 / 收貨地址 / 付費成功 / 客戶基本資訊。追問表第一列說:聽到一個名詞, 就追問「這個詞別的部門講的是同一件事嗎」,餵給 §1 詞彙表;不一樣就切 Bounded Context。 最後 §1 詞彙表 31 列,大半的根都在這一行。

這一段擋掉什麼

  • 擋掉「無中生有的架構」。Q5 把「有沒有模板」變成一題,答「沒有」就寫死 0 筆 ——不能事後說「照慣例」。
  • 擋掉「一次問二十題把人問死」。5 個決定點是硬上限,而且堵死了用子問題偷渡。

Q7 那 33 個字,生出了整個 Bounded Context 切界

「要進入結帳一定要先鎖起來,最多結帳失敗再釋放」——這句話裡有三個新東西, 需求方一個都沒有命名:庫存(有一個數量要被獨立守住)、庫存鎖定(被保留、不可再賣的數量)、 結帳作業(鎖的載體)。

而切界的理由不是「兩個部門講不同的話」。§1.1 逐字寫著: 「訪談沒有出現兩個部門對同一個詞講不同意思……切界的實際依據是生命週期不一致 —— [Q7] 說庫存鎖定在『進入結帳』時就建立,[Q8] 說訂單要『付費成功後』才存在, 所以鎖比訂單早出生,無法住在訂單這個聚合根裡。」

兩句話的時間差,推出五個 context 與兩個端點(POST /checkouts 與 POST /orders)。第 2 課與第 4 課在這裡合流:邊界不是照組織畫的,是照生命週期畫的。

對照:上一場的 agent 需求方,同類題目答得出來 —— 而那是現編的

先前用 agent 扮演需求方時量到過(.scratch/ddd-harness/issues/04): 它的 prompt 明寫「你心裡沒有的東西就說你還沒想過。不要現編。」,而實測是 「守得住範圍、守不住細節」 —— 被問庫存 / 付款 / 地址時正確答「先不考慮」;被問具體格式時就現編一個:

  • 訂單編號「比如 ORD-20260818-001 這樣」 → 凍結 SPEC 裡 ORD- 出現 0 次
  • 延遲「最好是秒級的」 → 凍結 SPEC 一個字都沒提效能

現編的答案標得出完全合法的 [Qn]。逐字稿裡真的有那句話, 來源標記檢查會說「有來源」,而那句話本身是編的。 真人需求方答「目前沒想到」的時候,那是真的沒有——這是這一跑最貴、也最不像產出的產出。

「不擅自把『購物者』判成『購物車』的錯字。」

那幾乎肯定就是錯字。一個人在寫「客人離開了那雙鞋怎麼辦」的時候寫下「把購物者留著」, 99% 是在講購物車。而訪談者不准替他決定那 1%。

代價寫在同一格裡:「本次實作一律不含購物車(取較保守的 [Q19]), 但『問客人要不要清空』這個行為因此也沒有被實作。」 ——洞留著,而且標明留洞的後果是什麼,不是靜靜地選一邊。

為什麼要這麼硬:錯字判對了沒人會發現,判錯了也沒人會發現。 一個不留痕跡就能做的判斷,做了一百次之後,規格裡有多少是需求方說的、多少是訪談者腦補的, 誰都答不出來。

這一段擋掉什麼
  • 擋掉「問一次沒答就算了」。Q13 的洞被追了三輪,而且第二次的「像是答案的答案」 被正確地判成另一件事。
  • 擋掉「誘導出一個答案」。三次都是原樣重問或明說「這是重問」, 不是換個講法問到他隨便給一個 —— 誘導出來的答案照樣標得出合法的 [Qn]。
  • 擋掉「訪談者替需求方拿主意」。三條矛盾原樣列出,連錯字都不判。
  • 擋掉「暫定被當成定案」。暫定 [Qn] 是五格來源標記裡獨立的一格, 「先給…就好」寫進規格時帶著這個標記,下游看得到它不穩。

第二幕做的是兩段轉換,中間隔著一道海關:

散文 → YAML:把一個 agent 關進空房間

  1. 工作目錄整個砍掉重建 —— 每次從零,不留上次的殘骸。
  2. 房間裡只放三個檔:散文規格、schema.sql(合約)、匯入工具。 生成器、驗收 harness、任何既有的 yaml 都不放 —— 那些是答案卷。
  3. 完成的定義寫死在 prompt 裡:「跑 import,它會印出逐條錯誤, 改到它印 ok 為止」。所以這是一個 agent 自己跑得動的迴圈: 寫 → 匯入 → 讀錯誤 → 改 → 再匯入。中間沒有人審。
⚠️ 而「答案卷不能進房間」這條,這一跑差點被自己的警語破功

schema.sql 是複製給受測 agent 讀的兩個檔之一。它裡面有一句凍結紀律:

⚠️ 註解不要寫具體資料值。2026-08-18 這裡曾寫著「Alice 與 Bob」, 而 Bob 只存在於 agent 拿不到的 data.sql;受測 agent 讀了這行註解、照著填,並誠實揭露來源。 schema 註解是 agent 讀得到的東西,寫進去的具體值就是洩題。

那句警語自己把那兩個名字寫在裡面。它一邊說「不要寫具體資料值」, 一邊示範了兩個具體資料值,而它躺在受測 agent 讀得到的檔裡。已改掉,並補一句:

講失效模式不需要舉實際的值 —— 舉了就等於把答案附在警語後面。

同一次清掉五處(還有前一個案子的實際欄位名)。「寫在該寫的地方」不保證那句話沒有副作用 ——警語跟它警告的東西,住在同一個會被讀到的檔裡。

prompt 裡有第三種欄位分類:「條件式必填」

原文:「不是選填,用得到就一定要有,否則對應的檢查會靜靜地不適用。」

這一跑有兩條,而第二條把 agent 逼進了一個死角:

  • res_total_field(列表的總金額欄)—— 只要有任何一條「列表某欄等於某數字」的斷言就必須給。 「總額 = Σ(數量 × 單價)」那條不變式靠它認人,沒宣告就永遠不檢查。
  • res_customer_id_field(列表的客人編號欄)—— 只要有任何一條預期被拒的情境就必須給, 因為每個被拒的請求都要斷言「列表裡沒有這個客人的列」,而它比對這一欄。

而這份規格從頭到尾沒有「客人編號」這個東西:§1 的「客戶」是角色、沒有識別碼, 而 B-2「誰是誰」是阻斷級,§10 明寫不得實作任何使用者身分模型。

agent 的處理,逐字抄自它的 YAML 註解:

⚠️ 本案沒有客戶識別碼……憑空發明一個 customerId 等於替 B-2 投票。 E3 的列表一列裡真的能認出「這一列是誰的」的欄位只有 customerName, 所以本合約以它當比對鍵;fixture 的 customer_id 因此就是客人的名字。

這個判斷是對的。而下一段會看到,這段話下游一個字都看不到。

YAML → DB:六步,而順序本身是設計

  1. 讀 YAML,頂層必須是 mapping
  2. 跨列檢查(第 2 階)全部先跑完 —— 有問題就 一次印出全部,不是撞到第一個就停
  3. 舊的 db 先刪掉 —— db 是產物,不是資產
  4. 現場從 schema.sql 建表
  5. 打開 FK 檢查 —— SQLite 預設不檢查外鍵
  6. 逐表寫入。schema 的 CHECK / FK / TRIGGER 在這一步擋 = 第 1 階
兩個設計點

「任何一條掛掉就整個不寫 —— 部分匯入比匯入失敗更難查。」 要嘛拿到一個完整的 db,要嘛什麼都沒有 —— 跟需求方在 [Q14] 講的「有費用但沒訂單就先退費,不要留一半」是同一條原子性。

第 2 階跑在第 1 階前面。python 那層能一次印出所有問題,讓 agent 一輪改完; schema 是撞到一條就中止,拿它當主要迴圈會變成一次只修一個。

第 5 步那行 PRAGMA:一個被修過的例子

SQLite 預設不檢查外鍵。少掉 PRAGMA foreign_keys = ON, 所有 FK 守衛全部靜靜失效 —— schema 檔看起來一模一樣,匯入照樣印 ok,測試照樣全綠, 只是什麼都不擋了。同一句 INSERT,差別只在有沒有那行:

開了  → 擋下:FOREIGN KEY constraint failed
沒開  → 寫進去了,違法 fixture 成功掛在成功情境上

⚠️ 這件事的紀錄本身也被修正過兩次,而修正的方向很有教育意義:

  • 先前寫著「這句 PRAGMA 只有一份載體,刪掉就全滅」。實測發現有兩份 (schema.sql 與 spec_store.py),而且任一份單獨存在就足以讓 FK 生效 —— 要兩份都刪才會靜靜失效。
  • 先前寫著「沒有任何測試在驗它真的開了」。現在有了,而且刻意驗行為、不驗「那一行還在」: 兩支測試各自隔離一份載體,每一支都先確認「破壞本身生效了」,不然會拿到假通過。

那兩支測試的註解記著它們自己犯過的錯:原本各自寫 assert PRAGMA_LINE not in stripped, 而那是恆真形狀 —— 常數一旦跟 schema.sql 對不上(空白、大小寫), replace 是 no-op,而那句 assert 恰好因此空洞地成立。 實測過:把 = ON; 改成語意相同的 =ON;,測試照樣綠。

連「驗守衛的測試」自己都會恆真。破壞要先證明破壞生效了,才輪得到證明守衛擋得住。

為什麼要 YAML 這一層,不讓 agent 直接寫 DB

YAML 擋不住任何東西。沒有型別、沒有外鍵、沒有跨列不變式 —— 寫錯的 YAML 一樣是合法的 YAML。它只買到兩件事:agent 寫得順, 以及人 diff 得出來、進得了 git 給人 review。

擋的工作全在匯入那一步。所以那句「匯入印 ok」才有意義 —— 那個 ok 是海關蓋的章,不是 agent 自己說的。

核心設計

schema 的每一條 CHECK / FK / TRIGGER,都取代了散文裡的一句叮嚀。

散文說「來源標記五格,不得自創第六格」→ schema 寫成 provenance CHECK IN ('Qn','暫定','推導自','模板既定','本案自決')。

差別是:叮嚀會被忽略,CHECK 不會。

不用 DB 會怎樣 —— 三個真的會發生的

用點餐單想:第一格先勾「哪一種」,勾便當要填主菜,勾飲料要填冰塊甜度。 沒人管的話,你可以勾飲料然後填「主菜=雞腿」—— 單子看起來填好了,廚房做不出東西。 DB 就是那個會當場說「你勾飲料,冰塊沒填」的店員。

① 忘了填期望值

某條斷言寫「status 這一欄要等於某個字」,卻忘了寫那個字是什麼。

沒有 DB:YAML 合法,沒人抱怨。生成器拿到空的期望值 → 生出「status 必須等於 null」。於是實作寫對了反而紅, 而你會盯著實作看半天。

有 DB:匯入當場說「該帶 expected_text,實際帶了(無)」。

② 欄位名打錯一個字

寫成 statuss。

沒有 DB:生成器去 JSON 撈 statuss → 撈不到 → null → 測試紅。 你會以為實作壞了,跑去改實作,找一小時才發現是規格打錯字。

有 DB:FK 擋住 ——「你斷言了欄位 statuss,但規格宣告的欄位清單裡沒有它」。

③ 規格自己算錯 —— 這個最要命

明細寫「2 雙 × 3200 元」,期望的總金額卻寫 3200。

沒有 DB:測試生得出來、跑得起來、紅。你去查實作 —— 實作算 6400, 是對的。錯的是規格。

但規格是驗收的來源,沒有人會去懷疑它。你只會覺得「實作有 bug」, 然後把對的實作改成錯的去迎合它。

有 DB:匯入當場說「期望 3200,但各明細的『數量 × 單價』加總是 6400 —— 兩者不一致」。

一句話的差別

沒有 DB,錯誤會延後到「跑測試」才爆,而且爆出來的樣子指向錯的地方。 有 DB,錯誤在「交件」當場爆,而且指得出是哪一列、哪一欄。

階誰擋擋得住什麼
第 1 階schema 的 CHECK / FK / TRIGGER 五格來源標記寫不進第六格;違法 fixture 只掛得上「預期被拒」的情境; 斷言指向沒宣告的欄位寫不進去;模板既定 指不出授權文件就 ABORT
第 2 階匯入工具的跨列不變式 總額 ≠ Σ(數量×單價) 匯不進去;拒絕情境的客人不得借用成功情境的; 指名測試指到不存在的情境

整份驗收刻意不 import 任何實作類別

唯一引用的專案類別是啟動用的 Application,全部只走 HTTP, 所以它不綁實作的類名、不綁內部結構。

這不是潔癖,是目標的字面實作:同一份規格餵兩個 model,產出兩份長得完全不同的實作, 能被同一套驗收明確判定。驗收一旦 import 了實作類別,那句話就不成立了。

而這件事做得到的前提,是簡潔架構。領域行為要能從 HTTP 邊界完整觀察到 (adapter 在外層、領域在內層),outside-in 的驗收才寫得出來。 領域邏輯若散在 controller 裡、或要 mock 內部類別才測得到,這種驗收根本寫不出來 —— 第 5 課那三條原則不是另一個主題,是這一套能成立的必要條件。

欄位名不是猜的

那些 customer / sku / unitPrice / customerName, 生成器不寫死——全部從規格宣告的 wire 合約讀,請求側與回應側兩邊讀同一份。 規格沒宣告的欄位就不生對應的斷言。

理由是實測撞出來的:規格不宣告 wire shape,下游兩個模型會各取各的名字, 同一份規格產出的兩份實作兩邊都過不了同一套驗收,而失敗訊息全長成 but was: null——領域行為對不對完全看不見,紅的原因看不出是命名。

wire 合約(§1.2)對外:約束 HTTP 的 JSON 欄位名。

先前這兩者之間沒有任何機械連結,因為 store 裡根本沒有詞彙表。 這一跑詞彙表進 store 了(31 條),對譯檢查第一次跑得起來:

順帶,禁用同義詞那張表被逼出一件散文自己沒發現的事:「『總價』指全單不含運費的金額」 這一列,散文說「一律改用商品金額合計」,而 §1 詞彙表裡根本沒有這個詞條 —— 它只出現在禁用清單的那一格。落檔 agent 因此只能把「一律改用」留空, 並寫下理由:「指得到的替代詞不存在,不是沒有替代概念;要補的是 §1 少一個詞條。」 一條 FK 逼出了散文的一個洞。

反向那 7 條更直接:詞彙表宣稱要上線的 shippingFee(運費)、 checkoutId(結帳識別碼),合約裡根本沒有這個欄位 —— 那正是第五段講的、掉在 store 外面的那半份規格,從另一個方向被量到。

所以 Ubiquitous Language 在這條線上的狀態,現在是有數字的:

  • 需求方的話 ↔ 詞彙表:✅ 來源標記綁著
  • 詞彙表 ↔ wire 欄位名:⚠️ 有檢查了,但它住第 2 階(報告,不是硬擋),而且這一跑 列表側 5/7 對不到
  • 詞彙表 ↔ 實作的類別 / 方法名:❌ 完全沒有東西在看

最後那條不是忘了做,是結構性的:驗收刻意不 import 實作類別, 它就天生看不到實作叫什麼名字,而且不能靠放寬驗收來解 —— 放寬就毀掉「兩份不同實作被同一套驗收判定」。 唯一看得到類別名的是 ArchUnit,而現有三種規則沒有一種是命名類的。

⚠️ 而對譯檢查做成報告不做成 FK,是刻意的:硬擋只拿得到「匯入失敗」, 拿不到「7 個裡差幾個」那個數字,而這件事的價值就在那個數字上。

代理編碼那個 class 的 javadoc

⚠️ 這個 class 全綠,不代表這些規格條文成立。這裡每一條的 fixture 都不包含它的 Given/When 所描述的那個動作—— schema 沒有那個動詞,所以規格作者用別的東西近似它, 並在 proxy_for 裡自白覆蓋到哪一半。每個測試方法的 javadoc 都帶著那段自白,逐條讀得到。

而每一條方法上面真的帶著它:

/** G1 —— 來源:Qn SPEC.md L213-L216(來源 [Q3] [Q8],逐字見 L521、L526)

 * 也不在 fixture 裡,本情境驗的是「一次下單請求成立並落進列表」。 */

為什麼還是生出來跑:它們仍擋得住「連近似的那一半都壞了」,而且留著才看得見缺口多大。 補上缺的動詞之後,這個 class 會自己變空——它的大小就是缺口的大小。 這一跑它裝了 4 條,而真驗收只有 1 條 —— 缺口比驗收大。

這裡踩過一次「揭露死在邊界」

proxy_for 剛做好時,生成器只在「預期被拒」那條路徑印警語, 而當時的代理編碼全是成功情境形狀——於是生成的 Java 裡「代理編碼」四個字出現 0 次。 揭露好好地躺在 store 裡,讀 Java 的人看到的是一疊乾淨的情境。

揭露要走到讀的人面前才算數,存在 store 裡不算。 ——而上一段剛講過,這一跑同一件事在更上游又發生一次:註解裡的誠實,連 store 都沒進去。

生成物進 git,再檢查它沒漂

drift check 重新從 spec 生成一次,跟 commit 的內容比,不一樣就紅。它同時擋兩條路:

  • agent 手改生成物 → 重新生成的結果跟 commit 的不一樣 → 紅
  • agent 改 spec 想放寬檢查 → 生成物跟 spec 不一致 → 紅 (它改 spec 又重新生成的話,diff 會出現在 git 裡,而生成物在凍結清單內)
這一段擋掉什麼
  • 擋掉「驗收綁死某一份實作」——不 import 實作類別、只走 HTTP。
  • 擋掉「欄位名用猜的」——從 wire 合約讀,沒宣告就不生。
  • 擋掉「手改測試讓它變綠」——drift check 雙向擋。
  • 擋掉「湊出來的情境混進驗收數字」——分 class,自白從 store 一路長進 javadoc。
  • 擋掉「來源在傳遞中掉了」——來源標記跟著條文長進 Java 的 javadoc。
  • 沒擋掉:實作的內部命名。驗收看不到類別名(而那是刻意的), ArchUnit 又沒有命名類的規則 —— 詞彙表管得到邊界,管不到裡面。
但這一段有一塊「做了還沒接上」

drift check 沒有綁進任何 build。那個 build 檔逐位元組凍結,綁不進去;現在是手動或 hook 在跑。 檢查本體是第 2 階,綁法還住第 4 階。

這是整條線反覆出現的那個病的另一個實例:寫在該寫的地方 ≠ 接上了。 要問的是——實際會讀到它的那條路徑,經過這裡嗎?

2 可滿足性有一份能讓它全綠的實作嗎? 只有宣告同一份 wire 合約的 spec,才拿既有實作當綠燈預言機
3 逐條可紅最小破壞一處,只有對應那條變紅嗎? 破壞清單綁特定情境語意,換 spec 會撞名不撞義

第 1 段最反直覺:純粹「跑得綠」反而是壞消息。骨架沒有實作,不該有任何東西會過 ——會過就表示這套驗收有恆真的成分。

為什麼第 1 段不夠,一定要配第 2 段

全紅只證明「這套驗收不是恆真」。但它也可能是無解的 —— 寫了一條沒有任何實作能通過的情境(互相矛盾的斷言、要求一個不可能的狀態), 那也會全紅,而且長得一模一樣。

「不是恆真」與「有解」是兩件事,兩個都要證。少一個就有漏洞: 只證前者 → 可能永遠填不完;只證後者 → 可能一開始就綠。

(這一跑的第 2 段是由第四幕本身回答的:實作 agent 真的填到全綠了 —— 第八段。)

那 4 個綠燈,一位元的資訊都沒有

三件事疊在一起,才長出那 4 個假綠燈
  1. 它們不是這份規格生的。architecture_rule 是 0 列(第五段), gen_archunit 一個檔都沒生。跑起來的那支 ArchitectureTest 是從凍結骨架繼承來的,守的是 com.shop.domain / usecase / adapter —— 而那幾個 package 名是那個檔案發明的, 不是這份規格宣告的。
  2. 它們在空專案上必然綠。每條規則都帶 allowEmptyShould(true), 這是刻意的(骨架階段 domain 還是空的,骨架的紅燈只該來自驗收)。 後果是:那個 that() 命中 0 個 class,綠燈裡沒有任何資訊。 一個什麼都不寫的 agent 在這裡是免費綠的。
  3. 而 agent 只要把 class 放到別的 package,整套就靜靜地不適用 —— 不是紅、不是報錯,是綠,而且看起來跟「完全遵守架構規則」一模一樣。

補這個洞的是另一支檢查 package_landing_check: store 裡宣告過的每一個自有 package,原始碼樹底下必須至少有一個 class 落在它裡面。 它對這一跑的判定是:

宣告過的 package:0 個 → 本次不適用(不是通過)     exit 3

沒有那支檢查,報表會是「9 條測試 4 條綠」。

「不適用」是刻意的第三態,而且它出現了三次

對不同合約印 ❌ 0/4 綠,讀起來像壞了——而壞掉的東西會被拿去修。 真相是「這一段對這份 spec 問錯了問題」,不是「這份 spec 沒過」。

這一跑「不適用」出現在三個地方,都是不同的東西:

  • gen_archunit:store 裡沒有規則可生成
  • package_landing_check:一個 package 都沒被檢查到(exit 3)
  • 空骨架的 ArchUnit 4 綠:規則掃到 0 個 class

三個都不是通過,而且三個都會被折進「綠燈數」裡,如果沒有人堅持把它們印在最上面。 這條規矩在這條線上是寫死的:「不適用」不准算成「通過」,它自成一類。

兩層的偵測方法完全不同,不能互相代替。

綠燈擋不住「不管實作怎麼寫都會綠」的測試。用 mutation testing 去問 「哪條測試什麼都沒約束到」——而這件事最有價值的部分,是它記下了三個試過並失敗的指標。

這三個數字的來源

下面的 47 條、HL1/HL2,量的是另一個實驗裡手寫的單元測試, 不是這條管線生成的驗收。列在這裡是因為那三次失敗本身是可轉移的教訓。

  • 「殺了 0 個 mutant」→ 錯。拿一條已知的恆真測試去驗,它殺了 7 個—— 因為 @BeforeEach 讓 fixture 建構路徑上的 mutant 會弄倒全班, 恆真測試繼承了它沒賺到的擊殺。
  • 「獨佔擊殺 = 0」→ 訊號被雜訊淹掉。47 條裡標了 33 條——健康的測試本來就互相重疊。
  • 「貢獻沒超出全班共同集合」→ 第二個已知陽性上漏抓。 那條在測試內自己 new Order(...),交集因此不含它殺的建構子 mutant。
最重要的一句

mutation testing 分不出「恆真」與「碰不到」。 兩者長得一模一樣:都沒有獨佔貢獻、都只死在很多測試共用的 mutant 上。

所以它交的是分診佇列——把 47 條縮到 8 條要人讀,而不是替人判。 判別要靠讀那條測試在斷言什麼。

這一段擋掉什麼
  • 擋掉「綠燈就是通過」。空骨架必須全紅,否則驗收有恆真成分。
  • 擋掉「不適用被讀成通過」。三態報表,而這一跑三處不適用全部是綠色的樣子。
  • 擋掉「規則掃到 0 個 class 卻算它守住了」。package_landing_check 判 exit 3。
  • 擋掉「用一個看起來合理的指標宣布乾淨」。三個候選指標都在 已知陽性上驗過才被否掉,而不是想一想覺得不錯就上。

⚠️ 這一課最重要的一句話

「全綠」只證明了 1 條真情境。

另外 4 條是代理編碼(綠了不代表原文成立),4 條是空專案也會綠的架構檢查。 一個只讓 G16 過的實作——也就是「任何請求一律回 400、列表永遠是空的」——也會全綠。

寫斷言的時候要問的那句話,在這裡是最貴的:如果這條綠了,我到底知道了什麼?

⚠️ 但 TDD 產出的測試,沒抓到 TDD 產出的 bug

事後的架構 review 在這 9 條內圈測試上找到兩個已知陽性。兩個都綠著。

陽性一:守 C8 的測試用 !isStatic 過濾,看不見 Order.restore。

// Order.java  ——  place 有守不變式
public static Order place(…) {
    if (items == null || items.isEmpty()) {
        throw new DomainRuleViolation("EMPTY_ORDER", "訂單至少要有一個訂單品項");
    }
    return new Order(…, OrderStatus.PLACED);
}

// Order.java  ——  restore 沒有,直接進 private constructor
public static Order restore(…, OrderStatus status) {
    return new Order(…, status);
}

// OrderImmutabilityTest.java —— 它這樣列舉「改得動訂單的入口」
boolean isInstanceApi = Modifier.isPublic(method.getModifiers())
        && !Modifier.isStatic(method.getModifiers());

restore 是 static,被濾掉了。一支宣稱「訂單身上沒有第二個改得動它的東西」的測試, 看不見那條能憑空造出任意狀態訂單的路。

⚠️ 而落點檢查會說「C8 有內圈測試 ✅」——而它是對的,也是沒用的。 落點存在,但那條測試的列舉範圍漏掉了半個 interface。 這是第三種病:不是恆真(加一個 public 實例 mutator 它就紅),是範圍不足 ——落點檢查抓不到,恆真分診也抓不到。

陽性二:changeStatusTo(null) 讓狀態變成 null。

// OrderStatus.java —— 終點回 null
case RECEIVED -> null;

// Order.java —— 守衛用 != 比對它
public void changeStatusTo(OrderStatus target) {
    if (target != status.next()) {
        throw new DomainRuleViolation("INVALID_STATUS_TRANSITION", …);
    }
    this.status = target;
}

一張 RECEIVED 的訂單:status.next() 是 null, changeStatusTo(null) → null != null → false → 不丟例外 → this.status = null。而 C9(單向前進)與 C17(被拒時原地不動) 宣稱擋的正是這個 —— 那三條非法轉移測試,一條都沒有試 null。

⚠️ 這兩條合起來說明一件事:「每條契約都指得出一條內圈測試」是一個可被形式滿足的規則。 8/17 這個數字是真的,而數字背後那 8 條裡,至少有一條看不見它該看的一半。

這條線上反覆出現的同一種失效

一句話

規則寫得可被形式滿足,就會被形式滿足。

  • 驗收寫得可被形式滿足 → 發現會被驗收吃掉(這一跑:5 條裡 4 條代理編碼)
  • 完成訊號寫得可被形式滿足 →「匯入印 ok」「9 條測試全綠」
  • 誠實出口寫得可被形式滿足 → proxy_for 讓任何情境都湊得出 ok
  • 來源標記寫得可被形式滿足 → 需求方現編的答案照樣產出合法的 [Qn]
  • 落點檢查寫得可被形式滿足 → 方法名叫 C8_xxx 就算有落點
  • 連驗守衛的測試自己都可被形式滿足 → assert X not in stripped 在 replace 是 no-op 時空洞成立

還有一條不同的病:寫在該寫的地方 ≠ 接上了。 而這一跑給了它到目前為止最完整的一個實例 ——

同一句真話,死了三次
  1. 落檔 agent 發現規格與 schema 對不上,寫進 YAML 註解 → 註解不進 store
  2. 生成器照 store 生,生出單階段的合約 → 讀 Java 的人看不到那句話
  3. 實作 agent 撞上同一個矛盾,再發現一次,寫進 ASSUMPTIONS.md → 靠人讀

三個 agent 都做對了,而規格的對外合約還是被悄悄改掉了。 要問的永遠是同一句:實際會讀到它的那條路徑,經過這裡嗎?

寫斷言、寫完成訊號、寫預測時,都先問同一句

如果這條綠了 / 中了,我到底知道了什麼?

這一跑的答案是:9 條綠燈,知道了 1 件事 ——「數量 0 或負數的請求會被拒,而且不會留下殘骸」。 那也是真的知道了一件事,而且是從一句廢話一路逼出來的。 剩下的 16 條 GWT、9 條契約、10 條架構規則去哪裡了,現在每一條都查得出來。 ——這才是這條線目前真正買到的東西。
