第 5 課 · DDD × Agent Harness

簡潔架構

三條原則,決定 agent 改一行的爆炸半徑有多大。

第 4 課守住的東西,會在這一課被拆掉

你上一課做了一個 Order:沒有 setter、items() 回傳複本、 invariant 在 root 內強制。很好。

然後有人要做一支 API,把訂單回傳成 JSON。序列化工具讀不到私有欄位,於是——

public class Order {
    public Order() { }                       // ← 序列化需要無參數建構子
    public void setTotal(Money t) { ... }    // ← 序列化需要 setter
    public List<OrderItem> getItems() {      // ← 直接回傳本體,不是複本
        return items;
    }
}

三行,第 4 課全白做。而這正是 agent 最會做的事:它看到「序列化失敗」這個錯誤, 最短路徑就是加 setter。它不會知道那個 private 是刻意的。

擋住這件事的不是提示詞,是架構——讓那支 API 從一開始就拿不到 Order。

三條原則

把 Clean Architecture(簡潔架構)收成三條原則。 這一課就只有這三條。

一、分層原則

Clean Architecture 有四層:Entities、Use Cases、Interface Adapters、Frameworks & Drivers。
層放什麼電商例子
Entities
(最內)		 不管有沒有這套軟體都成立的業務規則 Order、OrderItem、Money ——第 4 課的 Aggregate 住這裡
Use Cases 這套軟體特有的流程:誰、依什麼順序、做哪幾件事 PlaceOrderUseCase:預留庫存 → 建立訂單 → 送出通知
Interface Adapters 翻譯。把外面的格式轉成內層看得懂的,反之亦然 OrderController(HTTP ↔ 輸入物件)、 JpaOrderRepository(SQL ↔ Order)
Frameworks & Drivers
(最外)		 別人寫的東西:框架、DB、外部服務 Spring、JPA、PostgreSQL、金流 SDK
先擋兩個一定會冒出來的問題

「到底幾層?」——四層是起點,不是規定。Uncle Bob 原文寫得很清楚:

the circles are schematic. You may find that you need more than just these four. There's no rule that says you must always have just these four. However, The Dependency Rule always applies.

這些圈只是示意。你可能會發現不只需要這四層。沒有任何規定說你一定要剛好四層。不過,相依性規則永遠適用。

你查資料會看到 3 層、4 層、六角形架構⋯⋯它們講的是同一件事,只是切得粗細不同、 名字不同。不可動的只有相依性規則,層數按專案複雜度自己決定。判準也是原文那句: 越往內越抽象、越是政策;越往外越具體、越是機制。

「跟我看過的那些名字怎麼對?」

Clean ArchitectureEvans 的 DDD 分層Spring 專案常見目錄
EntitiesDomaindomain/ model/
Use CasesApplicationservice/
Interface AdaptersUser Interface + 部分 Infrastructure controller/、repository 的實作
Frameworks & DriversInfrastructureSpring、JPA、DB 本身

但這張表會騙人,因為兩套四層的形狀不一樣——這是最關鍵的一點:

  • DDD 的四層是垂直堆疊,相依由上往下:UI → Application → Domain → Infrastructure。Domain 依賴 Infrastructure(它要往下呼叫才存得了資料)。
  • Clean Architecture 是同心圓,相依由外往內。 同一個 Infrastructure 從最底下被搬到最外圈,箭頭因此反了: Infrastructure 依賴 Domain,Domain 完全不知道資料庫存在。

這就是 Clean Architecture 相對於傳統分層真正改掉的那一件事,其他大致相同。 可以理解成:同一批責任重新排一次,把「技術」從地基改成外殼。 所以 Evans 的 Infrastructure 在右邊會被拆成兩塊——你寫的接軌程式碼歸 Interface Adapters, 框架與 DB 本身歸 Frameworks & Drivers。

另外最右欄是「目錄名字」,不是「層」,見下面〈別看資料夾〉那段。

判準是「這東西為什麼會改」: 金流商換一家 → 最外層改;下單流程多一步風控 → Use Cases 改; 「訂單總額 = 明細加總減折扣」這條變了 → Entities 改。 一個東西如果會因為兩種完全不同的理由而改,它八成跨了層。

表會忘,下面四個問題不會。判斷任何一個東西住哪一層,由內往外問:

  1. 沒有這套軟體、沒有電腦,這件事也成立嗎? → Entities
  2. 這是在描述「我們家這套系統的做事順序」嗎? → Use Cases
  3. 這是在翻譯格式嗎?(JSON ↔ 物件、SQL ↔ 物件) → Interface Adapters
  4. 這是別人寫的嗎? → Frameworks & Drivers

DDD 那些戰術概念也照這四問各就各位:Aggregate / Entity / Value Object 在 Entities;Use Case、往外傳的資料結構在 Use Cases;Controller、Presenter、 ORM mapping、repository 實作在 Interface Adapters。 repository 的介面宣告在內側——Evans 原本掛在 Domain 層、本課這一派掛在 Use Cases 層, 位置有出入,但重點從來都是「介面在內、實作在外」,不是它掛哪一格。

二、相依性原則

Uncle Bob 的原句:

Source code dependencies can only point inwards. Nothing in an inner circle can know anything at all about something in an outer circle.

原始碼的相依只能往內指。內圈裡的任何東西,都不准知道外圈有什麼。

最常見的誤解

「相依」講的是原始碼,不是執行時的呼叫方向。

執行時控制流當然會往外跑——use case 一定得存資料庫、一定得回應 HTTP。 往外跑的方法是內層定義介面、外層來實作:

// Use Cases 層。介面「宣告」在內層,因為需求是內層的
public interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);
}

// Interface Adapters 層。實作在外層
public class JpaOrderRepository implements OrderRepository { ... }

PlaceOrderUseCase 只 import OrderRepository, 永遠不知道 JPA 存在。控制流往外,原始碼相依往內——兩件事。

三、跨層原則

當 Entities 層的物件跨越離開 Use Case 層往外傳遞時,不要直接把 Entities 層的物件 傳出 Use Case 層,而是要在 Use Cases 層定義往外傳遞的介面與資料結構。

回到開頭那支 API。違規版:

// ❌ Interface Adapters 層直接拿到 Entities 層的物件
@GetMapping("/orders/{id}")
public Order get(@PathVariable String id) {
    return findOrder.byId(id);      // Order 直接被序列化成 JSON
}

兩個後果,而且都不會馬上痛:

  • 封裝被序列化需求逼開。就是開頭那三行。第 4 課的 invariant 沒了。
  • API 的欄位跟領域模型綁死。之後把 total 改名、 把 status 拆成兩個欄位——外部 API 契約跟著壞,而你原本只是想改領域模型。

正解是在 Use Cases 層定義一個往外傳的資料結構:

// Use Cases 層
public record OrderView(String orderId, String status, long totalCents) { }

// Interface Adapters 層拿到的是 OrderView,不是 Order
@GetMapping("/orders/{id}")
public OrderView get(@PathVariable String id) {
    return findOrder.byId(id);
}

Order 可以繼續一個 setter 都沒有。

這一課的核心

分層不是為了整齊,是為了讓「改這裡會影響到哪裡」有一個確定的答案。

相依性原則保證影響只會往外擴散,不會往內。所以動 Interface Adapters 層, Entities 層一定安全——這不是慣例,是 import 方向決定的事實。

一個型別到底該放哪一層

上面兩節講了原則,但真正動手時的問題永遠是這一個: 我手上這個檔案該放進哪個資料夾?先看整個 package 長怎樣:

com.shop
├── domain/                      ← Entities 層
│   ├── Order.java
│   └── OrderId.java
├── usecase/                     ← Use Cases 層
│   ├── CancelOrderUseCase.java
│   ├── OrderRepository.java     ← 介面「宣告」在這裡
│   └── OrderView.java           ← 回傳用的 record 也在這裡
└── adapter/                     ← Interface Adapters 層
    ├── OrderController.java
    └── JpaOrderRepository.java  ← 「實作」在這裡
// ===== usecase/OrderRepository.java =====
package com.shop.usecase;

import com.shop.domain.Order;              // 內層的內層,合法
import com.shop.domain.OrderId;

public interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);
}

// ===== adapter/JpaOrderRepository.java =====
package com.shop.adapter;

import com.shop.usecase.OrderRepository;   // ← 外層 import 內層,合法 ✅
import jakarta.persistence.EntityManager;  // ← 外層 import 框架,合法 ✅

public class JpaOrderRepository implements OrderRepository { ... }

把介面移到 adapter/ 會怎樣?那 use case 就得寫成:

package com.shop.usecase;

import com.shop.adapter.OrderRepository;   // ❌ 內層 import 外層 —— 違規

就這一行,Dependency Rule 破了。CancelOrderUseCase 非提到 OrderRepository 這個型別不可(欄位型別、建構子參數都要寫它的名字), 所以那個型別住在哪,就決定了這個 import 往哪指。

一條規則

一個型別,要放在「所有用到它的層」當中最內的那一層。

  • OrderRepository:Use Cases 用它(宣告欄位、呼叫方法)、 Interface Adapters 用它(實作)→ 最內是 Use Cases
  • OrderView:Use Cases 用它(產生並回傳)、 Interface Adapters 用它(序列化成 JSON)→ 最內是 Use Cases
那為什麼 OrderView 不乾脆再往內放進 Entities?

因為 Entities 層根本不在候選名單裡——翻遍 domain/, 沒有任何一個檔案提到 OrderView。領域模型不需要知道有人要把它顯示成什麼樣。

更重要的是那個藏在問題背後的假設:越內層越安全,所以往內放比較保險。錯。 往內移一層,是做出一個承諾:「這東西是業務本身的一部分,不會因為技術或應用而改。」

用第一個判準問:沒有電腦、公司改用紙本作業,這東西還在嗎? Order 跟「已出貨不可取消」還在; OrderView(orderId, status, totalCents) 不在——它是「某支 API 現在要回這幾個欄位」。

更好用的測試:這個型別的欄位清單是誰決定的? Order 由業務規則決定,OrderView 由畫面 / API 的消費者決定。 由消費者決定形狀的東西,不能住在最內層。

放錯的實際後果:最不穩定的東西被塞進最該穩定的地方(前端改版會去動領域模型那層); 而且會傳染(下一個人接著加 OrderListView、OrderPdfView); 最後變動理由混在一起——而「因為不同理由而改」正是分層要拆開的東西。

注意對稱性:把 Entity 直接往外傳(跨層原則在擋的),跟把 View 往內塞, 是同一個錯誤的兩個方向。

這種「內層宣告、外層實作」的介面,在六角形架構(Ports and Adapters)裡就叫 Port——之後讀到這個詞,講的就是這件事。

順著一個請求走一遍

上面全是靜態的。真正讓分層變得看得見的,是跟著一次請求走完整趟—— 使用者按下「取消訂單」:

#發生什麼檔案層
1POST /orders/123/cancel 進來,JSON 轉成輸入物件 OrderControllerInterface Adapters
2跑流程:載入訂單 → 取消 → 存回去 CancelOrderUseCaseUse Cases
3檢查「已出貨的訂單不可取消」,不合就爆炸 Order.cancel()Entities
4把 Order 轉成資料表的列、寫進去 JpaOrderRepositoryInterface Adapters
5真的執行 SQLJPA / PostgreSQLFrameworks & Drivers

只有第 3 步是真正的業務規則。「已出貨的訂單不可取消」不管你用什麼資料庫、 有沒有 API、甚至公司改用紙本作業,都還是成立。其他四步全是機制。

第 2 步呼叫第 4 步,但 CancelOrderUseCase 的原始碼裡沒有 JPA 這個字。 它呼叫的是 OrderRepository 這個介面(宣告在它自己那層),實際跑的是 JPA 實作。 執行時往外走,原始碼相依往內——這就是 Dependency Rule 那句話動起來的樣子。

現在就可以驗一次

挑你專案裡任何一支 API,把一次請求經過的檔案照順序列出來,每個標一層。 兩件事會馬上現形:

  • 有沒有哪一步跳層(Controller 直接呼叫 JPA,沒經過 use case)
  • 有沒有哪個「應該是 Entities 層」的檔案,import 了框架

這比讀十遍定義有效。

別看資料夾

如果你手上是個 Spring 專案,現在心裡大概已經把 controller/ / service/ / repository/ 三個目錄對到三層去了。那個對應是假的。

大部分專案的 service/ 裡塞滿了 @Transactional、 @Autowired、直接呼叫 JPA、甚至處理 HTTP 例外——按層來說,那些有一半屬於外圈。 目錄名字對得上,內容對不上。同理,@Repository 只是 Spring 的 bean 標籤, 不代表「Repository 是一層」——它是一個介面加一個實作,橫跨兩層。

判斷一個檔案屬於哪一層,看它 import 了什麼,不要看它放在哪個資料夾。

資料夾是給人看的,import 是編譯器認的。相依性原則管的是後者。

這對 harness 的用途

以下的對應是推論

四層與 Dependency Rule 是既有共識(Uncle Bob 2012,連結在頁尾); 收成「分層 / 相依性 / 跨層」這三條的講法,是本教學自己的整理。 而「分層 ≈ agent 的爆炸半徑上限」、「相依方向是可機械檢查的驗收條件」這兩個用法, 也是本教學自己接上去的,不是引用來的。

簡潔架構的性質對 agent 的意義
每層職責明確 一張票說得出「要動哪幾層」。說不出來,或答案是「全部」—— 那是票沒切好,不是架構的問題。這跟第 4 課的 「改到第二個 Aggregate 就該拆票」是同一種訊號,只是換一個尺度。
相依方向單向 這是少數可以完全機械檢查的東西。Entities 層的檔案 import 到 Spring、 import 到 JPA,就是違規,一條 CI 檢查就擋得住——不需要任何人在 review 時想起來。 能變成檢查的規則,就不該留在提示詞裡(第 4 課同一句話)。
跨層要轉資料結構 agent 最常見的抄近路——「把 Entity 直接 return 出去」—— 有了明確且可測的錯誤定義。你不用預測它會怎麼偷懶,只要讓那條路是死的。

再往上收一層:前四課產出的都是文件(詞彙表、邊界、驗收、規則), 第 4 課開始把規則搬進型別,這一課把它搬進目錄結構。 目錄結構是 agent 一定讀得到、而且不需要理解就會受限的東西—— 它不必同意分層,它只是 import 不到。

換你了

相依性原則說的「相依只能由外往內」,講的是什麼?

Agent 為了讓 API 回得出 JSON,在 Order 上加了無參數建構子與 setter。這違反了哪一條,後果是什麼?

動手練習

挑你自己系統裡最近做過的一張票,不要挑漂亮的,挑真實的:

自我檢查
  • 第一格答案是「四層都動」嗎?那不一定是壞事(新 feature 常常如此), 但如果每張票都四層全動,代表分層只存在於目錄名稱裡。
  • 第三格幾乎一定填得出來——大部分 Java 專案的 Entity 上都有 ORM 標註。 填出來之後真正該問的是:這些東西值不值得清掉? (答案常常是「不值得」,那也是個答案,寫下理由就好。)
  • 第四格如果寫不出來,通常是因為層與目錄沒有對應關係—— 檢查不了的原因是「哪些檔案算 Entities 層」沒有機械化的答案。那就是下一件該做的事。
  • 老毛病,每一課都問一次:你上面寫的東西裡,有沒有又用到一個沒定義的詞?
