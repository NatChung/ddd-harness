第 2 課 · DDD × Agent Harness

Bounded Context

一個詞可以有兩個意思 —— 只要你畫得出那條線。

從你上一課撞到的東西開始

上一課你寫「訂單完成」,我改成「訂單成立」,理由是那是兩個不同時刻。 但這個修法其實只解了一半。真正的問題不是你選錯字,是——

這一課的核心

「訂單完成」在結帳眼裡是付款授權成立,在倉儲眼裡是已出貨, 在財務眼裡是已入帳對帳完畢。三個都對。 它們不是三個錯誤解讀等你去挑一個,是三個部門真的各自需要那個詞指向不同時刻。

所以修法不是逼所有人同意一個定義(做不到,而且不該做), 而是畫出邊界:在這條線裡面,這個詞只有一個意思;跨過線,就翻譯。

Fowler 的說法

Fowler 舉的例子是一家電力公司:「meter」這個字在不同部門是不同的東西—— 裝機部門講的是實體電表,計費部門講的是計費點,兩者不對應。 日常對話可以糊過去,軟體不行。他的結論很短:

you need a different model when the language changes Martin Fowler, bliki: BoundedContext

語言變了,你就需要另一個模型。

反過來讀更有用:語言在哪裡變,邊界就在哪裡。 你不用先想清楚系統該怎麼切模組——你去聽人講話, 聽到同一個詞被兩群人用成不同意思,那裡就是一條邊界。

而 Bounded Context(限界上下文)就是那條線圍出來的範圍: 一個模型有效的範圍。在裡面,每個詞剛好一個意思。

看程式碼比較快

大部分系統的樣子,一個 Order 統治全部:

// ❌ 誰都需要它,所以誰都往裡面加欄位
public class Order {
    private String orderNo;

    private List<CartItem> items;          // 結帳要的
    private Coupon coupon;
    private String paymentAuthCode;

    private String warehouseCode;          // 倉儲要的
    private List<PickTask> pickTasks;
    private BigDecimal volumetricWeight;

    private String invoiceNo;              // 財務要的
    private BigDecimal taxAmount;
    private BigDecimal exchangeRate;

    private OrderStatus status;            // ← 這是誰的 status?
    // ⋯ 再 30 個欄位
}

那個 status 就是你上一課的「訂單完成」。一個欄位,三個部門搶。 加一個 SHIPPED,財務的 switch 少一個 case; 加一個 INVOICED,倉儲的狀態機多一條不該存在的邊。

切開之後:

// checkout/Order.java —— 結帳的 Order
public class Order {
    private final OrderNo orderNo;
    private final List<CartItem> items;
    private final Coupon coupon;
    private PaymentAuthorization authorization;
    private CheckoutStatus status;   // 只講「成立 / 未成立」
    // 結帳不知道儲位,也不需要知道
}

// fulfillment/Shipment.java —— 倉儲眼裡它根本不叫 Order
public class Shipment {
    private final OrderNo orderNo;   // ← 唯一的接點
    private final Address shipTo;
    private final List<PickTask> pickTasks;
    private ShipmentStatus status;   // 只講「揀貨 → 出貨」
}

// billing/Invoice.java —— 財務眼裡它是 Invoice
public class Invoice {
    private final OrderNo orderNo;   // ← 唯一的接點
    private final Money taxAmount;
    private final InvoiceNo invoiceNo;
    private InvoiceStatus status;    // 只講「開立 → 入帳」
}

三個 status,三個獨立的 enum,誰也改不到誰。 三個 context 之間唯一共用的是 OrderNo——它是翻譯的接點,不是共用的模型。

直覺會抗拒這件事

看起來像是「同一筆訂單存了三份,重複」。但它們不是同一個東西的三份拷貝, 是三個不同的東西,剛好由同一筆生意產生。倉儲永遠不會需要優惠券折抵金額; 財務永遠不會需要儲位。硬合在一起省下的那點「不重複」, 代價是三個部門的變更永遠互相牽動。

這跟你的 harness 有什麼關係

以下是推論,不是引用

DDD 講 Bounded Context 時,對象是人跟團隊。「Bounded Context 可以拿來界定 agent 的作業範圍」 是本教學自己建立的對應,不是 Evans 或 Fowler 說的。理由站得住(失效模式相同), 但你對外講的時候值得把這層標清楚。

邊界對 harness 的用處有三個,而且都很具體:

邊界決定沒有邊界會怎樣
一次任務載入多少
context 只放這個 context 的模型與詞彙		 整個 repo 倒給 agent,它在 40 個欄位裡猜哪些跟任務有關
agent 可以改到哪
越界的修改直接視為錯誤		 改結帳的 bug,順手動了倉儲的狀態機,你在 review 時才發現
詞彙表該掛在哪一層
每個 context 一份,不是全 repo 一份		 全域詞彙表裡「完成」只能有一個定義 —— 於是三個部門有兩個要被迫講錯話

一句話:一個 Bounded Context ≈ 一次 agent 任務的作用半徑。 上一課的 Ubiquitous Language 是詞彙,這一課的 Bounded Context 是那份詞彙表的有效範圍。 兩個合起來才是完整的一句:「在這個範圍裡,這些詞是這些意思。」

動手練習

在你自己的系統裡找一條真的邊界。方法照 Fowler 那句:去想哪兩群人(或哪兩個模組) 把同一個詞用成不同意思。填完這五格:

自我檢查
  • 那個詞在兩側的意思,是不是真的都對?如果其中一側其實是誤用,那不是邊界,那是該修的 bug。
  • 你填的「翻譯接點」,跨過邊界後意思會變嗎?會變就不能當接點——再找一個。
  • 最後一格填得出具體東西嗎?填不出來,可能這條線不重要,換一條。
  • 上一課的老毛病:你的描述裡有沒有又用到一個沒定義的詞?
