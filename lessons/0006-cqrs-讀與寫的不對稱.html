第 6 課 · DDD × Agent Harness

CQRS

前五課的規矩,有一半的程式碼其實不需要遵守。

一個你早該問的問題

第 4 課要你把 Order 收成 Aggregate,只持有 CustomerId,不持有 Customer 物件。第 5 課要你把 Entity 擋在 Use Case 層裡面,往外傳要另外定義資料結構。

那麼——訂單列表頁要顯示顧客姓名,怎麼辦?

照前五課的規矩走,你會做出這種東西:載入 Order Aggregate、 拿它的 CustomerId 再去載入 Customer Aggregate、 組成 DTO、一頁 20 筆做 20 次。慢、囉唆,而且你心裡知道哪裡不對。

更糟的是,這種痛會逼人做出錯誤的修正:把 Customer 塞回 Order 的 Aggregate 裡——這正是第 4 課明講的錯誤判準(「常常一起查詢」不是判準)。 規矩本身把人逼向違反規矩。

這一課的核心

因為那些規矩從一開始就不是為「讀」訂的。

Aggregate、invariant、分層、跨層轉資料結構——每一條都在防同一件事: 把資料寫壞。而查詢不會把資料寫壞。

拿防寫壞的規矩去管讀取,就是在付一筆完全沒有對價的成本。

CQRS 就是把這件事講白

CQRS(Command Query Responsibility Segregation)的主張, Martin Fowler 一句話:

you can use a different model to update information than the model you use to read information

你可以用一套模型來改資料,用另一套模型來讀資料。

改資料用一套模型,讀資料用另一套。就這樣——沒有更多了。

Command 側(會改狀態)Query 側(只讀)
走哪些規矩 前五課全套:Aggregate、invariant、分層、跨層 幾乎都不走
有沒有領域物件 有,而且是核心 沒有,而且刻意不要有
回傳什麼 成功 / 失敗,或一個 id 畫面要的形狀,直接就是 View Model
做錯的後果 資料永久壞掉,而且之後每次讀都跟著錯 這一次的答案錯,改完就對了

推到底就是:不會改變系統狀態的 Query,不需要套用 DDD,甚至根本不必設計領域物件 ——直接讀資料庫、產生前端要的 View Model 就好。

注意「甚至根本不必」。這不是「可以偷懶」,是刻意不做。 為查詢設計領域物件,得到的是維護成本,不是保護。

寫成 code 長這樣

// ---------- Command 側:全套 ----------
public class CancelOrderUseCase {
    private final OrderRepository orders;          // 回傳 Aggregate

    public void execute(CancelOrderInput in) {
        Order order = orders.findById(new OrderId(in.orderId()));
        order.cancel(in.reason());                 // invariant 在 Order 裡守
        orders.save(order);
    }
}

// ---------- Query 側:沒有 Aggregate,沒有領域物件 ----------
public class OrderListUseCase {
    private final OrderQueryRepository query;      // 專給查詢用的另一個介面

    public List<OrderListItem> execute(OrderListFilter filter) {
        return query.search(filter);               // 一次查詢,直接回畫面要的東西
    }
}

// 這就是畫面要的形狀,不是領域模型
public record OrderListItem(
    String orderId, String customerName, String statusLabel,
    long totalCents, LocalDate placedAt) { }

看 customerName 這個欄位。Command 側的 Order 只有 CustomerId——那條規矩沒有鬆動。Query 側直接 join 出名字就好, 不需要為了顯示一個名字,去動 Aggregate 的邊界。

兩邊各有各的 repository 介面,這是重點:OrderRepository 回傳 Aggregate、 給 Command 用;OrderQueryRepository 回傳 View Model、給 Query 用。 同一張表,兩條路。

這裡確實違反了第 5 課

Query 側從 Use Case 直接吐畫面要的資料結構、繞過領域模型—— 這是刻意允許的跨層捷徑,不是你忘了守規矩。

代價是重複:同一份資料在 Command 側與 Query 側各有一套表示法, 欄位改了兩邊都要動。這筆代價是你明知道而且接受的,不是意外。

能這樣抄近路的唯一理由,是這條路不會把資料寫壞。 哪天有人在 Query 側偷偷加了一行 UPDATE,這個豁免立刻失效—— 那已經不是 Query 了。

Fowler 叫你不要用

這一課到目前為止聽起來太順了,所以必須把警告原話放上來:

You should be very cautious about using CQRS. […] for most systems CQRS adds risky complexity.

你應該非常謹慎地使用 CQRS。……對大多數系統來說,CQRS 增加的是有風險的複雜度。

他說他看過不少團隊(而且是能力好的團隊)因為用了 CQRS 而變慢。 這不衝突——要分清楚兩件常被混為一談的事:

做什麼成本
分開模型 同一個資料庫,查詢走自己的路、不經過 Aggregate 很低。本課教的就是這個,大部分系統都該做
分開儲存 寫入與讀取用不同的資料庫,靠同步機制對上 很高。從此要處理「讀到舊資料」這件事,以及它引發的一整排問題

Fowler 警告的主要是第二種。第一種只是承認「讀跟寫不一樣」, 你就算不叫它 CQRS 也早就該做了。

這個兩層區分是本教學的整理

Fowler 原文談的是 CQRS 整體的風險(尤其與 event-based 模型、分離儲存搭配時), 他並沒有寫成上面這張「分開模型 / 分開儲存」的兩層表。 這個切法是本教學為了讓你分辨「該做的那一半」而做的整理,不是引用來的。

Event Sourcing 這一課完全不碰。它常跟 CQRS 綁在一起講 (Fowler 也提到兩者搭配得好),但那是另一個決定、另一組代價。 CQRS 不需要 Event Sourcing 也成立。

這對 harness 的用途

以下的對應是推論

CQRS 本身是既有 pattern(Fowler 在文中寫明這個 pattern 他是先從 Greg Young 那裡聽來的;繁中的落地整理見頁尾)。 但「先判 Command / Query 來決定驗收要多嚴」這個用法,是本教學自己接上去的。

前五課都在加規矩。這一課第一次告訴你哪裡可以不加—— 而這比加規矩更有用,因為到處都嚴格的 harness 沒有人會遵守。

性質對 agent 的意義
風險不對稱 每張票開工前先問一句:這是 Command 還是 Query? Command 側:詞彙表、invariant、Given-When-Then 一個都不能少。 Query 側:主要看形狀對不對、快不快——錯了改掉就好,不會留下壞資料。
Query 側沒有 invariant 那一側可以放手讓 agent 跑。沒有規則要守,就沒有規則會被繞過; 最壞的情況是查出來的東西不對,而那一眼就看得出來。
兩側各有 repository 介面 「這張票只該碰 OrderQueryRepository」是一句可檢查的界線。 agent 動到 OrderRepository 就是越界——不用讀它的程式碼也知道。

這也順便解釋了一個你大概已經觀察到的現象: 讓 agent 做查詢、報表、列表頁,通常又快又準;做業務流程,常常出事。 不是它在後者比較笨,是後者有 invariant 而前者沒有—— 錯誤在 Query 側會當場現形,在 Command 側會沉到資料裡。

動手練習

拿你自己系統裡最近三張票,一張一張過:

自我檢查
  • 判斷理由寫的是「會不會改狀態」嗎?如果寫的是「這張比較單純」 或「這張主要是撈資料」,那是感覺不是判準——重看「標記為已讀」那題。
  • 最後一格挑的那支,最好是「痛得最明顯」的那支(最慢、或程式碼最扭曲的), 不是最好改的那支。CQRS 值不值得,要用真的有痛的地方來驗證。
  • 如果三張票全是 Command,很正常——但也表示你手上還沒有可以放手給 agent 跑的活。
  • 老毛病:你上面寫的東西裡,有沒有又用到一個沒定義的詞?
