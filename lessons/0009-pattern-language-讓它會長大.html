第 9 課 · DDD × Agent Harness

Pattern Language

你手上有八個工具了。工具箱不是語言。

這個詞一直被刻意避開

前八課從來沒有定義過 pattern language(模式語言)這個詞, 即使它是整套教學的目標。原因寫在 RESOURCES.md 裡: 第一手來源沒收到之前,不定義這個詞。現在收到了,所以這一課可以講。

一、pattern,以及為什麼是「語言」

Christopher Alexander,1977 年,《A Pattern Language》。他講的不是軟體,是建築。

Each pattern describes a problem which occurs over and over again in our environment, and then describes the core of the solution to that problem, in such a way that you can use this solution a million times over, without ever doing it the same way twice.

每一個 pattern 描述一個在我們環境裡反覆出現的問題,然後描述那個問題的解法核心 ——描述的方式要讓你能把這個解法用上一百萬次,而且每一次都不會做得一模一樣。

「用一百萬次,每次都不一樣」是重點。pattern 不是範本,不是可以複製貼上的東西; 它是問題 + 解法核心,每次落地的樣子都不同。

「語言」那兩個字才是關鍵

Alexander 對 pattern language 的定義只有一句:

A pattern language is a network of patterns that call upon one another.

模式語言是一個由彼此互相呼叫的 pattern 所構成的網路。

差別不在數量,也不在品質,在於 pattern 之間有沒有互相呼叫。

一百個很棒的 pattern 各自獨立擺著,那是工具箱——你得自己知道什麼時候拿哪一個。 一套 pattern language 裡,大的 pattern 會告訴你「接下來該用哪幾個小的來補完我」, 所以你可以從一個問題走到下一個問題,不必事先知道全貌。

這就是為什麼 Alexander 用「語言」而不是「清單」——就像文法讓你造出無限多句子, pattern 之間的交叉引用讓你組出無限多設計。

陳建村的中文版說法:「模式語言由一群相互關聯的模式所組成」,目的是達到 Alexander 說的 Quality Without A Name(無名特質);而它的實際作用是 「提供了溝通的共同基礎,讓一般人可以使用模式語言來解決複雜的設計問題」。

注意最後那句——溝通的共同基礎。這個詞你在第 1 課就見過了。

二、你已經有一套了

前八課不是八篇獨立的文章。把它們照抽象層次排開:

層pattern擋掉什麼
流程層 Event Storming(第 7 課) 不知道要建模什麼
語言層 Ubiquitous Language(第 1)、Bounded Context(第 2) 語言漂移、範圍漂移
驗收層 Given-When-Then(第 3)、Design by Contract(第 8) 判定漂移、責任不明
模型層 Aggregate 與 invariant(第 4) 一致性破口、任務大小沒有判準
架構層 簡潔架構三原則(第 5)、CQRS(第 6) 爆炸半徑不明、到處都嚴格

照這張圖走一遍就會發現:你從來不需要一次想全部。 每個 pattern 在解完自己的問題之後,會產生一個新問題,而那個新問題有明確的下一站。

每一條箭頭都在前面幾課出現過
  • hotspot 撞出歧義 → 用參考卡 01 判斷該拆詞還是畫界(第 7 → 1/2)
  • Brandolini 說討論變熱就「define a clear acceptance test」(第 7 → 3)
  • 第 4 課:文件會被忘記,所以把規則變成物理定律(第 3 → 4)
  • 第 4 課末:「同一帳號一天不能下超過 10 筆」單一 Aggregate 守不住(第 4 → 5)
  • 第 6 課:那些規矩本來就只為防寫壞而訂,查詢不必付(第 4/5 → 6)
  • 第 8 課:契約寫不出來,通常是 Aggregate 邊界錯了(第 8 → 4,反向的箭頭)

這些不是後來硬接的。每一課都是從前一課的缺口長出來的—— 那正是「互相呼叫」的意思。

三、讓它會長大

到這裡為止,這套語言是死的——它只包含我教你的東西。真正會複利的部分是下面這個。

MISSION 裡有一條:agent 犯了錯 → 錯誤被轉成 pattern 或驗收條目 → 同類錯誤不再發生。 問題是「轉成什麼」。答案不只一個,而且強度差很多。

下面這道階梯是本教學的整理

Alexander 與 Teddy 講的是 pattern language 本身。把「agent 犯的錯」對應到 「該用哪一階擋住」這道階梯,是本教學自己組出來的,不是引用來的。

agent 犯了錯,先別急著改提示詞。問這一句:

這個錯誤,下次要靠什麼擋住?

然後從最強的往下找,挑做得到的最強那一階:

階手段為什麼強
1
最強		 型別 / 會拋例外的方法
(第 4、8 課)		 agent 做不到那件錯事。不需要它讀、不需要它記得、不需要它同意
2 機械檢查(CI、import 規則)
(第 5 課)		 做得到但會被擋下來。不需要人在 review 時想起來
3 可執行的驗收(Given-When-Then)
(第 3 課)		 錯了會有明確的失敗,而且每次都跑
4 詞彙表 / 原則檔的一條
(第 1 課、CLAUDE.md)		 要被讀到才有效,但至少寫下來了、而且跨任務
5
最弱		 提示詞裡多一句叮嚀 要被讀到、被記得、被遵守,而且換模型後未必還吃得住
最常見的錯誤處理方式,是最弱的那一階

agent 又犯了同樣的錯,大部分人的反應是在提示詞裡加一句更明確的叮嚀。 它會有效——通常有效個幾次。

然後叮嚀愈積愈多,變成噪音,彼此開始衝突,而且沒有人敢刪, 因為不知道哪一句還在擋著什麼。換一個模型,整批重新賭一次。

第 4 課那句話在這裡回來了:這條能不能變成一個會拋例外的方法簽章? 能的話,提示詞裡那一句就該刪掉——而且一定要真的刪掉, 否則你會同時維護兩份規則,那是第 8 課 Meyer 罵的那件事。

往上搬一階,就是在寫一個新 pattern

做完這件事,你手上會多一個東西:一個「問題 → 解法核心」的配對,而且它會被下次用到。 那就是一個 pattern。它接在哪個既有 pattern 後面,那條線就是新的箭頭。

語言就是這樣長大的——不是你坐下來設計它,是每次踩到坑就往上搬一階,順手把線接上。

這個 workspace 自己就是例子

learning-records/ 那幾份就是這個迴圈,只是犯錯的主體是人不是 agent:

  • LR 0004:你把拆詞誤判成畫邊界 → 產出參考卡 01(第 4 階:寫下來的判準)
  • LR 0009:你在第 8 課跳過了「是不是契約」那一關 → 課文把散文改寫成 Q1 → Q2 的編號步驟(從第 5 階搬到第 4 階,而且變成流程)

錯誤沒有被當成「你要更小心」,而是被當成教材的缺口。同一個東西, 換成 agent 也一樣運作。

最容易被誤認成第 2 階的東西

CLAUDE.md、提示詞這類東西每次都會被自動讀進去, 所以感覺像個機制、像有東西在跑。

但自動的是注入,不是遵守。 機械檢查的定義是:違反會有明確的 fail。提示詞裡沒有 fail 這回事, 只有「希望它照做」。

快篩:不照做的時候,會發生什麼?答案是「沒事」→ 那就是第 4–5 階的文字約定, 不管它被讀進去幾次。

這條規則現在住在第幾階?

下面每一項都是同一批規則的不同寫法。判斷它現在的強度。

先問一句再作答:這句話在描述一個「什麼東西」? 一段程式碼?一條 CI 規則?一個測試?一句寫在文件裡的話? 階數由載體決定,不由句子裡的關鍵字決定—— 詳見參考卡 02。

Order 沒有 setter,外面拿到的 items 是複本
CI 有一條規則:domain 目錄 import 到框架就 fail
CLAUDE.md 寫著「domain 層不要用框架」
一條 scenario:庫存為 0 時結帳按鈕不可點擊
詞彙表:已出貨 = 交給貨運;已送達 = 客戶簽收
addItem() 在訂單非 DRAFT 時丟 IllegalStateException
提示詞每次都提醒「改完明細記得 total 要重算」
一個測試:對已成立的訂單呼叫 addItem 必須拋例外

換你了

一份「一百個很棒的 pattern 的清單」,跟一套 pattern language,差別在哪?

agent 第三次犯同一個錯了。你在提示詞裡加了一句更明確的叮嚀。這個做法的主要問題是?

動手練習

兩題。第一題比第二題重要得多。

(一)拿最近一次 agent 真的犯的錯,跑一次階梯。

(二)畫出你自己那張網。不用畫全,畫你真的用過的部分就好。

自我檢查
  • 第一題「為什麼不行」那幾格才是重點。寫「做不到」很容易, 寫得出為什麼做不到才有價值——那個理由常常是可以改掉的 (例:「型別擋不住,因為那個規則跨三個 Aggregate」→ 那是第 5 課的問題,不是做不到)。
  • 「要刪掉什麼」那格如果是空的,這次就沒有真的往上搬。 只是多加了一層,兩份規則並存 —— 那正是 Meyer 罵的東西。
  • 第二題如果箭頭很少,不代表你的做法不好,代表你的 pattern 還是工具箱。 箭頭是使用經驗長出來的,不是設計出來的。
  • 老毛病,最後問一次:你上面寫的東西裡,有沒有又用到一個沒定義的詞?
