第 8 課 · DDD × Agent Harness

Design by Contract

依合約設計 —— 順便刪掉你程式裡一半的防禦性檢查。

第 4 課只做了三分之一

第 4 課教你把 invariant 寫進 Aggregate:「訂單總額必須等於明細加總」,任何時候都成立。

但 invariant 只管物件自己的狀態。它管不到兩件事:

  • 呼叫我之前,你得先保證什麼?(「訂單必須還在 DRAFT 狀態」)
  • 我做完之後,保證給你什麼?(「明細一定多一筆,而且 total 一定重算過」)

把這三件事寫全,就是 Design by Contract(依合約設計)。 Bertrand Meyer 1992 年提出,而且他從一開始就把它當成兩方的合約來談,不是當成檢查。

先看一份真的合約

Meyer 原文用的例子是快遞:你在巴黎,要寄一個包裹。

角色義務(Obligations)權利(Benefits)
Client
(你)		 包裹不超過 5 公斤、每邊不超過 2 公尺。付 100 法郎。 包裹在四小時內送達收件人。
Supplier
(快遞公司)		 四小時內送達收件人。 不必處理太大、太重、或沒付錢的包裹。

看右下角那格——那是整堂課的重點。

Meyer 的說法是,合約保護兩邊:

It protects the client by specifying how much should be done. […] It protects the contractor by specifying how little is acceptable: The contractor must not be liable for failing to carry out tasks outside of the specified scope.

它保護 client,方式是講明「要做到多少」——client 有權得到某個結果。它也保護 contractor,方式是講明「做到多少就算數」:contractor 不必為了沒做約定範圍之外的事而負責。

一方的義務,就是另一方的權利。你保證包裹不超重,快遞公司就有權不處理超重的情況—— 它不必寫「如果包裹 500 公斤怎麼辦」的程式碼。

三種條款

搬到程式上,合約有三條:

條款是什麼誰負責
Precondition
前置條件		 呼叫這個方法之前必須成立的事 呼叫方(client)
Postcondition
後置條件		 方法正常結束時保證成立的事 被呼叫方(supplier)
Invariant
不變量		 這個類別的每個方法進出時都成立的事 被呼叫方(第 4 課教的就是這個)

Meyer 原本的語言 Eiffel 有內建語法(require / ensure)。 Java 沒有,所以要自己寫:

public class Order {   // invariant: total == sum(items) - discount,任何時候

    public void addItem(ProductId productId, int qty, Money unitPrice) {
        // ---- precondition:呼叫方的責任 ----
        if (status != DRAFT)
            throw new IllegalStateException("訂單成立後不可加明細");
        if (qty <= 0)
            throw new IllegalArgumentException("數量必須大於 0");

        items.add(new OrderItem(productId, qty, unitPrice));
        recalculateTotal();

        // ---- postcondition:我的責任 ----
        assert total.equals(sumOfItems().minus(discount));
    }
}

Meyer 的 Eiffel 版本長這樣,對照著看比較清楚:

put_child (new: NODE) is
    require
        new /= Void                          -- precondition
    do
        ... Insertion algorithm ...
    ensure
        new.parent = Current                 -- postcondition
        child_count = old child_count + 1     -- old 是呼叫前的值
    end

這一課真正的價值

不是「多寫兩種檢查」。是下面這兩句話,Meyer 原文:

A precondition violation indicates a bug in the client (caller). The caller did not observe the conditions imposed on correct calls.

A postcondition violation is a bug in the supplier (routine). The routine failed to deliver on its promises.

違反 precondition,代表 bug 在 client(呼叫方)——呼叫的人沒有遵守正確呼叫該有的條件。違反 postcondition,則是 bug 在 supplier(被呼叫的常式)——它沒有做到自己承諾的事。

這一課的核心

「這是誰的錯」從此有明確答案,不需要討論。

程式炸了,看它炸在哪一種條款上:
炸在 precondition → 呼叫的人錯了,他沒遵守約定。
炸在 postcondition → 被呼叫的人錯了,他沒做到承諾。

沒有契約的時候,同樣一個 NullPointerException,可以吵一個下午: 「你應該檢查啊」/「這本來就不該傳 null 進來」。那個爭論的本質是責任沒有事先分配。

然後你就可以刪程式碼了

這是 DbC 最反直覺、也最有用的一條。Meyer 對防禦性程式設計的評語:

Adding possibly redundant code "just in case" only contributes to the software's complexity — the single worst obstacle to software quality in general, and to reliability in particular. The result of such blind checking is simply to introduce more software, hence more sources of things that could go wrong at execution time, hence more checks, and so ad infinitum.

為了「以防萬一」而加上可能是多餘的程式碼,只會增加軟體的複雜度——而複雜度正是軟體品質最大的單一障礙,對可靠度來說尤其如此。這種盲目檢查的結果,只不過是引入了更多程式碼,因而多出更多執行時可能出錯的來源,因而又需要更多檢查,如此無止盡地循環下去。(ad infinitum 是拉丁文,「以至無窮」。)

注意破折號後面那句修飾的是複雜度,不是「多餘的程式碼」——他說複雜度是頭號敵人, 而「以防萬一」的程式碼只是製造複雜度的一種方式。而且這是一個沒有停止點的迴圈: 檢查碼本身也是程式碼,也會出錯,於是又想加檢查來防它。

他給了一條絕對規則:

Either you have the condition in the Require, or you have it in an If instruction in the body of the routine, but never in both.

這個條件要嘛放在 require(前置條件)裡,要嘛放在常式內文的 if 裡,絕不兩邊都放。

並且直說:「This principle is the exact opposite of the idea of defensive programming, since it directs programmers to avoid redundant tests.」 (這條原則跟防禦性程式設計的想法剛好相反,因為它要求程式設計師避免多餘的檢查。)

換句話說:每個條件只有一個負責人。寫進 precondition,就是呼叫方的事, 方法裡面不准再檢查一次;要方法自己處理,那就別放進 precondition。 兩邊都寫,等於兩邊都不負責。

最容易搞混的一件事

「庫存不足」不是契約違反。

契約條款講的是錯誤——不該發生、發生了就是有人寫錯程式。 而「庫存不足」「付款被拒」「網路逾時」是預期之內的結果,它們是正常業務流程的一部分, 該用一般的回傳值或例外處理,不是用 assert。

Meyer 講得很清楚:assertion 不是用來描述那些「特殊但預期得到、需要特別處理」的情況—— 那種請用普通的 if。

快篩:這件事發生了,是「有人程式寫錯」還是「今天生意就是這樣」? 前者才是契約。

還是覺得抽象?換這個更好用的問法——這件事真的發生時,你希望使用者看到什麼?

使用者該看到判定
「很抱歉,此商品庫存不足」 業務結果——正常流程,要好好處理
500 錯誤、工程師半夜被叫起來 契約違反——這是 bug,該當場炸掉

把業務結果寫成 precondition 的後果很具體:庫存不足會變成丟例外、變成 500、 進 error log、觸發告警——你會被自己的正常生意吵醒。

分兩層問,不要一次判 
Q1  這件事發生了,是「有人程式寫錯」還是「今天生意就是這樣」?
        生意就是這樣  → 不是契約,結束
        有人寫錯      → 進 Q2

Q2  它什麼時候必須成立?
        呼叫某方法之前   → Precondition
        某方法結束時     → Postcondition
        隨時            → Invariant

下面的分類練習,最常錯的不是 Q2 分不清楚,而是整個跳過 Q1 ——因為業務規則跟契約條款寫成句子的時候長得一模一樣。

寫不出契約的時候,通常是邊界錯了

舉一個看板系統的例子。用 DbC 的角度重看它,會發現: Card.move() 的 precondition 需要知道「目標 Stage 裡總共有幾張卡」—— 但 Card 這個 Aggregate 根本沒有那個資訊。

結論不是「想辦法把資訊塞進 Card」,而是這個方法放錯地方了,該搬到 Workflow。

他的結論句是:「透過撰寫合約讓領域模型與通用語言更加完整。」

所以契約是一種診斷工具
  • precondition 寫不出來(需要的資訊不在這個物件手上)→ 第 4 課的 Aggregate 邊界劃錯了,或方法放錯物件
  • postcondition 寫不出來(說不清楚做完會變怎樣)→ 這個方法做了太多事,該拆
  • 條件裡出現一個沒定義的詞(「訂單必須是有效的」)→ 第 1 課的老問題,「有效」是什麼意思

寫契約的過程本身會逼出這些問題,而且是在寫實作之前。

這對 harness 的用途

以下的對應是推論

DbC 是既有方法(Meyer 1992)。但下面「LLM 是天生的 defensive programmer」、 以及「precondition 是給 agent 的減法指令」這兩個用法,是本教學自己接上去的。

LLM 是天生的防禦性程式設計師。你叫 agent 寫一個方法,它會加 null 檢查、 加邊界檢查、加 try-catch、加「以防萬一」的分支——因為它不知道什麼是被保證的, 所以它把所有情況都當成可能發生。

那正是 Meyer 在罵的東西,而且在 agent 場景下更嚴重:那些多出來的分支沒有測試涵蓋、 沒有人看得懂為什麼存在,而且下一個 agent 看到它們會再加更多。

契約的性質對 agent 的意義
precondition 是保證 它是一道減法指令:「這些情況你不必處理。」 agent 最缺的就是這個——它永遠不知道可以不做什麼。
違反時的歸屬明確 agent 改壞了東西,例外訊息本身就說得出是它呼叫錯還是實作錯。 不用人去判讀。
契約寫在方法簽章旁邊 它跟程式碼放在一起,不會像文件那樣過期, 而且 agent 讀那個方法時一定會讀到——不必塞進提示詞。

跟第 3 課的分工:Given-When-Then 是外部驗收,一個 scenario 測一條路徑, 跑測試時才檢查;契約是內建的,每一次呼叫都檢查,包含你沒想到要測的那些路徑。 兩個一起用——測試守回歸,契約守每一次呼叫。

分分看

下面每一句,是哪一種條款——還是根本不是契約?

呼叫 cancel() 之前,訂單狀態必須是「已成立」
addItem() 回來之後,total 一定等於明細加總
訂單的 total 任何時候都等於明細加總減折扣
庫存不足時,下單會失敗
傳進來的 quantity 必須大於 0
save() 回來之後,這筆訂單一定查得到
付款閘道逾時沒有回應
訂單的折扣金額不得大於總金額

換你了

程式在 precondition 這一行炸了。這是誰的 bug?

一個條件已經寫進 precondition 了,方法內部要不要再檢查一次比較保險?

動手練習

挑你系統裡一個真的 public 方法,幫它補一份合約:

自我檢查
  • 你寫的 precondition 裡,有沒有其實是「業務會失敗」的東西? (「庫存必須足夠」通常不是 precondition ——庫存不足是生意的常態,不是呼叫方的錯。)
  • postcondition 那格如果寫不出來,通常是這個方法做了太多事。 試著用一句話講完它保證什麼——講不完就該拆。
  • 第五格(卡住的地方)才是最有價值的一格。 卡在 precondition = 需要的資訊不在這個物件手上 → Aggregate 邊界可能錯了; 卡在用詞 = 第 1 課的老毛病又出現了。
  • 如果第四格找到了重複檢查:先別急著刪。先問「這個條件到底該是誰的責任」, 決定了再刪掉另一邊——這才是 Meyer 那條規則的意思。

下一步該讀什麼

原始出處: Applying "Design by Contract" — Bertrand Meyer, IEEE Computer, October 1992(免費 PDF)。 本課的快遞合約例子、precondition/postcondition 的歸屬、對防禦性程式設計的批評、 以及那條「never in both」的絕對規則,全部出自這篇。 這篇我實際讀過(前五頁,即概念的部分),引用句都是原文。 ⚠️ 後半的例外處理與 rescue clause 機制沒讀,本課也沒講。

本課相關

  • 第 4 課:Aggregate —— 那課的 invariant 是本課三種條款之一;本課補上另外兩種
  • 第 3 課:Given-When-Then —— 外部驗收 vs 內建契約,兩個一起用
  • 第 1 課:Ubiquitous Language —— 契約寫不出來,常常是因為詞沒定義
  • 第 7 課:Event Storming
  • 第 9 課:Pattern Language —— 把前八課收攏成一套會長大的語言
那份合約貼給我,我只看兩格: 你有沒有把「業務會失敗」寫成 precondition(最常見的錯), 以及你卡住的那一格——契約當診斷工具的價值全在那裡。
