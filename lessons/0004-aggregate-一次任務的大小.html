第 4 課 · DDD × Agent Harness

Aggregate

把規則從提示詞搬進程式碼 —— 順便決定一次任務該多大。

前三課都在你之外

詞彙表、邊界、驗收——這三樣都是寫給 agent 看的文件。 文件的問題是:它要被讀、被記得、被遵守,任何一環斷掉就失效。

這一課換一種做法:把規則做成「違反就會爆炸」的程式碼。 那種規則不需要被讀,也不需要被記得。

先講 invariant

Invariant(不變量)是一條任何時候都必須成立的規則。 不是「應該」、不是「通常」——是只要它不成立,系統就處於錯誤狀態。

例:訂單的總金額,必須等於所有明細金額加總減掉折扣。 這條不能有例外,也不能「晚一點再對上」。

大部分系統的 Order 長這樣:

// ❌ 只是個資料袋
public class Order {
    public List<OrderItem> items;   // 誰都能改
    public Money total;              // 誰負責讓它跟 items 一致?
}

order.items.add(newItem);   // total 沒動 → invariant 破了,而且沒人知道

這裡真正的問題不是「有人會忘記呼叫 recalculate」,而是這個類別讓「忘記」變成可能。 規則存在於某個人的腦袋裡、或某份文件裡,不存在於程式碼裡。

Aggregate:把入口收成一個

Aggregate 是一組必須一起保持正確的物件, 由一個 Aggregate Root 當唯一入口。外面只拿得到 root, 碰不到內部。

public class Order {                       // ← Aggregate Root
    private final OrderId id;
    private final CustomerId customerId;   // ← 是 ID,不是 Customer 物件
    private final List<OrderItem> items = new ArrayList<>();
    private Money total;
    private OrderStatus status;

    public void addItem(ProductId productId, int qty, Money unitPrice) {
        if (status != DRAFT)
            throw new IllegalStateException("訂單成立後不可加明細");
        items.add(new OrderItem(productId, qty, unitPrice));
        recalculateTotal();                // ← invariant 在這裡被維護
    }

    public List<OrderItem> items() {
        return List.copyOf(items);         // ← 外面拿到複本,改不到本體
    }
    // 沒有 setTotal(),沒有 getItems() 回傳可變 list
}

差別不在多寫了幾行,在於每一個 public 方法結束時,invariant 都成立, 而且外面沒有路徑可以讓它不成立。

這一課的核心

「訂單成立後不可加明細」這條規則,現在不需要任何人記得。

你不用在提示詞裡寫、不用在 code review 抓、不用在文件裡宣導。 agent 寫出違反它的程式碼時,那行呼叫會直接拋例外——在測試裡、在 CI 裡、在它自己跑的時候。

前三課是把規則講清楚,這一課是把規則變成物理定律。

邊界畫在哪:問 invariant,不要問「有沒有關係」

最常見的錯誤是照「這些東西看起來有關」來分組。正確的判準只有一個:

哪些東西必須在同一個時刻都正確?
這句話要怎麼實際去驗

「必須同時正確」是判準,但它不好用——太抽象。實際去驗的問法是:

「晚一點再對上,會不會有人算錯錢?」

  • 訂單總額 ↔ 明細:那一瞬間有人看到的金額就是錯的 → 同一個
  • 訂單成立 ↔ 寄確認信:晚 3 秒、晚 3 分鐘,沒人受害 → 不同

特別注意:「一起改」不等於同一個 Aggregate。下單的當下會一起扣庫存、 發通知、寫 log,四件事同時發生,但只有訂單自己那一組不能有一瞬間不一致。 同理,別把「同時正確」記成「同步」——同步講的是時序,同時正確講的是一致性, 差一個字,判準就滑掉了。

組合判斷
訂單 ↔ 訂單明細 同一個。總金額必須等於明細加總,少一個都不行,而且要立刻。
訂單 ↔ 顧客 不同。顧客改了名字,已成立的訂單不會因此變錯。關係緊密,但不需要同時正確。

另外兩條規矩,都是從這個判準長出來的:

  • 一次交易只改一個 Aggregate。改兩個就代表你認為它們要同時正確——那它們應該是同一個。
  • Aggregate 之間用 ID 互相參照,不是物件參照。 持有 Customer 物件,很容易一不小心就順手改了它。持有 CustomerId 就改不到。
如果你腦中已經自動對到資料庫了

「Aggregate 像 DB 的關聯、Entity 像 Table」——這是熟資料庫的人最自然的第一個類比, 而且方向剛好是反的。

對得上的只有一點:Entity 靠 id 辨識、不靠欄位值,這跟 primary key 同構。其餘都不對:

  • FK 表達「有關係」,Aggregate 表達「必須同時正確」—— schema 裡沒有任何欄位在表達後者。訂單 ↔ 顧客有 FK 卻是不同 Aggregate; 商品 ↔ 可售庫存常在同一張表,也是不同 Aggregate。 下面那六題,答案全都跟 FK 對不上,那是刻意挑的。
  • Entity 有行為,Table 沒有。把 Entity 當 Table,就會做出 「一堆 getter/setter 的資料袋 + 邏輯放 Service」——正是本課開頭要修掉的東西。
  • Value Object 裝不進這個類比。Money 住 Entities 層, 但它不是一張表,只是嵌在別人表裡的兩個欄位。
  • 正規化的目標是消除重複,Aggregate 的目標是保護 invariant。 目標不同,切出來的線自然不一樣。

快篩:把 FK 全部拿掉,你的判斷會不會改變? 不會 → 你用的是 invariant 判準;會 → 你正在讓 schema 決定領域模型。

真要用資料庫的詞類比,換這個:Aggregate 比較像「一個 transaction 的邊界」, 不是「一組 FK 關聯」——「一次交易只改一個 Aggregate」直接就對上了, 而且它抓得到「同時正確」那個時間性質,那正是 FK 表達不出來的。

還有一件事現在先講,第 5 課會用到:不是所有 invariant 都住得進 Entity。 「同一個帳號一天不能下超過 10 筆訂單」是一條沒有例外的規則,但它跨越很多張 Order, 單一個 Aggregate 守不住它。這種規則會往外挪一層——挪到哪、為什麼,是下一課的事。

這對 harness 的三個用途

以下第二、三點是推論

Aggregate 與 invariant 是 DDD 的既有概念(Evans 提出,Vernon 的書講得最清楚)。 但「Aggregate ≈ 一次 agent 任務的天然大小」、「用型別把叮嚀下放成例外」這兩個用法, 是本教學自己接上去的。

Aggregate 的性質對 agent 的意義
一次交易只改一個 一張 ticket 只碰一個 Aggregate。作用半徑明確,不用猜任務該多大—— 改到第二個 Aggregate 就是訊號:這張票太大了,該拆。
root 是唯一入口 agent 沒有路徑繞過規則改內部狀態。不是「它應該不會」,是「它做不到」。
invariant 在 root 內強制 很多提示詞裡的叮嚀可以刪掉。每刪掉一句,context 就少一分噪音, 也少一個換模型後可能失效的假設。

最後一點值得多說一句。你 harness 裡那些「記得要⋯」「不要⋯」的規則, 每一條都該問一次:這條能不能變成一個會拋例外的方法簽章? 能的話就搬進去——寫在 code 裡的規則不會被遺忘、不隨模型改變、而且免費地被每一次測試檢查。

動手練習

在你自己的系統裡找一條真的 invariant——一條只要不成立、系統就是錯的規則。 然後看看它現在守不守得住:

自我檢查
  • 你寫的 invariant 裡有「應該」「盡量」「通常」嗎?有就不是 invariant,是願望。
  • 第 4 格填得出來嗎?幾乎一定填得出來——public setter、回傳可變 list 的 getter、 直接寫資料庫的 script。填不出來的話,通常是你還沒真的去看那個類別。
  • 「必須同時正確」的那組東西,是不是塞了「只是常一起用」的東西進去?
  • 老毛病:裡面有沒有又用到一個沒定義的詞?
