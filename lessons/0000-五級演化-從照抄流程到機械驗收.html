開場 · DDD × Agent Harness

五級演化

從照抄流程,到機械驗收。

賭注

同一份需求,今天這個模型跑出一個東西,下個月換一個模型跑出另一個
——而你沒辦法一眼說出哪個對。

整條路只追一件事

模型不會變 deterministic,那是它的本質。 你能做的是讓「對不對」變 deterministic。

第 1 級照抄組織圖

公司本來怎麼跑,就讓 agent 怎麼跑:一條線走下去,任何一關說不行就退回。

AI 加速的是每一格。
真正吃掉時間的是退回,而那條路一格都沒短。

說明

這是一條真實跑過的線,已抽象化、不點名。拆掉它那筆 commit 第一句是: 「推行不下去,棄案。」

第 2 級照抄 Scrum

不抄整個組織,只抄一格:Planning。 輸入 User Story,產出 What(AC) 與 How(Task),後面直接交給 AI 去翻 code。

它把「對不對」推給 AC,但沒有人在檢查 AC 本身寫得夠不夠。

這個形狀現在滿地都是

GitHub Spec Kit · OpenSpec · BMAD-METHOD(角色分得最像 Scrum: analyst / PM / architect / scrum master / dev / QA)· Kiro(AWS,把 spec 做進 IDE)· Taskmaster · Agent OS。

名字不一樣,骨架都是需求 → 規格 → 任務 → 實作。挑哪個不是重點, 重點是它們都停在同一個地方。

第 3 級Superpowers

一套定義完整的 AI 工作流:寫死的九步,一步一步逼你走完才准動工。

綠色那兩步是唯一機器說了算的地方。
其餘七步,還是模型說了算。

先埋一條界線,第 5 級回收

該隨模型能力縮的是流程步驟(它防的是偏題,模型變聰明就抵銷了), 不是 red-green 這種機械關卡(它防的是作弊,永遠不會被抵銷)。

混在一起講,就會得到「模型變強就不用寫測試了」——那是錯的。

第 4 級mattpocock-skills

完全相反的走法:一個 skill 只解一個問題,做完收工,可自由拼裝。

強在兩件事:

  • 短到誇張。那支爆紅的拷問 skill,扣掉 front-matter, 整份指令 4 行、106 個英文字——因為他用的是模型訓練資料裡的經典術語當指令。 說一句 Data Clumps,等於說了一百字。
  • 不綁架你。沒有非走不可的順序,你手上有什麼就從哪一支接進去。

2026-08-19 從本機安裝的版本抄出來的現況(不是二手轉述):

/grilling —— 整份指令就這 4 行(106 字)
  1. 相逼問到我們達成共識為止;走過決策樹的每一個分支,
     一個一個解掉決策之間的相依。每一題都給你的建議答案。
  2. 一次只問一題,等我回覆才問下一題。一次問一堆會讓人不知所措。
  3. 事實,你自己去環境裡查(檔案、工具),不要問我;
     決定,是我的 —— 每一個都拿到我面前等我回答。
  4. 在我確認達成共識之前,不准動手。

/grill-me        →「Run a `/grilling` session.」            ← 1 行,4 個字
/grill-with-docs →「Run a `/grilling` session,
                        using the `/domain-modeling` skill.」   ← 1 行,8 個字
注意最後那一行

「拷問 + 領域建模」這件事,在他手上就是一行 skill——把 /grilling 接上 /domain-modeling。

他已經把 DDD 掛上去了。差別只在:那一行沒有規定要問哪些問題。

AI 幫你找洞。但洞的清單是 AI 列的 —— 它不知道你的 domain 有哪些坑。

把三份 prompt 打開來數

三份都做「動工前先把事情問清楚」,長度差很多——但真正的差別不是長度,是字花在哪:

prompt非空行字元字花在

mattpocock		 4542 怎麼問

HARD-GATE、9 步 checklist、流程圖、存檔路徑、自審、審核關卡

前兩份加起來 9,048 個字元,沒有任何一句規定要問什麼。 brainstorming 最接近的一句是「ask clarifying questions — understand purpose / constraints / success criteria」:三個桶子,沒有清單。

問什麼交給 LLM,你就沒有分母。
「還缺什麼」這句話,在那個世界裡問不出口。

第 5 級多的就三件事
  • 要問什麼 —— 每一題都得標「它補哪一格」。標不出來的題不要問,那是閒聊。
  • 要什麼答案 —— 答案有固定的落點:哪個詞、哪條規則、哪條驗收。
  • 答案要有依據 —— 他親口說的 / 推導出來的 / 我們自己決定的,一律標清楚。

第 5 級DDD + Clean Architecture

前四級都在改流程。
第五級改的是:問題本身從哪裡來。

三句話

1. 落成表,不落成散文。散文讀起來很順,但你數不出它缺幾格。

2. review 的對象是表。在表上抓缺漏,比在 code 裡抓便宜一百倍。

3. 回收第 3 級那條界線。ArchUnit 跟 red-green 同一類——機械關卡,不隨模型變聰明而縮。

誰在查:語意歸 LLM,「少了什麼」歸 script

「這兩格矛不矛盾」是語意判斷,LLM 做。但它跟「叫 AI 自己看看有沒有問題」差很遠 ——該有哪幾格不是它決定的,清單先寫死了。

而「少了什麼」有 script 在數,六支,判準刻意寫笨 (寫成「大致上都有記到」這支就白做了):

  • landing_check —— 第 N 輪問出去的每一題,有沒有出現在第 N+1 輪那張落點表裡
  • glossary_check —— 每個對外欄位名對不對得到詞彙表:差幾個、差哪幾個
  • provenance_check —— 宣稱「他親口說的」值,逐字稿裡真的有嗎
  • contract_triage —— 哪幾條契約守不住、哪幾條指不出測試
  • package_landing_check —— 規格宣告的 package,實作真的有 class 嗎
  • vacuous_tests —— 哪條測試什麼都沒約束到

還有一條共用鐵律:「不適用」不算「通過」——沒東西可查的,自成一類、有自己的離開碼, 不准折進通過數裡。守衛沒有壞掉,是不再適用了,而不適用不會有人發現。

所以整堂課的強制有三級:

層級誰在擋在哪一級
script 級red-green、ArchUnit ——機器跑,跑不過就是紅的第 3、5 級
清單級LLM 查語意,但照固定清單查;缺什麼很明顯第 5 級的表
模型自覺「你檢查一下」——查得好不好全看它今天怎麼樣前四級的 review

清單級不如 script 級,但比模型自覺強太多——差別就在「缺漏會不會現形」。

為什麼中間要過一次 DB —— 不然 GWT 會生錯,而且指向錯的地方

YAML 擋不住任何東西:沒有型別、沒有外鍵,寫錯的 YAML 一樣是合法的 YAML。 它只買到兩件事——agent 寫得順、人 diff 得出來。

擋的工作全在匯入那一步:schema 的每一條 CHECK / FK,都取代了散文裡的一句叮嚀。 叮嚀會被忽略,CHECK 不會。所以圖上綠的是匯入那一格,不是 YAML。

那為什麼不叫 agent 直接寫進 DB?因為 YAML 買到的是另外兩件事: agent 寫得順,以及人 diff 得出來、進得了 git 給人 review。 直接寫 DB 就沒有那份可審的中間產物了。

最要命的那個例子:明細寫「2 雙 × 3200 元」,期望的總金額卻寫 3200。

  • 沒有 DB:測試生得出來、跑起來紅。你去查實作 —— 實作算 6400,是對的。 錯的是規格,但規格是驗收的來源,沒有人會去懷疑它 —— 你只會覺得實作有 bug,然後把對的實作改成錯的去迎合規格。
  • 有 DB:匯入當場說「期望 3200,但各明細的數量 × 單價加總是 6400 —— 兩者不一致」。

沒有 DB,錯誤延後到跑測試才爆,而且爆出來的樣子指向錯的地方。

提問清單:借 DDD 的詞

詞逼你回答什麼
Ubiquitous Language這個詞在我們這裡到底指哪一刻?
Bounded Context同一個詞在兩群人嘴裡是不同的東西 → 畫線,兩邊各自定義
Aggregate哪些東西必須一起對?(順便決定一次任務該多大)
Given-When-Then給定什麼、發生什麼、就必須得到什麼 → 機器判得動
為什麼只有四個

DDD 戰術層的 building block 一般列七個:Entity、Value Object、Aggregate、 Domain Event、Repository、Factory、Service。

這門課只借其中一個(Aggregate),另外三個是戰略層兩個 + BDD 一個。 因為這裡要的是一份提問清單,不是建模百科——七個全教會變成「又一套方法論」。

Clean Architecture 那一層(分層、相依方向、爆炸半徑)在第 5 課。

四條但書 —— 有人說「所以 AI 能寫完整個系統了」的時候用
  1. 「全綠」只證明了 1 條真情境。
  2. 17 條 GWT 只有 1 條走到實作面前。掉的是庫存鎖、付款、退費、狀態流轉 ——真正的生意邏輯。
  3. 架構那幾條綠燈是骨架繼承來的。空專案上 ArchUnit 必然綠,一位元的資訊都沒有。
  4. 只有一份實作。「兩個模型被同一套驗收判定」還沒做到。

五級是同一個動作,做了五次

1 → 2「誰該進來審」:從人的行事曆 → 流程
2 → 3「對不對」:從人的眼睛 → red-green
3 → 4「該怎麼走」:從寫死的流程 → 可拼裝的工具
4 → 5「該問什麼」:從 AI 手上 → 你的 domain

這個梯子不是我事後排的,是它自己在爬。

那條照抄組織圖的線,被拆掉之前自己把拷問式問法加進了第一關; 寫那套小 skill 的人,自己接上了 DDD 的共用術語表。兩邊都往同一個方向走了一格。
