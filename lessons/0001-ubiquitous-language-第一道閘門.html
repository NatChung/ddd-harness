整套教學的主軸

你沒辦法讓模型變成 deterministic —— 那是它的本質,換哪個模型都一樣。 你能做的是讓「對不對」變成 deterministic。 兩個模型寫出不一樣的程式碼沒關係,只要同一套規格與驗收能明確判定兩邊各自通過或不通過, 你的 harness 就成立了。

Ubiquitous Language 是什麼

Martin Fowler 的定義很短:

the practice of building up a common, rigorous language between developers and users Martin Fowler, bliki: UbiquitousLanguage

把開發者與使用者之間共同、嚴謹的語言建立起來的做法。

重點在 rigorous(嚴謹)這個字。Fowler 給的理由是一句話:

software doesn't cope well with ambiguity 同上

軟體不擅長處理含糊。

2003 年講這句話時,「軟體」指的是編譯器和你的同事。今天多了一個讀者:agent。 而且它處理含糊的方式比人更糟——人遇到含糊會問你,模型遇到含糊會挑訓練資料裡最常見的那個解讀, 然後很有自信地往下做。不同模型的訓練分佈不同,挑的自然不同。這就是語言漂移。

這裡標註一下

「Ubiquitous Language 可以拿來當 agent 的防漂移機制」——這個對應是本教學自己建立的推論, 不是 DDD 原典或 Fowler 說的。DDD 講這件事時,對象是人。 推論本身站得住(失效模式相同),但你在跟別人講的時候,值得把這層講清楚。

一個真實會出事的例子

假設規格上有這麼一句話,看起來完全沒問題:

訂單成立後,扣掉對應的庫存。

「訂單成立」是哪一刻?至少有三個合理答案,而且每一個都有真實系統這樣做:

解讀後果
使用者按下「送出訂單」沒付錢的訂單也扣庫存 → 庫存被灌爆
金流授權成功多數電商的實際做法
倉庫產生出貨單超賣,因為扣得太晚

三個模型讀同一句話,可能給你三種實作,而且三份程式碼看起來都是對的。 Code review 也未必抓得到——它不是 bug,是規格沒講。

修法:寫一則詞彙條目

修法不是把那句話寫長一點,是把詞本身釘死,釘一次,之後所有規格共用:

訂單成立(Order Placed)
指金流授權成功、且庫存預留成功的那一刻。
兩者其一失敗都不算成立。

不要用:下單完成、結帳成功、訂單建立
區分:「結帳送出」是使用者按下按鈕的動作,
      發生在訂單成立之前,兩者不可互換。

四個部分,缺一不可:詞、定義、禁用的同義詞、容易混淆的鄰居。 第三、四項才是真正在幹活的——它們把模型會滑過去的那些路徑封起來。

自我檢查

寫完拿這三題檢查,三題都要能過:

  • 定義裡有沒有再用到另一個沒定義的詞?(最常見的失敗)
  • 「不要用」那一行是不是真的有東西?如果想不出同義詞,通常代表這個詞其實不含糊,換一個。
  • 把定義念給一個不懂這個系統的人聽,他能不能指出那一刻發生在什麼時候?

下一步該讀什麼

主要來源(建議讀這篇,五分鐘): Martin Fowler — Bounded Context。 本課的兩句引文出自他的姊妹篇 UbiquitousLanguage,但這篇更值得先讀:它示範了一個真實案例 (電力公司裡「meter」這個字在不同部門是不同的東西),並帶出一句會貫穿第 2 課的話—— you need a different model when the language changes。 語言在哪裡變,邊界就在哪裡。

想看已經有人把這套做成工具的樣子:GitHub Spec Kit ——把規格流程固化成 constitution → specify → plan → tasks → implement,支援 30 幾種 coding agent。 拿它對照本教學的概念會發現很多東西只是換了個名字,不過更值得拆的是你自己正在用的那套 harness。
