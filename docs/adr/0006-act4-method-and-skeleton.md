# ADR 0006 — 幕四的方法論與骨架:外圈是規格的,內圈是實作的

## Status

Accepted(2026-08-18)

## Context

幕四是五幕裡**唯一沒有方法論的一幕**,也正好是**唯一沒跑過**的一幕。
§10 對實作 agent 只寫了「填到驗收全綠」—— **那是驗收條件,不是做法**,
而中間怎麼填完全沒有規定,正是 agent 最容易鑽的地方。

⚠️ **開場先推翻了這張票自己的前提。** 票 09 與 `PIPELINE.md` 幕四那格都寫著
「骨架不存在」。查證後那句話是錯的:

```
4567d31 feat(ddd): examples/shop 骨架 —— 跨模型實驗的 harness(規格包 + 驗收 + 機械檢查)
```

`examples/shop/app/` 是 checked in 的,而且**建立它的 commit message 逐字叫它「骨架」**:
`build.gradle`(Spring Boot 3.4.5 + JPA + H2 + ArchUnit)、gradle wrapper、
`Application.java`(17 行,javadoc 寫「由 harness 提供,實作者不需要修改」)、
`data.sql`、`application.properties`、兩支測試 —— 而 `main/java` 底下
**零個實作 class**。那就是一個「wiring 給滿、domain 全空」的骨架。

實作則是**整個 repo 一份都沒留**:分層實驗只留下 ASSUMPTIONS 與 REPORT,Java 沒進 git。

**所以真正不存在的是「服務訪談那份規格的骨架」**,而那是一道差額題,不是從零那題:
訪談那份 §10 要三套測試(現有兩套,而且是別份規格的)、兩支外部替身(完全沒有)、
package 名不同(`com.shop.*` vs `order/*`)、wire 欄位名整組不同。

## Decision

### 1. 「三套全綠」保留,但架構那套的「不適用」必須顯形

查證:`ArchitectureTest.java` 每條規則都帶 `allowEmptyShould(true)`,而且註解明寫
「骨架階段 domain/ 還是空的」。**空專案掃不到任何 class → 那套全綠。**
於是一個**什麼都不寫**的 agent,三套裡有一套是免費綠的。

不拿掉 `allowEmptyShould`(那會把「沒東西可掃」偽裝成「架構違規」,是製造假訊號),
改成:**空骨架階段架構那套必須被報成「不適用」而不是「通過」** ——
與 ADR 0005 §6 對譯檢查那條**同一條規則**,兩處刻意用同一個講法,免得漂。

⚠️ 對照:驗收那兩套的「空骨架全紅」是**結構保證**的 —— 兩支測試的 import 全部是
Spring / ArchUnit / assertj,**一個實作型別都沒有**,所以空骨架編得起來、
每條驗收都在 runtime 紅。全紅在那半是真的,在架構那半不是。

### 2. 外部替身站在進程外(HTTP 假服務)

§10 要 `FakeMembershipSystem` / `FakePricingSystem`,而且要模擬
**查無此人 / 查無此商品 / 逾時**三種。三條路:

- **資料表**(現況 `data.sql` 建 `customers` 就是這樣)—— **表達不出逾時**,
  而 C17「外部系統不可用時不建立訂單,回可重試的 `UPSTREAM_UNAVAILABLE`」沒有逾時就驗不到。
- **Java 介面 + Fake 實作**(§10 字面上的寫法)—— ❌ **骨架得先宣告 port 的型別與方法名**,
  直接打破本線最核心的不變式:驗收之所以判定得了兩份長得完全不同的實作,
  靠的就是**測試不 import 任何實作 class**。
- **HTTP 假服務** ✅ —— 三種回應都做得到,而且對 agent 來說它只是一個會回 404、會 timeout
  的端點;要怎麼包成 port、叫什麼名字**完全是實作自己的事**。

⚠️ **後果:§10 那格要改寫**(它現在寫的是 Java class 名)。§10 是訪談產出的規格,
不是 harness —— 改它等於我們替規格做了一個決定,**標 `本案自決` 並記下來**。

### 3. package 形狀歸規格擁有(與 ADR 0004 對稱)

生成的 ArchUnit 規則照規格宣告的 package 名寫死(`architecture_rule.from_package`
/ `to_package`)。接上第 1 條的 `allowEmptyShould(true)`:

> **agent 只要把 class 放到別的 package,整套架構檢查就全部靜靜地不適用 ——
> 不是紅、不是報錯,是綠,而且看起來跟「完全遵守架構規則」一模一樣。**

這跟 `res_total_field` 那個坑逐字同一種病。而風險是真的:凍結骨架用
`com.shop.domain` / `com.shop.usecase`,訪談那份 §10 寫 `order/domain` /
`order/application` / `order/adapter`,**兩套本來就對不上**。

定案:骨架建空目錄,**並加一條檢查 —— 規格宣告過的每個 package,實作完成後必須真的有
class**;沒有的話報「不適用」,不算通過。原料現成(store 裡就有全部宣告過的 package 名),
成本跟 `verify_generated.py` 同一層。

**「package 形狀歸規格擁有」與 ADR 0004 的「wire shape 歸規格擁有」是同一條原則的兩個實例**:
規格自決之後必須寫成合約,實作照做,**而且要有東西在看**。

### 4. 走 outside-in TDD,但不外包整包

讀過 `mattpocock-skills:tdd` 與 `:implement` 之後(票 09 明寫「沒讀過就外包等於
換一份沒讀過的合約」),**三處直接打架**:

| | 那份合約要什麼 | 這裡的定義 |
|---|---|---|
| **完成訊號** | 「**完整測試套件**綠」 | **內圈測試不得算進全綠** —— 照它做,agent 可以寫一條恆真測試把自己送過關 |
| **seam 誰定** | 「寫任何測試前先寫下 seam,**跟使用者確認**」 | 幕四是 `claude -p` 隔離跑,**沒有使用者**;agent 自己跟自己確認 = 形式滿足 |
| **收尾** | `/code-review` + commit 到當前 branch | bare dir、沒有 git、沒有 reviewer |

**借三樣,不外包:**

1. **`tautological` 的定義直接借用**,寫進 §10。它比這裡任何一份文件都準:
   > 斷言用跟程式碼同樣的方式重算期望值…所以它**依構造必然通過,永遠不可能跟程式碼意見相左**。
   > 期望值必須來自獨立的真相來源 —— 一個已知good的字面值、一個算過的例子、**規格**。
2. **「seam 要先講定」改成「seam 由規格指定」** —— 不是問人,是**查表**。
   `domain_contract` 的每一條就是一個 seam 候選,`guarded_in`(守在哪個物件內)
   直接就是「這條測試該打在哪個物件上」。**票 06 與票 09 在這裡接起來:
   契約表就是內圈測試的清單來源。**
3. vertical slice(一次一條測試)、「refactor 不屬於迴圈」。

**內圈測試不得算進「全綠」,而且要用結構分開,不靠自律** ——
單獨的 source set / 單獨的 task,`完成的定義` 只認生成的那三套。
(同「代理編碼生到另一個 class」那招:算不算數用結構分開。)

### 5. 內圈的檢查:落點 + 恆真分診,兩個都不是判決

讓幕四走 TDD 的**唯一理由**是「內圈測試是微尺度契約的載體」(票 06 那半)。
內圈若全是恆真的,就什麼都沒買到 —— 契約還是沒被驗,只是多了一堆綠燈。
而票 09 已記:**無人監督的 agent TDD,產出的內圈測試預設就該假設有恆真成分**
(HL1/HL2 那條 `no-setter` 反射測試是實測過的已知陽性)。

- **落點檢查(主)**:**每條契約要指得出至少一條內圈測試**。這是今天已經做過兩次的
  同一個形狀(票 05 答案落點、票 06 契約指名測試),只是這次落點在內圈。
  它只問「有沒有」,不判斷好不好,所以不會犯「懲罰寫得好的那一方」那個病。
  它也讓今天量到的 `enforcement = none 20/20` 第一次有機會動起來。
  ⚠️ **上限(要印進報表)**:內圈測試靠**方法名帶契約編號**指認自己,而那是一條約定
  —— 隨便一條測試取名 `C1_xxx` 就通過。**它只證明落點存在,不證明那條測試真的在驗 C1。**
- **恆真分診(副)**:對內圈跑一次 `vacuous_tests`,印分診佇列。
  它**分不出「恆真」與「碰不到」**,所以是佇列不是判決。
- **PIT 守內圈**:票 09 已判定**撐不起來**,不做。

### 6. 骨架從凍結那個改,而且它歸類為受測品

**做法**:從 `examples/shop/app/` 複製一份改。它的結構已經驗過(不 import 實作 class、
空骨架編得起來)。**手寫一份新的**是重做已經對的東西;**從 store 生成**是搬階目標
但現在做不到 —— package 名與 wire 欄位 store 裡有了,**外部系統 store 裡完全沒有模型**,
假服務要有幾個端點、回什麼,沒地方讀。

**分類**:骨架是**餵給第四幕 agent 的輸入**,改了它後續的跑就不能跟先前比 ——
與 `interview-prompt.md`、`act1/` 三份、`run_act2.sh` 的 heredoc 同一種性質。
而且它更危險:骨架裡有 `data.sql`、`application.properties`、假服務的回應內容,
**那些是 agent 讀得到的具體資料值**,洩題面比 schema 註解大得多。

三條紀律:

1. 檔頭寫警語(照 `run_act2.sh` 2026-08-18 補的那份)
2. 每跑在 run 目錄留骨架的快照或 blob 雜湊,**寫報告前先 diff**
3. 洩題面列清單:哪些檔 agent 讀得到、哪些值是答案卷

## Considered Options

| | 為什麼沒選 |
|---|---|
| 拿掉 `allowEmptyShould(true)` 讓架構那套也紅 | 把「沒東西可掃」偽裝成「違規」,製造假訊號 |
| 完成定義只認驗收兩套 | 等於把機械檢查降級成參考資料 |
| 外部替身用資料表 | 表達不出逾時 → C17 驗不到 |
| 外部替身用 Java 介面 + Fake | 骨架得宣告 port 型別,打破「測試不 import 實作 class」 |
| 外包整包給 `:implement` / `:tdd` | 三處要改,改完就不是那個 skill 了,而且改過的地方沒人維護 |
| 不走 TDD,只補最小規定 | 誠實,但微尺度契約仍然只有「一個例子」在驗,票 06 那半永遠補不起來 |
| 用 PIT 守內圈 | 票 09 已判定撐不起來 |

## Consequences

**這場 grill 生出來的工作(已開票 10–13):**

- **10** 擴充骨架成訪談那份規格的骨架 + 受測品三條紀律
- **11** package 落點檢查(宣告過的 package 必須真的有 class)
- **12** §10 改寫:HTTP 假服務、內圈不算全綠、tautological 定義、seam 由契約表指定
- **13** 契約 → 內圈測試落點檢查 + 內圈恆真分診

**擱著的:**

- ⚠️ **外部系統沒有進 store**,所以「骨架從 store 生成」這條搬階路今天走不了。
  那是另一張票的前提,不是這場能解的。
- 內圈測試靠方法名指認契約 —— 那是可被形式滿足的約定,**上限印進報表,不當賣點**。
