需求方:衡岳管理顧問(老闆本人受訪,不寫程式)`[Q1]`
訪談輪次:6 輪,Q1–Q28,逐題落點見文末 §12。

> **來源標記只有五格,不得自創第六格:**
> `[Qn]` 他親口說的 / `暫定 [Qn]` 他說了但講「先這樣」 / `推導自 [Qn]` 從他的答案算出來 /
> `模板既定 <文件 L行>` 架構常備前提 / `本案自決` 他沒說但非決不可。

## §0 開工前必讀:這份規格有洞,而且洞是標出來的

實作 agent 請先讀 §6 的**阻斷級**清單與 §11 的**不得開工**清單。
規格裡有洞是正常的;**把洞交出去而不標明,你就會自己填,那才是災難。**

還有一件事必須先講明白,它決定了這套系統的定位:

> ### 需求方列了五條「絕對不可以發生」,系統真正擋得住的只有一條。

| # | 需求方的規矩 `[Q11]` | 這套系統的處置 | 機械檢查 |
|---|---|---|---|
| R1 | 請款單寄出後才發現工時記錯(前年多算 11 萬,親自去道歉) | 怎麼補救 `[Q15]` **沒有答案** | ⛔ **阻斷級,不得實作** |
| R2 | 同一筆工時被算兩次(同一天記在兩個案子底下) | `[Q16b]` 明確要求**不要系統判定對錯**,只要行政與經理**看得出來** | ❌ **無**,靠人看 |
| R3 | 售前免費拜訪跑進可計費 | `[Q17]` 明確說**顧問憑常識填,不是系統去卡** | ❌ **無**,靠人看 |

後果必須寫在這裡:**「行政整理」與「組裡經理 / 老闆過目」這兩道人工關卡,
是 R2、R3、R5 唯一的防線。** 任何把這兩關當成流程形式而簡化掉的實作,都違背本規格。

> **實作命名必須照此表,不得另創同義詞。**
> DDD 型態只能從這份清單選,不得用實作型別(`Decimal`、`String` 不是 DDD 型態):

| **工時明細** TimesheetEntry | 工時單上的一列。一列 = 某顧問某天在某案子上做的一件事 | **Entity**(生命週期在工時單內) | — | `[Q6]` `[Q12]` |

### §1.1 禁用同義詞清單(必填)

| 禁止裸用的詞 | 為什麼 | 一律改用 |
|---|---|---|
| **請款單 / 帳單 / invoice** | `[Q7]`:「骨子裡是同一份東西換個樣子出去,不是完全獨立的兩套資料」。取兩個名字會讓人以為是兩個聚合 | **工時單**;要指「已寄給客戶的那份」就寫 **工時單(狀態 = `SENT`)** |
| **發票** | `[Q7]`:「那是會計另外開的,跟這個不算同一件事,我們不管那塊」 | **本系統不得出現這個詞**,連欄位名都不行 |
| 工時 / 工時數 / duration / time | 同一個東西三種叫法 | **時數 hours** |
| 單價 / 時薪 / price / rate | 「單價」會被誤讀成商品定價 | **費率 hourlyRate** |
| 專案 / case / job | — | **案子 project** |
| 金額 / 總價 / amount(裸用) | 三個層級的錢必須分清楚,混用會直接算錯帳 | **lineAmount**(單筆)/ **subtotalAmount**(打折前小計)/ **totalAmount**(最終應收) |
| 折數 / 打折 / discount(裸用) | 「85 折」與「折 15%」互為相反,混用必出錯 | **discountRate**,定義為**乘數**(0.85) |

### §1.2 Bounded Context

**不切。單一 context。**

理由:訪談中唯一的同名不同義候選是「工時單 vs 請款單」,而 `[Q7]` 明確回答那是**同一份資料的兩種樣子**,不是兩套。發票 `[Q7]` 已排除在系統外。
來源:`推導自 [Q7]`。

### §1.3 狀態(階段或狀態)—— **兩個列舉,不要混在一起**

**(一)工時單狀態 `TimesheetStatus`**(欄位 `status`,見 E2)

| 狀態 | 意思 | 來源 |
|---|---|---|
| `OPEN` | 寄出前。**行政、組裡經理、老闆都還在改、還在挑毛病,發現問題就退回** | `[Q8]` |
| `PENDING_CLIENT_CONFIRMATION` | 已把工時明細送給客戶確認,等客戶點頭。**只有 `requiresClientConfirmation = true` 的客戶會經過這一站** | `[Q7]` `[Q14]` |
| `CLIENT_CONFIRMED` | 客戶說沒問題,可以正式請款 | `[Q21]` |
| `SENT` | **已寄給客戶,定案。內容不得再改** | `[Q8]` |

**(二)明細狀態 `EntryStatus`**(欄位 `entries[].status`,見 E1)

| 狀態 | 意思 | 來源 |
|---|---|---|
| `DRAFT` | 顧問填到一半、還沒交出去。**不計入任何金額** | `[Q24]` |
| `SUBMITTED` | 已交出,計入 `subtotalAmount` | `推導自 [Q24]` |

> ⚠️ **工時單沒有 `DRAFT`,明細沒有 `OPEN`。** 兩個列舉的值不重疊,實作不得共用一個 enum。
> 工時單一經建立(A4)即為 `OPEN`。

> ⚠️ **需求方沒有把「行政整理完」「經理看過」「老闆看過」講成三個獨立狀態。**
> `[Q8]` 的原話是「這幾關都還在改、還在挑毛病……真正定案是寄出去給客戶那一刻」。
> 因此本規格**只有一個 `OPEN`**,不發明三段審核狀態。想加的話請先回去問需求方。

> ⚠️ **`DRAFT` 掛在哪一層,是推導不是原話。**
> `推導自 [Q24][Q6]`,推導步驟:一張單是客戶×月、多位顧問共用 `[Q6]`;
> 若草稿掛在**單**這一層,一個顧問寫到一半就會凍住整張單、擋住其他人 —— 與 `[Q24]`
> 「不要逼人家一次填完」的意圖相反。故 `DRAFT` 掛在**明細**這一層,單本身直接是 `OPEN`。
> 列入 §7 待確認 A5。

## 端點

**(§2 · wire shape)**

> **整節標 `本案自決`。** 需求方 `[Q1]` 明說「我不寫程式,完全不懂技術這塊」,
> 我沒有問他任何欄位名 —— **問了才是失職**。
>
> 但自決完必須寫成合約。**下面每一個欄位名都是釘死的,不得改名、不得增刪。**
> 不釘死的話,兩份實作會各取各的名字,同一套驗收兩邊都過不了,
> 而且失敗訊息會全部長成 `but was: null`,領域行為對不對完全看不見。
>
> 表示法約定:金額一律 **JSON number,整數,無小數**,單位新台幣元;
> 時數一律 **JSON number**,0.5 的倍數;日期 `YYYY-MM-DD`;時間戳 ISO-8601 帶時區;
> 月份 `YYYY-MM`;幣別欄固定字串 `"TWD"`。

### E2. 取一張工時單 — `GET /timesheets/{timesheetId}`

**回應 JSON,逐欄:**

| 欄位名 | 型別 | 說明 | 來源 |
|---|---|---|---|
| `timesheetId` | string | 工時單識別碼 | `本案自決` |
| `clientId` | string | 客戶識別碼 | `[Q4]` |
| `clientName` | string | 客戶名稱 | `本案自決` |
| `billingMonth` | string `YYYY-MM` | 這張單是哪一個月的 | `[Q4]` |
| `status` | string | §1.3(一)**工時單狀態**四值之一 | `[Q8]` `[Q21]` |
| `requiresClientConfirmation` | boolean | **掛在客戶身上的固定條件**。true 的客戶每個月都要先給明細確認才能請款 | `[Q14]` `[Q7]` |
| `entries` | array | 明細陣列,每列欄位同 E1 回應(去掉 `timesheetId`) | `[Q6]` `[Q12]` |
| `subtotalAmount` | number | **打折前**小計,整數 = Σ 各筆 `lineAmount` | `推導自 [Q25b]` |
| `discountRate` | number | 乘數。不打折的客戶固定 `1.00`,那三家 `0.85` | `[Q22]` `[Q25a]` |
| `discountAmount` | number | 折掉多少錢,整數 = `subtotalAmount - totalAmount` | `推導自 [Q25b][Q26]` |
| `totalAmount` | number | **最終應收,整數**。= `floor(subtotalAmount × discountRate)` | `[Q25b]` `[Q26]` |
| `currency` | string | 固定 `"TWD"` | `[Q18]` |
| `sentAt` | string ISO-8601 或 `null` | 寄給客戶的時間。有值代表已定案不可改 | `[Q8]` |

> ⚠️ **這個回應會依呼叫者角色被過濾,見 C11。** 顧問呼叫時,
> `entries` 只含他自己的那幾筆,且看不到別人的 `hourlyRateAmount` / `lineAmount`;
> `subtotalAmount` / `discountAmount` / `totalAmount` 對顧問角色一律回 `null`。`[Q28]`

### E5. 某顧問某天的跨客戶紀錄 — `GET /consultants/{consultantId}/daily-entries?workDate=2026-08-12`

這是 R2 的**唯一**落點:`[Q16b]` 要的不是攔阻,是「行政跟經理翻的時候,**看得出**這個人這天在兩個地方都寫了東西,**自己去判斷**是不是真的重複」。

**回應 JSON:`{ "consultantId": ..., "workDate": ..., "entries": [ ... ] }`**,
每列欄位:`entryId` / `timesheetId` / `clientId` / `clientName` / `projectId` / `projectName` / `hours` / `description` / `billable`。

> **這是唯讀的跨聚合根查詢,不做任何判定、不回傳任何「疑似重複」旗標。**
> 給人看可以跨邊界;擋人不行。見 §10 A-6。

### E6. 修改一筆工時明細 — `PUT /timesheets/entries/{entryId}`

S12(已寄出 → 拒絕)、S20(草稿轉正)、S21(行政改別人的、留痕)三條情境都需要這個端點。
**沒有它,下游只能自己發明一個,兩份實作就會各發明各的。**

**請求 JSON,逐欄:**

| 欄位名 | 型別 | 必填 | 說明 | 來源 |
|---|---|---|---|---|
| `hours` | number | ✅ | 修改後的時數,仍須為 0.5 的正倍數 | `[Q13]` |
| `description` | string | ✅ | 修改後的一句話 | `[Q12]` |
| `billable` | boolean | ✅ | 修改後算不算錢 | `[Q17]` |
| `isDraft` | boolean | ✅ | `true→false` 即為「草稿轉正」,此後計入金額 | `推導自 [Q24]` |
| `actorId` | string | ✅ | **誰在改**。寫入 `lastModifiedBy`,不得由伺服器猜 | `[Q27]` |

**回應 JSON(200):** 與 E1 回應**逐欄相同**。

> `workDate` / `consultantId` / `clientId` / `projectId` **不在可改欄位裡** ——
> 改這幾個等於把明細搬到另一張單或另一個人頭上,需求方從未談過這件事。
> 要搬只能刪掉重記,而**刪除規則沒問到(§6 B12)**。`本案自決` A9。

## 情境(Given-When-Then)

**(§3)**

> 每條可一比一翻成自動化測試。金額單位一律新台幣元,時數單位一律小時。
> 情境用的固定資料:
> - 客戶 `C-FORGE`「台中鍛件」——**85 折**,`requiresClientConfirmation = true`
> - 客戶 `C-FOOD`「南方食品」——**不打折**(`discountRate = 1.00`),`requiresClientConfirmation = false`
> - 顧問 `U-LEE` 小李,費率 **1,100**;`U-CHEN` 小陳,費率 **3,000**;`U-WANG` 王經理,費率 **5,000**

### 一、算錢

**S1 — 記一筆可計費明細,金額 = 時數 × 費率**
- **Given** 客戶 `C-FOOD` 2026-08 的工時單存在,狀態 `OPEN`,目前 0 筆明細
- **When** `U-CHEN` 新增明細:`workDate=2026-08-03`、`hours=3`、`billable=true`、`projectId=P-1`
- **Then** 該筆 `hourlyRateAmount = 3000`、`lineAmount = 9000`、`currency = "TWD"`
- **And** 單的 `subtotalAmount = 9000`、`discountRate = 1.00`、`discountAmount = 0`、`totalAmount = 9000`
- 來源:`[Q5]` `[Q22]` `[Q18]`

**S2 — 不可計費的明細,金額為 0,但仍留在單上**
- **Given** 同 S1 的單,已有 S1 那筆(小計 9,000)
- **When** `U-CHEN` 新增明細:`workDate=2026-08-04`、`hours=2`、`billable=false`(售前免費拜訪)
- **Then** 該筆 `lineAmount = 0`,且 `hours` 仍為 `2`(**時數照記,只是不算錢**)
- **And** 單的 `subtotalAmount` 仍為 `9000`、`totalAmount = 9000`
- **And** 單的明細筆數 = 2
- 來源:`[Q17]`(R3)

**S3 — 不打折客戶:總額 = 小計,不進位不捨去**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`
- **And** 已有兩筆:`U-CHEN` 3 小時 @3,000 = 9,000;`U-LEE` 1.5 小時 @1,100 = 1,650
- **When** 讀取這張單
- **Then** `subtotalAmount = 10650`、`discountRate = 1.00`、`discountAmount = 0`、`totalAmount = 10650`
- 來源:`[Q5]` `[Q25b]`

**S4 — 折扣客戶:整張單加總完才打一次折(不是逐筆打)**
- **Given** 客戶 `C-FORGE` 2026-08 工時單,狀態 `OPEN`
- **And** 唯一一筆:`U-WANG` `workDate=2026-08-06`、`hours=2`、`billable=true` → `lineAmount = 10000`
- **When** 讀取這張單
- **Then** `subtotalAmount = 10000`、`discountRate = 0.85`、`totalAmount = 8500`、`discountAmount = 1500`
- **And** 明細那筆的 `lineAmount` **仍是 `10000`,不是 8,500** —— 折扣不落在明細上
- 來源:`[Q25b]`(「整案 85 折,是那家客戶整體給的優惠,不是針對某一筆工作打折」)

**S5 — 折扣算出零頭:無條件捨去,公司吸收 ★**
- **Given** 客戶 `C-FORGE` 2026-08 工時單,狀態 `OPEN`
- **And** 唯一一筆:`U-LEE` `workDate=2026-08-12`、`hours=0.5`、`billable=true` → `lineAmount = 550`
- **When** 讀取這張單
- **Then** `subtotalAmount = 550`
- **And** `550 × 0.85 = 467.5`,**`totalAmount = 467`**(無條件捨去,不是 468)
- **And** `discountAmount = 83`
- 來源:`[Q26]`(「算公司的,無條件捨去……我寧可公司少拿一點,也不要再發生算錯錢、多收客戶錢這種事」)
- 註:這個 467.5 是訪談中實際算出來的。需求方在 `[Q22]` 說「就算打折算出來也還是整數」,
  **那句話對五個費率裡的 1,100 那一級不成立**,當場回報後他改口並定案為無條件捨去。

**S6 — 捨去只發生一次,發生在總額,不在明細**
- **Given** 客戶 `C-FORGE` 2026-08 工時單,狀態 `OPEN`
- **And** 三筆:`U-LEE` 0.5 小時 = 550;`U-LEE` 1.5 小時 = 1,650;`U-CHEN` 0.5 小時 = 1,500
- **When** 讀取這張單
- **Then** 三筆的 `lineAmount` 分別為 `550` / `1650` / `1500`(皆為整數,**未被打折**)
- **And** `subtotalAmount = 3700`
- **And** `3700 × 0.85 = 3145`,`totalAmount = 3145`、`discountAmount = 555`
- **And** 對照:若改成逐筆打折再捨去,會得到 `467 + 1402 + 1275 = 3144` —— **本規格要的是 3145,不是 3144**
- 來源:`推導自 [Q25b][Q26]`,推導步驟寫在 §7 A6

### 二、時數與費率

**S7 — 時數不是 0.5 的倍數 → 拒絕(業務規則不通過)**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`
- **When** `U-CHEN` 新增明細,`hours = 1.3`
- **Then** 拒絕,回 `400`,錯誤碼 `HOURS_NOT_HALF_HOUR_MULTIPLE`
- **And** 單的 `subtotalAmount` 與明細筆數**完全不變**
- 來源:`[Q13]`(「半小時一個單位,不收 15 分鐘那種零頭」)

**S8 — 時數為 0 或負 → 拒絕**
- **Given** 同上
- **When** `hours = 0`(或 `hours = -2`)
- **Then** 拒絕,回 `400`,錯誤碼 `HOURS_NOT_POSITIVE`
- 來源:`本案自決` A2 —— **負數的唯一用途是沖銷更正,而那條路已被 §6 B1 阻斷。**
  B1 解掉後這條必須重審。

**S9 — 升職:升職前做的工時,照升職前的費率算 ★**
- **Given** `U-LEE` 在 2026-08-20 由費率 1,100 調為 2,000
- **And** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`
- **When** 分別記入 `workDate=2026-08-05`、`hours=2` 與 `workDate=2026-08-25`、`hours=2`
- **Then** 前者 `hourlyRateAmount = 1100`、`lineAmount = 2200`
- **And** 後者 `hourlyRateAmount = 2000`、`lineAmount = 4000`
- **And** 單的 `subtotalAmount = 6200`
- 來源:`[Q9]`(「用舊費率。升職以前做的工時,就是照他升職以前的費率算」);
  「取哪一天的費率」= `workDate` 那天,`推導自 [Q9]` A7

### 三、寄出定案與不可變(R4 —— 唯一擋得住的那條)

**S10 — 已寄出的單,之後調費率,金額一毛都不動 ★**
- **Given** 客戶 `C-FORGE` 2026-07 工時單,狀態 `SENT`,`sentAt = 2026-08-01T10:00:00+08:00`
- **And** 該單 `subtotalAmount = 10000`、`totalAmount = 8500`
- **When** 2026-08-20 `U-WANG` 的費率由 5,000 調為 6,000
- **And** 重新讀取該 2026-07 的單
- **Then** `subtotalAmount` 仍為 `10000`、`totalAmount` 仍為 `8500`
- **And** 每筆 `hourlyRateAmount` 仍為寄出時的快照值
- 來源:`[Q11]` R4(「上個月開多少,就永遠是多少,不會回頭改」)+ `[Q9]`(「記多少就是多少,不會因為後來狀況變了就跟著變」)

**S11 — 已寄出的單,新增明細 → 拒絕(業務規則不通過)**
- **Given** 客戶 `C-FORGE` 2026-07 工時單,狀態 `SENT`,`subtotalAmount = 10000`
- **When** 任何角色嘗試新增一筆明細到該單
- **Then** 拒絕,回 `409`,錯誤碼 `TIMESHEET_ALREADY_SENT`
- **And** 該單 `subtotalAmount` 仍為 `10000`、明細筆數不變、`sentAt` 不變
- 來源:`[Q8]`(「真正定案是寄出去給客戶那一刻,那之後理論上就不該再動」)+ R4

**S12 — 已寄出的單,修改既有明細 → 拒絕**
- **Given** 同 S11
- **When** 行政嘗試把某筆的 `hours` 由 2 改為 3
- **Then** 拒絕,回 `409`,錯誤碼 `TIMESHEET_ALREADY_SENT`
- **And** 該筆 `hours` 仍為 `2`、`lastModifiedAt` 不變
- 來源:同 S11
- ⛔ **「那如果真的記錯了怎麼辦」不在本規格內 —— §6 B1 阻斷級。不得自行設計補救路徑。**

### 四、給客戶確認這條路

**S13 — 需事前確認的客戶,未經確認不得寄出**
- **Given** 客戶 `C-FORGE` 2026-08 工時單,`requiresClientConfirmation = true`,狀態 `OPEN`
- **When** 送出 `action = "SEND"`
- **Then** 拒絕,回 `409`,錯誤碼 `CLIENT_CONFIRMATION_REQUIRED`
- **And** 狀態仍為 `OPEN`、`sentAt` 仍為 `null`
- 來源:`[Q7]` `[Q14]`(「就是那兩家,每個月都要先過這一關」)

**S14 — 不需事前確認的客戶,可直接寄出**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,`requiresClientConfirmation = false`,狀態 `OPEN`,`totalAmount = 10650`
- **When** 送出 `action = "SEND"`
- **Then** 狀態變為 `SENT`、`sentAt` 有值
- **And** `totalAmount` 仍為 `10650`
- 來源:`[Q7]`(「多數客戶我們是彙整完直接變成請款單寄出去」)

**S15 — 客戶說「這筆我不認」→ 退回可改,不是拒絕結案 ★**
- **Given** 客戶 `C-FORGE` 2026-08 工時單,狀態 `PENDING_CLIENT_CONFIRMATION`,`subtotalAmount = 3700`
- **When** 送出 `action = "CLIENT_REJECT"`、`reason = "8/12 那 0.5 小時我們沒收到人"`
- **Then** 狀態變為 `OPEN`(**可改狀態**),`sentAt` 仍為 `null`
- **And** 明細一筆不少,`subtotalAmount` 仍為 `3700`(**退回不等於自動刪除爭議那筆**)
- 來源:`[Q21]`(「退回去改,行政跟顧問對清楚,改完再跑一次確認,客戶點頭才正式請款」)

**S16 — 改完重跑確認,客戶點頭後才准寄**
- **Given** 承 S15,行政經由 E6 把爭議那筆 0.5 小時改為 `billable = false`(其 `lineAmount` 由 `550` 變 `0`),`subtotalAmount = 3150`
- **And** 該筆明細**仍在單上**,`hours` 仍為 `0.5`(**沒有刪除任何東西 —— 刪除規則沒問到,見 §6 B12**)
- **When** 依序送出 `SEND_TO_CLIENT` → `CLIENT_CONFIRM` → `SEND`
- **Then** 狀態依序為 `PENDING_CLIENT_CONFIRMATION` → `CLIENT_CONFIRMED` → `SENT`
- **And** `3150 × 0.85 = 2677.5` → `totalAmount = 2677`(無條件捨去)
- 來源:`[Q21]` + `[Q26]`

### 五、補記、草稿、留痕、看得見

**S17 — 事後補記不擋,但要記下什麼時候補的**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`;現在是 `2026-08-14T18:00:00+08:00`(星期五)
- **When** `U-CHEN` 一次補記 `workDate=2026-08-10` 到 `2026-08-14` 共五筆,每筆 `hours = 8`
- **Then** 五筆**全部成立,一筆都不擋**
- **And** 五筆的 `recordedAt` 皆為 `2026-08-14T18:00:00+08:00`,與各自的 `workDate` 差距分別為 4 / 3 / 2 / 1 / 0 天
- 來源:`[Q19]`(「不擋,但要記下每一筆是什麼時候補進去的,遲交的要能被看出來」)
- ⛔ **「差幾天算遲交」沒問到 → §6 B2。** 本規格只保證 `recordedAt` 被記下來;
  **不得實作任何「遲交」旗標或警示**,因為判準是需求方的政策,不是工程判斷。

**S18 — 一天記十幾小時,不擋**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`
- **And** `U-CHEN` 在 `workDate=2026-08-03` 已記了 8 小時
- **When** 同一天再記 6 小時
- **Then** **成立,不擋**,該顧問該日合計 14 小時
- 來源:`[Q16b]`(「不要擋死總時數……有時候忙起來一天記十幾小時也是有的,你把它擋住,反而卡到正常在做事的人」)

**S19 — 同一顧問同一天跨兩個客戶:兩筆都成立,而且並排看得到 ★**
- **Given** `U-LEE` 在 `workDate=2026-08-12` 已於客戶 `C-FORGE` 記 4 小時(早上台中鍛件)
- **When** 同一天於客戶 `C-FOOD` 再記 4 小時(下午食品廠)
- **Then** **兩筆都成立,系統不擋、不警告、不標記疑似重複**
- **And** 兩筆分別落在**兩張不同的工時單**(`C-FORGE` 2026-08 與 `C-FOOD` 2026-08)
- **And** 呼叫 `GET /consultants/U-LEE/daily-entries?workDate=2026-08-12` 回傳**兩筆**,
  各自帶著 `clientName`「台中鍛件」與「南方食品」
- 來源:`[Q16a]`(「一天兩個客戶很正常」)+ `[Q16b]`(「我要的是被看得到……不需要系統自動判定對錯」)

**S20 — 草稿留著,不進金額**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`,`subtotalAmount = 9000`
- **When** `U-CHEN` 新增一筆 `isDraft = true`、`hours = 2`、`billable = true`
- **Then** 該筆存在,`status = "DRAFT"`
- **And** 單的 `subtotalAmount` 仍為 `9000` —— **草稿不計入金額**
- **And** 該顧問重新讀取時,那筆草稿還在
- 來源:`[Q24]`(「要幫他留著,不要逼人家一次填完……如果沒送出就整個不見,那大家會恨死這套東西」);
  「草稿不計入金額」為 `推導自 [Q24]`,列 §7 待確認 A5

**S21 — 行政改別人的明細:准,但留得出是誰動的**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`
- **And** 一筆由 `U-CHEN` 填的明細,`hours = 3`、`lastModifiedBy = "U-CHEN"`
- **When** 行政 `A-001` 把 `hours` 改為 `2`
- **Then** 修改成立,`hours = 2`、`lineAmount = 6000`
- **And** `lastModifiedBy = "A-001"`、`lastModifiedAt` 更新
- 來源:`[Q27]`(「能改,但要留得出來是誰動的……不然出事沒人負責」)

**S22 — 顧問看不到別人的費率和金額 ★**
- **Given** 客戶 `C-FOOD` 2026-08 工時單有兩筆:`U-CHEN` 3 小時 @3,000、`U-LEE` 1.5 小時 @1,100
- **When** `U-CHEN` 呼叫 `GET /timesheets/{id}`
- **Then** `entries` 只有**他自己那一筆**
- **And** 該筆 `hourlyRateAmount = 3000`、`lineAmount = 9000`(**看得到自己的**)
- **And** `subtotalAmount`、`discountAmount`、`totalAmount` 皆為 `null`
- **And** 回應中**不含任何** `U-LEE` 的資料
- 來源:`[Q28]`(「顧問自己上去只看得到自己的費率跟自己這個月做了多少、值多少錢,看不到別人的……我不希望顧問彼此看得到對方賺多少,這在我們這行是很敏感的事」)

**S23 — 組裡經理看得到自己那組,老闆全看得到**
- **Given** 同 S22 的單,`U-CHEN` 與 `U-LEE` 同屬 `G-1` 組,經理為 `M-1`
- **When** `M-1` 呼叫 `GET /timesheets/{id}`
- **Then** `entries` 含兩筆,金額三欄皆有值(`subtotalAmount = 10650`)
- **And** 老闆 `O-1` 呼叫時,結果與 `M-1` 相同
- 來源:`[Q28]`
- ⛔ 「顧問怎麼歸組」「經理跨組看不看得到」未問到 → §6 規格沉默

### 六、系統中途失敗(第 3 類,不得缺席)

**S24 — 寫到一半掛掉:整筆不算數,絕不留半筆 ★**
- **Given** 客戶 `C-FOOD` 2026-08 工時單,狀態 `OPEN`,`subtotalAmount = 9000`、明細 1 筆
- **When** 新增一筆 `hours = 2`、`billable = true`,**持久化過程中程序中斷**
- **Then** 重新讀取該單:明細仍為 **1 筆**、`subtotalAmount` 仍為 `9000`
- **And** **不存在任何 `lineAmount` 已算好但明細沒進去、或明細進去了但小計沒更新的中間狀態**
- 來源:`本案自決` A3
- ⚠️ **誠實揭露:這一題我沒有問過需求方**,訪談在我問到之前就結束了。
  依第五節判準,「留不留半筆」猜錯的後果是**工程上難以維護**,不是需求方賠錢或被客訴,
  故歸類為**技術判斷**,採用建議並標 `本案自決`,列入 §7 待確認。

**S25 — 外部系統回失敗:本規格無法撰寫,原因如下**
- ⛔ **這一類 GWT 是空的,而且我不寫一條假的來充數。**
- 需求方**從頭到尾沒有提過任何外部系統**。我在第五輪與第六輪都報備要跟他確認一句
  「這整件事有沒有要接你們現有的任何系統」,**但訪談在我問出口之前就結束了。**
- 「沒有外部系統」是一個**我沒有得到過的答案**,不准當成事實寫進規格。
- → §6 **阻斷級 B3**。
