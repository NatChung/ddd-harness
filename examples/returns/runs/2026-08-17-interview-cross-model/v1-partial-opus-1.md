這是型態清單的缺口,照實回報,**不新增第六種標記**。

## §1 附表:禁用同義詞清單

| 禁止裸用 | 為什麼 | 一律改用 |
|---|---|---|
| **「退貨」單獨使用** | 三個部門講的是三件不同的事:客服=申請動作、倉庫=收貨驗收、財務=不用這個詞([輪1-Q1]) | 依語境用 **退貨單** / **退貨申請** / **退貨驗收** / **退款**,四選一 |
| 「**退款**」指整件事 | 財務語彙,只指錢出去那一筆 | 整件事 = **退貨單** |
| 「**退貨案件**」 | 受訪者明確否決:「我們內部沒人這樣講」[輪2-Q3] | **退貨單** |
| 「**驗收**」單獨使用 | 會與進貨驗收混淆 | **退貨驗收** | 
| 「**金額**」裸用 | 至少四種錢:商品金額 / 運費 / 折扣分攤額 / 退款金額 | 明確指名該四者之一 |
| 「**換貨**」 | 受訪者明說「換貨是另一件事,先不算在這裡」[輪1-Q1] | 不在本 context 出現;要談就開別的 context |
| 「**單號**」裸用 | 至少三種:訂單號、退貨單號、寄件單號 | 明確指名 |

> 表中「驗收→退貨驗收」「金額→分四種」「單號→分三種」為 `本案自決`(依據:訪談已出現同名不同義的實例,
> 同類風險預防性納管),見 §6 A-04。其餘各列皆有受訪者原話。

# §1.1 Bounded Context 切分

**本節存在的理由:** 訪談確認了同名不同義——「退貨」一詞在客服 / 倉庫 / 財務三邊指三件事,
且財務根本不用這個詞([輪1-Q1] 原話:「財務那邊根本不講退貨,他們講『退款』」)。

**切分決定(`本案自決`,見 §6 A-02):切成 2 個 context,不是 3 個。**

| Context | 保留哪些詞 | 聚合根 |
|---|---|---|
| **退貨(Returns)** | 退貨單、退貨申請、退貨驗收、退貨明細行、特批、申請期限、未使用判定 | 退貨單 |
| **退款(Payout)** | 退款、退款失敗名單、原付款方式、第三方金流 | 退款 |

**為什麼客服與倉庫不各切一個 context:** 兩者對同一張退貨單接力操作、共用同一份明細行與狀態機,
語彙差異已用 §1 的統一命名 + 禁用同義詞清單解掉;硬切會讓一張單的狀態機被兩個 context 撕開。
**為什麼財務要切出去:** 財務的語言自成一套(只講退款)、生命週期不同(退款會失敗、要重試、要對帳、
有失敗名單)、且掛在外部第三方金流上——這三點都是 context 邊界的訊號。

**跨界關聯:**
- 退貨 → 退款:**事件式,下游關係(Customer/Supplier)**。`退貨驗收已通過` 事件觸發退款建立,
  **非同一筆交易**(依據:[輪1-Q3] 驗收與出款分屬倉庫與財務兩個作業,受訪者描述為先後步驟)。
- 訂單 → 退貨:**上游,Conformist + 快照**。退貨單建立時把「出貨日、品項、商品金額、運費、
  折扣、原付款方式」快照進退貨單,之後不再回頭讀訂單(`本案自決` §6 A-05)。
- 商品目錄 → 退貨:**上游,外部規則集**。「生鮮不可退」的判定資料在商品目錄。

**⚠️ 待確認:** 此切分未經受訪者確認——他從未被問過系統邊界,只被問過詞彙。切界是**架構決定**,
若之後確認財務退款走既有的出納系統而非本案範圍,Payout context 應改為純外部整合。

# §2 GWT 清單

> 命名:`G-<行為><序號>`。每個會改變狀態的行為都給三類失敗路徑:
> ①業務規則不通過 ②外部系統回失敗 ③**系統中途失敗**。第③類不得缺席;不適用者寫明理由。
>
> **狀態機(`推導自 [輪1-Q3]` 的流程順序):**
> `待審核` →(客服審過)`待寄回` →(倉庫收到)`待驗收` →(驗收通過)`待退款` →(退款成功)`已完成`
> 分支:`已駁回`(審核未過)/ `驗收未通過`(退回客服)/ `退款失敗` / `已取消`(僅審核前)
