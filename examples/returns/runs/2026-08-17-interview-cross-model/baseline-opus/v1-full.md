| 禁用 | 理由 | 一律改用 |

| **換貨** | `[R1-Q1]` 明確排除,是另一件事 | (不得出現在本系統詞彙) |

## §1.1 Bounded Context

**觸發理由**:`[R1-Q1]` 明說同一個詞「退貨」在客服 / 倉庫 / 財務口中是三件不同的事;`[R1-Q3]` 三段流程的負責人各不相同。符合切 context 的判準。

**切界決定本身標 `本案自決`**(受訪者沒有講過「context」這種話),依據見下。

| Context | 保留哪些詞 | 聚合根 | 誰負責 |
|---|---|---|---|
| **退貨受理**(客服) | 退貨申請、退貨單、退貨單號、可退規則表、主管特批、退貨期限、寄回期限 | **退貨單** | 客服 / 客服主管 |
| **退貨驗收**(倉儲) | 退貨驗收、驗收標準表、簽收、入倉 | **退貨驗收** | 倉庫 |
| **退款**(財務) | 退款、退款金額、退款失敗名單、原付款方式 | **退款** | 財務 |

**跨界關聯**:

- 退貨受理 → 退貨驗收:以 **`退貨申請已核准`** 事件通知(E2);退貨驗收以退貨單號為外部參照,**不共用交易**。
- 退貨驗收 → 退款:以 **`退貨驗收已通過`** 事件觸發(E6)。此即 `[R1-Q3]`「一定是收到貨才退錢」的落地方式。
- 退貨受理 ← 訂單(**本案未納入的既有上游**):退貨單需要簽收日、品項、原付金額、券分攤。`本案自決`:申請成立時**快照**這些資料進退貨單,不即時回查訂單(依據見 §6-A-01)。
- 退貨受理 ← 退貨驗收:驗收不通過時以 **`退貨驗收已退回`** 事件把球踢回客服(E7)。

**依據**:三個 context 的邊界剛好落在 `[R1-Q3]` 講的三個負責人交接點上,交接點也正是他自己描述的「經過哪些人」的斷點。
**待確認點**:退貨驗收與退款是否真的需要各自的聚合根,或只是退貨單的兩個階段 —— 受訪者說「退貨單」是整件事,`[R2-Q3]` 沒有裁決到聚合邊界這一層。

## §2 GWT 清單

> 編號 G1…,§3 的「指名測試」欄回指這些編號。金額單位一律 TWD。

### A. 申請與審核

**G1 — 期限內申請被受理**
Given 一張訂單,品項「球鞋 A」簽收日 2026-08-01,尚無任何退貨紀錄
When 客人於 2026-08-08 23:59:59 提出退貨申請
Then 系統建立退貨單,狀態=`已申請`,退貨期限記為 2026-08-08 23:59:59
來源 `[R2-Q1]`

**G2 — 逾期 1 秒即拒絕**
Given 同 G1
When 客人於 2026-08-09 00:00:00 提出退貨申請
Then 拒絕受理,理由=逾退貨期限,不建立退貨單
來源 `推導自 [R2-Q1]`(推導步驟:他說「算到簽收日加七天那天的 23:59:59 為止」,則下一秒即逾期)

**G3 — 生鮮食品一律拒絕**
Given 品項為生鮮食品,簽收日 2026-08-01
When 客人於 2026-08-02 提出退貨申請(仍在 7 天內)
Then 拒絕受理,理由=不可退品項;**且客服主管特批不得推翻**
來源 `[R1-Q2]`(「生鮮食品一律不能退,這個沒得談」)

**G4 — 已完成退貨的品項不得再退**
Given 品項「球鞋 A」已有一張狀態=`已退款` 的退貨單
When 客人再次對「球鞋 A」提出退貨申請
Then 拒絕受理,理由=已退過
來源 `[R1-Q2]`(注意:與 G12 的關係有爭議,見 §7-X2)

**G5 — 拆封未使用可退**
Given 客人上傳照片,商品已拆封、外觀無使用痕跡
When 客服審核
Then 通過前端初篩,退貨單狀態=`已核准`;**是否「用過」的最終認定保留給倉庫**
來源 `[R1-Q2]` `[R2-Q1]`

**G6 — 照片明顯有問題 → 駁回並可重申**
Given 客人上傳照片,商品明顯已使用
When 客服駁回
Then 退貨單狀態=`已駁回`,系統以 email + 簡訊通知客人**駁回原因**,且該品項的申請次數計為 1
來源 `[R1-Q5]`(c) `[R2-Q5]`

**G7 — 同一品項第 3 次申請被拒**
Given 品項「球鞋 A」已有 2 次退貨申請紀錄(皆被駁回)
When 客人第 3 次對同品項提出申請
Then 拒絕受理,理由=已達同品項申請上限 2 次
來源 `[R2-Q2]`(d) `[R1-Q5]`(c)

**G8 — 主管特批在額度內成立**
Given 情形不在可退規則表內,退款金額 8000,該客服主管本月已特批 19 次
When 客服主管特批核准
Then 退貨單狀態=`已核准`,並寫入特批紀錄(批准人、理由、時間),本月特批次數 → 20
來源 `[R1-Q2]` `[R2-Q5]`

**G9 — 特批單筆超額被拒**
Given 同 G8,但退款金額 10001
When 客服主管嘗試特批
Then 拒絕,理由=超過單筆特批上限 10000
來源 `[R2-Q5]`

**G10 — 特批月配額用盡被拒**
Given 該客服主管本月已特批 20 次
When 再次嘗試特批
Then 拒絕,理由=已達當月特批上限 20 次
來源 `[R2-Q5]`

**G11 — 非客服主管不得特批**
Given 情形不在可退規則表內
When 一般客服嘗試特批
Then 拒絕,理由=無特批權限
來源 `[R2-Q5]`(「特批只有客服主管能批,別人不行」)

**G12 — 同一訂單第 4 次退貨被拒**
Given 一張訂單已有 3 張已完成的退貨單
When 客人對該訂單再提第 4 次退貨申請
Then 拒絕受理,理由=同一訂單分次退貨上限 3 次
來源 `[R2-Q4]`(e)

### B. 寄回、取消、逾期

**G13 — 期限內寄回進入待驗收**
Given 退貨單狀態=`已核准`,核准日 2026-08-01
When 客人於 2026-08-06 前寄回且倉庫簽收
Then 退貨單狀態=`待驗收`,取消功能關閉
來源 `[R2-Q2]`(a)(c)

**G14 — 逾期未寄自動失效,且事前已提醒**
Given 退貨單狀態=`已核准`,核准日 2026-08-01,寄回期限 2026-08-06
When 2026-08-05 到達 → 系統發出提醒;2026-08-06 過後客人仍未寄回
Then 退貨單狀態=`逾期失效`,不再受理該單
來源 `[R2-Q2]`(a)(b)
備註:失效判定基準是「客人寄出」還是「倉庫簽收」,**未答**(§5-S02,政策級,阻斷本條)

**G15 — 倉庫簽收前可取消**
Given 退貨單狀態=`已核准`,倉庫尚未簽收
When 客人取消
Then 退貨單狀態=`已取消`;客人仍可在退貨期限內重新申請
來源 `[R2-Q2]`(c)(d)

**G16 — 倉庫簽收後不可取消**
Given 退貨單狀態=`待驗收`(倉庫已簽收)
When 客人取消
Then 拒絕,理由=倉庫已簽收,不可取消;狀態不變
來源 `[R2-Q2]`(c)

### C. 驗收

**G17 — 驗收通過**
Given 退貨單狀態=`待驗收`,商品符合驗收標準表
When 倉庫驗收通過並入倉
Then 退貨單狀態=`驗收通過` → `待退款`;發出 `退貨驗收已通過`;以 email + 簡訊通知客人「倉庫收到貨」
來源 `[R1-Q3]` `[R2-Q1]`(c) `[R2-Q5]`(通知)

**G18 — 驗收不通過:壞 / 少 / 錯**
Given 退貨單狀態=`待驗收`,收到的商品毀損、少件或非原品項
When 倉庫驗收
Then **不入倉**,退貨單狀態=`驗收退回`,案件回到客服;不產生任何退款
來源 `[R1-Q5]`(b)

**G19 — 協商結果一:客人補齊**
Given 退貨單狀態=`驗收退回`(少件)
When 客服與客人談定補齊,客人寄出缺件並經倉庫簽收
Then 退貨單狀態回到 `待驗收`,重新驗收
來源 `[R1-Q5]`(b)

**G20 — 協商結果二:整張作廢**
Given 退貨單狀態=`驗收退回`
When 客服與客人談定作廢
Then 退貨單狀態=`已作廢`,商品寄回客人,**回程運費由客人負擔**,退款金額 = 0
來源 `[R1-Q5]`(b)

### D. 金額計算

**G21 — 原訂單運費不退**
Given 訂單:球鞋 A 2000、運費 35.5、無折扣券;全數退貨
When 計算退款金額
Then 退款金額 = 2000(運費 35.5 不退)
來源 `[R1-Q4]`

**G22 — 部分退 + 券按原價比例分攤 + 零頭無條件進位給客人**
Given 訂單三件:A 1000、B 1000、C 1000,折扣券折 100,實付 2900 + 運費;客人只退 A
When 計算退款金額
Then A 的券分攤 = 100 × (1000 / 3000) = 33.33… → **對客人有利方向取值**,退款金額 = 1000 − 33 = 967(即分攤額向下、退款額向上,零頭由公司吸收)
來源 `[R1-Q4]` `[R2-Q4]`(c)(d)
備註:**進位到「元」還是「角」未答**(§5-S04);此例採進位到元,標 `本案自決`(§6-A-03)

**G23 — 回程運費客人自付**
Given 任何一張退貨單
When 計算退款金額
Then 客人寄回的運費不計入退款,系統不代收亦不從退款扣抵
來源 `[R1-Q4]`
備註:回程運費的實際收取方式**從未問過**(§5-S05)

### E. 貨沒收到

**G24 — 查無件、金額 ≤ 2000 → 公司吸收直接退款**
Given 客人提供寄件單號,向物流查詢查無此件,退款金額 1800
When 客服處理
Then 公司吸收,直接進入退款,無須倉庫驗收
來源 `[R1-Q5]`(a) `[R2-Q5]`(b)
⚠️ **本條與 `[R1-Q3]`「一定是收到貨才退錢,沒有例外」直接衝突,見 §7-X1。裁決前不得實作。**

**G25 — 查無件、金額 > 2000 → 需主管核准**

When 客服處理
Then 不得自行退款;須客服主管核准後才進入退款,核准留紀錄
來源 `[R1-Q5]`(a) `[R2-Q5]`(b)

**G26 — 客人拿不出寄件單號**
Given 客人聲稱已寄出但無寄件單號
When 客服處理

### F. 退款與退款失敗

**G27 — 正常退款**
Given 退貨單狀態=`待退款`,退款金額 967,原付款方式=信用卡尾號 1234
When 財務執行退款

**G28 — 金流回失敗 → 自動重試**
Given 退款出款,金流回應失敗(卡片失效)
When 系統處理
Then 每隔 1 小時自動重試,最多 3 次;期間狀態=`退款中`
來源 `[R1-Q5]`(d) `[R2-Q5]`(c)

**G29 — 3 次皆失敗 → 進失敗名單**
Given 已自動重試 3 次仍失敗
When 第 3 次失敗
Then 退貨單狀態=`退款失敗`,寫入退款失敗名單;財務於次日 10:00 檢視名單;客服聯絡客人換帳戶
來源 `[R1-Q5]`(d) `[R2-Q5]`(c)

**G30 — 換帳戶需主管核准**
Given 退貨單狀態=`退款失敗`,客人提供新帳戶
When 客服要變更收款帳戶
Then 須客服主管核准才生效;核准留紀錄
來源 `[R1-Q5]`(d)
備註:換帳戶核准**是否計入每月 20 次特批配額,未答**(§5-S07)

### G. 系統中途失敗(第 3 類失敗路徑,不得缺席)

**G31 — 出款已送出但本地狀態未寫入**
Given 金流已收單並實際出款成功,系統在寫入 `已退款` 之前掛掉
When 系統復原
Then 退貨單狀態停在 `退款中`,並帶上「出款結果未確認」子旗標(**是 `退款中` 的旗標,不是第 14 個狀態**),**不得自動觸發 G28 的重試**;需以冪等鍵向金流查詢實際結果後才決定下一步;**任何情況下不得對同一退貨單重複出款**
來源 `本案自決`(§6-A-04);風險由 `[R1-Q5]`(d) 的自動重試機制推導而來
⚠️ 這是本規格最貴的一條:若無冪等鍵,`[R1-Q5]`(d) 的「重試 3 次」會變成「重複退款 3 次」。

**G32 — 驗收入倉寫到一半掛掉**
Given 倉庫按下「驗收通過」,系統已扣寫驗收結果但尚未發出 `退貨驗收已通過`
When 系統復原
Then 退貨單狀態必須是 `待驗收` 或 `驗收通過` 之一,**不得存在中間態**;若已標 `驗收通過`,事件必須補送(至少一次送達),且下游對重複事件必須冪等
來源 `本案自決`(§6-A-04)

**G33 — 建立退貨單中途失敗**
Given 客人送出申請,系統已配發退貨單號但尚未落庫
When 系統復原
Then 不得留下孤兒單號,亦不得對同一次提交產生兩張退貨單(以客人端提交識別碼去重)
來源 `本案自決`(§6-A-04)

**其餘狀態轉移的中途失敗豁免說明**:G13/G15/G16 等純狀態轉移不涉及外部系統與金錢,以「單一交易內完成、失敗即整筆回滾」一句話覆蓋,不逐條展開。

### H. 通知

**G34 — 三個時點各發雙通道**
Given 退貨單分別到達「審核結果出來」「倉庫收到貨」「退款完成」
When 各時點到達
Then 每個時點都以 **email 與簡訊兩種通道**通知客人
來源 `[R2-Q5]`(受訪者主動補充)
備註:通知本身送不出去(email 退信 / 簡訊失敗)怎麼辦,**未問過**(§5-S19)

## §7 內部矛盾(不自行調和,標「需求方裁決」)

### X1 —— 「一定收到貨才退錢」 vs 「查無件 ≤2000 直接退款」

- `[R1-Q3]`:「**一定是收到貨才退錢**,我們不會先退錢再收貨,**這個沒有例外**。」
- `[R1-Q5]`(a):「查不到的話,**2000 元以下公司吸收、直接退款**給客人。」

兩句在同一輪訪談內互相打架:前者宣稱零例外,後者就是一個例外。
影響:**C13(invariant)與 C14(precondition)不能同時成立**;G24 無法實作。
**需求方裁決。** 裁決前 C13/C14/G24 全部凍結。

### X2 —— 「已退過的不能再退」的單位不明,與另外兩條上限規則互相拉扯

- `[R1-Q2]`:「**已經退過的不能再退**。」
- `[R2-Q2]`(d):「審核沒過的可以補資料重新申請,**同一品項最多申請兩次**。」
- `[R2-Q4]`(e):「可以分好幾次退,但**同一張訂單最多分 3 次**。」

若「退過」的單位是**訂單**,則第 3 句(可分 3 次)直接違反第 1 句。
若單位是**品項**,則需釐清:第 2 句的「兩次」數的是「申請次數」還是「完成退貨次數」——若是前者,一個品項可以申請兩次卻只能完成一次;若是後者,與第 1 句衝突。
**需求方裁決**(同時列為 §5-S21)。影響 C4、C5、C6、G4、G7、G12。

### X3 —— 「每次無條件進位給客人」× 「一張訂單可分 3 次退」可能讓退款總額**超過**實付金額

`推導自 [R1-Q4] + [R2-Q4](c)(e)`,推導步驟:

1. `[R1-Q4]`:券按原價比例分攤,除不盡的零頭**無條件進位、多的給客人**。
2. `[R2-Q4]`(e):同一張訂單最多**分 3 次**退。
3. 三次部分退,每次各自進位一次 → 客人最多可多拿 3 次進位差額。
4. 若三次加總涵蓋整張訂單,退款總額 = 實付 + (至多 3 次進位差額) > 實付。

金額不大(每次差 < 1 元),但**帳面上退款總額大於客人實付**,財務對帳會爆,也是一個可被利用的規則。
受訪者只考慮了「單次」的零頭,沒考慮「多次加總」。
**需求方裁決**——是要(甲)容忍溢出、(乙)最後一次退貨用「實付減去前幾次」倒扣、還是(丙)全訂單先算好分攤再切分。
影響:C20 目前沒有測試可指名,就是卡在這裡。

### X4 —— 「沒有用過」的認定點有兩個,前端擋掉的算不算一次駁回

- `[R2-Q1]`(c):「客服在前端**只看照片**,先擋掉明顯有問題的,**真正認定還是倉庫說了算**。」
- `[R2-Q2]`(d):「**審核沒過的**可以補資料重新申請,同一品項最多申請兩次。」

客服憑照片擋掉 = 不是最終認定,但它是不是「審核沒過」、要不要吃掉客人 2 次配額中的 1 次?
另一面:倉庫驗收判定「用過」時,走的是 `[R1-Q5]`(b) 的驗收退回協商流程,還是視同審核沒過?訪談沒有涵蓋「驗收判定為已使用」這條路徑——`[R1-Q5]`(b) 只列了壞 / 少 / 錯三種。
**需求方裁決。** 影響 G5、G6、G18、C5。

### X5 —— 取消可到「倉庫簽收」為止,但逾期失效的基準可能是「寄出」

- `[R2-Q2]`(c):取消的界線是**倉庫簽收**。
- `[R2-Q2]`(a)(b):5 天內**寄回**,逾期自動失效。

「寄回」與「簽收」是兩個不同時點。若失效以寄出日判(S02 甲案),會出現:客人第 4 天寄出(未逾期)但第 8 天才到倉,期間退貨單狀態既非失效、也還沒不能取消——這段真空期的規則未定義。若失效以簽收日判(乙案),則物流延遲會讓守規矩的客人被判失效。
兩句本身不算硬矛盾,但**合起來會產生未定義區間**。
**需求方裁決**(與 S02 綁在一起)。影響 G13、G14、G15。
