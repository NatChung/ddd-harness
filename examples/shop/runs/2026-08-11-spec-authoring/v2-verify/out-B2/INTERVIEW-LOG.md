## 問答紀錄

### Q1 使用者與範圍

- **Q(PM)**:這個系統的使用者就兩種——下單的客人、看訂單的你——除此之外還有誰會用?例如客服代客下單?
- **PM 建議**:本輪只做這兩個行為(客人建立訂單、你看訂單列表),不引入其他角色。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:SPEC「範圍摘要」+「明確不在範圍」(其他角色/代客下單,訪談否決)。

### Q2 顧客資料誰管

- **Q(PM)**:顧客資料誰管?我們要做會員系統嗎?
- **PM 建議**:若已有現成顧客來源就不要重做,本系統只引用。
- **A(主管)**:「不用,顧客名單是 CRM 那邊維護的,你們讀得到就好。」
- **來源**:腳本第 2 條
- **落點**:GLOSSARY(Customer:唯讀、CRM 擁有)、SPEC 規則 R6、SPEC「明確不在範圍」(會員系統/顧客維護,訪談否決)、ARCH A1/A2(CustomerRepository 唯讀)。

### Q3 CRM 顧客資料的長相(追問)

- **Q(PM)**:那 CRM 的顧客資料長什麼樣子?我們讀得到哪些欄位?
- **PM 建議**:至少要有一個唯一編號讓訂單能指回顧客。
- **A(主管)**:「就一張表,顧客編號和姓名。」
- **來源**:腳本第 2 條(追問)
- **落點**:GLOSSARY(customerId、customerName)、SPEC 規則 R6、S-03、列表欄位「誰買的 = customerName」。

### Q4 商品資料哪裡來

- **Q(PM)**:客人下單時選的商品是哪裡來的?需要管一份商品目錄嗎?
- **PM 建議**:本輪不建商品主檔;下單時明細直接帶品名、單價、數量,商品目錄以後有需要再做。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:GLOSSARY(OrderItem:productName/unitPriceAmount/quantity)、SPEC 端點 POST /orders 的 request 形狀、SPEC「明確不在範圍」(商品主檔/庫存,訪談否決)。

### Q5 明細數量下限

- **Q(PM)**:一張訂單最少要有幾條明細?可以是空的嗎?
- **PM 建議**:至少一條,空訂單沒有業務意義,直接拒絕。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:SPEC 規則 R1、情境 S-04。

### Q6 數量與單價的限制

- **Q(PM)**:每條明細的數量、單價有沒有限制?例如數量可不可以是 0 或負的?
- **PM 建議**:數量是 ≥1 的整數;單價 ≥0(允許 0 元贈品),不允許負數。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:SPEC 規則 R2、R3、情境 S-05、S-06;GLOSSARY(quantity、unitPriceAmount)。

### Q7 幣別

- **Q(PM)**:訂單金額會有不同幣別嗎?一張訂單裡會不會混幣別?
- **PM 建議**:若有多幣別,幣別掛在訂單層級,一張訂單只有一種。
- **A(主管)**:「會有不同幣別的訂單,但一張訂單裡不會混。」
- **來源**:腳本第 3 條
- **落點**:GLOSSARY(currency 掛 Order 層級)、SPEC 規則 R4、情境 S-09。

### Q8 總額誰算

- **Q(PM)**:訂單總額是誰算的?客人自己填,還是系統算?
- **PM 建議**:系統算,不收外部傳入的總額。
- **A(主管)**:「當然系統算,就是每條明細數量乘單價加起來。」
- **來源**:腳本第 6 條
- **落點**:GLOSSARY(totalAmount 為推導值)、SPEC 規則 R5、情境 S-01、S-02。

### Q9 資料表示法(金額精度、時間、狀態碼、錯誤格式)

- **Q(PM)**:金額、時間、狀態這些資料在系統裡要用什麼表示法存和傳?
- **PM 建議**:金額用最小幣值單位(minor units,如 cents)的整數;時間用 ISO-8601 UTC;狀態程式內用英文代碼;錯誤回傳固定格式的錯誤碼。
- **A(主管)**:「這是你們的事,你決定。」
- **來源**:off-script-技術
- **PM 決定(記錄在案)**:
  1. 金額一律最小幣值單位整數(Java `long`),禁止浮點;幣別為 ISO 4217 三碼大寫字串。
  2. 時間一律 ISO-8601 UTC(Java `Instant`,序列化如 `2026-08-12T03:00:00Z`)。
  3. 訂單狀態程式內為 enum 代碼 `CREATED`;中文「已成立」只是顯示文字(見 Q13、Q14)。
  4. 錯誤回應固定格式 `{"error": "<錯誤碼>"}`,HTTP 400;錯誤碼:`CUSTOMER_NOT_FOUND`、`EMPTY_ITEMS`、`INVALID_QUANTITY`、`INVALID_UNIT_PRICE`、`INVALID_CURRENCY`。
- **落點**:GLOSSARY(金額/時間/幣別/狀態表示法)、SPEC 規則 R9、情境 S-07、錯誤格式一節、ARCH A3。

### Q10 訂單成立後能不能改

- **Q(PM)**:訂單成立之後能不能改?例如改數量、加明細?
- **PM 建議**:成立後鎖定,要改就走之後的取消/重下(若有)。
- **A(主管)**:「不行,成立就鎖定。」
- **來源**:腳本第 1 條
- **落點**:GLOSSARY(Order:成立即鎖定)、SPEC 規則 R7、SPEC「明確不在範圍」(修改訂單,訪談否決)、ARCH A5(無 update 語意)。

### Q11 取消訂單、修改訂單功能

- **Q(PM)**:那取消訂單、修改訂單這兩個功能,這一輪要做嗎?
- **PM 建議**:先不做,範圍守小。
- **A(主管)**:「先不用,以後再說。」
- **來源**:腳本第 5 條
- **落點**:SPEC「明確不在範圍」(取消訂單、修改訂單,訪談否決)。

### Q12 狀態機(術語被打回)

- **Q(PM)**:訂單的 state machine 需要定義哪些 state transitions?
- **A(主管)**:「聽不懂,講人話。」
- **來源**:off-script-技術(術語,被打回)
- **落點**:無決策;改以 Q13 的問法重問。

### Q13 訂單成立之後還有什麼變化

- **Q(PM)**:換個問法——訂單成立之後,還會有像「出貨了」「完成了」這種要記錄的變化嗎?
- **PM 建議**:本輪只有一種狀態「已成立」;出貨、完成等流轉以後再加。程式內部這個狀態的代碼叫 `CREATED`,你看到的畫面上一律顯示「已成立」。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:GLOSSARY(OrderStatus 唯一值 CREATED ↔ 顯示「已成立」)、SPEC 規則 R8、SPEC「明確不在範圍」(出貨/完成等狀態流轉,訪談否決)、ARCH A4(中文顯示屬 adapter 層)。

### Q14 列表頁要看到什麼

- **Q(PM)**:訂單列表頁,你要看到哪些欄位?
- **PM 建議**:顧客姓名、狀態、總額(含幣別)、下單時間。
- **A(主管)**:「誰買的、狀態、總共多少錢、哪天下的。狀態給我看中文,寫『已成立』。」
- **來源**:腳本第 4 條
- **落點**:SPEC 端點 GET /orders 的 response 欄位、情境 S-08;GLOSSARY(statusLabel、createdAt)。

### Q15 列表順序

- **Q(PM)**:列表的順序呢?最新的排前面可以嗎?
- **PM 建議**:依下單時間新到舊。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:SPEC 端點 GET /orders(排序規則)、情境 S-09。

### Q16 登入與權限

- **Q(PM)**:看列表需要登入或權限管控嗎?別人不能看?
- **PM 建議**:本輪不做認證授權,先在內部環境用;正式上線前再補。
- **A(主管)**:「沒想過,先照你的建議。」
- **來源**:off-script-業務
- **落點**:SPEC「明確不在範圍」(認證/授權,訪談否決)。

### Q17 收尾總結(confirm shared understanding)

- **Q(PM)**:我總結一下:系統做兩件事——客人建立訂單(選 CRM 裡的顧客、填明細品名/單價/數量,系統算總額,一張訂單一種幣別,成立即鎖定、唯一狀態「已成立」),以及你看全部訂單列表(誰買的、狀態中文、總額含幣別、哪天下的、新到舊)。不做:會員系統、商品主檔、修改/取消訂單、後續狀態流轉、登入權限。這樣對嗎?
- **A(主管)**:「就這樣,照這做。」
