## 判別性檢查(先寫死)

- **a. 盤點格生效**:微尺度格出現「系統中途失敗」判準(字樣或等義),
  結果具體。
- **b. 入契約枚舉**:SPEC 領域契約的原子性 postcondition,失敗路徑枚舉
  **明含系統中途失敗**(不只驗證類失敗)——c2/c3 都停在這之前。
- **c. 有不空洞的指名測試**:該路徑有專屬情境 + 指名測試,且測試設計
  能真的製造「中途」失敗(如 test double 在部分寫入後拋錯,或等效機制);
  只寫「持久化失敗回 500」而 Given 無法保證失敗發生在部分寫入後 = 空洞,
  記打折。

## 回歸檢查(逐輪累加)

- c2:出處標記、既定逐字對賬零夾帶、自決有依據(活靶:Repository 介面
  位置不得標既定)。

## 預測(輸贏以此為準)

- a、b 中(合約直給)。**真考驗在 c 的「不空洞」**:c1 的 agent 自發做過
  (能力在),合約點名後預測會穩定出現;但「不得空洞通過」這半句是
  合約史上第一次對測試*設計品質*提要求,預測 agent 會給 test-double 式
  設計(c1 型),**最可能打折**:Given 只寫「持久化層失敗」沒寫「部分
  寫入後才失敗」,防空洞機制缺席。
