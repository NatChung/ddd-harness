# INTERVIEW-LOG — 下單系統需求訪談

訪談引擎:`/grilling`(mattpocock-skills:grilling,一次一題、追根究柢)。
受訪者:營運主管(不懂技術詞)。
本 log 是 spec 包的出處總帳:SPEC 與 GLOSSARY 的每條規則以 `[Qn]` 回鏈到此。

來源分類:`開場` / `答案庫#n` / `fallback-業務`(stakeholder 沒想過,照 PM 建議)/
`fallback-技術`(stakeholder 交由 PM 決定)/ `收尾`。

---

## Q0(開場,stakeholder 主動給)

- **A**:「我要一個系統,客人能下單,我能看到所有訂單。」
- **來源**:開場(需求原句)。
- **落點**:SPEC 端點清單(POST /orders、GET /orders)、GLOSSARY(Order、PlaceOrder、ListOrders)。

## Q1

- **Q**:下單的客人是誰?你們手上有顧客名單嗎?需要我們幫你管理顧客、做會員那類的東西嗎?
- **A**:「不用,顧客名單是 CRM 那邊維護的,你們讀得到就好。」
- **來源**:答案庫#2。
- **落點**:GLOSSARY(Customer 唯讀外部參照)、ARCHITECTURE A2/A3(顧客唯讀)、SPEC「明確不在範圍」(會員系統)。

## Q2

- **Q**:那份顧客名單長什麼樣子?裡面記了哪些東西?
- **A**:「就一張表,顧客編號和姓名。」
- **來源**:答案庫#2(追問)。
- **落點**:GLOSSARY(Customer、CustomerId 欄位:顧客編號、姓名)、SPEC S1/S7 前提資料。

## Q3

- **Q**:不在那份名單上的人,可以下單嗎?
- **A**:「沒想過,先照你的建議。」
- **來源**:fallback-業務。
- **PM 建議(經 stakeholder 同意採用)**:只有名單上的顧客能下單;顧客編號查無此人就整筆拒絕,系統不留下任何東西。
- **落點**:SPEC R2(precondition)、R6(原子性)、情境 S3。

## Q4

- **Q**:一張訂單裡,一條一條要買的東西,每條要記些什麼?
- **A**:「沒想過,先照你的建議。」
- **來源**:fallback-業務。
- **PM 建議(經 stakeholder 同意採用)**:每條明細記「品名、單價、數量」;品名自由填寫,不做商品目錄。
- **落點**:GLOSSARY(OrderLine)、SPEC S1 請求資料、SPEC「明確不在範圍」(商品目錄)。

## Q5

- **Q**:可以下一張裡面什麼都沒有的空訂單嗎?數量填 0 或負的可以嗎?
- **A**:「沒想過,先照你的建議。」
- **來源**:fallback-業務。
- **PM 建議(經 stakeholder 同意採用)**:訂單至少要有一條明細;每條數量至少 1;單價不可為負數(0 允許,例如贈品)。違反就整筆拒絕、不留殘骸。
- **落點**:SPEC R3(precondition)、R6(原子性)、情境 S4/S5/S6。

## Q6

- **Q**:訂單總共多少錢,是客人自己報一個數字,還是系統算?怎麼算?
- **A**:「當然系統算,就是每條明細數量乘單價加起來。」
- **來源**:答案庫#6。
- **落點**:SPEC R5(postcondition)、情境 S1/S2。

## Q7

- **Q**:金額會有不同幣別嗎?一張訂單裡會不會同時有美金又有台幣?
- **A**:「會有不同幣別的訂單,但一張訂單裡不會混。」
- **來源**:答案庫#3。
- **落點**:GLOSSARY(Money、Currency)、SPEC R4(invariant)、情境 S1/S7。

## Q8

- **Q**:訂單成立之後,客人或你們還能改裡面的內容嗎?
- **A**:「不行,成立就鎖定。」
- **來源**:答案庫#1。
- **落點**:SPEC R1(invariant)、情境 S8、ARCHITECTURE A4。

## Q9

- **Q**:那要不要做「取消訂單」或「修改訂單」的功能?
- **A**:「先不用,以後再說。」
- **來源**:答案庫#5。
- **落點**:SPEC「明確不在範圍」(取消訂單、修改訂單;訪談否決)。

## Q10

- **Q**:你說要看到所有訂單——那個列表,每筆訂單要讓你看到什麼?
- **A**:「誰買的、狀態、總共多少錢、哪天下的。狀態給我看中文,寫『已成立』。」
- **來源**:答案庫#4。
- **落點**:SPEC 情境 S7、R7(狀態顯示)、GLOSSARY(OrderStatus)。

## Q11

- **Q**:金額、日期這些東西系統內部怎麼記、回給你的內容長什麼樣子,你有什麼要求嗎?
- **A**:「這是你們的事,你決定。」
- **來源**:fallback-技術。
- **PM 決定(全數記錄於此,供 spec 引用)**:
  1. 金額一律以「最小貨幣單位的整數」表示(如 cents),欄位名 `amountMinor` / `unitPriceMinor` / `totalAmountMinor`;不使用浮點數。
  2. 幣別用 ISO 4217 三碼(如 `TWD`、`USD`),訂單層級單一欄位 `currency`(結構上使明細無法混幣別)。
  3. 日期時間用 ISO-8601(UTC),欄位 `orderedAt`。
  4. 狀態內部存 enum `CREATED`;對外(列表回應)顯示中文字串「已成立」,映射放 adapter 層。
  5. 介面形狀:`POST /orders`(下單)、`GET /orders`(列表);成功建立回 HTTP 201;前置條件違反回 HTTP 422;對 `/orders` 的 PUT/PATCH/DELETE 回 HTTP 405。
- **落點**:GLOSSARY(Money、Currency、OrderStatus 表示法)、SPEC 全部情境的數字/格式、ARCHITECTURE A5/A6。

## Q12(收尾)

- **Q**:總結:客人(限 CRM 名單上的顧客)能下單,一張訂單至少一條明細(品名/單價/數量)、單一幣別、總額系統算;成立即鎖定,不做取消修改;你能看列表(誰買的、狀態中文「已成立」、總額、日期)。顧客資料唯讀自 CRM。這樣對嗎?
- **A**:「就這樣,照這做。」
- **來源**:收尾。
- **落點**:全包定稿。
