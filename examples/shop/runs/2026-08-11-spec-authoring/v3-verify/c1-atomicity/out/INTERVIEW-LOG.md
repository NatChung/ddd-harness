# INTERVIEW-LOG — 下單系統訪談紀錄

- 引擎:`/grilling`(mattpocock-skills:grilling),一次一題、每題附 PM 建議答案。
- 模式:self-play;stakeholder 為腳本化營運主管。標記規則:
  - 來源 = `答案庫#n`(腳本內建答案)/ `fallback-業務`(「沒想過,先照你的建議」)/
    `fallback-技術`(「這是你們的事,你決定」)/ `腳本-人設`(「聽不懂,講人話」)/ `腳本-收尾`。
  - 落點 = 該決策落進哪份文件的哪一節。
- SPEC 與 GLOSSARY 中的 `[Qn]` 一律回鏈到本檔的題號。

## Q0 — 開場(stakeholder 主動給)

- **A**:「我要一個系統,客人能下單,我能看到所有訂單。」
- 來源:需求原句。
- 落點:SPEC 端點清單(`POST /orders`、`GET /orders`);GLOSSARY(Order、PlaceOrder、ListOrders)。

## Q1 — 訂單成立之後,還能不能改內容?

- **PM 建議**:建議鎖定,事後改單另開流程。
- **A**:「不行,成立就鎖定。」
- 來源:答案庫#1。
- 落點:SPEC 領域規則 R1(invariant);SPEC「明確不在範圍」(修改訂單);GLOSSARY(Order 不可變性)。

## Q2 — 顧客資料誰管?需要我們做會員系統嗎?

- **PM 建議**:若已有 CRM,建議不重複做會員。
- **A**:「不用,顧客名單是 CRM 那邊維護的,你們讀得到就好。」
- 來源:答案庫#2。
- 落點:ARCHITECTURE(Customer 唯讀邊界);SPEC「明確不在範圍」(會員系統/顧客 CRUD);GLOSSARY(Customer)。

## Q3 — (追問)那顧客資料長什麼樣子?我們讀得到的是哪些欄位?

- **A**:「就一張表,顧客編號和姓名。」
- 來源:答案庫#2(追問)。
- 落點:GLOSSARY(CustomerId、Customer);SPEC 列表情境(誰買的=姓名);ARCHITECTURE(customers 表 schema)。

## Q4 — 訂單的錢會有不同幣別嗎?一張訂單裡會不會出現兩種幣別?

- **PM 建議**:建議一張訂單固定一種幣別。
- **A**:「會有不同幣別的訂單,但一張訂單裡不會混。」
- 來源:答案庫#3。
- 落點:SPEC 領域規則 R6(invariant,單一幣別);GLOSSARY(Currency、Money);SPEC「明確不在範圍」(混合幣別、幣別換算)。

## Q5 — 你看「所有訂單」那個列表時,每一筆要看到什麼?

- **PM 建議**:建議至少:顧客、金額、日期、狀態。
- **A**:「誰買的、狀態、總共多少錢、哪天下的。狀態給我看中文,寫『已成立』。」
- 來源:答案庫#4。
- 落點:SPEC `GET /orders` 回應欄位 + 情境 S9;GLOSSARY(OrderStatus 顯示值「已成立」);ARCHITECTURE(顯示轉換放 adapter)。

## Q6 — 取消訂單、修改訂單這兩個功能要嗎?

- **PM 建議**:第一版建議先不做,保持範圍小。
- **A**:「先不用,以後再說。」
- 來源:答案庫#5。
- 落點:SPEC「明確不在範圍」(取消訂單、修改訂單,來源=訪談否決)。

## Q7 — 訂單「總共多少錢」這個數字,是客人報給我們,還是系統自己算?

- **PM 建議**:一定要系統算,不能信外部傳入。
- **A**:「當然系統算,就是每條明細數量乘單價加起來。」
- 來源:答案庫#6。
- 落點:SPEC 領域規則 R7(total = Σ 數量×單價,系統計算);GLOSSARY(TotalAmount、OrderLine)。

## Q8 — 一張訂單裡面要記哪些東西?每條明細要有什麼?

- **PM 建議**:每張訂單一到多條明細;每條明細記:商品名稱、數量、單價。
- **A**:「沒想過,先照你的建議。」
- 來源:fallback-業務(腳本外)。**PM 建議被採納**:明細 = 商品名稱 + 數量 + 單價;一張訂單至少一條明細。
- 落點:SPEC 領域規則 R2(至少一條明細)、`POST /orders` request 形狀;GLOSSARY(OrderLine、ProductName、Quantity、UnitPrice)。

## Q9 — 如果客人下單到一半系統出錯(比如存到一半失敗),客人或你會不會看到「半張訂單」?

- **PM 建議**:失敗就當作整件事沒發生——系統裡不能留半張訂單或孤兒明細,列表看不到任何殘缺資料。
- **A**:「沒想過,先照你的建議。」
- 來源:fallback-業務(腳本外)。**PM 建議被採納**:下單全有全無,失敗不留殘骸。
- 落點:SPEC 領域規則 R8(postcondition:每條失敗路徑的原子性保證)、情境 S3–S8 的 Then;ARCHITECTURE(交易邊界在 usecase)。

## Q10 — 下單的客人一定要在 CRM 名單裡嗎?名單外的人來下單怎麼辦?

- **PM 建議**:名單外拒單——訂單一定要對得到一個已存在的顧客,不然「誰買的」會是空的。
- **A**:「沒想過,先照你的建議。」
- 來源:fallback-業務(腳本外)。**PM 建議被採納**:顧客必須存在於 CRM 顧客表,否則拒單。
- 落點:SPEC 領域規則 R3(precondition)、情境 S4。

## Q11 — 數量填 0 或負的、單價填負的,這種單要收嗎?

- **PM 建議**:不收——數量至少 1;單價不可以是負數(0 可以,例如贈品)。
- **A**:「沒想過,先照你的建議。」
- 來源:fallback-業務(腳本外)。**PM 建議被採納**:Quantity ≥ 1;UnitPrice ≥ 0。
- 落點:SPEC 領域規則 R4、R5(precondition)、情境 S5、S6。

## Q12 — 金額要用 decimal 還是 integer cents 存?ID 要 UUID 嗎?

- **A**:「聽不懂,講人話。」
- 來源:腳本-人設(被技術詞問)。
- 落點:無(改口重問,見 Q13)。

## Q13 — (換講法)錢在系統裡怎麼記、訂單編號怎麼給、列表用什麼順序排、出錯時畫面訊息長怎樣——這些系統內部細節你要管嗎?

- **A**:「這是你們的事,你決定。」
- 來源:fallback-技術(腳本外)。**PM 決定**(記錄如下,實作 agent 不得再改):
  1. 金額一律以最小貨幣單位整數表示(cents 整數),不用浮點、不用小數。
  2. 幣別為 3 個大寫英文字母代碼(ISO 4217 形式,只驗格式不驗清單)。
  3. 訂單編號(OrderId)由系統產生,對外為不透明字串。
  4. 下單時間(PlacedAt)由系統取當下時間,UTC、ISO-8601 表示。
  5. 列表排序:下單時間新到舊。
  6. 錯誤回應:HTTP 422(業務規則違反)/ 500(系統內部失敗),body 為 `{"error": "<訊息>"}`。
  7. 狀態欄位在兩個端點的回應中一律回中文顯示值「已成立」。
- 落點:GLOSSARY(Money/Currency/OrderId/PlacedAt 單位與表示法);SPEC 各情境的具體數值;ARCHITECTURE(顯示轉換、交易邊界)。

## Q14 — 收尾總結:系統只有兩件事——客人下單(成立即鎖定、系統算總額、失敗不留殘骸)、你看所有訂單(姓名/已成立/總額/日期)。顧客名單讀 CRM 的表,取消修改先不做。這樣對嗎?

- **A**:「就這樣,照這做。」
- 來源:腳本-收尾。
- 落點:全案定稿。
