# 第四幕的預期紅集合 —— 改過的版本(仍寫在跑之前)

`PREDICTION.md`(跑第二幕之前寫的)預測第四幕會是「OL1 → 只有 S4 紅」。
**那條現在作廢**,理由在下面。改的版本寫在這裡、跑之前,不去改原檔。

## 為什麼要改

原預測假設 S4(空單拒絕)會進 store,而 OL1 沒有拒絕邏輯 → 只有它紅。
實際上 **S4 沒進 store**(importer 擋每個 step 的 `items` 非空),
進去的是 `S1 / S2 / S10 / S11` —— 四條全是成功路徑,一條拒絕情境都沒有。

同時看到一件原預測沒想到的事,見下。

## 生成物的欄位名跟凍結的 app 對不起來

生成的斷言讀這些欄位:`customer_id` / `status` / `currency` / `total_cents` / `created_at`。
凍結的 `OrderListItem` 回的是:`orderId` / `customerName` / `statusLabel` / `totalCents` / `placedAt`。

**一個都對不上。**

而這不是 agent 做錯了。訪談那份規格把 HTTP 形式明標為 `本案自決`,
從沒指定過 JSON 欄位名 —— agent 只能自己取,它取了 snake_case。

## 真正的洞:合約被切成兩半,而兩半碰不到面

`gen_acceptance.py` 裡,**送出訂單與取回列表的管線是寫死的**
(`body.get("orderId")`、`.filter(r -> orderId.equals(r.get("orderId")))`),
而**斷言讀哪個欄位是從 store 來的**。

於是:
- **管線那半**假設了一組固定的 API 形狀,規格作者看不到、改不動;
- **欄位那半**是 store 裡的自由文字,規格作者想寫什麼寫什麼;
- **schema 裡沒有任何地方能宣告「列表的一列長什麼樣」** —— 所以兩半不可能對得起來,
  除非規格作者剛好猜中生成器心裡那組名字。

凍結那 5 條情境上量不到這件事:那份 SPEC.md **直接把 response JSON 範例寫在裡面**
(`orderId` / `customerName` / `statusLabel` / `totalCents` / `placedAt`),
agent 照抄就對了。**是散文裡的一段範例在補 schema 的洞,而不是 schema 自己守得住。**

→ 這是 `list_field_*` 這三個 kind 的設計缺口:它們吃 `field` 當自由文字,
卻沒有對應的「欄位存在且叫這個名字」的宣告點。

## 改過的預期

| 段 | 預期 | 理由 |
|---|---|---|
| 空骨架 → 4/4 紅 | ✅ 應該過 | 骨架沒有實作,跟被測規格是哪份無關 |
| OL1 → 4/4 綠 | ❌ **預期全紅** | 欄位名全不對。**紅的原因是命名,不是領域行為分歧** |
| 逐條可紅 | **不算數** | `BREAKS` 只有 S1–S5,現有 id 中只有 S1/S2 會跑,而兩者語意跟凍結那份撞名不撞義。且 OL1 已經全紅,再破壞也看不出差別 |

**⚠️ 這一輪第四幕不構成對管線的驗收。** 它量到的是「兩份不同規格 + 一個半寫死的生成器」
的交互作用。**跑它是為了看紅的原因對不對得上這份預測**,不是為了拿綠燈。
