## 預測二:兩個行為面的觀測(這次沒有被要求)

1. **agent 還會不會自己交「落不了檔的清單」?**
   上一跑它交了,而且逐條附上擋住它的那條約束 —— **prompt 從來沒要求它揭露**,
   完成的定義只是「import 印 ok」。這次 prompt 長了很多、規則也多了,
   我預測**它仍然會交**,但如果不交,那才是有意思的:表示上一次的揭露是
   「規則少、有餘裕」的副產品,不是這個 agent 的穩定性質。
2. **`proxy_for` 會不會真的被填?**
   上一跑 S10 的代理編碼是**自願揭露**在註解與 `given_when` 裡的。
   現在它是 schema 欄位,但**沒有任何機械手段擋得住不填**(那正是票 02 blocked 的原因)。
   預測會填 —— 但這一條只有一個樣本,填了也證明不了偵測力。

## 順帶要交的東西(票 02 自己寫的)

**掃這一跑有沒有代理編碼** —— 票 02 blocked 在「第二個形狀不同的已知陽性」,
而它自己寫著取得方式是「下次跑第一~四幕時,把這件事列成產出的一部分」。
S10 那條是已知的第一個;要找的是**形狀不同**的第二個,不是同一條再數一次。

## 跑之前補的兩行 prompt(以及為什麼那不算作弊)

`run_act2.sh` 原本把 `res_total_field` / `res_customer_id_field` 寫成「選填」,
但 importer 是**條件式必填**。不補的話 agent 只能靠撞錯誤訊息才知道 ——
那正是上一跑記下的「**完成的定義若由工具給,工具的每一條錯誤訊息就是指示的一部分**」。

補它是讓**指示與工具一致**,不是給答案:補的是欄位什麼時候必填,
沒有告訴它哪些情境該用 `expects_rejection`、也沒有給任何欄位的值。
落檔率仍然要靠它自己讀散文判斷。
