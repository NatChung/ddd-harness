### 禁用同義詞清單

| 禁止裸用的詞 | 為什麼 | 一律改用 |
|---|---|---|
| **「總價」指不含運費的金額** | 需求方 Q6 曾說「單價 x 數量 = 總價」(不含運費),Q26 裁決總價**含**運費。舊語意仍可能出現在任何人口中 | 不含運費的那個數 = **品項小計**(單一品項)或 **商品金額合計**(全單);含運費的 = **總價** |
| **`orderTotal` / `grandTotal` / `finalPrice` / `amount`(裸用)** | 實作端最容易各取各的名 | 一律 `totalAmount`(= 總價),見 §1.2 |
| **「地址」** | Q2 講「收貨地址」、Q20 講「地址」,Q30 確認是同一個。裸用會讓人以為另有帳單地址 | **收貨地址** / `shippingAddress` |
| **「單」/「訂單」指給上游的那張** | Q23「轉下定給他」、Q28「我再另外開單做」——那是另一個東西 | 客人的 = **訂單**;給上游的 = **上游下定單** |
| **「鎖」** | Q7 只說「鎖起來」,沒說鎖誰 | **庫存鎖定** |
| **「購物車」** | Q19 說不在這裡、Q22 又說要留著(§7 矛盾未解),裸用會讓實作者以為要做 | 本次一律不得出現在程式碼中,直到 §7-2 被裁決 |
| **「客人 / 客戶 / 用戶」混用** | Q1/Q3 說「客人」「客戶」,Q25 說「用戶」——是不是同一個角色他沒說 | 下單的一方一律 **客戶**;查詢端的一方一律 **用戶**;兩者是否為同一人見 §5 |

## §1.1 Bounded Context

**切界是一個決定,來源 `本案自決`。**

**依據**:訪談沒有出現兩個部門對同一個詞講不同意思(唯一一次同名不同義是需求方自己前後不一的「總價」,已由 Q26 裁決,不構成切界理由)。切界的實際依據是**生命週期不一致**——`[Q7]` 說庫存鎖定在「進入結帳」時就建立,`[Q8]` 說訂單要「付費成功後」才存在,所以**鎖比訂單早出生**,無法住在訂單這個聚合根裡。

| Context | 保留哪些詞 | 對外關聯 |
|---|---|---|
| **Ordering(訂單)** | 訂單、訂單品項、單價、數量、品項小計、運費、總價、收貨地址、客戶基本資訊、已成立/已出貨/收到 | 以「結帳識別碼」引用 Checkout;以「付款識別碼」引用 Payment |
| **Checkout / Inventory(結帳與庫存)** | 結帳作業、庫存、庫存鎖定、可出貨、1 小時期限 | 以事件通知 Ordering;以 SKU 字串被引用 |
| **Payment(支付,外部)** | 付費成功、退費 | 由 Ordering 透過一個 port 呼叫,**領域層不得認識任何支付廠商** |
| **Reporting(報表)** | 每月銷量 | 只讀 Ordering 的資料,不回寫 |
| **Upstream Purchasing(上游採購)** | 上游下定單 | **本次不實作**(`[Q28]`「不算在這次」),但 `[Q28]` 說「但是這個系統沒錯」,故保留為未來的 context,不當成外部系統 |

架構後果寫在 §9。

## §1.2 wire shape(端點的欄位名)

**整節 `本案自決`。** 需求方不懂技術,訪談中沒有問過他任何欄位名——依訪談指示 §1.2,這是對的;但自決完必須寫成合約,否則下游兩個實作會各取各的名,同一套驗收兩邊都過不了。

**通用約定**:JSON、UTF-8;所有金額為**整數**,單位 TWD 元;所有時間為 ISO-8601、帶時區(`2026-08-19T14:03:00+08:00`);欄位名 lowerCamelCase。

### E1. `POST /checkouts` —— 進入結帳(建立庫存鎖定)

**為什麼有這個端點**:`[Q7]`「要進入結帳一定要先鎖起來」+ `[Q8]`「付費成功後有訂單」→ 鎖庫存與建訂單必然是兩個時刻,不能塞進同一次呼叫。

Request:
```json
{
  "customer": {
    "name": "王小明",
    "email": "ming@example.com",
    "shippingAddress": "台北市信義區市府路 1 號"
  },
  "items": [
    { "sku": "NIKE-DUNK-LOW-US9", "unitPrice": 3200, "quantity": 2 }
  ],
  "shippingFee": 120
}
```
- `unitPrice` 與 `shippingFee` 由呼叫方帶入:商品主檔與運費規則在訪談中從未出現(見 §5 阻斷級)。**這是為了讓 §3 的總價 invariant 可被驗證所做的權宜決定,不是最終設計**(§6 A-7)。

Response `201`:
```json
{
  "checkoutId": "9f1c...-uuid",
  "currency": "TWD",
  "items": [
    { "sku": "NIKE-DUNK-LOW-US9", "unitPrice": 3200, "quantity": 2, "lineSubtotal": 6400 }
  ],
  "shippingFee": 120,
  "totalAmount": 6520,
  "expiresAt": "2026-08-19T15:03:00+08:00"
}
```

Error `409` `OUT_OF_STOCK`(見 E5 錯誤格式),`details.sku` 指出是哪一款。

### E2. `POST /orders` —— 付費成功後產生訂單

Request:
```json
{
  "checkoutId": "9f1c...-uuid",
  "paymentId": "pay_20260819_0001"
}
```

Response `201`:
```json
{
  "orderId": "3b7e...-uuid",
  "status": "PLACED",
  "placedAt": "2026-08-19T14:11:22+08:00",
  "currency": "TWD",
  "customer": {
    "name": "王小明",
    "email": "ming@example.com",
    "shippingAddress": "台北市信義區市府路 1 號"
  },
  "items": [
    { "sku": "NIKE-DUNK-LOW-US9", "unitPrice": 3200, "quantity": 2, "lineSubtotal": 6400 }
  ],
  "shippingFee": 120,
  "totalAmount": 6520
}
```

Errors:`410 CHECKOUT_EXPIRED`(超過 1 小時)、`402 PAYMENT_NOT_SUCCEEDED`、`404 CHECKOUT_NOT_FOUND`。

### E3. `GET /orders` —— 後台人員看所有訂單(**列表一列的欄位**)

Response `200`:
```json
{
  "orders": [
    {
      "orderId": "3b7e...-uuid",
      "placedAt": "2026-08-19T14:11:22+08:00",
      "status": "PLACED",
      "customerName": "王小明",
      "itemCount": 2,
      "currency": "TWD",
      "totalAmount": 6520
    }
  ]
}
```
`itemCount` = 所有品項的數量加總(不是品項種類數)。

### E4. `PATCH /orders/{orderId}/status` —— 改狀態

Request:`{ "status": "SHIPPED" }`,允許值 `SHIPPED` / `RECEIVED`。
Response `200`:同 E2 的訂單物件。
Errors:`409 INVALID_STATUS_TRANSITION`、`400 ORDER_IS_IMMUTABLE`(試圖改狀態以外的欄位)。

### E5. `GET /reports/monthly-sales?month=YYYY-MM` —— 每月銷量

Response `200`:
```json
{ "month": "2026-08", "currency": "TWD", "orderCount": 42, "unitsSold": 87, "salesAmount": 271400 }
```

### 錯誤共用格式
```json
{ "error": { "code": "OUT_OF_STOCK", "message": "…", "details": { "sku": "NIKE-DUNK-LOW-US9" } } }
```

### 名詞對照(防止下游各取各的名)

| 訪談用語 | wire 欄位 |
|---|---|
| 客人 / 客戶 | `customer`(`name` / `email` / `shippingAddress`) |
| 鞋子 SKU | `sku` |
| 數量 | `quantity` |
| 單價 | `unitPrice` |
| 品項小計 | `lineSubtotal` |

| 成立時間 | `placedAt` |
| 訂單狀態 | `status` |

## §2 GWT 清單

### 下單主路徑

**G1 — 單一品項,庫存足夠,付費成功 → 訂單產生**(來源 `[Q3]` `[Q8]`)
- Given:SKU `NIKE-DUNK-LOW-US9` 庫存 5 雙,單價 3200,運費 120
- When:客戶以數量 2 建立結帳作業,取得 `checkoutId`;第三方支付回報 `pay_0001` 付費成功;以該 `checkoutId` + `paymentId` 建立訂單
- Then:回 `201`;`totalAmount` = 6520;`status` = `PLACED`;該 SKU 可售庫存為 3

**G2 — 多雙不同的鞋,總價依 Q26 裁決的公式計算**(來源 `[Q16]` `[Q21]` `[Q26]`)
- Given:SKU A 單價 3200 庫存 5;SKU B 單價 4500 庫存 2;運費 120
- When:同一次結帳,A 買 2 雙、B 買 1 雙,付費成功後產生訂單
- Then:`lineSubtotal` 分別為 6400 與 4500;`totalAmount` = 6400 + 4500 + 120 = **11020**

### 下單失敗路徑(三類)

**G3 —(第 1 類:業務規則不通過)庫存不足 → 報錯,無法結帳**(來源 `[Q7]`)
- Given:SKU A 可售庫存 1 雙
- When:客戶以數量 2 建立結帳作業
- Then:回 `409 OUT_OF_STOCK`;**不建立任何結帳作業、不建立任何庫存鎖定**;該 SKU 可售庫存仍為 1

**G4 —(第 2 類:外部系統回失敗)付費沒有成功 → 沒有訂單,鎖定釋放**(來源 `[Q8]` `[Q7]`)
- Given:結帳作業已建立,SKU A 鎖定 2 雙
- When:第三方支付回報付款失敗
- Then:回 `402 PAYMENT_NOT_SUCCEEDED`;**不存在任何訂單**;該 SKU 可售庫存回到鎖定前的數字

**G5 —(第 3 類:系統中途失敗)已收到錢、訂單寫到一半掛掉 → 退費**(來源 `[Q14]` `[Q18]`)
- Given:結帳作業已建立且尚未過期,第三方支付已回報 `pay_0002` 付費成功
- When:建立訂單的持久化過程中系統中斷
- Then:**不留下半筆訂單**(查不到任何 `PLACED` 訂單引用 `pay_0002`);系統對 `pay_0002` 發出退費;該 SKU 的庫存鎖定被釋放
- 需求方原話:「優先確認有費用 但沒訂單,先退費,因為內容也不見了」——**他選的是退費,不是補建訂單**,實作不得改成事後補單

**G6 —(第 3 類:退費本身的中途失敗)退費呼叫失敗 → 可重試且不重複退**(來源 `本案自決`,依據 `[Q18]`「我們接第三方支付做」)
- Given:G5 的情境,退費呼叫第一次逾時
- When:系統重試退費
- Then:同一個 `paymentId` 最終只被退一次

**G7 — 結帳後 1 小時內未完成 → 庫存鎖定釋放**(來源 `[Q22]`)
- Given:結帳作業建立於 14:00,SKU A 鎖定 2 雙,`expiresAt` = 15:00
- When:到 15:00 仍未產生訂單
- Then:該 2 雙回到可售庫存;以該 `checkoutId` 建立訂單回 `410 CHECKOUT_EXPIRED`

**G8 — 訂單成立後,鎖定的庫存轉為可出貨**(來源 `[Q17]`)
- Given:G1 的訂單已產生
- Then:該筆被鎖住的 2 雙狀態為**可出貨**,既不回到可售庫存、也不再是庫存鎖定

### 訂單成立後

**G9 — 訂單成立後不得修改內容**(來源 `[Q24]`「只會更改狀態」)
- Given:已成立的訂單
- When:嘗試修改品項、數量、單價、運費、收貨地址或客戶基本資訊
- Then:回 `400 ORDER_IS_IMMUTABLE`;訂單內容一個位元都沒變

**G10 — 改狀態為已出貨**(來源 `暫定 [Q27]`)
- Given:`status` = `PLACED` 的訂單 → When:改為 `SHIPPED` → Then:回 `200`,`status` = `SHIPPED`

**G11 — 改狀態為收到**(來源 `暫定 [Q27]`)
- Given:`status` = `SHIPPED` → When:改為 `RECEIVED` → Then:回 `200`,`status` = `RECEIVED`

**G12 — 不合法的狀態轉移被擋下**(來源 `本案自決` §6 A-12)
- Given:`status` = `RECEIVED` → When:改為 `SHIPPED` → Then:回 `409 INVALID_STATUS_TRANSITION`

### 查詢

**G13 — 後台人員看到所有訂單**(來源:需求方第一句原話 + `[Q25]`)
- Given:三張分屬不同客戶的訂單 → When:後台人員呼叫 `GET /orders` → Then:三張都在列表裡,每列欄位如 §1.2 E3

**G14 — 每月銷量**(來源 `[Q29]`)
- Given:2026-08 有 2 張訂單(共 3 雙,金額 6520 + 4500 = 11020),2026-07 有 1 張
- When:查詢 `month=2026-08`
- Then:`orderCount` = 2、`unitsSold` = 3、`salesAmount` = 11020

**G15 — 用戶只看得到自己的訂單**(來源 `本案自決` §6 A-8)
- ⚠️ **這一條依賴身分驗證機制,而身分驗證在訪談中從未出現(§5 阻斷級 B-2),本條在該項解決前不得實作。**

### 值域

**G16 — 數量 0 或負數被拒**(來源 `本案自決` §6 A-6):回 `400`,不建立結帳作業
**G17 — 金額為負被拒**(來源 `本案自決` §6 A-1):`unitPrice` 或 `shippingFee` 為負 → 回 `400`

## §3 領域契約(Design by Contract)

## §4 Domain Event 清單

| 事件名 | 什麼時候發生 | 誰在等它 | 跨聚合根 / 跨 context | 來源 |
|---|---|---|---|---|
| **庫存已鎖定** `StockReserved` | 客戶進入結帳、每個品項取得鎖定時 | 結帳作業(組成自己的內容);逾時釋放的計時 | 跨聚合根(庫存 → 結帳作業) | `[Q7]` |

| **付費已失敗** `PaymentFailed` | 第三方支付回報沒收到錢 | 庫存(釋放鎖定) | 跨 context | `[Q8]` |
| **訂單已成立** `OrderPlaced` | 付費成功且訂單持久化完成 | ①庫存(把鎖定轉可出貨)②「準備出貨」那一端 —— 需求方 `[Q9]`「就準備出貨」、`[Q23]` 出貨由上游公司做、`[Q28]` 轉下定「不算在這次」,**故本次只發出事件,沒有訂閱者** | 跨聚合根 + 未來跨 context(Upstream Purchasing) | `[Q8]` `[Q9]` `[Q23]` `[Q28]` |

| **已退費** `PaymentRefunded` | 已收到錢但訂單未建立成功時 | 庫存(釋放鎖定);對帳(本次不做) | 跨 context | `[Q14]` `[Q18]` |

| **訂單已收到** `OrderReceived` | 訂單狀態改為收到 | 目前無訂閱者(同上) | 否 | `暫定 [Q27]` `[Q24]` |

### §3 每一條「跨聚合根,邊界可能錯」的處置

| 標記 | 契約 | 處置 |
|---|---|---|
| **X-1** | **C6**(沒有付費成功不得產生訂單) | **新增一個聚合根:結帳作業**。付款結果由 `PaymentSucceeded` / `PaymentFailed` 事件寫進結帳作業,`POST /orders` 只讀結帳作業自己的狀態就能判定 C6 —— 判定不再需要看訂單以外的即時資料。**這是 `本案自決`,依據是 `[Q7]` + `[Q8]` 的時間差** |
| **X-2** | **C10 / C12 / C15**(訂單成立 → 庫存轉可出貨;付費失敗 → 釋放;逾時 → 釋放) | **規則移到庫存聚合根**,由 `OrderPlaced` / `PaymentFailed` / 逾時觸發的 `StockReservationReleased` 事件驅動。**但「訂單成立與庫存轉可出貨是不是同一筆交易」需求方從未被問到**,故本次採用**同一筆交易內完成**(依據:`[Q17]`「就變成可出貨」語氣是立即的),並列為待確認 |
| **X-3** | **C13**(已扣款、訂單未成 → 退費) | **不新增聚合根,以補償流程處理**:退費是 `PaymentRefunded` 事件驅動的獨立動作,不與訂單建立同一筆交易(否則訂單建立失敗時退費也會被回滾)。冪等由 C14 保證 |

### §1.1 Bounded Context 的架構後果

- 五個 context 各自一個頂層 package(R3),彼此只透過 port 與事件往來(R4 / R9)。
- `upstream`(上游下定單)本次**不建 package**,但 `OrderPlaced` 事件必須發出且可被訂閱 —— `[Q28]`「不算在這次,但是這個系統沒錯」的直接後果。
