| 詞彙 | 定義 | DDD 型態 | 單位或表示法 | 來源 |

| **總金額** | 本筆訂單的應付總額 | Value Object | 新台幣(TWD),整數(元),計算方式=單價×數量 | [Q4] [Q9] |
| **下單時間** | 訂單成立的時刻 | Value Object | ISO 8601 時間戳(本案自決) | [Q4] |

### §1.1 禁用同義詞清單

實作命名**必須**照上表，禁止使用以下同義詞或縮寫:
- ❌ `訂單ID` / `Order ID` / `orderId` — 用 **訂單號碼**
- ❌ `客戶` / `用户` / `buyer` — 用 **客人** 
- ❌ `商品編碼` / `SKU` / `product code` — 用 **商品 ID**
- ❌ `金額` / `price` (單數) — 區分 **單價**(一件商品) vs **總金額**(整筆訂單)
- ❌ `件數` / `count` — 用 **數量**
- ❌ `成立時間` / `createdAt` — 用 **下單時間**(明確指下單動作完成的時刻)

## §1.2 Wire Shape — JSON 欄位規範

`本案自決` — 需求方不懂技術，本欄位名由實作決定。但以下結構為合約。

### 下單請求 (客人端)

```json
{
  "items": [
    {
      "product_id": "string",
      "quantity": "positive integer"
    }
  ],
  "customer_name": "string"
}
```

| 欄位 | 型態 | 必填 | 說明 | 來源 |
|---|---|---|---|---|
| `items` | 陣列 | ✓ | 訂單中的商品清單 | [Q1] |
| `items[].product_id` | 字串 | ✓ | 商品 ID(驗證:客人輸入錯誤時拒絕) | [Q1] [Q7] |
| `items[].quantity` | 正整數 | ✓ | 購買數量(驗證:客人輸入錯誤時拒絕) | [Q1] [Q7] |
| `customer_name` | 字串 | ✓ | 客人姓名 | [Q4] |

### 下單回應 (成功)

```json
{
  "order_number": "string",
  "customer_name": "string",
  "items": [
    {
      "product_id": "string",
      "unit_price": "integer (TWD)",
      "quantity": "positive integer",
      "subtotal": "integer (TWD)"
    }
  ],
  "total_amount": "integer (TWD)",
  "currency": "TWD",
  "status": "established",
  "created_at": "ISO 8601 timestamp"
}
```

| 欄位 | 型態 | 說明 | 來源 |
|---|---|---|---|
| `order_number` | 字串 | 系統分配的訂單號碼 | [Q2] |
| `customer_name` | 字串 | 客人姓名(原樣回傳) | [Q4] |
| `items[].product_id` | 字串 | 商品 ID | [Q1] |
| `items[].unit_price` | 整數 | 單價(新台幣,元) | [Q9] |
| `items[].quantity` | 正整數 | 數量 | [Q1] |
| `items[].subtotal` | 整數 | 該商品的小計 = unit_price × quantity | 推導自 [Q9] |
| `total_amount` | 整數 | 訂單總金額(新台幣,元) | [Q4] [Q9] |
| `currency` | 字串常量 | "TWD" | [Q1] |
| `status` | 字串列舉 | "established" | [Q2] [Q8] |
| `created_at` | ISO 8601 | 訂單成立時刻 | [Q4] |

## §2 情境(Given-When-Then)

### GWT-001: 客人成功下單

**Given** — 前置條件
- 系統中已有商品記錄: 商品 ID "PROD-001", 單價 500 元
- 系統中已有商品記錄: 商品 ID "PROD-002", 單價 300 元
- 未存在訂單號碼 "ORD-20260818-0001"

**When** — 動作
- 客人發送下單請求:
  ```
  customer_name: "王小明"
  items: [
    {product_id: "PROD-001", quantity: 2},
    {product_id: "PROD-002", quantity: 1}
  ]
  ```

**Then** — 可斷言結果
- 系統回應 HTTP 200
- 回應包含:
  - `order_number`: "ORD-20260818-0001"
  - `status`: "established"
  - `total_amount`: 1300 (= 500×2 + 300×1)
  - `currency`: "TWD"
  - `created_at`: 當下時刻的 ISO 8601 時間戳
  - `items[0].subtotal`: 1000 (= 500×2)
  - `items[1].subtotal`: 300 (= 300×1)
- 訂單已被系統持久化

**來源** — [Q2] 訂單馬上成立並返回號碼; [Q4] 顯示訂單號、客人名、狀態、金額、時間; [Q9] 金額計算

---

### GWT-002: 客人輸入錯誤的商品 ID,下單被拒

**Given** — 前置條件
- 系統中商品記錄不包含商品 ID "INVALID-PROD"
- 客人尚未確認訂單

**When** — 動作
- 客人發送下單請求:
  ```
  customer_name: "李小花"
  items: [
    {product_id: "INVALID-PROD", quantity: 1}
  ]
  ```

**Then** — 可斷言結果
- 系統回應 HTTP 400 (或 422)
- 回應包含:
  - `status`: "draft"
  - `error`: "Invalid product_id: INVALID-PROD"
  - `customer_name`: "李小花"
  - `items`: 原請求的商品清單
- 訂單**不被成立**、**不產生訂單號碼**
- 客人可修正後重新提交

**來源** — [Q7] 輸入錯誤時系統拒絕; [Q8] 失敗時訂單回到「草稿」狀態

---

### GWT-003: 客人輸入錯誤的數量,下單被拒

**Given** — 前置條件
- 系統中已有商品 ID "PROD-001", 單價 500 元
- 客人尚未確認訂單

**When** — 動作
- 客人發送下單請求:
  ```
  customer_name: "陳大明"
  items: [
    {product_id: "PROD-001", quantity: -5}
  ]
  ```

**Then** — 可斷言結果
- 系統回應 HTTP 400 (或 422)
- 回應包含:
  - `status`: "draft"
  - `error`: "Invalid quantity: must be positive integer"
  - `customer_name`: "陳大明"
- 訂單**不被成立**

**來源** — [Q7] 輸入錯誤時系統拒絕; [Q1] 數量為正整數

---

### GWT-004: 客人查詢所有訂單列表

**Given** — 前置條件
- 系統中已成立以下訂單:
  - ORD-001: 王小明, 狀態 "established", 總金額 1300, 下單時間 2026-08-18 09:00:00Z
  - ORD-002: 李小花, 狀態 "established", 總金額 500, 下單時間 2026-08-18 10:30:00Z

**When** — 動作
- 營運主管請求訂單列表

**Then** — 可斷言結果
- 系統回應 HTTP 200
- 回應包含所有成立的訂單，各筆包含:
  - `order_number`
  - `customer_name`
  - `status`: "established"
  - `total_amount` (整數,新台幣)
  - `currency`: "TWD"
  - `created_at` (ISO 8601)

**來源** — [Q4] 看到訂單號、客人名、狀態、金額、下單時間

## §3 領域規則(Design by Contract)

| 編號 | 型態 | 規則敘述 | 守在哪個聚合根 | 來源 |
|---|---|---|---|---|
| **C1** | Invariant | 商品 ID 必須存在於商品目錄中 | 訂單聚合根(驗證時) | [Q7] |
| **C2** | Invariant | 數量必須為正整數 | 訂單聚合根 | [Q1] [Q7] |
| **C3** | Invariant | 單價必須≥0、以新台幣整數表示 | 訂單聚合根 | [Q9] |
| **C4** | Invariant | 總金額 = Σ(商品i的單價 × 數量i)、以新台幣整數表示、無四舍五入 | 訂單聚合根 | [Q9] |
| **C5** | Postcondition(成功) | 下單成功後,訂單狀態轉為 "established",產生唯一訂單號碼並返回給客人 | 訂單聚合根 | [Q2] [Q8] |
| **C6** | Postcondition(失敗) | 輸入驗證失敗(商品 ID 無效或數量無效)時,訂單停留在 "draft" 狀態、不產生訂單號碼 | 訂單聚合根 | [Q7] [Q8] |

## §4 Domain Event 清單

| 事件名 | 何時發生 | 誰在等它 | 跨聚合根/Context | 來源 |
|---|---|---|---|---|
| **訂單已成立** (OrderEstablished) | 客人確認下單、系統驗證通過、狀態轉為 "established" | 倉庫、財務(待確認) | 可能跨 | [Q10] |

**說明:** 訪談中僅確定「訂單成立後倉庫要知道去出貨、財務可能要記帳」,但具體的事件消費方、通知機制、是否同步/非同步尚未決定。

## §6 規格沉默(阻斷級)

| 項目 | 所屬格 | 說明 | 影響的契約 | 建議 |
|---|---|---|---|---|
| **系統中途失敗時的狀態保證** | GWT 失敗路徑 | 訪談方回答「不知道」(Q6)。如果下單過程中數據庫斷連、服務掛掉,訂單應停在什麼狀態?是部分存入(髒資料)還是完全回滾? | C5, C6 | **技術判斷**:建議採用強原子性(All-or-Nothing):要麼訂單完整存入並狀態轉為 "established",要麼完全不存入且回傳失敗。理由:髒資料會導致客訴與財務混亂。建議與訪談方確認。 |
| **後續通知機制與消費方** | Domain Event | 訪談方回答「倉庫要知道去出貨、財務可能要記帳,但具體要通知誰、怎麼通知還沒確定」(Q10)。系統是立即同步通知、還是非同步隊列?通知哪些系統? | §4 | **業務政策**:涉及倉庫與財務流程,猜錯會延誤出貨或帳務。**不採用**,留待需求方決定。 |
| **客人的唯一標識** | GLOSSARY | 訪談中僅提及「客人名字」,未明確客人是否需要 ID、郵箱、電話以唯一識別重複名字的客人 | — | **業務政策**:同名客人的區分方式會影響訂單查詢與後續聯絡。建議與訪談方確認。 |
| **商品 ID 的格式** | wire shape | 訪談中未指定商品 ID 是數字、字符串或特定格式 | C1 | **技術判斷**:建議固定為字串(更靈活)。待確認。 |
| **訂單號碼的格式與自增策略** | wire shape | 訪談中未指定訂單號碼的編碼規則(是否日期前綴、自增順序等) | C5 | **技術判斷**:建議採用格式 "ORD-YYYYMMDD-NNNNN"(日期+自增序號),確保可讀且具時間意義。待確認。 |

## §8 ASSUMPTIONS (本案自決項)

| 項目 | 自決內容 | 依據 | 待確認點 |
|---|---|---|---|
| **JSON 欄位名** | `order_number`, `customer_name`, `total_amount`, `currency`, `created_at`, `status`, `items`, `product_id`, `unit_price`, `quantity`, `subtotal` 等 | 需求方不懂技術,無法提供欄位名。RESTful API 慣例採用蛇形 snake_case。 | 需求方是否滿意這些欄位名選擇? |
| **訂單號碼格式** | "ORD-YYYYMMDD-NNNNN" (日期+五位自增序號) | 可讀性與時間可追溯性 | 需求方是否認可此格式? |
| **商品 ID 型態** | 字串(而非純數字) | 更具靈活性,支援英文與數字混合 | 需求方原有系統中商品 ID 是什麼格式? |
| **時間戳格式** | ISO 8601 (e.g. "2026-08-18T12:34:56Z") | 國際標準,跨系統相容 | 接受? |
| **系統中途失敗時的原子性** | All-or-Nothing:訂單狀態要麼是 "established"(完整持久化), 要麼完全失敗且不存入 | 預防髒資料與客訴 | 需求方是否同意此策略? |
