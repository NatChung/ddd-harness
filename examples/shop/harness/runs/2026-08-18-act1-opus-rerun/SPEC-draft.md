# 電商下單與訂單清單 —— 規格草案

> **來源標記說明(五格,不得自創第六格)**
> `[Qn]` = 需求方第 n 題親口說的 ・ `暫定 [Qn]` = 他說了但語氣不定,不可當穩定規則實作 ・
> `推導自 [Qn]` = 從他的答案邏輯上必然,已寫出推導步驟 ・ `模板既定 <文件 L行號>` = 架構常備前提 ・
> `本案自決` = 他沒說但非決不可,附依據與待確認點。
>
> **本案 `模板既定` 為 0 筆。** 這個情境沒有任何被授權為「架構模板」的文件;訪談指示本身
> 明文禁止被當成架構模板引用行號。因此 §9 全部架構規則一律是 `本案自決`。

## 一、GLOSSARY(§1)

### 1.1 禁用同義詞清單

| 禁止裸用的詞 | 為什麼 | 一律改用 |
|---|---|---|
| 會員 / 買家 / 使用者 | 「會員」是**會員系統**那一側的概念;本案只認得一個編號,不擁有會員 | 客人 Customer / 客人編號 CustomerId |
| 價錢 / 售價 / 價格 | 沒說清楚是「商品現在的牌價」還是「這張單當初定住的價」,而這兩者會不一樣 `[Q6]` | 單價 UnitPrice(訂單上的快照);牌價一律說「商品價目系統的現價」 |
| 總價 / 金額合計 / 應付金額 | 「應付」暗示付款流程,本案沒有付款 | 總金額 TotalAmount |
| 購物車 / 草稿單 / 未完成訂單 | 系統裡**不存在**這種東西 `[Q13]`,留著這個詞會誘導實作出一張表 | (不得使用;要講就講「客人畫面上尚未送出的內容,不屬本系統」) |
| 商品名稱 | 本案對外回應**不含**商品名稱(需求方未要求) | (不得出現在本案的欄位與型別中) |
| 訂單狀態變更 / 狀態機 | 只有一種狀態,沒有轉移 `[Q16]` | (不得使用) |

### 1.2 Bounded Context

發現同名不同義,故切界。**這是一個決定,標 `本案自決`**,依據為 `[Q10]` `[Q15]` 兩句「不是這次要做的東西自己管的」。

| Context | 保留哪些詞 | 是誰的 |
|---|---|---|
| **訂單**(本案唯一要做的) | 訂單、訂單品項、數量、單價、小計、總金額、單號、成立日期、訂單狀態 | 本案 |
| **會員**(界外) | 客人的身分、名字、是否存在 | 會員系統 `[Q10]` |
| **商品價目**(界外) | 商品現在賣多少錢 | 商品價目系統 `[Q15]` |

跨界關聯:訂單 context **單向**向外查,兩個界外系統都不知道訂單存在。訂單只留下界外系統的**編號**
(`customerId`、`productId`)與**成立當下抄下來的單價**;名字不抄、即時查 `[Q10]`。
架構後果寫在 §9。

## 端點

> 對應合約 §1.2 wire shape。
>
> **整節標 `本案自決`。** 需求方不懂技術,依訪談鐵律不得問他欄位名,也不得拿「他大概會這樣叫」來充數。
> 但自決完必須寫成合約:下面每一個欄位名、型別、單位、缺值行為都是**實作不得更改**的約定。
> 沒有這一節,兩份實作會各取各的欄位名,同一套驗收測試兩邊都過不了,而且失敗訊息會全部長成
> `but was: null`,領域行為對不對完全看不見。

金額欄位一律是**整數,單位「分」**。`39800` 代表新台幣 398.00 元。任何實作不得改用元、
不得用浮點數、不得用字串帶小數點。

### 端點一:建立訂單 `POST /orders`

**請求 body** —— 逐欄:

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `customerId` | string | 是 | 客人編號,原樣傳會員系統認得的值 `[Q5]` `[Q10]` |
| `items` | array | 是 | 至少 1 筆 `推導自[Q11]`(空陣列 → 總金額 0 → 依 C4 不得成立) |
| `items[].productId` | string | 是 | 商品編號 |
| `items[].quantity` | integer | 是 | 整數 ≥ 1;**同一 `productId` 合併後**不得超過 100 `[Q3]` `[Q11]` `[Q19]` `推導自[Q18]` |

**請求裡沒有、而且不准有的欄位:** `unitPrice`、`lineAmount`、`totalAmount`、`currency`、
`orderNumber`、`status`、`placedOn`。價錢一律由系統向商品價目系統查 `[Q6]`,客人送上來的
任何價錢欄位都必須被忽略或拒絕——否則客人可以自己決定要付多少錢。

```json
{
  "customerId": "C-100234",
  "items": [
    { "productId": "P-A001", "quantity": 2 },
    { "productId": "P-B007", "quantity": 1 }
  ]
}
```

**成功回應 `201 Created`** —— 逐欄:

| 欄位 | 型別 | 說明 |
|---|---|---|
| `orderNumber` | string | 對外單號,客人可報給客服 `[Q20]` |
| `customerId` | string | 同請求 |
| `status` | string | 恆為 `"PLACED"` `[Q16]` |
| `currency` | string | 恆為 `"TWD"` `[Q2]` |
| `totalAmount` | integer | 總金額,單位分,恆 > 0 `[Q11]` |
| `placedOn` | string | `YYYY-MM-DD`,不含時分秒 `[Q20]` |
| `items` | array | 合併後的品項,同商品只會出現一列 `[Q18]` |
| `items[].productId` | string | 商品編號 |
| `items[].quantity` | integer | 合併後的數量 |
| `items[].unitPrice` | integer | **成立當下的快照價**,單位分 `[Q6]` |
| `items[].lineAmount` | integer | `unitPrice × quantity`,單位分 |

```json
{
  "orderNumber": "ORD-8F3K7M2QX4",
  "customerId": "C-100234",
  "status": "PLACED",
  "currency": "TWD",
  "totalAmount": 39800,
  "placedOn": "2026-08-18",
  "items": [
    { "productId": "P-A001", "quantity": 2, "unitPrice": 15000, "lineAmount": 30000 },
    { "productId": "P-B007", "quantity": 1, "unitPrice":  9800, "lineAmount":  9800 }
  ]
}
```

**失敗回應** —— 統一形狀,兩欄:

| 欄位 | 型別 | 說明 |
|---|---|---|
| `errorCode` | string | 大寫底線常數,見下表 |
| `message` | string | 給人看的說明,**不得**被測試斷言內容(只斷言 `errorCode`) |

| `errorCode` | HTTP | 何時 | 來源 |
|---|---|---|---|
| `QUANTITY_OUT_OF_RANGE` | 400 | 任一品項數量 < 1 或 > 100 | `[Q3]` `[Q11]` `[Q19]` |
| `EMPTY_ORDER` | 400 | `items` 為空 | `推導自[Q11]` |
| `TOTAL_AMOUNT_NOT_POSITIVE` | 400 | 算出來總金額 = 0 | `[Q11]` |
| `CUSTOMER_NOT_FOUND` | 400 | 會員系統回「查無此人」 | `[Q10]` |
| `PRODUCT_NOT_FOUND` | 400 | 商品價目系統回「查無此商品」 | `[Q15]` |
| `UPSTREAM_UNAVAILABLE` | 503 | 會員或商品價目系統連不上 / 逾時 | `[Q15]` |

HTTP 狀態碼的挑選是 `本案自決`(見 §6-A4)。**不論哪一種失敗,一律不得建立訂單、不得留下殘骸** `[Q9]` `[Q15]`。

### 端點二:列出所有訂單 `GET /orders`

**請求:** 無參數。沒有排序、沒有篩選、沒有分頁 `[Q4]`(見 §5)。

**成功回應 `200 OK`** —— 一列逐欄:

| 欄位 | 型別 | 說明 | 來源 |
|---|---|---|---|
| `orders` | array | 全部已成立訂單;**未送出的內容不會出現在這裡** | `[Q4]` `[Q13]` |
| `orders[].orderNumber` | string | 單號,客服比對用 | `推導自[Q20]` |
| `orders[].customerId` | string | **一定有值** | `[Q15]` |
| `orders[].customerName` | string \| **null** | 即時向會員系統查;**查不到就是 `null`** | `[Q10]` `[Q15]` |
| `orders[].status` | string | 恆為 `"PLACED"` | `[Q16]` |
| `orders[].currency` | string | 恆為 `"TWD"` | `[Q2]` |
| `orders[].totalAmount` | integer | 總金額,單位分 | `[Q4]` `[Q2]` |
| `orders[].placedOn` | string | `YYYY-MM-DD` | `[Q4]` `[Q20]` |

```json
{
  "orders": [
    { "orderNumber": "ORD-8F3K7M2QX4", "customerId": "C-100234", "customerName": "王小明",
      "status": "PLACED", "currency": "TWD", "totalAmount": 39800, "placedOn": "2026-08-18" },
    { "orderNumber": "ORD-3RJ5W9TP6H", "customerId": "C-100777", "customerName": null,
      "status": "PLACED", "currency": "TWD", "totalAmount": 15000, "placedOn": "2026-08-17" }
  ]
}
```

需求方說「撈不到名字就顯示編號,不要整個畫面壞掉」`[Q15]`。合約把這句話**切成兩層**:
API 層回 `customerName: null` 並保證 `customerId` 有值;「顯示編號」是呈現層拿 `null` 時的行為。
**API 不得為了補這一格而把編號塞進 `customerName`** —— 那會讓下游分不出哪個是名字。

## 情境(Given-When-Then)

對應合約 §2 GWT 清單。

所有情境的幣別皆為 TWD,金額皆為**整數・分**。客人一律為 `C-100234`(會員系統中存在,名字「王小明」),
除非該條另行指定。

### 成功路徑

**S1 單一商品下單**
Given 商品價目系統中 `P-A001` 單價為 15000 分;And 會員系統中 `C-100234` 存在
When 以 `customerId=C-100234`、`items=[{P-A001, 2}]` 送出建立訂單
Then 回應 201;And `totalAmount` = 30000;And `items[0].unitPrice` = 15000;And `items[0].lineAmount` = 30000;
And `status` = `"PLACED"`;And `currency` = `"TWD"`;And `orderNumber` 非空。 `[Q1]` `[Q2]` `[Q6]`

**S2 多樣商品,總金額為各列小計加總**
Given `P-A001` = 15000 分,`P-B007` = 9800 分
When 送出 `items=[{P-A001, 2}, {P-B007, 1}]`
Then 回應 201;And `totalAmount` = 39800(= 15000×2 + 9800×1)。 `[Q1]`

**S3 同一商品加兩次,合併成一列**
Given `P-A001` = 15000 分
When 送出 `items=[{P-A001, 2}, {P-A001, 3}]`
Then 回應 201;And `items` **長度為 1**;And `items[0].quantity` = 5;And `items[0].lineAmount` = 75000;
And `totalAmount` = 75000。 `[Q18]`

**S4 數量剛好 100,可以成立**
Given `P-A001` = 15000 分
When 送出 `items=[{P-A001, 100}]`
Then 回應 201;And `totalAmount` = 1500000。 `[Q19]`

**S5 免費贈品與付費商品同一張單**
Given `P-A001` = 15000 分;And 贈品 `P-GIFT1` 單價為 **0 分**
When 送出 `items=[{P-A001, 1}, {P-GIFT1, 1}]`
Then 回應 201;And `items[1].unitPrice` = 0;And `items[1].lineAmount` = 0;And `totalAmount` = 15000。 `[Q19]`

**S6 訂單成立後商品調價,舊訂單金額不動**
Given `P-A001` = 15000 分;And 已用 `items=[{P-A001, 2}]` 成立訂單 `ORD-X`,`totalAmount` = 30000
When 商品價目系統把 `P-A001` 改成 20000 分;And 呼叫 `GET /orders`
Then `ORD-X` 那一列的 `totalAmount` 仍為 **30000**。 `[Q6]`
*(斷言只到 `totalAmount`:`GET /orders` 一列不含 `items`,也沒有訂單明細端點,`unitPrice` 在此無法觀測。總金額不變 + C1 已足以證明快照成立。)*

**S7 重複送出兩次,就是兩張單**
Given `P-A001` = 15000 分
When 用完全相同的內容連續送出兩次建立訂單
Then 兩次都回 201;And 兩個 `orderNumber` **不相同**;And `GET /orders` 看得到兩列。 `[Q12]`

**S8 列出所有訂單**
Given 已成立訂單 `ORD-1`(`C-100234`「王小明」,30000 分,2026-08-18)與 `ORD-2`(`C-100777`「陳大文」,15000 分,2026-08-17)
When 呼叫 `GET /orders`
Then 回應 200;And `orders` 有 2 列;And 每列都含 `customerName`、`status`、`totalAmount`、`placedOn` 四項;
And `ORD-1` 那列 `customerName` = `"王小明"`、`totalAmount` = 30000、`placedOn` = `"2026-08-18"`、`status` = `"PLACED"`。 `[Q4]` `[Q20]`

**S9 沒送出的內容不會出現在清單**
Given 系統從未收到任何建立訂單請求(客人只是在自己畫面上挑東西)
When 呼叫 `GET /orders`
Then 回應 200;And `orders` 為**空陣列**;And 系統中不存在任何草稿或購物車紀錄。 `[Q13]`

### 失敗路徑第 1 類:業務規則不通過

**S10 數量為 0**
When 送出 `items=[{P-A001, 0}]` → Then 回應 400;And `errorCode` = `QUANTITY_OUT_OF_RANGE`;And `GET /orders` 沒有新增任何一列。 `[Q3]` `[Q11]`

**S11 數量 101**
When 送出 `items=[{P-A001, 101}]` → Then 回應 400;And `errorCode` = `QUANTITY_OUT_OF_RANGE`;And 未建立訂單。 `[Q11]` `[Q19]`

**S11a 同一商品分兩列送出,合併後超過 100**
Given `P-A001` = 15000 分
When 送出 `items=[{P-A001, 60}, {P-A001, 60}]`
Then 回應 400;And `errorCode` = `QUANTITY_OUT_OF_RANGE`;And 未建立訂單。
`推導自[Q11][Q18]` —— 兩列各自都 ≤ 100,但 `[Q18]` 要求合併成一列 120,而 `[Q11]` 的上限是針對同一商品的總件數。
**這一條沒有釘死的話,兩份實作會一個放行、一個擋掉。**

**S11b 同一商品分兩列,其中一列數量為 0**
Given `P-A001` = 15000 分
When 送出 `items=[{P-A001, 0}, {P-A001, 5}]`
Then 回應 400;And `errorCode` = `QUANTITY_OUT_OF_RANGE`;And 未建立訂單。
`推導自[Q3][Q18]` —— 下限在**合併前**逐列判定,`0` 不得靠合併成 5 被洗掉。

**S12 品項為空**
When 送出 `items=[]` → Then 回應 400;And `errorCode` = `EMPTY_ORDER`;And 未建立訂單。 `推導自[Q11]`(推導步驟:空陣列 → 各列小計加總 = 0 → 違反「總金額 0 不得成立」)

**S13 整張單全是 0 元贈品**
Given `P-GIFT1`、`P-GIFT2` 單價皆為 0 分
When 送出 `items=[{P-GIFT1, 1}, {P-GIFT2, 2}]`
Then 回應 400;And `errorCode` = `TOTAL_AMOUNT_NOT_POSITIVE`;And 未建立訂單。
`推導自[Q11][Q19]` —— 需求方說這種單「不會發生」,但他也說 0 元不得成立;規則照樣要擋。

**S14 客人編號查無此人**
Given 會員系統回報 `C-999999` 不存在
When 以 `customerId=C-999999` 送出 → Then 回應 400;And `errorCode` = `CUSTOMER_NOT_FOUND`;And 未建立訂單。 `[Q10]`

**S15 商品查不到**
Given 商品價目系統回報 `P-ZZZZ` 不存在
When 送出 `items=[{P-ZZZZ, 1}]` → Then 回應 400;And `errorCode` = `PRODUCT_NOT_FOUND`;And 未建立訂單。 `推導自[Q15]`

**S16 已成立的訂單不得修改**
Given 已成立訂單 `ORD-X`,`items=[{P-A001, 2}]`
When 任何人(客人或客服)嘗試把數量改成 3
Then 系統**不提供任何達成此事的對外介面**;And `ORD-X` 的 `quantity` 仍為 2、`totalAmount` 不變。
斷言方式見 §9-A5(機械檢查:端點清單不得出現訂單的更新/刪除操作)。 `[Q14]`

### 失敗路徑第 2 類:外部系統回失敗

**S17 會員系統連不上**
Given 會員系統逾時或拒絕連線
When 送出合法的建立訂單請求
Then 回應 503;And `errorCode` = `UPSTREAM_UNAVAILABLE`;And **未建立訂單**;And `GET /orders` 沒有新增任何一列。 `[Q15]`

**S18 商品價目系統連不上**
Given 會員系統正常、商品價目系統逾時
When 送出合法的建立訂單請求
Then 回應 503;And `errorCode` = `UPSTREAM_UNAVAILABLE`;And 未建立訂單。 `[Q15]`

**S19 清單頁撈名字時會員系統連不上**
Given 已成立訂單 `ORD-1`(`C-100234`)與 `ORD-2`(`C-100777`);And 會員系統此刻連不上
When 呼叫 `GET /orders`
Then 回應 **200**(不是 5xx);And `orders` 仍有 2 列;And 兩列的 `customerName` 皆為 `null`;
And 兩列的 `customerId`、`totalAmount`、`placedOn`、`status` 皆正確。 `[Q15]`

### 失敗路徑第 3 類:系統中途失敗

**S20 訂單寫到一半,程序中斷**
Given `items=[{P-A001, 2}, {P-B007, 1}, {P-GIFT1, 1}]`(三列)
When 在訂單主體已寫入、第三列品項尚未寫入時,程序被強制中止(模擬當機 / 持久化中斷)
Then 系統恢復後呼叫 `GET /orders`,**看不到這張單**;
And 持久化層中不存在任何屬於這張單的殘留列(不得出現「有訂單、只有兩列品項」的半成品)。 `[Q9]`

**S21 持久化在提交點失敗**
Given 建立訂單的所有檢查都通過
When 寫入資料庫時拋出例外
Then 回應 5xx;And `GET /orders` 沒有新增任何一列;And 不留下任何殘骸。 `[Q9]`

需求方原話:「要嘛就是一張完整、東西都有的單,要嘛就當作沒發生過,不能有那種缺東缺西的半成品。」

**§1.2 Bounded Context 的架構後果:** 三個 context 落成 `order`(本案唯一實作)、
`membership`(僅 port + adapter)、`pricing`(僅 port + adapter)三個 package。
`order.domain` 不得 import 另外兩個 package 的任何型別;跨界資料一律在 `application` 層以本案自己的
型別接住(`customerId: string`、`unitPrice: Money`),不得讓外部系統的 DTO 滲進 domain。
