# ASSUMPTIONS —— 第四幕(實作)自決紀錄

規格沒寫清楚、或規格與釘死的驗收互相打架的地方,一律在這裡逐條交代。

---

## 一、wire 合約:規格 §1.2 與生成的驗收互相打架

驗收測試檔不得修改,而它釘住的 JSON 形狀與 SPEC.md §1.2 不一致。
以下四條一律**以驗收釘住的形狀為準**,並在此標明被犧牲掉的是規格的哪一句。

| 自決內容 | 依據 | 待確認點 |
|---|---|---|
| `GET /orders` 回**裸的 JSON 陣列**,不是 §1.2 E3 的 `{"orders":[...]}` | 驗收把回應讀成 `List<Map<String,Object>>`(`OrderAcceptanceTest#listRows`),包一層 `orders` 會直接解析失敗。驗收不得修改,所以只剩這一種形狀走得通 | 猜錯的話,任何照 §1.2 E3 寫的下游(前端、報表)會拿不到資料,得多剝一層;真正該修的是讓 §1.2 與生成器對齊 |
| `placedAt` 是**只有日期**的字串 `yyyy-MM-dd`,不是 §1.2 通用約定的「ISO-8601、帶時區」 | 驗收用 `LocalDate.parse(...)` 讀這個欄位。`LocalDate.parse` 走的是 ISO_LOCAL_DATE,餵它 `2026-08-19T14:11:22+08:00` 會在第 10 個字元炸掉。要讓驗收綠,這個欄位只能是日期 | 猜錯的話,「同一天的兩張訂單誰先誰後」查不出來,§1.2 E3 想要的時間點資訊在對外合約上整個消失;日後補時間欄位是破壞性變更 |
| `POST /orders` 的 request 是 `{"customer": <字串>, "items":[{sku, quantity, unitPrice, currency}]}` —— 沒有 `checkoutId`、沒有 `paymentId`、沒有 `shippingFee`、沒有 `customer` 物件(name/email/shippingAddress) | 驗收送的就是這個形狀,且它是唯一的下單入口。規格 §1.2 E1/E2 那兩段的欄位在這份釘死的合約裡送不進來 | 猜錯的話,§1.2 E1/E2 那套兩階段(先結帳、後下單)的合約整個對不上;B-1(商品主檔)解掉之後這份 request 本來就要重畫 |
| request 的 `customer` 字串當成**客戶的名字**(§1 GLOSSARY「名字」),對外回 `customerName` | 驗收送 `"customer":"王小明"` 並斷言列表的 `customerName` 等於 `"王小明"` —— 那是人名,不是編號。§1 GLOSSARY 的「客戶基本資訊」是 名字 + email + 收貨地址,這份合約只送得進其中的名字 | 猜錯的話(它其實是客人編號),列表顯示的是編號而不是姓名;而且 email 與收貨地址在本次實作中根本沒有落地,§1.2 E2 回不出那兩欄 |

## 二、規格沉默處的自決

| 自決內容 | 依據 | 待確認點 |
|---|---|---|
| 運費一律以 **TWD 0** 帶入訂單;訂單聚合根裡 C2 的公式本身仍然含運費那一項 | §6 A-7 說運費由呼叫方帶入,但這份釘死的 request 沒有運費欄位,呼叫方送不進來。把運費從公式裡拿掉會讓 C2 變成 [Q6] 那個已被 [Q26] 否決的舊語意,所以公式留著、值填 0 | 對外看到的 `totalAmount` 目前恆等於商品金額合計。B-3(運費怎麼算)裁決前,任何一筆真實訂單都會少收運費 |
| `currency` 從缺時視為 `TWD`;送進非 `TWD` 的值回 **400** | §1 GLOSSARY 金額「幣別固定 TWD」、§5 多幣別明確不在範圍。從缺視為 TWD 是因為系統只有這一種幣別,補上去不會有第二種解釋 | 若日後真的要多幣別(§5 說不做),「從缺 = TWD」這個預設會變成沉默的錯帳來源 |
| `quantity` 或 `unitPrice` **從缺(null)** 時回 400,跟送 0 / 負數同一類處理 | 規格只寫了值域被違反要 400(G16/G17),沒寫欄位從缺。從缺的請求同樣組不出一個滿足 C4/C5 的訂單,歸同一類最不會有第二種解釋 | 呼叫方分不出「我漏帶了欄位」與「我帶錯了值」;錯誤碼不同(`INVALID_AMOUNT` vs `INVALID_QUANTITY`)但 HTTP 狀態相同 |
| 客戶名字與 SKU **不做非空檢查** | 規格 §3 沒有任何一條契約管這兩個。不寫在規格裡的檢查就是自己加需求 | 空字串的名字會落地;若日後需要,那是一條新的契約,不是實作細節 |
| 成立日期用 **Asia/Taipei** 換算 | §6 A-11 明寫每月銷量以 Asia/Taipei 分月;成立日期跟著同一個時區才不會出現「報表算八月、訂單寫七月」 | 若日後有跨時區的營運據點,分月切法要重新裁決 |
| 錯誤回應用 §1.2〈錯誤共用格式〉`{"error":{"code","message","details"}}`;值域類的 `code` 為 `INVALID_QUANTITY` / `INVALID_AMOUNT` / `INVALID_CURRENCY` / `EMPTY_ORDER` | §1.2 給了信封格式,但沒有給值域類的錯誤碼(它只列了 `OUT_OF_STOCK` 等五個)。信封照抄,碼自決 | 這四個碼還沒進 §1.2,下游若照規格窮舉錯誤碼會漏掉它們 |
| 訂單識別碼用 **UUID v4**(`OrderId.newId()`) | §6 A-2 直接指定 | 同 A-2:若營運要人類可讀單號,格式要另訂 |
| 落地的資料表叫 `orders`(不是 `order`) | `order` 是 SQL 保留字,H2 建表會失敗。純粹是持久化細節,領域層看不到 | 無 —— 這一格不影響任何對外合約 |

## 三、實作範圍:做了什麼、沒做什麼

| 自決內容 | 依據 | 待確認點 |
|---|---|---|
| 只實作 `POST /orders` 與 `GET /orders` 兩個端點;**沒有**實作 §1.2 的 E1(`POST /checkouts`)、E4(`PATCH /orders/{id}/status`)、E5(`GET /reports/monthly-sales`) | 外圈驗收只有 G1 / G2 / G13 / G16 / G17 五條,全部只走這兩個端點。而且釘死的 `POST /orders` request 裡沒有 `checkoutId` —— 就算建了結帳作業聚合根,也沒有任何一條路徑走得到它,那是進不去的死碼 | 結帳作業、庫存、支付、報表這四塊在本次交付裡完全不存在。任何以為「規格 §1.2 五個端點都在」的下游都會落空 |
| 訂單狀態的變更做成**領域方法** `Order#changeStatusTo`,但**沒有** HTTP 端點 | C9 / C16 / C17 三條契約都守在訂單聚合根內,依工作契約第四節,內圈測試是這些契約唯一的載體 —— 不實作等於把三條可實作的契約丟掉。反過來,補上 PATCH 端點就是造一片沒有驗收看著的對外表面 | 狀態目前從外面改不動,每一張訂單都停在 `PLACED`。E4 要不要開、開了誰有權呼叫,依附 B-2(身分驗證,阻斷級) |
| 沒有發出 §4 的任何 Domain Event(`OrderPlaced` 等) | §4 自己寫著本次沒有訂閱者;而會用到事件的那幾條契約(C10/C12/C15)跨的是庫存與結帳作業,這次沒有那兩個聚合根,事件發出去沒有任何一端在等 | [Q28] 的上游下定單日後要接進來時,`OrderPlaced` 得補上;補的時候要一併決定它跟訂單落地是不是同一筆交易(§9 X-2 那一格至今未確認) |

## 四、明令留白的部分(**不是**自決,是規格擋著不准動)

以下三塊在需求方裁決前不得實作,本次一個位元都沒碰:

1. **訂單的重複送出 / 冪等處理** —— 沒有去重、沒有冪等鍵、沒有防連點;也沒有刻意允許重複。同一份 request 送兩次會產生兩張訂單。
2. **商品可售性檢查** —— 沒有下架檢查、沒有庫存檢查、沒有缺貨拒絕。這連帶使 §3 的 C1 與 C11 在本次沒有落地處。
3. **C8 相關的聚合邊界最終形態** —— 沒有新增聚合根、沒有搬動邊界。
   (順帶記一筆:工作契約說「C8 是標 ⚠️ 的那條跨聚合根契約」,但 SPEC.md §3 裡標 ⚠️ 的是 **C6 / C10 / C12 / C13 / C15**,C8 是「訂單成立後除狀態外不得修改」、守在訂單內。本實作照 SPEC.md 走,並把邊界一動不動地留著,兩種讀法下的指示都滿足。)

另外 §5〈明確不在範圍〉整節同樣沒做:分頁、搜尋、篩選、排序、折扣、運費規則、收款、通知、其他訂單狀態、修改與取消、收件資訊、權限分級、多幣別。§10 阻斷的 B-1(商品主檔)與 B-2(身分驗證)也沒有任何痕跡 —— `GET /orders` 一律回所有訂單,不做任何身分判斷。
