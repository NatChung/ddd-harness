## ⚠️ 主發現:規格與它自己的驗收互相打架,而規格輸了

`ASSUMPTIONS.md` 第一節逐條記著,而且是實作 agent **自己發現並寫下來的**:

| 規格 §1.2 說 | 釘死的驗收要求 | 被犧牲的是 |
|---|---|---|
| `GET /orders` 回 `{"orders":[...]}` | 裸的 JSON 陣列 | 規格 |
| `placedAt` 是 ISO-8601 帶時區 | 只有日期 `yyyy-MM-dd`(驗收用 `LocalDate.parse`) | 規格 —— **「同一天兩張訂單誰先誰後」在對外合約上整個消失** |
| `POST /orders` request 是 `{checkoutId, paymentId}` | `{customer:<字串>, items:[…]}` | 規格 —— **兩階段(先結帳、後下單)整套對不上** |
| 客戶 = 名字 + email + 收貨地址 | 只送得進一個字串 | 規格 —— **email 與收貨地址在本次實作中根本沒有落地** |

**它選了驗收,而且選對了**(驗收不得修改是硬規則),然後逐條寫明「被犧牲掉的是規格的哪一句」。

### 這條鏈怎麼斷的

```
規格說         POST /orders = {checkoutId, paymentId}
  ↓ 幕二        store 的 wire_contract 表達不了兩階段
                → agent 改用 E1 的欄位,並在 YAML 註解裡說明
  ↓            **註解在 import 時被丟掉**
  ↓ 幕三        生成器照 store 生,生出來的是單階段的形狀
  ↓ 幕四        實作 agent 看到規格說 X、測試要 Y,選了 Y 並寫進 ASSUMPTIONS
```

**規格在第二幕就輸了,而輸的那一刻沒有任何機械檢查在看。**
整條鏈上**只有最後一個 agent 發現並寫下來**,而它是靠人讀的 markdown。

→ **這是票 15 最強的一個證據**,而且比票 15 開票時掌握的更完整:
票 15 只量到「誠實寫在註解裡」,這一跑量到那個丟失**一路傳到了實作**,
並且**改寫了對外合約**。

## 這一跑買到什麼、沒買到什麼

**買到**:管線閉環了。一句話 → 30 題 → 550 行規格 → 5 條情境 → 9 條測試全綠 + 23 個 class。
`run_act4.sh` 的三樣設計(結構隔離內圈、雜湊防竄改、seam 由契約表指定)在真實資料上都生效。

**沒買到**:
- **「全綠」只證明了 1 條真情境。** 一個只讓 G16 過的實作也會全綠 —— 這次它做得多得多,
  但那是這個模型的行為,不是驗收逼出來的。
- **17 條 GWT 只有 1 條、17 條契約只有 8 條**走到了實作面前。
- **架構那 4 條是凍結骨架繼承來的**,不是這份規格生的(§9 的 10 條一條都沒落檔,票 16)。
- **沒有第二份實作。** MISSION 要的是「兩個模型的實作都能被同一套驗收判定」,這次只有一份。
