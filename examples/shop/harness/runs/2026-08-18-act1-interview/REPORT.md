## handoff 指定的三題

### 1. 完整度 —— 只靠問,問出幾條?

| | 情境數 | 說明 |
|---|---|---|
| 凍結 `SPEC.md`(人寫的) | 5 | 全是成功路徑,一條拒絕情境都沒有 |
| 訪談 r0(掉了第四輪) | 12 + 1 留白 | |
| 訪談 r4(補回第四輪) | 15 + 2 留白 | |

**訪談問出來的比人手寫的多三倍,而且多的那些是人手寫那份完全沒有的類別**:
拒絕情境(空單 / 數量 0 / 數量負 / 未登入)、不可變性(改單 / 取消)、
快照語意(調價不動舊單)、原子性(寫到一半掛掉)。

⚠️ **但這不等於訪談贏了。** 兩份規格的**交集近乎為零**:凍結那份談的是
「列表這一列長什麼樣」(姓名是 join 出來的、日期是 ISO),訪談那份談的是領域不變量。
**同一句原始需求,兩條路走出兩個不重疊的規格。** 這件事本身比條數有意思。

### 2. 正確性 —— 空骨架全紅 + OL1 全綠?

```
✅ 空骨架 → 4/4 紅        紅的是 ['S1','S10','S11','S2']
❌ OL1     → 0/4 綠       全紅
❌ 逐條可紅               不算數(見下)
```

- **第一段過,而且這段仍然有效** —— 它證明生成的驗收不是恆真的,與被測規格是哪份無關。
- **第二段全紅,原因 100% 是欄位名。** 每一條的失敗訊息都是 `but was: null` 或
  `Map.get(...)` 回 null。而 `list_row_exists` **先過了** —— POST 成功、列表撈到那一列,
  只有欄位查不到。**領域行為很可能是對的,但這個 harness 看不見。**
- **第三段不算數**,跑之前就寫下了:`BREAKS` 的 key 是 `S1`–`S5`,綁的是凍結那份的語意,
  而訪談那份的 S1–S5 是別的東西。**撞名不撞義。**

### 3. 漏了什麼、多編了什麼

**漏了什麼:比預期少得多,而且不是 prompt 的錯。**

我原本預測「列表顯示姓名還是編號」是追問表沒逼出來的洞。查證後**預測錯了**:
Q19 問得比凍結 SPEC 還準(同時問了「存哪裡」和「要看的時候怎麼辦」),
需求方也答了。r4 版拿到答案後,**還是把「列表要不要額外撈姓名顯示」列為未答**
—— 因為他答的是「訂單上不存姓名」,沒答「列表要不要去撈」。

**這兩件事確實是兩件事,而訪談 prompt 分得出來。** 凍結那份 SPEC 是作者直接決定的
(沒有訪談,所以沒有這個區分)。→ **完整度這一題的真正答案:訪談沒漏,它把那個洞
正確地標成洞了。**

⚠️ **但完整度這個數字要打一個折(2026-08-18 稍晚查到)。**
它把「訪談問出來的」跟「**訪談者自己餵進去、對方沒否認的**」算在同一邊了。
實例就在這份產出裡:`SPEC-draft.md` 寫「唯一例外是 S9 的 100/120,那組數字是
**他在 Q9 親口確認的**」—— 而需求方的回答全文是「不會,舊的那筆單就是顯示他當時
下單的價格」,**從沒說過 100 或 120**。那組數字是訪談者自己放進誘導式提問裡的
(「舉例:客人昨天用 100 元買了一件,今天你們把這個商品改成 120 元」)。
凍結的 SPEC 裡也沒有 100/120(它用 1500/5100)。
→ **來源標記分不出「他真的說了」與「我餵給他、他沒否認」**,
細節與另一種形狀見 `.scratch/ddd-harness/issues/03`。

**多編了什麼:這份規格自己回答得了 —— 但只在「有沒有標來源」這一層。**
每條都標了出處,`本案自決` 集中在 §ASSUMPTIONS(r0 五條、r4 七條),全是技術判斷
(小數位、時間精度、原子性、單號格式、HTTP 形式)。**業務政策一條都沒自決。**
→ 標記制度讓「多編了什麼」變成可機械抽查的欄位,不是要靠人通讀比對的事。

## 四站,四種掉法

這是這次跑最主要的產出。**同一個系統,同一個早上,同一種病的四個變種。**

| # | 掉在哪 | 形狀 | 偽裝成什麼 |
|---|---|---|---|
| 1 | 第一幕內部,最後一輪 | 需求方答了,**orchestrator 的迴圈把它當死碼丟掉**,訪談者沒收到 | **「談完了」** |
| 2 | 第一幕落檔 | 檔案寫成了,回報的 process 死了(`final.json` 0 位元組) | **「跑掛了,要重跑」** |
| 3 | 我抄 r0 | 我在 06:37 抄走,而寫入到 06:39:44 才停 | **「拿到了」** |
| 4 | 我抄 r4 | 同 #3,而且**我先用一個壞掉的檢查證明了「process 已經死了」** | **「它掛了,趕快搶救」** |

**共同形狀:拿「檔案存在與否」當完成訊號。** 檔案存在只證明有人開始寫。

### 第 4 種:我自己示範了「工具訊息會逼出錯誤結論」

我跑 `ps aux | rtk proxy grep -c "[c]laude -p"` 拿到 `0`,據此判定 process 死了、
檔案是遺體,於是立刻搶救並 commit 了一份**寫到一半**的 r4(35692 B,
最終是 37374 B),commit message 還寫著「process 又是死在回報那步」。

實際上那個 job **好好地跑完了**(`rc=0`、`r4.json` 3785 B、11 turns / $3.50)。
`rtk proxy` 放在管線右側收 stdin 時不成立,那個 `0` 是**工具的假陰性**,不是事實。

→ 兩條:
1. **判定「死了」要看 job 自己的退出碼,不要看 `ps` 的間接證據** ——
   尤其那個 `ps` 還經過一層會改寫指令的 hook。
2. 這正是第二幕那條教訓的另一面:上次是**工具訊息逼出 agent 指示外的產出**,
   這次是**工具訊息逼出我一個錯誤的結論,而我照著它動作了**。
   兩次都是「唯一的判準來自工具,而工具是錯的」。

### 第 1 種最貴,細節見 `FINDING-transport-loss.md`

需求方對 Q16–Q20 的完整回答**白紙黑字在 `transcript.md` 裡**(段 19),
但從沒進到訪談者的 session。

⚠️ **更正**:我第一版把原因寫成「orchestrator 死在轉交」——**錯了**。
實際是迴圈的 off-by-one:問 N 輪、只轉交 N-1 輪,最後一次的 `message = answers`
是死碼。**每一次跑都會丟掉最後一輪,不是這次運氣不好。**
更正讓事情更嚴重,不是更輕:**偶發的崩潰會自己現形,結構性的丟棄不會。**

後果:

- **一條假阻斷。** Q18 被標成「阻斷級,不得實作商品可售性檢查」,
  而他實際說的是「**不用擋,庫存這件事這個系統不用管**」。
  **假阻斷比漏一條規格貴** —— 它讓下游停在那裡等一個已經到了的裁決。
  而它跟真阻斷長得一模一樣:兩者都是「沒說 + 猜錯有人賠錢」。
  **規格沉默分不出「他沒說」與「他說了但沒送到」。**
- **`transcript.md` 看起來完整無缺。** 60KB、兩側俱全、答案就在裡面。
  要發現這件事得去數「哪一段在誰的 session 裡」,而 transcript 的格式
  (`## [user]` / `## [assistant]` 交錯)**恰好把這個資訊抹掉了**
  —— 段 19 標的是 `[assistant]`,跟訪談者的發言同一個標籤。
  → **transcript 要記 session 邊界,否則它會把「送掉了」渲染成「談完了」。**

### 補跑第四輪買到了什麼(意外拿到的對照組)

⚠️ **對照有瑕疵**:訪談者是在**寫完規格、被告知訪談結束之後**才收到第四輪的。
所以這個差集是「事後補一輪」的價值,不是「不中斷的訪談」的價值。

| | r0 | r4 |
|---|---|---|
| 情境 | 12 + 1 留白 | 15 + 2 留白 |
| 契約 | C1–C11 | C1–C14 |
| 架構規則 | 5 | 10 |
| 內部矛盾 | **無** | **1 條**(需裁決) |
| 阻斷級 | 2(其中 1 條是假的) | 3(全真) |

新增的四條:S11(下架照樣成立)、S12(訂單不存姓名電話地址)、
S14(單號不重複)、S17(依單號查 —— 留白)。

**最有意思的是那條內部矛盾**,r0 說「無」:
`[Q14]`「不用搜尋、不用篩選、也不用排序」對上 `[Q16]`「客人打電話進來,我就是用那個單號去查」。
訪談者**沒有替他調和**,兩種讀法都寫出來、標明「這兩種讀法會做出不同的系統,我不替他選」,
S17 留白不實作。→ **一輪訪談不只多幾條規格,它會讓既有的答案彼此打架。**
少收一輪,少的不只是那一輪的內容,還有它跟前面所有答案的交互。

## 第二幕:12 條進去,4 條出來 —— 而 agent 自己把帳算清楚了

`9 turns / 6.2 分 / $2.57`,import 印 ok。

它交的報告**以覆蓋率開頭,不是以 ok 開頭**,逐條列出 8 條落不了檔的情境
**與擋住每一條的那個約束**,並且明說它拒絕了三種可以湊綠的做法
(S5 填成 quantity 1、S4 硬塞一項商品、S3 省掉夾帶值)。
**沒有人要求它揭露這些** —— 完成的定義只是「import 印 ok」。

### 預測命中率:13 條裡 11 條精準,1 條機制錯,1 條沒想到

| 情境 | 預測 | 實際 |
|---|---|---|
| S1 S2 S11 | 進得去 | ✅ |
| S3 S7 S8 S9 S12 | 進不去(逐條理由) | ✅ 理由一致 |
| **S5 S6** | **`step_item` 的 `CHECK (quantity > 0)` 擋死** | ✅ **一字不差同一條約束** |
| S13 | 不該出現 | ✅ 沒出現,agent 另外說明了為什麼 |
| S4 | 「半個」——零項明細的 step 寫得進去 | ❌ **錯**:importer 另有守衛要求 `items` 非空 |
| S10 | 進不去 | ⚠️ agent 做了**代理編碼**並揭露 |

### 主結論:守衛與覆蓋率在這裡互相扣分

> **schema 的 CHECK 是為了「讓不合法的資料寫不進去」而設的。
> 而負面情境的 fixture,本質上就是不合法的資料。**

`CHECK (quantity > 0)` 同時擋掉兩種東西:手滑寫錯的規格,和「數量必須 ≥ 1」這條規則的驗收。
**凍結那 5 條情境上永遠量不到 —— 那 5 條裡一條負面情境都沒有。**

### 第三種假驗收:語意上不可能失敗的情境

S10 進去了,長這樣:同一個 `product_id` 送兩筆訂單(10000 與 12000),
斷言第一筆的 `total_cents` 仍是 10000。

**這條斷言不可能因為它宣稱要測的原因而失敗** —— 沒有任何東西調過價。
agent 在註解與 `given_when` 裡都揭露了這是代理編碼,處置是誠實的,
**但 harness 沒有任何機械手段擋得住它**。

這是第三個形狀的假驗收,而且 **mutation testing 也抓不到**:
不是「程式沒被測到」,是**情境的語意被誤述了**。
前兩個已知陽性(HL1 恆真、HL2 恆真)都是斷言層的,這個是**規格層**的。
→ 假驗收偵測要再加一格,而那一格目前是空的。

## 第三/四幕:合約被切成兩半,而兩半碰不到面

`gen_acceptance.py` 裡:

- **送單與取列表的管線是寫死的**(`body.get("orderId")`、`filter(r -> ...r.get("orderId"))`)
  —— 規格作者看不到、改不動;
- **斷言讀哪個欄位從 store 來**(`customer_id` / `status` / `total_cents` / `created_at`)
  —— 自由文字,想寫什麼寫什麼;
- **schema 裡沒有任何地方能宣告「列表的一列長什麼樣」。**

於是兩半不可能對得起來,除非規格作者剛好猜中生成器心裡那組名字。

**為什麼凍結那 5 條量不到:** 那份 `SPEC.md` 把 response JSON 範例**直接寫在散文裡**
(`orderId` / `customerName` / `statusLabel` / `totalCents` / `placedAt`),agent 照抄就對了。
→ **是散文裡的一段範例在補 schema 的洞,而不是 schema 自己守得住。**
訪談那份把 HTTP 形式明標 `本案自決`,洞就現形了。

這是 `list_field_*` 那三個 kind 的設計缺口:吃 `field` 當自由文字,
卻沒有對應的「這個欄位存在、而且叫這個名字」的宣告點。

## 落到第五幕的原料(洞 → 搬階 → 改 harness)

依「改了會複利」排序:

1. **`orchestrate.py` 每一輪的發問與回答各自落檔,轉交前後各記一次。**
   現在的形狀是「答完 → 轉交」一氣呵成,掛在中間時**沒有任何一方知道有東西掉了**。
2. **transcript 格式要記 session 邊界。** 不記的話它會把「送掉了」渲染成「談完了」——
   這次就是這樣差點過關。
3. **schema 要有辦法表達「這是負面情境,fixture 本來就違法」。**
   否則負面情境永遠落不了檔,而那正是訪談最會問出來的類別。
   (方向:負面 fixture 走另一組表 / 另一個 kind,CHECK 放寬的範圍要明說。)
4. **schema 要有「列表一列的形狀」的宣告點**,把生成器寫死的那半收進 store。
5. **假驗收偵測補「規格層」那一格** —— 代理編碼(S10 那種)目前只靠 agent 自願揭露。
