## 預測一:schema 表達不了訪談問出來的多數情境

`schema.sql` 是從凍結那 5 條倒推出來的(決定 10:第三幕倒推)。它的形狀是:
**步驟 = 送出一筆訂單**(alias / customer_id / items),**斷言 = 6 個 kind**
(`status_is` / `order_id_not_blank` / `list_row_exists` / `list_field_equals_text`
/ `list_field_equals_number` / `list_field_is_iso_date`)。

逐條預測(訪談的 S1–S13):

| 情境 | 預測 | 理由 |
|---|---|---|
| S1 單一商品成立 | ✅ 寫得進去 | 正好是凍結 SPEC 情境 1 的形狀 |
| S2 多明細加總 | ✅ | `list_field_equals_number` on totalCents |
| S3 總金額不接受人為指定 | ❌ **表達不了** | 要在請求裡「夾帶」一個欄位。步驟只有 customer_id + items,夾不進去 |
| S4 空單拒絕 | ⚠️ **半個** | 零項明細的步驟寫得進去(step_item 是另一張表),`status_is 400` 也寫得進去。但生成器會不會產出「預期失敗」的呼叫,沒驗過 |
| S5 數量 0 拒絕 | ❌ **schema 擋死** | `step_item` 有 `CHECK (quantity > 0)` |
| S6 數量負數拒絕 | ❌ **schema 擋死** | 同上 |
| S7 未登入拒絕 | ❌ | 步驟沒有「登入狀態」這個維度,customer_id 是必填非空 |
| S8 改已成立訂單 | ❌ | 步驟只能「送出一筆訂單」,沒有第二個動作 |
| S9 取消已成立訂單 | ❌ | 同上 |
| S10 調價後舊單不動 | ❌ | 沒有「改商品價格」這個動作 |
| S11 查看所有訂單 | ✅ | `list_row_exists` |
| S12 寫到一半掛掉 | ❌ | 沒有故障注入 |
| S13 重複送出 | **不該出現** | 散文明寫「不得實作」。若 agent 產出來了,是它把「寫在檔案裡」當成「要做」 |

**預測落點:12 條進得去 3–4 條(S1 / S2 / S11,S4 看生成器)。**

### 這條預測要是中了,量到的是什麼

不是「訪談產出太多」或「schema 太小」,是這件事:

> **schema 的 CHECK 是為了「讓不合法的資料寫不進去」而設的。
> 而負面情境的 fixture,本質上就是不合法的資料。**

`CHECK (quantity > 0)` 同時擋掉了兩種東西 —— 手滑寫錯的規格,和「數量必須 ≥ 1」
這條規則的驗收。**第二幕的守衛與第三幕的覆蓋率在這裡互相扣分**,而這在凍結那
5 條情境上永遠量不到:那 5 條裡一條負面情境都沒有。

## 預測二:第四幕的三段驗收,前兩段的意義不對稱

`acceptance_gwt.py` 三段:空骨架全紅 / OL1 全綠 / 逐條可紅。

1. **空骨架全紅 —— 預測會過,而且這段仍然有效。** 它證明生成的測試不是恆真的,
   跟被測規格是哪一份無關。
2. **OL1 全綠 —— 預測會紅,而且是預期中的紅。** OL1 是照凍結那份 SPEC 寫的,
   它沒有實作任何拒絕邏輯。訪談那份要是問出了「空單要擋」而 OL1 沒擋,紅的是
   **兩份規格的差集**,不是管線。
   → 這一段的紅**不得**拿來當「管線壞了」報。
3. **逐條可紅 —— 預測會給出無法判讀的結果。** `BREAKS` 表的 key 是 `S1`–`S5`,
   綁的是**凍結那份**的語意(S3 = customerName 的 join、S4 = 加總、S5 = ISO 日期)。
   訪談那份的 S3/S4/S5 是「金額不可指定 / 空單 / 數量 0」。**名字撞了、語意沒撞。**
   → 這一段的任何結果都不算數,除非先把 BREAKS 改成跟著情境語意走。

## 預測三:完整度 —— 訪談漏了凍結那份有的東西

凍結 SPEC 的情境 3:**列表要顯示顧客姓名,而訂單只持有 CustomerId,姓名是 join 出來的。**

訪談那份:詞彙表只有「客人編號」,`[Q2]` 記的必看資訊寫「是哪個客人下的」——
**編號還是姓名,沒有問出來。** 而 Q19(訂單記不記姓名/電話/地址)因訪談中止未答,
被歸到「不在範圍」。

**預測:這是訪談 prompt 的追問表沒逼出來的第一個洞。**
形狀是:「這個欄位給人看的時候長什麼樣」與「這個欄位存在哪裡」是兩件事,
追問表問了第二件,沒問第一件。

待驗:回 `transcript.md` 確認 Q2 的原話,不要只憑 SPEC-draft 的摘要就下結論。

1. **完整度** —— 只靠問,問出幾條情境?(訪談 12 vs 凍結 5,但要看**差集兩邊**)

   (S12 原子性、HTTP 動詞、小數 2 位)算不算「多編」。

   **這份規格是自己回答得了的** —— 那本身就是一個結果:標記制度讓這題可機械抽查。
