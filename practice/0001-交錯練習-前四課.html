交錯練習 01 · DDD × Agent Harness

沒有人會告訴你該用哪一課

六個情境,工具自己挑。

這份跟前面幾課不一樣

沒有選項,沒有即時回饋。前面幾課的練習都在「你已經知道這課在教什麼」的前提下作答, 那練的是套用;真正難的是認出這是哪一題——沒有人在旁邊說「這題用 Bounded Context」。

每題底下有折疊的診斷。先自己寫完再展開,先看答案的話這份練習就一點用都沒有, 它唯一在測的就是「你有沒有自己想出來」。

你手上有四個工具:

  • Ubiquitous Language —— 一個詞一個意思,含糊的詞拆成兩個
  • Bounded Context —— 兩套語言各自成立,畫界並定義接點
  • Given-When-Then —— 把「做對了沒」變成不用討論的判定
  • Aggregate / invariant —— 把規則變成違反就爆炸的程式碼

也可能不只一個、或四個都不是(有些問題不是模型問題)。每題都要說出 為什麼不是另外那幾個——那句才是重點。

1

客服在系統上看到一張訂單,跟客人說「還在處理中」。客人打去倉庫問,倉庫說 「這張早就處理完了,昨天就交給貨運了」。客人投訴。

你去看,兩邊都沒看錯:客服的畫面顯示「處理中」,倉庫的畫面顯示「已完成」。

▸ 看診斷(先自己寫完)

拆詞,不是畫邊界。「處理完」在這裡是同一條時間線上的兩個時刻: 出貨完成 → 配送 → 送達。倉庫講的是前面那個點,客服講的是後面那個點。 一條線上的兩個時刻被同一個詞蓋住 → 拆成兩個詞(例:已出貨 / 已送達),讓兩個畫面都顯示得出自己在講哪一個。

為什麼不是 Bounded Context:畫邊界的前提是兩套語言各自獨立演化, 硬合併會兩邊都壞。這裡不是——倉庫跟客服對「出貨」「送達」的理解完全一樣, 他們只是各自把其中一個叫成「完成」。拆完詞之後,兩邊講的是同一件事,沒有邊界可畫。

快篩:如果把兩個意思都攤開寫在紙上,兩邊都會說「對,這兩個都對,我只是習慣講其中一個」 → 拆詞。如果兩邊會為了哪個定義才對而吵起來 → 可能真的是邊界。

2

行銷系統跟財務系統都有「客戶」這張表,有人提議合併成一份主檔。你去問了兩邊:

  • 行銷的客戶:只留過 email 的訂閱者也算;同一個人有三筆記錄很正常,之後再合併; 刪掉沒差,重新蒐集就好。
  • 財務的客戶:一定要有統編或身分證字號;絕對不能合併——發票已經開出去了; 七年內不能刪。
▸ 看診斷(先自己寫完)

這題才是真的 Bounded Context。跟第 1 題對照著看:兩邊的「客戶」是 兩條平行、各自獨立演化的線,而且規則直接互斥(可合併 vs 絕不可合併)。 硬做成一份主檔,不是兩邊都得到想要的,是兩邊都壞掉——財務的不可合併會擋住行銷的日常作業, 行銷的自由刪除會讓財務違法。

產出該長的樣子:兩個 context 各自的「客戶」定義 + 接點。接點的測試是 跨界之後意思不變——這裡通常是一組對照(行銷的 contact id ↔ 財務的 customer id), 以及「什麼時候一筆行銷客戶會升格成財務客戶」(第一次成立訂單時)。 注意接點不能是「客戶」這個詞本身。

為什麼不是拆詞:拆詞的產出是兩個新詞、大家從此都用新詞。這裡做不到—— 行銷部門不會改口叫「行銷聯絡人」,財務也不會。兩邊在各自的地盤裡叫「客戶」都是對的, 這正是邊界存在的意思。

3

PM 寫的驗收條件:「庫存不足時,要適當地提示使用者。」

Agent 做出來了:結帳按鈕變灰,旁邊一行小字「此商品目前無法購買」。 PM 看了說不對。你問哪裡不對,PM 說「就是感覺不對,應該要更清楚一點」。

▸ 看診斷(先自己寫完)

判定漂移。「適當地」「清楚一點」不是驗收條件,是感想—— 沒有任何實作能被這句話判定為通過,所以 agent 做什麼都可能被打回, 而且被打回時它學不到東西(下一版只是換另一種猜法)。

產出:把它變成不用討論的 Given-When-Then。例:

Given 商品 A 的可售庫存是 0
When 使用者把 A 加入購物車並前往結帳
Then 結帳按鈕不可點擊
 And 商品列顯示「補貨中,預計 3 個工作天」
 And 提供「到貨通知我」按鈕

三條 Then 都是機械可判定的。PM 可能對其中一條有意見——那正是收穫, 爭論從「感覺不對」變成「第二條的文案要改」,那個爭論兩分鐘就結束了。

順帶一提:寫的過程八成會冒出「可售庫存」到底扣不扣掉別人購物車裡的量—— 那是第 1 課的問題,在這裡被逼出來。這很正常,寫驗收常常會揪出沒定義的詞。

4

月底對帳,發現有 12 張訂單的總金額跟明細加總對不起來。追下去:三個月前加的一支 「批次套用折扣」的排程,直接跑 UPDATE orders SET total = ...,沒有動明細。

有人提議:在那支排程裡補上重算明細的邏輯,並且在 code review 的檢查清單上加一條 「不可直接 UPDATE 金額欄位」。

▸ 看診斷(先自己寫完)

invariant 沒有被程式碼守住,只被人的自律守住。提議的兩個修法都只治這一次: 補上重算邏輯治的是這支排程,加檢查清單治的是「下次有人記得」。 第三支排程、或某個 agent 寫的一次性 script,會再犯一次。

產出:寫下 invariant(訂單總額 = 明細加總 − 折扣,任何時刻), 指出 Aggregate Root(Order),然後列出目前所有繞過 root 的路徑—— 直連資料庫的排程只是其中一條,通常還有 public setter、回傳可變 list 的 getter、 DBA 手動改。修法是把那些路徑一條條堵掉,讓折扣只能經由 order.applyDiscount(...) 這種會順便重算的方法發生。

為什麼不是驗收條件的問題:寫一條 Given-When-Then 來測「total 等於明細加總」當然可以, 也該寫。但測試只在你想到要測的路徑上跑;invariant 要的是沒有路徑。 兩者一起用:型別堵路,測試守回歸。

值得注意:這題也可以順手問「那 12 張已經錯掉的訂單怎麼辦」—— 資料修補跟結構修補是兩件事,別混在同一張票。

5

要把通知的寄送商從 A 換成 B,估了兩天。實際做的時候發現: 下單、退款、出貨這幾支流程的程式碼裡,到處都是 A 家 SDK 的型別 (ASendResult、ATemplateId),連「訂單成立」的流程都要 import 它。 兩天變成兩週。

▸ 看診斷(先自己寫完)

相依方向錯了(第 5 課)。「換一家寄信的」本來應該是最外層的事, 卻能讓 use case 的程式碼跟著改——因為內層 import 了外層的型別。

產出:在 Use Cases 層定義自己的介面與資料結構 (NotificationSender、以及一個屬於你自己的通知資料結構), A 家與 B 家各寫一個實作放在外層。內層永遠不知道誰在寄。 再加一條機械檢查:內層的檔案 import 到任何 SDK 套件就 fail。

這題的陷阱:它看起來像單純的重構或技術債,不像「模型問題」, 所以很容易被歸類成「沒有工具可用,認命做兩週」。能不能認出它有結構性解法, 就是這題在測的事。另外注意兩天估成兩週的根因不是估錯,是 沒有人知道爆炸半徑有多大——分層存在的意義就是讓那個半徑事先算得出來。

6

一張票:「優化結帳流程」。做了三週還沒收掉,每次 demo,PM 都說「這不是我要的」。 工程師覺得每次都在改需求,PM 覺得需求一直沒被理解。

▸ 看診斷(先自己寫完)

這題沒有單一正解,它在測你會不會停下來問「這是哪一種問題」。 三個診斷都成立,而且可以並存:

  • 「優化」沒有定義(第 1 課)。快一點?步驟少一點?轉換率高一點? 三個目標會做出三套完全不同的東西,而且互相衝突。
  • 沒有驗收條件(第 3 課)。「這不是我要的」之所以能一講三週, 是因為沒有任何一句話能判定做完了沒。
  • 票太大。三週沒收掉、每次 demo 都整批被否,通常代表這張票包了好幾件事。 第 4 課給了一個切法:一張票只碰一個 Aggregate;第 5 課給了另一個: 說得出動哪幾層。兩個都答不出來的票,先拆再說。

能不用工具的部分:也有一種可能是 PM 自己還不知道要什麼,那就不是模型問題, 是需求探索的問題——先做一個能點的原型,比寫任何文件都快。 認出「這題不需要我手上的工具」也是正確答案,只要說得出為什麼。

真正的紅旗:「每次都在改需求」與「需求一直沒被理解」是同一個現象的兩種說法。 只要驗收條件寫得出來,這兩句話就會同時消失——不是因為誰被說服了, 而是因為爭論的對象從人的意圖變成了紙上的條件。

全部寫完之後,回頭看一次
  • 第 1 題跟第 2 題你選了同一個工具嗎?那兩題長得很像,但一題是拆詞、一題是畫邊界。 如果選一樣,值得重讀 參考卡 01。
  • 「為什麼不是另外那幾個」那一格,你有沒有偷懶跳過? 挑對工具可能是運氣,說得出為什麼不是別的才是能力。
  • 有沒有哪一題你想用兩個工具?那通常是對的——第 3 題會逼出第 1 課的問題, 第 4 題該同時用 invariant 與測試。真實情境很少只需要一個。
  • 第三格你寫的是具體產出還是做法描述?寫「我會定義清楚」不算, 要寫出那個定義本身。
