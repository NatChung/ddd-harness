# ADR 0004 — wire shape 歸規格擁有;既有實作不再是綠燈預言機

## Status

Accepted(2026-08-18)

## Context

2026-08-18 把訪談產出的規格跑完第三、四幕,第二段驗收(`layered/OL1-integration` 全綠)
**0/4 綠**。查失敗訊息,每一條都是 `but was: null` 或 `Map.get(...)` 回 null ——
**全部是欄位名對不上,沒有一條是領域行為不合**。而 `list_row_exists` 先過了:POST 成功、
列表撈到那一列,只有欄位查不到。**命名的分歧把領域的分歧整個蓋住了。**

agent 沒做錯。訪談那份規格把 HTTP 形式明標為 `本案自決`,從沒指定過 JSON 欄位名
——它只能自己取,取了 snake_case(`customer_id` / `total_cents` / `created_at`),
而凍結的 app 回的是 camelCase(`customerName` / `totalCents` / `placedAt`)。

再查生成器,發現兩側是**非對稱**的:

- **請求那側全寫死**(`gen_acceptance.py:120-127`):`customerId` / `items` / `productId` /
  `quantity` / `unitPriceCents` / `currency` 是樣板常數,store 的 snake_case 欄位由生成器翻譯;
- **回應那側全自由**:`list_field_*` 的 `field` 是自由文字,想寫什麼寫什麼。

**兩側都沒有被宣告,只是一邊寫死、一邊放任。** 而 schema 裡沒有任何地方能宣告
「列表的一列長什麼樣」。

⚠️ 凍結那份規格之所以量不到這件事,是因為它把 response JSON 範例**直接寫在散文裡**
(`SPEC.md` L27–L37),agent 照抄就對了 —— **是散文裡的一段範例在補 schema 的洞,
不是 schema 自己守得住。**

一開始想的修法是「加一個 `list_row_field` 宣告表」。**那修不好。** 加了之後 agent 仍會
宣告 `customer_id`、斷言 FK 得過、import 印 ok,跑起來一樣全紅 —— 宣告點只擋得住**內部
不一致**,擋不住**跟實際 app 的分歧**。真正沒定的是所有權。

## Considered Options

1. **(採用)規格擁有** —— 規格自決並寫成合約,生成的驗收就是合約,實作照做。
2. **實作擁有** —— store 宣告「這份 spec 綁的是哪個既有 API」,欄位名從那裡來。
3. **兩層拆開** —— 領域斷言(總金額 = Σ)與 wire 斷言(那個數字在 JSON 裡叫什麼)分成
   不同的 kind,前者跨實作重用,後者明綁實作。

## Decision

**wire shape 歸規格擁有(選項 1)。** 規格必須把自決的 wire 形狀逐欄寫成合約;store 增
宣告表;生成器**兩側**都從那裡讀,不再寫死請求樣板。

理由是 MISSION 直接要求的那條:

> 拿同一份規格餵給兩個不同的 model,兩邊的實作都能被**同一套驗收**明確判定通過或不通過。

wire shape 不由規格固定的話,兩個模型會各取各的欄位名,**兩邊都不會過**,那套驗收就
判定不了任何事。**所以選項 1 不是偏好,是那條目標的前提。**

**選項 2 不採**:它把 harness 變成「對既有 API 寫測試」的工具,與量「規格→實作漂移」
的目的相反。

**選項 3 是對的方向但不是現在做。** 它點到一個真的混淆:`list_field_equals_number` 同時
承載「總額算對了」(領域)與「那欄叫 total_cents」(wire),兩個不同尺度擠在一個 kind 裡。
但拆它會讓本次範圍膨脹,而且選項 1 做完之後才看得出拆的價值。

## Consequences

### 一、洞在第一幕,不在 schema

規格把 HTTP 形式標 `本案自決` 是**對的** —— 需求方不懂技術,問他 JSON 欄位名沒有意義。
但**自決完必須落成合約**。現行 `SPEC-draft.md` 的 ASSUMPTIONS 只記了 `POST /orders` /
`GET /orders`,**沒記欄位名**。所以訪談 prompt 的產出要求要加一條:
**wire shape 的自決要逐欄寫明。**

### 二、「OL1 全綠」對新規格永久不適用,不要發明便宜的代用品

`harness/acceptance_gwt.py` 的第二段原本買的是**可滿足性** —— 第一段(空骨架全紅)
只證明驗收不是恆真,不證明它有可能綠。一套永遠不可能綠的驗收跟恆真的一樣沒用
(鐵律:綠 ＋ 逐條可紅)。OL1 是照另一份 wire 合約寫的,新規格不可能對著它綠。

處置是 **D + B**:

- **D**:把凍結那份的 wire shape 命名成一個**合約**;**宣告同一個合約的規格才拿 OL1 當
  綠燈預言機**。這幾乎免費,而且保住的是**生成器唯一的迴歸網**(凍結 5 條 + OL1 的 7/7)
  —— 拿掉就再也沒有「改生成器有沒有弄壞既有行為」的快速判準。
- **B**:其他規格的可滿足性**由第四幕證明**(agent 照規格實作,綠了就是可滿足)。

**刻意不採「靜態自洽檢查」當代用品**(例如「同一請求不能同時斷言 201 與 400」):
它會給人「第二段還在」的錯覺,但它證明的是「斷言之間不打架」,**不是「有東西能滿足它」**。
兩者差很遠,而混為一談正是這條線上反覆踩的那種洞。

### 三、報表要能印「不適用」,而不是印「失敗」

`acceptance_gwt.py` 現在對這種情況印 `❌ OL1 → 4/4 綠  綠的是 []`,讀起來像壞了,
實際是不適用。**這跟 transcript 把「送掉了」渲染成「談完了」是同一種病** ——
報表把「不適用」渲染成「失敗」,而**失敗會被拿去修**。第二段要能印出第三種結果。
