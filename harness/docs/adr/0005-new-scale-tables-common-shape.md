# ADR 0005 — 新尺度的表:共同形狀,以及「不適用」不算「通過」

## Status

Accepted(2026-08-18)

## Context

票 06 與票 08 各自要往 `schema.sql` 加一張表:

- **`domain_contract`** —— §3 領域契約(C1…Cn)目前**一張表都沒有**。大尺度有
  `architecture_rule`(配了 `gen_archunit`),小尺度有 `wire_contract`(生成器兩側都讀它),
  **微尺度什麼都沒有**。於是 C1「總金額 = Σ(單價 × 數量)」進得了 store 的唯一形式,
  是被寫成某一條情境的 `list_field_equals_number` 斷言 —— **invariant 被降級成 example**。
- **`glossary_term`** —— §1 詞彙表同樣沒有表。UL 要一致的四處裡,「詞彙表 ↔ wire 欄位名」
  目前是**自律**(訪談者自己多加一欄「對外欄位名」、落檔 agent 自己在 yaml 註解寫對譯規則),
  而**自願的東西換個模型就沒了**。

票 05(答案落點檢查)原本被歸在同一批,但它的產物是**報告**不是表 ——
它只跟這兩張共用**紀律**,不共用形狀。

兩張表由不同的人分別實作,而 `schema.sql` 是這條線最承重的檔。**分開設計 = 各自發明一種
形狀**,而這條線已經有兩種並存的做法(`forbidden_*` 的一 kind 一子表 vs
`scenario_assertion` 的條件式 CHECK),沒有共同形狀就會長出第三、第四種。
所以先定共同形狀,再派工。

## Decision

### 1. 共同的來源標記

兩張表都帶 `provenance`(五格 CHECK,與 `architecture_rule` / `acceptance_scenario`
**逐字相同**)+ `provenance_ref`(非空)。散文的 §1 與 §3 本來就每列都有「來源」欄,
這只是讓資料庫去逼它。

**不得為新表發明第六格或改寫格名。** 同一條規則寫在多個地方會漂 —— 這是本線反覆量到的失效。

「模板既定」的白名單 trigger **四張表都掛**,包含補上 `acceptance_scenario`
那個既有的洞(trigger 原本只掛在 `architecture_rule`,`schema.sql:59`)。

### 2. `domain_contract`:「指名測試」與「由誰強制」是兩欄,不得合併

- `enforcement` / `ladder_note` / `enforced_by` 三欄照抄 `architecture_rule`。
- 「指名測試」另開一張**關聯表**,FK 指 `acceptance_scenario` ——
  指向不存在的情境(打字錯成 `S99`)寫不進去。
- 關聯表另有「**指不出來的理由**」欄:C14「訂單清單只有內部人員能看」散文標的是
  `(無法指名,規格沉默)`,落進關聯表是**零列**,而零列跟「還沒填」長得一樣。
  ⚠️ 「零列時這欄必填」**SQLite 的 CHECK 寫不出來**(跨表),它住 `spec_store.py`
  的**第 2 階**,不是第 1 階。ADR 標明是為了不讓人誤讀成資料庫擋得住。

**為什麼兩欄不合併**:C1 的指名測試是 `S1, S2, S3, S5`,看起來「有人在守」。
但 C1 說的是「**任何時候**總金額都等於明細加總」,S2 只證明了「**這一筆**算對了」。
讓「有指名測試」算成「有機械檢查」,就把這張票要抓的降級整個蓋住。

**預期後果:這張票做完之後,`enforcement` 那一欄大多數列會誠實地寫 `none`。**
那是產出,不是失敗。票 06 已先寫下這個接受條件:「不要做到一半覺得數字難看又去湊。」

### 3. `domain_contract`:「守在哪」拆成三欄

散文那一欄現在塞了兩件事 —— 「訂單(自足)」是在回答誰守,
「⚠️ 跨聚合根,邊界可能錯…處置見 §9」是在拉警報。擠在一格,「哪些契約守不住」
就查不出來,只能靠人讀有沒有 ⚠️。

拆成:**守在哪個物件內** / **跨聚合根旗標**(0/1) / **處置**(旗標 = 1 時必填)。
分診佇列因此是一句 SELECT —— 與 `proxy_for` 同一個理由:把誠實的情況變成查得出來的欄位,
而不是躺在註解裡靠人讀到。

兩個刻意的差異:

- 欄位叫「守在哪個**物件**內」而不是「守在哪個**聚合根**內」——
  C8 填的是「金額 Value Object 自身」,**Value Object 不是聚合根**,原欄名跟裝的東西對不上。
- 「處置」存**本文**,不存「見 §9」。指標會製造本線最常見的那條病:
  **寫在該寫的地方 ≠ 接上了** —— 指過去了,而下游沒有任何一步會讀 §9。

### 4. `glossary_term`

- **禁用同義詞另開子表**(一個詞擋得掉好幾種講法,是一對多),
  「一律改用」欄 FK 指回 `glossary_term`。
- **「對外欄位名」可空,而空白有語意**:「會員系統」「商品價目系統」「內部人員」
  是界外概念,API 上不出現。空白 = 這個詞不上線,**不是漏填**。
- **「DDD 型態」自由文字**,並在表的註解裡明寫它只住**第 4 階**。

  這一欄原本要做成固定清單(像來源標記那五格),查完兩份實際詞彙表之後放棄:

  | | 用了哪些型態 |
  |---|---|
  | 凍結的 `spec/GLOSSARY.md` | Aggregate Root、Aggregate 內部物件、Value Object、列舉、**動詞**、**狀態的顯示文字**、介面、View Model、Use Case、Adapter |
  | 訪談產出那份 | Aggregate Root、Value Object、**識別碼**、**階段或狀態**、**外部規則集**、**角色**、(界外資料,非本案型態) |

  兩份幾乎不重疊。現在鎖清單等於逼下一場訪談把自己的詞硬塞進別人的格子 ——
  **那會製造假資料,不是擋假資料**。等累積到兩三份真的訪談產出,看得到真正的值域,再走搬階。

### 5. 對譯檢查走第 2 階報告,不做 FK

票 08 要的檢查是「每個上線的欄位名都對得到詞彙表裡的一個詞」。**不做成 FK**,三個理由:

1. **硬擋會把要量的東西量不到。** 這張票的價值在「7 個列表欄位裡有 N 個對不到」那個 N。
   做成 FK,匯入直接失敗 —— 只知道失敗,不知道差幾個。
2. **現有的兩份 checked-in yaml 都沒有詞彙表**,硬 FK 一上全部匯不進去。
3. **這條檢查現在就抓得到東西,而且不只抓到「少一個詞」。** 拿真正餵進第二幕那份規格的
   詞彙表(11 個詞,**連「對外欄位名」這一欄都沒有** —— 那一欄是後來另一場訪談的訪談者
   *自己*多加的)去對落檔出來的 7 個列表欄位:

   | 欄位 | 對得到的詞 |
   |---|---|
   | `customerId` / `items` / `currency` / `placedAt` | ✅ 客人編號 / 訂單明細 / 幣別 / 成立日期 |
   | `status` | ⚠️ 對得到「已成立」,但那是**值**不是欄位 |
   | `totalCents` | ⚠️ 詞彙表寫「小數 2 位」,欄位卻是**分** —— 單位漂了 |
   | `orderId` | ❌ 詞彙表裡**根本沒有訂單編號這個詞** |

搬到第 1 階留給以後,而且那時候要走搬階流程,不是順手改。

> ### ⚠️ 事後更正(票 08-A 落地後,同日)
>
> **上面那張手算表是錯的,而且錯的方式正好是這張票要抓的東西。**
> 機器真的量出來是 **0 / 7 對得到**,不是 4 —— 列表側與請求側都是 7/7 對不到
> (`glossary_check.py`,語料為 `act2-from-interview/glossary.yaml`
> ↔ `act2-rerun/agent-acceptance.yaml`)。
>
> 差在哪:那 4 個「對得到」是**我在腦裡做的翻譯**(客人編號 → `customerId`),
> 而那份詞彙表**一格「對外欄位名」都沒有宣告** —— 規格裡沒有任何一處記著這個對應。
> 落檔 agent 其實做對了對譯,但它把對譯寫在 `agent-acceptance.yaml` 的**註解**裡:
> **做對了,而且沒留下任何機器看得見的痕跡。**
>
> 這正是本 ADR §5 選「先量」而不是「硬擋」的理由被兌現的地方 ——
> 硬擋只會拿到一句「匯入失敗」,量出來才看得到 0 與 4 之間那個差,
> 而那個差就是「自律」與「有守衛」的距離。
>
> 另補一條 §6 沒想到的:**「不適用」有第二種** ——
> 有詞彙表、但**沒有對外合約可以比**(本輪訪談那份就是,17 詞、0 份合約)。
> 它比第一種難看見:計數上什麼都不缺,只是沒有對面。報表用離開碼 3 把它分開。


### 6. 兩節選填,但「不適用」不准算成「通過」

新的兩個頂層區塊(`glossary_terms` / `domain_contracts`)在 `spec_store.py` 是**選填**。

必填的連鎖比看起來大:除了兩份 checked-in yaml 與 `runs/` 底下每一份跑出來的 yaml,
還會打到 **`fixtures/negative-scenarios.yaml` —— 那是測試在用的**。那份 fixture 存在的
目的是隔離負面情境,逼它長出一份詞彙表只是為了通過必填,等於在測試資料裡塞假東西。

但選填有它自己的病,而且本線吃過一次 —— `schema.sql` 對 `res_total_field` 的警語:

> **守衛沒有壞掉,是不再適用了,而不適用不會有人發現。**

所以選填**綁一條硬規定**:報表**不准把「不適用」算成「通過」**。它自成一類,印在最上面:

```
詞彙表:0 條 → 對譯檢查本次不適用(不是通過)
```

### 7. 順手補一條 `PRAGMA foreign_keys` 的行為測試

交給先動 schema 的那張票(06-A)。

⚠️ **更正一則先前的紀錄**:handoff 寫著這句 PRAGMA「`spec_store.py` 裡只出現一次」,
因而推論刪掉它會讓所有 FK 靜靜失效。實測過了 —— 它有**兩份載體**
(`schema.sql:15` 與 `spec_store.py:581`),而且 `schema.sql` 那份經 `executescript`
**是真的生效的**:只靠它,FK 就擋得住(`PRAGMA foreign_keys` 回 1,違規 INSERT 被
`FOREIGN KEY constraint failed` 擋下)。要**兩份都刪**才會靜靜失效。

還是補,理由換一個:本 ADR 剛剛新增了兩個 FK 守衛(指名測試 → 驗收情境、
一律改用 → 詞彙表),這句 PRAGMA 變成承重的了。測試要驗**行為**(FK 真的擋得住),
不驗「那一行還在」—— 兩份載體不管誰被刪都要紅。

## Considered Options

| | 為什麼沒選 |
|---|---|
| 三張表(05 也落檔) | 票 05 自己寫著「這張票要的是**檢查**,不是中途產物」,而選定的做法(跑完之後對 run 目錄跑,跟 `provenance_check` 同一層)一張表都不用開 |
| 「指名測試」= 一格自由文字 | `S99` 這種打字錯寫得進去,而且永遠不會有人發現 |
| 「指名測試」就算「由誰強制」 | 表會好看,而 invariant → example 的降級被蓋住 —— 那正是票 06 要抓的東西 |
| 「DDD 型態」做成固定清單 | 兩份實際詞彙表的型態用語幾乎不重疊,鎖清單會逼出假資料 |
| 對譯檢查做成 FK(第 1 階) | 量不到 N;弄爛既有 yaml |
| 兩節必填 | 會逼 `fixtures/negative-scenarios.yaml` 長出一份與它無關的詞彙表 |

## Consequences

**擱著沒解的三件,是明寫的,不是忘了:**

- **票 08 的「實作層命名(2↔3)要不要驗」沒有決定。** 它只擋 08-B(命名類的第四個
  ArchUnit rule kind),不擋 08-A。那題牽到「這條線要不要開始約束實作的內部命名」,
  是要當面拍板的取捨。
- **06-B / C 的算術型 invariant 仍 blocked 在票 01。** 要驗 C1「任何改變明細的操作都重算」,
  得能在一個情境裡建單 → **改明細** → 再看總額,而 schema 沒有「改明細」這個動作。
  現在的 S2 只證明了建構當下算對了,實作只在建構時算一次也會綠。
- ⚠️ **「指名測試」指得到的東西之後會擴大。** 票 09(第四幕方法論)若決定走 TDD,
  內圈的單元測試也會是候選。**本 ADR 記下「會擴大」,不鎖語意** ——
  現在 FK 只指得到驗收情境,那是今天的值域,不是定義。

**排序**:06-A 與 08-A 都動 `schema.sql`,**必須序列**(06-A 先)。05 可真平行。
