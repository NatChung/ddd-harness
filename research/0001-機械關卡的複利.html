研究筆記 2026-08-20 AI 全自動開發 / loop engineering

機械關卡的複利

AI 全自動寫 code 的 loop 到底成不成立、代價在哪、方法怎麼搬。 每一條都標了來源、樣本規模與證據等級。

Loop engineering 的本體不是「讓 AI 一直跑」，是 把人的判斷不斷往機械關卡上搬。 搬得動就複利，搬不動就是每週五清一次 slop。

已證實 · 一手案例

全自動已經有人真的做到了

這題已經不是推測。OpenAI 內部一個團隊用五個月、從空 repo 起， 交出一個有內部日活使用者與外部 alpha 測試者的產品， 全程沒有任何一行 code 由人手寫—— 應用邏輯、測試、CI 設定、文件、可觀測性、內部工具，全部由 Codex 產出。

0人手寫的程式行數
~1M五個月後的總行數
1,500開出並 merge 的 PR
3→7團隊人數（平均 3.5 PR／人／日，人變多之後吞吐還升）

目前 Codex 能從一個 prompt 走完：驗證現況 → 復現 bug → 錄下失敗影片 → 修 → 驅動 App 驗證 → 錄下修好的影片 → 開 PR → 回應 agent 與人的 review → 偵測並修復 build 失敗 → 需要判斷時才升級給人 → merge。

一手 OpenAI，Harness engineering: leveraging Codex in an agent-first world。 自報、未經外部稽核；greenfield（空 repo 起）；原文明言 “should not be assumed to generalize without similar investment”。

另一個一手案例：Anthropic

>80%2026-05 merge 進 codebase 的程式碼由 Claude 撰寫
8×2026 Q2 每位工程師每日 merge 量 vs 2024

同一篇自己打折：LOC 是爛指標、內部 3 月員工調查只有約 4 倍、attribution pipeline 有漏。 它唯一講到的工作內容變化是——人的 code review 變成新瓶頸。 注意這句：它指向驗證，不是指向「工程師改行做 harness」。

一手 Anthropic，Recursive self-improvement。 賣工具的人在量自己用工具的成效；該文同時是政策倡議文。

已量到的代價

人力沒有變少，是換了位置

OpenAI 曾經每週燒掉 20% 在清 AI slop

Codex 會複製 repo 裡既有的模式——包括不好的那些，於是必然漂移。 初期是人工處理：整個禮拜五都在清。清到發現不 scale， 才改成把「golden principles」編進 repo，再讓背景 agent 定期掃描偏差、 更新品質分級、自動開修正 PR。他們的比喻是垃圾回收：技術債像高利貸， 持續小額償還永遠好過讓它複利。

一手 同上，OpenAI harness engineering，「Entropy and garbage collection」一節。

整個產業量到的是同一個方向：驗證負擔

23–25%花在 toil 的工時比例——重度與輕度 AI 使用者完全一樣
25% / 15%其中花在「修正 AI 寫的 code」：重度 vs 輕度
38% / 27%說 review AI code 比 review 同事更費力 vs 更輕鬆
61%同意「AI 常產出看起來對、但不可靠的 code」

時間沒有省下來，是換了味道。DORA 從最大的樣本看到同一件事： 創作端省下的時間被重新分配到稽核與驗證。

廠商調查 Sonar，State of Code， n=1,149，2025-10 收樣。⚠️ Sonar 賣的就是驗證工具，「AI code 需要更多驗證」對它商業上有利； 且樣本已先篩選為「過去一年用過 AI」的開發者。

交付結果是兩面的，不是一面倒

DORA 2025 推翻了自己 2024 的結論：AI 採用與交付吞吐、產品表現 現在是正相關。但同一份報告：與交付穩定度仍然是負相關。 另有 30% 受訪者對 AI 產出的 code「幾乎不信任或完全不信任」。

大樣本調查 Google Cloud / DORA，2025 DORA Report， 近 5,000 位從業者 + 100 小時質性訪談。相關性、非因果；非機率抽樣。

上限

loop 的品質上限 = 判準能機械化的比例

這是整份研究裡唯一有實驗數字的因果線索，也是最該記住的一條。 Google 拿 90 個內部真實生產 bug 做對照：讓 agent 先寫出半形式的契約 （前置條件、後置條件、未定義行為）再寫測試，對上直接寫測試。

54.9%規格有涵蓋到被違反的那條契約時，抓到 bug 的比例
19.4%契約缺席時，抓到 bug 的比例
+9.8pp整體偵測率 63.2% vs 53.4%（p = 0.0352）
+38%token 成本

附帶一個更刺的結果：契約驅動產出的測試，被判定優於 baseline 的比例是 77.8%， 優於人類開發者自己寫的測試的比例是 56.7%。 line coverage 則沒有顯著差異（−0.4%，p = 0.37）——所以買到的不是覆蓋率，是判準。

預印本 Tufano, McClure et al.（Google）， Grounding AI Agents in Contracts: An Empirical Evaluation of Spec-Driven Test Generation， arXiv:2608.17177，2026-08。n=90 真實生產 bug（C++/Java/Python/Go）；Gemini 3 Flash； 未經同儕審查；驗的是「規格→測試生成」，不是整條 pipeline。

但 LLM 做結構化設計有明確的斷點

把 DDD 拆成五步讓 LLM 跑：①統一語言 ②event storming ③bounded context ④aggregate 設計 ⑤對應到技術架構。結果—— ①到③穩定產出可用的產物；④和⑤誤差累積到產物不可用。 作者的結論是 LLM 能增強、不能取代架構專業。

也就是說：語言與邊界這一層搬得上去，聚合根與架構對應這一層目前搬不上去。 知道斷點在哪，比相信整套都能自動化有用得多。

預印本 Eisenreich, Jusic, Wagner， Automating Domain-Driven Design: Experience with a Prompting Framework， arXiv:2603.26244，2026-03。⚠️ 單一企業案例，n=1——方向可信，強度不可推廣。

方法

從證據反推的八條做法

每條都附「這條是從哪個數字推出來的」，不是從直覺。

  1. 先量「判準機械化率」，再談自動化程度

    loop 跑不跑得動，取決於你能把多少「什麼算對」寫成機器判得出來的形式。寫不出來的部分，loop 就在那裡空轉或自我肯定。

    ← 契約有涵蓋 54.9% vs 缺席 19.4%（Google, arXiv:2608.17177）

  2. 契約要有自己的載體，不能靠「剛好有個例子蓋到」

    invariant 被寫成某一條情境的斷言時，「任何時候都成立」就被降級成「這一筆成立」。契約要能被單獨查詢、單獨分診、單獨統計。

    ← 同上；契約缺席那一格就是「規格裡沒有它的位置」的代價

  3. 知識庫當唯一真相，入口是目錄不是百科

    OpenAI 的 AGENTS.md 只有約 100 行、純粹當地圖，深度內容放結構化的 docs/。他們列了大檔案的四個死法：擠掉 context、什麼都重要等於都不重要、瞬間腐爛、無法機械驗證。

    ← OpenAI harness engineering，「give Codex a map, not a 1,000-page instruction manual」

  4. 文件新鮮度也要有 CI 擋

    他們用專門的 linter 與 CI job 驗知識庫是否最新、交叉連結是否完整；另有一個定期跑的「doc-gardening」agent 掃描與實際行為不符的文件並自動開修正 PR。

    ← 同上。agent 看不到的東西等於不存在——Slack 上那場對齊架構的討論，對 agent 而言就是沒發生過

  5. 強制邊界，放手實作

    固定分層 + 嚴格驗證的相依方向 + 有限的合法邊，用 custom linter 和 structural test 機械強制；但不規定實作怎麼寫。lint 的錯誤訊息刻意寫成「修復指示」，直接注進 agent 的 context。

    ← 「enforce invariants, not micromanage implementations」；這種架構通常是幾百人團隊才做，有 agent 之後變成前置條件

  6. 同一種品味只手動修一次，第二次就編成規則

    review 意見、重構 PR、使用者回報的 bug，全部回收成文件更新或直接編進工具。人的品味捕捉一次，之後每一行 code 都持續強制。

    ← 週五 20% 清 slop 清到不 scale 才學會的（OpenAI）

  7. 知道 LLM 的斷點在第三步

    統一語言、event storming、bounded context 可以讓模型主導；aggregate 設計與架構對應要人壓在那裡，否則前面的小誤差會累積成不可用。

    ← Eisenreich et al., arXiv:2603.26244（n=1，方向參考）

  8. 吞吐機器和量測儀器的 gate 鬆緊要相反，先想清楚你在做哪一個

    OpenAI 刻意放寬 merge gate——PR 短命、測試 flake 就重跑不擋，因為「修正很便宜、等待很貴」。他們自己註明：這在低吞吐環境是不負責任的。反過來，若你的 pipeline 目的是量測漂移，就該逐位元組不符即紅。同一個決定在兩種目的下答案相反。

    ← OpenAI「Throughput changes the merge philosophy」一節；這是本研究裡唯一的設計張力，沒有共識答案

邊界

這些證據不涵蓋什麼

  • 全部是 greenfield。OpenAI 那個案例從空 repo 起。整份研究找不到任何 brownfield（既有大型 legacy）的對照案例。這是最大的一個空白。
  • 兩個一手案例都是模型供應商自報，沒有外部稽核，而且都賣你正在評估的那個工具。
  • 兩篇論文都是 arXiv 預印本，未經同儕審查；DDD 那篇 n=1。
  • 普及率仍是少數。常態使用 agent 的開發者：大樣本調查 23–31%；即使是自選、AI 重度、資歷 11–15 年的讀者群也只有 55%。實測遙測顯示 merge 進去的 code 只有 22%（2025 Q4）／27.4%（2026 Q1）是 AI 撰寫的。
  • METR 的「AI 讓人慢 19%」不能拿來反駁這些。那是 2025 年 2–6 月的工具（Cursor + Claude 3.5/3.7），測的是 IDE 補全與 chat，不是 agent harness；n=16。METR 自己在 2026-02 說現在應該有加速了，只是他們的新數據「證據非常弱」。當成過時的窄快照，不是現行定律。
  • 批評 spec-driven development 的文章都是觀點文、零數據。正反兩邊在這件事上都沒有硬數據——這個空白本身就是資訊。
