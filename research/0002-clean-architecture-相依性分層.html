研究筆記 2026-08-21 Clean Architecture / DDD

相依性分層在解決什麼問題

為什麼層 DDD 常搭 Clean Architecture、結構式分層與相依性分層的差別、 以及一次 API request 的完整路徑。

兩者都叫「分層」，但規範的東西、保護的對象、以及 能在什麼時候被檢查出來，完全不同。 靠自律維持的架構不是架構，是共識。

體例

  • 原文的 code 是 TypeScript，本 repo 的教材是 Java。 這裡保留 TypeScript 原樣不轉——這是討論筆記，不是課， 跟 examples/shop/ 沒有對齊義務。

一

DDD 不是借用 Clean Architecture，是 Clean Architecture 從 DDD 的需求長出來

常見的誤解是 DDD 挑了 Clean Architecture 當房子。實際的因果相反。 Evans 在 Blue Book 第四章就寫了自己的 Layered Architecture （User Interface / Application / Domain / Infrastructure）， DDD 一直有自己的架構。

問題出在 2003 年那版的依賴方向是由上往下——Domain 直接依賴 Infrastructure。 Evans 的原話很明確：

“Develop a design within each LAYER that is cohesive and is dependent only on the layers below.” ⟨…⟩ “The infrastructure layer usually does not initiate action in the domain layer. Being ‘below’ the domain…”
— Evans, Domain-Driven Design, ch. 4（Final Manuscript, 2003）

結果是 Entity 被持久化框架侵蝕、Aggregate 的邊界被 lazy loading 決定， 最後蓋出 anemic model。

真正的斷點在 Repository

這個 pattern 要成立，interface 必須在內、implementation 必須在外。 Blue Book 第六章說 repository 要「Set up access through a well-known global interface」， 而且「the interface is simple and conceptually connected to the domain model」； 實作那頭則是「teams add a framework to the infrastructure layer to support the implementation of repositories」。

也就是說 DDD 的戰術模式在語意上已經內建了依賴反轉的要求， 只是 Evans 沒把它升格成架構規則，所以照第四章那條「只依賴下層」施工的人幾乎都做錯—— 第四章的規則與第六章的 pattern 在文字上就互相拉扯。

⚠️ 校正：「這本身已經是 dependency inversion」是後人的框架，不是 Evans 的話。 dependency inversion 這個詞在 Blue Book 全書出現 0 次 （對 2003 Final Manuscript 全文檢索）。介面在內、實作在外是他寫的； 叫它 DIP 是我們加的。

Cockburn 的 Hexagonal（2005）、Palermo 的 Onion（2008）、Uncle Bob 的 Clean（2012） 講的是同一件事的三種命名：讓 domain 成為依賴圖的終點。 所以與其說 DDD 用 Clean Architecture，不如說 Clean Architecture 是 DDD 分層的除錯版本。

Evans 本人也認過這件事。原文寫在 2013 年他給 Vernon《Implementing Domain-Driven Design》 寫的推薦序裡：

“It explains the hexagonal architecture, which has emerged as a better description of what we do than the layered architecture.”
— Eric Evans, Foreword to Vaughn Vernon, Implementing Domain-Driven Design (Addison-Wesley, 2013), p. xvii

⚠️ 已更正：討論筆記原文寫的是「Evans 本人 2014 年在 QCon 回顧時」。 那個場合與年份查不到。2014 年 Evans 的那場是 DDD eXchange（不是 QCon）， 主題是 challenging DDD 的基本假設——InfoQ 那份會議紀錄通篇沒提到架構風格。 （本 repo 查的是報導，沒有那場演講的逐字稿或錄影，所以只能說「查不到支持」， 不能說「他沒講過」。） 真正說得出處的是上面這句 2013 年的推薦序。細節見查證表第 10 條。

為什麼當年會設計成那樣

2003 年的 layering 是為了關注點分離，不是為了依賴方向， 心智模型是 call stack——上層呼叫下層，所以畫成垂直堆疊。 而最底層被命名為 Infrastructure，這個詞本身就是隱喻： 它暗示 DB 是地基、是你踩著蓋房子的東西，那大家依賴它就天經地義。

技術上也確實躲不掉，但那是分兩波的： 2003 年當道的是 EJB 2.x，entity bean 得繼承／實作 framework 的型別； annotation 那一波要更晚——Java annotation 出自 JSR-175， 2004 年通過、隨 Java 5 進語言，JPA／EJB 3.0 要到 2006 年。

⚠️ 已更正：原文寫「EJB / Hibernate 當道，Entity 得繼承 framework base class、掛 annotation」， 把兩個年代疊在一起了，而且 Hibernate 那半剛好相反—— Hibernate 當年的賣點正是「映射 POJO、不用繼承任何東西」。詳見查證表第 12 條。

二

Clean Architecture 的四圈

四圈與對應的 DDD 建構元素
圈層內容
Entities
最內圈		 企業級業務規則，跨 application 也成立。純資料 + 純運算， 沒有任何 import 指向外圈。對應 DDD 的 Entity / Value Object / Aggregate / Domain Service / Domain Event。
Use Cases
第二圈		 application 特有的流程編排：知道「取訂單 → 算折扣 → 存回去 → 發事件」 這個序列，但不知道訂單住哪裡。Repository / Gateway 的 interface 定義在這圈，transaction 邊界通常也落在這裡。 對應 Application Service / Command Handler。
Interface Adapters
第三圈		 翻譯層，兩個方向都由它負責。Controller / Presenter / ViewModel 把 HTTP request 轉成 input DTO；Repository 的實作、 ORM Model ↔ Entity 的 mapping 也在這圈。
Frameworks & Drivers
最外圈		 Web framework、DB engine、message broker、外部 SDK、DI container、 main()。理想上薄到只有 glue code。
Dependency Rule（唯一的硬規則）

原始碼的依賴只能由外指向內。 內圈不能提到外圈的任何名字——不能有它的 class、function、變數，連字串常數都不該有。 圈數可以增減，這條規則不能妥協。

DB 和 UI 為什麼被放在同一圈

這是刻意的，也是整件事的重點。判斷「外」的標準不是呼叫順序，是變動頻率與 I/O 距離。 DB 不在 app 下面，它在 app 旁邊，跟 UI 一樣只是外面世界跟你講話的一種方式。 Postgres 換成 DynamoDB、REST 換成 GraphQL，對「滿千折百不超過 30%」這條規則而言 是同一種等級的事件，都不該讓它重編譯。

Hexagonal 的命名在這件事上最精準： UI / API / CLI / test runner 是 driving side（外面打進來）， DB / MQ / 第三方 API 是 driven side（domain 定義 port、外面來實作）。 同一圈，但控制流方向相反——這個不對稱決定了誰定義 interface。

⚠️ 用詞校正：driving / driven 不是 2005 年原文的用語。 Cockburn 2005 那篇用的是 primary / secondary actor。 driving/driven 定於他 2024 年那本《Hexagonal Architecture Explained》， 書中的更新說明自陳：「In the preview edition we used driving/driven and primary/secondary. ⟨…⟩ Only driving/driven and primary/secondary apply to all three, actor, adapter and port.」 兩組都通行，但把 driving/driven 說成 2005 年的命名是錯的。

三

一次 API request 走完四圈

情境：POST /orders/{id}/coupon。 規則是「VIP 滿千折百，折扣不得超過訂單金額 30%，且不適用促銷商品」。

呼叫（往內）

  1. Framework / Router（最外圈）——收到 HTTP request，交給 Controller。

  2. Controller（Adapter 圈）——解析、驗格式、從 token 取 actorId， 產出 ApplyCouponCommand{ orderId, couponId }。

    這是 plain struct，沒有 Request 物件、沒有 header。 翻譯完之後，「HTTP」這個字在後面的路徑裡永遠不再出現。

  3. ApplyCouponUseCase（Use Case 圈）——開 transaction， 呼叫 OrderRepository.findById()。

    它需要的資料在 DB，但它只認得自己定義的 interface。

  4. PgOrderRepository（Adapter 圈）——跑 SQL， OrderMapper.toDomain(row) 把扁平的 Row 還原成不變量的 Aggregate， 回傳 Order。

  5. Order.applyDiscount()（Entity 圈，最內）——純運算、沒有 await， 回傳 Result<Order, DomainError>。

    整條路徑上唯一真正的商業判斷發生在這幾行。

回傳（往外）

  1. ApplyCouponUseCase——收 Result；成功就 repo.save() （再穿一次 port 往外）、發 domain event、commit，回傳 output DTO。

    失敗回傳的是 EXCEED_CAP 這種 domain 語彙，不是 400。

  2. Controller / Presenter——把 EXCEED_CAP 對應成 422， 加上 i18n 訊息。

    HTTP status code 的知識完整留在這圈。

  3. Framework——序列化成 HTTP response 送出。

三個容易看錯的點

第 3→4 步是唯一需要 DIP 的地方。 控制流從內往外跑，但原始碼依賴仍然由外指向內：use case import 的是 OrderRepository 這個 interface，它不知道 Postgres 存在，執行期才由 DI 接起來。

第 2 步的 Controller 和第 4 步的 PgOrderRepository 同屬 Adapter 圈， 深度上平起平坐，只有控制流方向不同（driving vs driven）。

Framework → Controller → UseCase 沒有跳層，而且就算跳了也合法。 舊 Layered 的 strict layering 要求「每層只能呼叫緊鄰的下一層」，Clean 是 relaxed 的： 由外往內的直接呼叫不需要任何機關，Controller 直接 import domain 的 Money 型別都沒問題。需要 DIP 的只有反方向那一半。

「跳層」有兩個意思，不要混

上面那段講的是參照上的跳層——Controller 直接寫出 Money 這個型別的名字。那是 import graph 往內指， Dependency Rule 完全允許。

另一個意思是控制流繞過中間層——Controller 不經過 use case， 自己開 transaction、自己打 SQL。那同樣沒有違反 Dependency Rule （方向仍然往內），但它是設計上的壞味道：流程編排漏到了翻譯層。

差別在於誰抓得到：前者不需要抓（它不是問題）， 後者抓不到——它正好落在下一節那張表裡「結構式分層」那一欄， 只能靠 review。這也是本 repo 第 5 課 動手練習裡「有沒有哪一步跳層」那一格在問的東西：那一格問的是後者。 

// use case 圈 — interface 住這裡
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>
  save(o: Order): Promise<void>
}

// entity 圈 — 純規則，transitive dependency 是空集合
class Order {
  applyDiscount(d: Money): Result<Order, DomainError> {
    if (d.gt(this.subtotal.percent(30))) return err('EXCEED_CAP')
    if (this.items.some(i => i.onSale))  return err('SALE_ITEM')
    return ok(this.withDiscount(d))
  }
}

// 測它不需要任何 test double
expect(orderWith(1000).applyDiscount(money(400))).toEqual(err('EXCEED_CAP'))
四

結構式分層 vs 相依性分層

這是整份文件真正要講的一件事。兩者都叫「分層」， 但規範的東西、保護的對象、以及能在什麼時候被檢查出來，完全不同。

兩種分層的逐項對照
結構式分層（strict layering） 相依性分層（Dependency Rule）
規範對象 呼叫紀律：A 不准跳過 B 直接呼叫 C import graph 的方向：箭頭一律指向內
管不管方向 不管。你可以嚴格遵守每層只呼叫下一層，domain 照樣依賴 ORM 只管方向。跳幾層無所謂
實際保護到誰 幾乎沒有。它是流程規範，不是變動隔離 內圈。變動傳播被拓樸擋住
檢查時機 Review 期。「請不要跳層呼叫」只能靠人記得、靠 code review 抓，事後才發現 編譯期／CI。「domain 不准 import pg」是 build 就能擋的—— Gradle module、Nx tag、eslint import boundaries、Go internal package
違規的後果 程式照跑，只是不好看 build 失敗，根本進不了 main branch
關鍵差異：可機械檢（machine-checkable）

結構式分層的規則是一句人話，必須有人在 review 時記得它。 相依性分層的規則可以編碼成 build system 的 module 依賴宣告， 違反它的 commit 根本編譯不過。 靠自律維持的架構不是架構，是共識，而共識會隨著人員流動和交期壓力蒸發。

相依性分層換來的三件具體的事

  • 變動半徑可預測。Postgres 換成 DynamoDB，波及面到 mapper 為止—— 這個保證是拓樸給的，不是靠小心。折扣規則改了，只有 domain 那個檔案動。
  • 可測性是副產品，不是目標。domain 的 transitive dependency 是空集合， 所以測它不需要任何 test double。這不是「我們有寫測試的紀律」， 而是「不可能寫出需要看 DB 的 domain test」——約束比紀律可靠。
  • 決策可以延後。只要 DB 在外圈，你可以先用 in-memory 把 use case 全部寫完，再決定用什麼 DB。反過來，如果 domain 依賴 ORM， 你在第一天就把後面兩年鎖死了。

「transitive dependency 是空集合」這個講法跟 Palermo 2008 年那篇同源。 他的原話是：「Transitive dependencies are still dependencies.」—— 傳統分層裡 UI 其實是耦合到 data access 的，只是中間隔了一層看不見。

常見疑問：那為什麼不把邏輯全寫在最外層？

執行期確實所有東西都在最外層被組裝起來。Composition root（main）住在最外圈， 它 import 所有東西、new 出所有物件，把 PgOrderRepository 塞進 ApplyCouponUseCase——Uncle Bob 自己把 Main 當成 最髒的那個元件、系統的「ultimate detail」，並且說它是個 plugin。

這完全合法，因為 Dependency Rule 管的是 source-code import graph， 不是 object graph：main 認識所有人是安全的， 因為沒有人認識 main，它的入度是 0，整個換成 CLI 或 Lambda handler， 內圈一個檔都不用改。

但邏輯本身的位置決定的不是執行結果，而是那段程式碼的 import 集合。 applyDiscount 寫在 Entity 圈，transitive dependency 是空的， 能單獨 new 出來測、能被任何 driver 呼叫。 同一段 if-else 貼進 Controller，它就繼承了 Controller 的全部依賴： 要觸發它得先有 HTTP request 物件、要測它得換 framework、要換 GraphQL 就得複寫一份。 邏輯沒變，可觸發面積變了。

用函式的角度看更清楚，就是 functional core / imperative shell： main 做的是 partial application，把 (repo, db, clock) => (cmd) => Result 的前半段固定死。 分層在這個視角下不是階層，是「已解析依賴」與「未解析依賴」的分界線—— 不用 class、只用 closure 和 module，這條界線依然存在。

五

什麼時候不該套

Clean Architecture 的成本是 mapping 樣板（Entity ↔ ORM Model ↔ DTO 三層轉換）， 只在規則密度夠高時才划算。如果一個 use case 單薄到只有 CRUD—— 多數 supporting subdomain 都是——直接 controller 打 SQL 是對的。 只拿戰術模式、跳過 strategic design 的取捨，是 DDD 社群最普遍的誤用。

替代方案也確實存在。Vertical Slice Architecture + CQRS 按 feature 切而非按 layer 切，每個 slice 自己決定要不要抽象： 複雜的走整套 domain model，簡單的直接查。 Event Sourcing 更是 DDD 原生的架構風格， 聚合狀態就是事件流的 fold，跟 Clean 的分層正交。

可以用自己的架構，只是任何選項最後都得回答同一個問題： domain 的可測性怎麼保？ Clean Architecture 只是目前回答得最省事的那個。

本 repo 對照：第 6 課 講的是同一個取捨的另一半——為什麼「讀」那一側可以整套跳過這些規矩。 那一課刻意不碰 Event Sourcing，並且明講 CQRS 不需要 Event Sourcing 也成立； 本節把 Event Sourcing 當成獨立的架構風格提及，兩邊的立場一致，沒有衝突。

六

對 AI harness 的意義

同一條路徑，把 PgOrderRepository 換成 InMemoryOrderRepository， 就能不起 DB 跑完整套 use case。這給出三檔粒度不同的回饋迴圈： 純 domain（毫秒級）、in-memory use case（十毫秒級，驗編排）、 真 DB 的 integration test（秒級，驗 mapping 和 SQL，數量刻意少）。

Agent 在這種結構裡的行為差異很明顯。讓它改 applyDiscount， 錯了會有確定性的 assert failure 秒回；讓它改 PgOrderRepository， 錯了可能是 N+1 或 transaction 邊界問題，那種錯誤只有 integration test 或 production 才看得見。 state control 的交棒順序，跟這四圈由內而外的順序基本上重合。

而「檢查時機」那一欄在 agent 進場後會被放大。 Agent 為了讓測試變綠會抄近路，它的最短路徑通常就是在 domain 裡直接 import 那個能拿到資料的東西。你能不能在 CI 上擋住這件事， 決定了你敢不敢跟它交出 state control。從這個角度看， Dependency Rule 就是一條寫給 harness 用的 invariant—— 它跟 TDD 同類，都是外部的、非 AI 的客觀驗證機制，只是一個驗行為、一個驗結構。

這一節是推論，不是驗過的

上面三段對 harness 的接法，本 repo 沒有跑過任何一次量測—— 沒有「三檔迴圈各自的實測秒數」、沒有「加了 import 檢查之後 agent 抄近路減少多少」的資料。 它跟 第 5 課 的〈這對 harness 的用途〉一樣，是接上去的說法，不是引用來的，也不是驗過的。

In other words, all coupling is toward the center.」 同篇另有「Transitive dependencies are still dependencies.」

10 「Evans 2014 年在 QCon 回顧時認為 Hexagonal 比 Layered 更好」 已更正 場合與年份都對不上。2014 年 Evans 的那場是 DDD eXchange（不是 QCon）， 主題是 challenging DDD 的基本假設，InfoQ 的會議紀錄未提架構風格。 （查的是報導不是逐字稿，所以判定是「查不到支持」，不是「他沒說過」。） 正確出處：Evans 給 Vernon《IDDD》寫的推薦序（2013, p. xvii）： 「It explains the hexagonal architecture, which has emerged as a better description of what we do than the layered architecture.」 （核對自 Pearson 官方 sample pages PDF）

12 「2003 年 EJB / Hibernate 當道，Entity 得繼承 framework base class、掛 annotation」 已更正 年代疊錯，而且 Hibernate 那半相反。Java annotation 出自 JSR-175 （2004 年通過，隨 JDK 1.5 進語言）；JPA／EJB 3.0 是 2006 年。 2003 年成立的是 EJB 2.x 的 base class 耦合； Hibernate 當年的賣點恰恰是映射 POJO、不要求繼承。 本文已改寫成分兩波敘述。
