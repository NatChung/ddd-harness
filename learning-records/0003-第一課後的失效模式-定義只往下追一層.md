# 第 1 課後觀察:嗅覺對,但定義只往下追一層就停

2026-08-09,Nat 完成第 1 課(Ubiquitous Language)。Q1 答對,Q2 答錯(選了含「完成」的選項),
練習寫了一則「訂單完成」的詞彙條目。

## 已經有的能力

**抓得到「使用者動作 ≠ 系統事件」這個嗅覺。** 他的條目主動指出「按下付款」不等於付款成功,
「有可能錢還沒付成功」——這是含糊詞最常藏東西的地方,不是新手會注意到的層次。
他的金流領域知識足夠支撐真實例子(authorized / captured 的差別)。

## 失效模式(這才是要盯的)

1. **循環定義。** 定義「訂單完成」寫成「當 payment 成功後,再標記為**完成**」——
   被定義的詞出現在自己的定義裡。
2. **只往下追一層就停。** 把「訂單完成」錨定到「payment 成功」,但沒察覺
   「payment 成功」本身同樣沒定義(按下確認 / authorized / captured / 對帳入帳,四個不同時刻)。
   他在「區分」欄碰到了這個問題,卻沒有回頭修「定義」欄。
3. **命名衝突未察覺。** 電商慣例裡「訂單完成」通常指履約終態(已出貨、過退貨期),
   他拿它來指付款成功。等於**一個詞裝了兩個概念**,而他選擇了跟業界慣例相衝的那個。
4. **「不要用」欄位寫成了錯誤描述**(「按下付款,當做訂單完成」)而非同義詞清單。
   格式沒抓到:那一欄要列的是**別人會拿來指同一件事的其他講法**,把它們封掉。
5. **Q2 錯的意義**:他選了含「完成」的選項,而「完成」正是他自己在練習裡列為慣犯的詞。
   → **認得出某個詞含糊 ≠ 讀規格時會對它警覺。** 後者才是 harness 要的能力,需要另外練。

## Implications

- **每次練習都要跑遞迴檢查**:「定義裡的每一個名詞,是不是也都已經定義了?」
  單次的自我檢查不夠,要變成習慣動作。往下追到「外部系統送進來的具體回應」才算到底。
- **命名衝突(一個詞裝兩個概念)是第 2 課 Bounded Context 的天然引子。**
  可以直接從他這則條目接過去:同一個「訂單」,在結帳、倉儲、財務三個地方根本是三種東西。
  這比抽象講邊界有效得多——用他自己寫的東西當入口。
- 第 2 課起可以放心用金流 authorized/captured 這類真實例子,他跟得上。
