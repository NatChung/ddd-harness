# 第 4 課後:把「必須同時正確」壓縮成「同步」

2026-08-10,Nat 主動回報第 4 課的理解(沒有做練習,是口頭複述):

> Aggregate ⇒ 可以理解為多個不同東西,但一定要在業務邏輯上同步就是同一個 Aggregate
> Invariant ⇒ 規則,直接寫到 CODE 裡

兩條都抓到重點,但各有一處失準。

## 診斷一:「同步」是他自己的壓縮,而且壓錯方向

教材寫的是「必須在同一個時刻都正確」,他複述成「業務邏輯上同步」。
**「同步」會把判準從「一致性」滑向「時序」**——聽起來像「要一起更新」,
而「一起更新」正是第 4 課 sorter 裡刻意排除的錯誤判準
(「常常一起查詢」「同時發生」都不是判準)。

他還沒踩到這個坑,但這個詞遲早會帶他踩:下單當下會一起扣庫存、發通知、寫 log,
四件事同時發生,只有訂單那一組不能有一瞬間不一致。

**給他的操作型測試**:「晚一點再對上,會不會有人算錯錢?」
會 → 同一個 Aggregate;不會 → 不同。這比「必須同時正確」好用,
因為它逼人去想**延遲的後果**,而不是去想**兩件事的關係緊不緊密**。

## 診斷二:invariant 被等同於「規則」

「規則,直接寫到 code 裡」——後半正確,前半範圍太寬。
教材有寫「不是應該、不是通常」,但沒有給出**篩子**,只給了定義。
補上的篩子:句子裡出現「應該 / 通常 / 盡量 / 大部分情況下」→ 不是 invariant。

另外補了一個教材沒講、但第 5 課會用到的點:
**不是所有 invariant 都住在 Entity。**「同一個帳號一天不能下超過 10 筆訂單」
跨越很多張 `Order`,單一 Aggregate 守不住,會變成 use case 層的檢查。
這句同時是第 4 課 → 第 5 課的橋。

## 教材的責任

第 4 課的原句「哪些東西必須在同一個時刻都正確?」在**定義上**沒有錯,
但它是一個**判準**,不是一個**測試**——沒有告訴人怎麼實際去驗。
他把它壓縮成「同步」,正是因為那句話還不夠可操作。

→ 已在第 4 課補上「晚一點再對上,會不會有人算錯錢?」這個延遲測試,
以及「一起改 ≠ 同一個 Aggregate」的明講。

## Implications

- **這是 LR 0003 / 0004 之後第三次出現同一個形狀的問題**:他理解得夠好、
  但在**自己重述**的時候會把精確的條件壓縮成一個較鬆的日常詞
  (0003 是定義只往下追一層,0004 是把拆詞誤判成邊界,這次是同時正確 → 同步)。
  **往後每個核心判準,除了定義之外都要附一個「怎麼實際去驗」的測試句。**
  純定義他會照收,但複述時就漏掉條件了。
- 值得注意的是:**他這次是主動回報理解、而不是做練習**。這是他目前為止最省力
  也最有效的自檢方式(第 3、4 課的練習他都沒做)。往後可以直接鼓勵這種
  「用你自己的話講一次」,不用逼他寫完整練習。
