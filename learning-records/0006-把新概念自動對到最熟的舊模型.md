# 第 4 課後(二):把 Aggregate 自動對到「DB 關聯 / Table」

2026-08-10,Nat 在讀第 5 課的途中回頭問第 4 課:

> Aggregate 很像 DB 裡的關聯,Entities 像 Tables,我理解正確嗎?

## 診斷

**方向是反的,而且是那種會一路錯下去的反。**

對得上的只有一點:Entity 靠 id 辨識而非欄位值,跟 primary key 同構。其餘全錯:

- **FK 表達「有關係」,Aggregate 表達「必須同時正確」**——schema 裡沒有任何欄位承載後者。
  第 4 課那六題分類,答案全都跟 FK 對不上(訂單↔顧客有 FK 但不同 Aggregate;
  商品↔可售庫存常同一張表但不同 Aggregate)。那是刻意挑的,他沒看出那個模式。
- **Entity 有行為,Table 沒有。**這個類比會直接把人帶去貧血模型
  ——資料袋 + Service,正是第 4 課開頭要修掉的東西。
- **Value Object 裝不進這個類比**(`Money` 住 Entities 層但不是表)。
- 正規化的目標是消除重複,Aggregate 的目標是保護 invariant,目標不同。

給他的快篩:**「把 FK 全部拿掉,你的判斷會不會改變?」** 不會 → 用的是 invariant 判準。

也給了一個真的對得準的替代類比:**Aggregate 像「一個 transaction 的邊界」,
不是「一組 FK 關聯」**——「一次交易只改一個 Aggregate」直接對上,
而且它抓得到「同時正確」的時間性質,那是 FK 表達不出來的。

## 這是一個新的失效模式,不是舊的變形

LR 0003 / 0004 / 0005 都是**壓縮失準**(條件被複述成較鬆的日常詞)。
這次不同:**他把新概念整個對映到自己最熟的既有模型上**,而那個模型的形狀不對。

值得注意的是,**這正是本教學教學策略的副作用**。MISSION 寫著
「新概念接到他已經會的東西上教」(Java / OO / design patterns / 資料庫)。
這個策略有效,但代價是:**他會自動去接,而且會接到最近的那個 schema,即使那個是錯的。**
他沒有等教材給類比,他自己先給了一個。

## 教材的責任

第 4 課**只在選擇題的錯誤選項裡**提了「同一張表」,正文從頭到尾沒有正面處理資料庫類比。
對一個資料庫熟的讀者來說,這個類比會在讀第一段時就自動成形,而課文一路都沒有攔它。

→ 已在第 4 課「邊界畫在哪」那節補上一個 `.box warn`:四點對照 + FK 快篩 +
transaction 邊界的替代類比。

## Implications

- **往後每引入一個新概念,先問一句「他最可能把這個對到什麼舊東西上」,
  然後主動把那個錯誤類比擺出來打掉。**被動等他問是運氣好——這次他問了,
  但他也可能就這樣帶著錯的模型往下走三課。
- 高風險清單(他熟、而且形狀接近到會誤導的):資料庫 schema、Java 的 package/module、
  MVC 的 Model、Spring 的 Service/Repository 慣例、design patterns 裡的既有名詞。
  **第 5 課的 Interface Adapters 層特別危險**——它跟 Spring 的 `@Repository`
  長得很像但不是同一件事。
- 他**願意在讀新課途中回頭質疑舊課**,這是很好的訊號(而且比做練習省力)。
  搭配 LR 0005 的觀察:他的自檢方式是「用自己的話講一次,然後拿來對」。
  繼續鼓勵這個,不要改成要求他寫完整練習。
