# 第 5 課:用「這東西面向誰」判斷層別,而不是用 import

2026-08-11,Nat 做第 5 課的分層練習,**8 題答對 5 題**。貼出來的兩題錯題是:

- `OrderRepository` 這個介面的**宣告** → 他答 Interface Adapters(正解 Use Cases)
- `OrderView` 這個回傳用的 record → 他答 Interface Adapters(正解 Use Cases)

(第三題錯的他沒貼,已問但他接著問了別的,未取得。)

## 診斷

**兩題錯在同一個地方:他用「這東西是給誰用的 / 朝向哪一邊」判斷層別。**
`OrderRepository` 是要給資料庫用的、`OrderView` 是要吐給前端的,所以兩個都往外放。
直覺一致、可預測——但判準錯了。

正確判準是**誰的程式碼裡出現了它的名字**,也就是 import 方向。
`CancelOrderUseCase` 非提到 `OrderRepository` 這個型別不可(欄位型別、建構子參數),
所以型別放哪就決定了那個 import 往哪指;放外層,內層就得 import 外層,一行就違規。

給他的通則:**一個型別要放在「所有用到它的層」當中最內的那一層。**
這一條同時收掉他這兩題,理由完全相同。

## 追問(這題問得好)

他接著問:**「那為什麼 `OrderView` 不放在 Entities 那一層?」**

問題背後的假設是「越內層越安全,往內放比較保險」。回覆分兩層:

1. 規則的前半句已經排除了——Entities 層沒有任何檔案提到 `OrderView`,不在候選集裡。
2. 更重要的是拆掉那個假設:**往內移一層是做出一個承諾**
   (「這東西是業務本身的一部分,不因技術或應用而改」),不是免費的保險。

給了一個比「沒有電腦也成立嗎」更好操作的測試:
**這個型別的欄位清單是誰決定的?** 業務決定 → 可以往內;
**消費者(畫面/API)決定 → 不能住最內層。**

也點出對稱性:**把 Entity 往外傳(跨層原則在擋的)跟把 View 往內塞,是同一個錯的兩個方向**
——都把「因不同理由而改」的東西黏在一起。

## 教材的責任

第 5 課原本只給了 `OrderRepository` 介面的**單一片段**,沒有 package 佈局,
所以**看不到 import 方向**——而 import 方向正是這一課唯一的判準。
只給片段就出題,等於要他憑直覺猜。

→ 已在第 5 課新增〈一個型別到底該放哪一層〉:完整 package 樹、三個檔案的 import、
「移到 adapter 就違規」的一行證明、`.box key` 的最內層規則、
以及 `.box warn` 專門回答「為什麼不放 Entities」。順帶帶出 Port 這個詞。

## Implications

- **他的錯誤是有系統的、可預測的,不是隨機的。**「面向外面 → 放外層」會一路影響後續:
  domain event、Input DTO、Presenter 介面,全都是同一個題型。
  **第 6 課之後若再出分層題,要刻意混入這一類。**
- 這也是 LR 0006 那條的延續:他會自動接到既有心智模型
  (那次是 DB schema,這次是「介面 = 對外的東西 = 放外面」)。
- **出分層題必須先給看得見 import 的完整脈絡**,不能只給類別片段。
  這是本 workspace 出題方式的通則,不只這一課。
- 他這次的追問(「為什麼不再往內」)品質很高——**他開始檢驗規則的邊界,而不只是套用規則**。
  這是 LR 0004 擔心的「認得出題型 vs 會用解法」正在改善的訊號。
